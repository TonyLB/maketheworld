# Ephemera: `mtw.ephemera.thinking` (steady-state notes)

Subsystem for **durable thinking artifacts**: **schedule** rows (work queued / claimable) and **thinking results** (completed work, success or failure), stored in the Ephemera Dynamo table and (later) surfaced via **EventBridge** and the **Ephemera API**.

**Task plan (process, ordering, verification):** [`taskPlanning/lambda/ephemera/dataSource/thinking/AGENT.thinking.planning.md`](../../../../taskPlanning/lambda/ephemera/dataSource/thinking/AGENT.thinking.planning.md)

**Client companion (subscribe, dashboards):** [`taskPlanning/charcoal-client/AGENT.thinkingDashboard.planning.md`](../../../../taskPlanning/charcoal-client/AGENT.thinkingDashboard.planning.md)

## Dynamo keys and row lifecycle (locked)

- **Job partition** **`EphemeraId`:** `JOB#${generationId}` (UUID string; same as the run **generation** for the first consumer).
- **Job metadata:** one row per job on that partition with sort key **`Meta::Job`**.
- **Job adjacency (membership):** for each work item, a lightweight row **`JOB#${generationId}`** + **`DataCategory`:** `TASK#${workItemId}` (same string as the task partition id below). Associates the work item with the job; **schedule and result bodies** live on **`TASK#${workItemId}`** (**`Meta::Schedule`**, **`Meta::Result`**), not on this adjacency row.
- **Task partition** **`EphemeraId`:** `TASK#${workItemId}`. Holds task-owned rows addressed by **`DataCategory`**, including **`Meta::Result`** (thinking result payload) and **`Meta::Schedule`** (schedule state; persisted via **`mtw.ephemera.thinking.scheduling`** when callers use **`sendPutThinkingSchedule`**).
- **Lifecycle:** schedule and membership may exist before a unit finishes; the **result** row appears under **`TASK#${workItemId}`** + **`Meta::Result`** when work completes (success or failure). Listing a job's work items still uses **`Query`** on **`JOB#${generationId}`** with `begins_with(DataCategory, "TASK#")` for adjacency lines.

Indexes and lookup patterns beyond this summary: see the task plan **Decisions** and [`template.yaml`](../../../../template.yaml) (`DataCategoryIndex`).

## Read surfaces vs authoritative writes

- **`@tonylb/mtw-gateways`:** shared **read** helpers under **`@tonylb/mtw-gateways/ts/ephemera/thinking`**: key builders (`JOB#`, `TASK#`, `Meta::Job`, `Meta::Result`, `Meta::Schedule`), **`Query`** on the job partition for **adjacency only** (never treat those rows as schedule or result payloads), **`GetItem`** on **`JOB#${generationId}`** + **`Meta::Job`** (`getJobMetaItem`), **`GetItem`** on **`TASK#${workItemId}`** + **`Meta::Result`** for results and **`GetItem`** on **`TASK#${workItemId}`** + **`Meta::Schedule`** for schedule, normalization to **`ThinkingResultEvent`** / **`ThinkingScheduleEvent`**, **`createThinkingResultReadCacheHandler(ephemeraDB)`** (**`ThinkingResultReadCache`**) and **`createThinkingScheduleReadCacheHandler(ephemeraDB)`** (**`ThinkingScheduleReadCache`**); result and schedule caches are keyed by **`workItemId`** only. There is **no** `internalCache` handler for **`Meta::Job`** or the job partition in MVP; read job metadata and adjacency via **`getJobMetaItem`** / **`queryTaskRowsForJob`** or **`ephemeraDB`** directly. Follow [`packages/mtw-gateways/AGENT.md`](../../../../packages/mtw-gateways/AGENT.md) and the package **ownership table**. Ephemera registers **`internalCache.ThinkingResults`** and **`internalCache.ThinkingSchedules`**; pipeline code should prefer those or the package **`fetch`** helpers over raw **`ephemeraDB`** for result and schedule row shapes.
    - **Physical row (thinking result):** on **`TASK#${workItemId}`** + **`Meta::Result`**, persisted items carry **`ThinkingResultEvent`** fields at the **top level** (`schemaVersion`, `generationId`, `workItemId`, `segment`, `ok`, `completedAt`, optional `errorCode`, `errorMessage`, `verbose`) alongside `EphemeraId` and `DataCategory`. Keys are stripped before validation. The persistence slice must match this shape.
    - **Physical row (schedule):** on **`TASK#${workItemId}`** + **`Meta::Schedule`**, persisted items carry **`ThinkingScheduleEvent`** fields at the **top level** (`schemaVersion`, `generationId`, `workItemId`, `segment`, `scheduleStatus`, optional `enqueuedAt`) alongside `EphemeraId` and `DataCategory`. Keys are stripped before validation. The scheduling **`EphemeraDataSource`** (or persistence module it owns) must match this shape; after writes, call **`internalCache.ThinkingSchedules.invalidate(workItemId)`** when reads in the same invocation must see fresh data.
    - **Physical row (job metadata):** on **`JOB#${generationId}`** + **`Meta::Job`**, the item stores **`schemaVersion`**, **`generationId`**, **`jobStatus`**, optional **`createdAt`** (from **`Put Thinking Job Create`**) alongside `EphemeraId` and `DataCategory`. **`workItemIds`** are not duplicated on this row; membership is **`TASK#${workItemId}`** adjacency lines only. Run-level failure fields from **`Put Thinking Job Error`** (`failedAt`, `errorCode`, `errorMessage`, `lastFailedWorkItemId`, updated `jobStatus`, `schemaVersion`) are merged with **`ephemeraDB.optimisticUpdate`** (after **`getItem`**; if the row is missing or has no **`generationId`**, the handler no-ops). Conflicting concurrent updates retry with backoff via the shared optimistic-update path.
- **`lambda/ephemera/dataSource/thinking` (and related ephemera modules):** **`EphemeraDataSource`** code and other ephemera-owned paths perform **writes** (puts, conditional finalize, enqueue/claim) and orchestration. Thinking **result** writes live in [`results/persistThinkingResult.ts`](results/persistThinkingResult.ts). **Schedule**, **job bootstrap**, and **job-level error** writes live under [`scheduling/`](scheduling/): [`persistThinkingSchedule.ts`](scheduling/persistThinkingSchedule.ts) (**`Meta::Schedule`**, overwrite **`putItem`**), [`persistThinkingJobCreate.ts`](scheduling/persistThinkingJobCreate.ts) (**`Meta::Job`** + adjacency **`putItem`**), [`persistThinkingJobError.ts`](scheduling/persistThinkingJobError.ts) (**`Meta::Job`** partial update). **`Meta::Schedule`** uses overwrite **`putItem`** so `scheduled` / `claimed` / `cancelled` transitions replace the row; unlike **`Meta::Result`**, there is no **`nonCollidingPutItem`** gate on schedule. **`mtw-gateways`** does not own mutation paths (see package **Non-goals**).

Task plan split and checklists: [`taskPlanning/lambda/ephemera/dataSource/thinking/AGENT.thinking.planning.md`](../../../../taskPlanning/lambda/ephemera/dataSource/thinking/AGENT.thinking.planning.md) (**Read surfaces in mtw-gateways vs writes in ephemera**).

## Verbose MVP and idempotency

- **Verbose:** MVP defaults to **verbose** artifacts; tightening defaults and retention is a follow-on (see task plan).
- **Idempotent writes:** **`Meta::Result`** uses **`ephemeraDB.nonCollidingPutItem`** (conditional **`attribute_not_exists(DataCategory)`** on the task partition sort key). **First successful write wins** for a given **`workItemId`**; duplicate finalize attempts are treated as **`alreadyFinalized`** (Lambda retry-safe). **`asyncSuppressExceptions`** on the Dynamo client can swallow other failures as a false return value; callers do not distinguish duplicate vs error for MVP. **Job adjacency** rows (**`JOB#${generationId}`** + **`DataCategory` `TASK#${workItemId}`**) use overwrite-safe **`putItem`** so membership stays aligned with finalize. **`Meta::Job`** bootstrap uses overwrite **`putItem`** (retry-safe). **`Put Thinking Job Error`** uses **`optimisticUpdate`** so concurrent patches merge with compare-and-set semantics (retries on conflict). **`Meta::Schedule`** uses overwrite **`putItem`** (status updates are last-write-wins for MVP).
- **Job-level vs per-step failure:** **Per-step** failure is **`TASK#${workItemId}`** + **`Meta::Result`** with **`ok: false`** (and error metadata) for **that** hop. **Job-level** failure is **`Put Thinking Job Error`** updating **`Meta::Job`** so the whole run is not left **`running`** when a critical step fails. Coyote hypothesis often performs **both** in one handler (see **Failure handling** under **Hypothesis bootstrap**); the rows and contracts differ.
- **Write path (results):** [`results/persistThinkingResult.ts`](results/persistThinkingResult.ts) and **`mtw.ephemera.thinking.results`** in [`results/index.ts`](results/index.ts). After a new result insert, **`internalCache.ThinkingResults.invalidate(workItemId)`** runs for read-after-write.
- **Write path (schedule + job partition):** **`mtw.ephemera.thinking.scheduling`** in [`scheduling/index.ts`](scheduling/index.ts) is the **authoritative writer** for **`Meta::Schedule`**, **`Meta::Job`**, and job adjacency on **`JOB#${generationId}`**; Coyote and other callers **orchestrate** via **`send...`** helpers only. The DataSource subscribes to **`api.ephemera`** **`Put Thinking Schedule`**, **`Put Thinking Job Create`**, and **`Put Thinking Job Error`** (header names and payloads: [`../../AGENT.event.md`](../../AGENT.event.md)). Ingress uses **`sendPutThinkingSchedule`**, **`sendPutThinkingJobCreate`**, and **`sendPutThinkingJobError`** in [`../apiEphemera.ts`](../apiEphemera.ts) (not CoyoteGame bus events for schedule or job rows). [`persistThinkingSchedule.ts`](scheduling/persistThinkingSchedule.ts) handles schedule lines; [`persistThinkingJobCreate.ts`](scheduling/persistThinkingJobCreate.ts) and [`persistThinkingJobError.ts`](scheduling/persistThinkingJobError.ts) handle **`Meta::Job`** and bulk adjacency. After each schedule write, **`internalCache.ThinkingSchedules.invalidate(workItemId)`** runs; job rows are not cached in **`internalCache`** for MVP. Hypothesis / pipeline code should prefer the **`send...`** helpers when enqueueing or bootstrapping jobs so work stays on the same internal command path as other **`api.ephemera`** durability; persist modules may be called directly only where **`messageBus.flush()`** ordering is already guaranteed without an extra send.
- **Bus ingress (results):** the results DataSource subscribes to internal **`Thinking Result`** envelopes whose **`header.dataSourceKey`** is **`mtw.ephemera.coyoteGame`** (publisher). The hypothesis pipeline posts those envelopes via **`sendCoyoteThinkingResult`** in [`hypothesisThinkingPersistence.ts`](../coyoteGame/generators/pipelines/hypothesis/hypothesisThinkingPersistence.ts) (not **`api.ephemera`**). **`mtw.ephemera.thinking.results`** validates **`getContent`** with **`isThinkingResultEvent`** and persists **`Meta::Result`**.

## Hypothesis bootstrap (Coyote pipeline)

When [`generateHypothesis`](../coyoteGame/generators/pipelines/hypothesis/generateHypothesis.ts) runs, [`hypothesisThinkingPersistence.ts`](../coyoteGame/generators/pipelines/hypothesis/hypothesisThinkingPersistence.ts) executes **once at run start** (before LLM hops):

- Mint **`generationId`** and one **`workItemId`** per **`ThinkingSegment`** that will run (`candidates`, `planSelect`, `narrativeBeats`). Harness **`runUntil`** / **`runOnly`** modes bootstrap **only** segments for that invocation (not always all three).
- Post **`Put Thinking Job Create`** (`jobStatus: 'running'`, optional `createdAt`) then **`Put Thinking Schedule`** pre-items (`scheduleStatus: 'scheduled'`, `enqueuedAt`) for each active segment.
- **Immediate durability:** commands use a dedicated bus lane `thinkingBootstrap:${uuidv4()}`, then **`await messageBus.flush(laneId)`** so **`mtw.ephemera.thinking.scheduling`** persists before Bedrock work. This does not reuse the Coyote handler's `hypothesisLane:*` (nested lane flush is intentional).
- Ids are stored on **`CoyoteHypothesisPipelineState.thinking`** for later slices (results emit, job error). Production passes **`messageBus`** from [`internalCache/index.ts`](../../internalCache/index.ts).

**Results emit (success path):** after each segment completes, [`coyoteHypothesisPipeline.ts`](../coyoteGame/generators/pipelines/hypothesis/coyoteHypothesisPipeline.ts) calls **`emitHypothesisThinkingResult`** with segment-specific **`verbose`** (see builders in **`hypothesisThinkingPersistence.ts`**). Envelopes use lane **`thinkingResults:${generationId}`** and **`await messageBus.flush(laneId)`** before the next hop. Emit points: **`seamCombineRender`** (`candidates`), **`parsePlanSelectionHandoff`** (`planSelect`), **`parseNarrativeBeatRecord`** (`narrativeBeats`). Harness **`runUntil`** / **`runOnly`** end at the same step indices so only bootstrapped segments that finish emit.

**Failure handling (all failures after bootstrap):** when **`runPipeline`** returns **`ok: false`** and **`CoyoteHypothesisPipelineState.thinking`** is set, [`finalizeHypothesisThinkingOnRunFailure`](../coyoteGame/generators/pipelines/hypothesis/hypothesisThinkingPersistence.ts) runs **before** the pipeline mapper. It maps **`failedStepName`** to a **`ThinkingSegment`** where applicable, posts **`Thinking Result`** with **`ok: false`** (plus **`errorCode`**, **`errorMessage`**, failure **`verbose`**) for that segment when it is active for the harness, then **`sendPutThinkingJobError`** so **`Meta::Job`** is not left **`running`**. Both use lane **`thinkingResults:${generationId}`** with a single **`flush`**. Steps with no segment mapping (e.g. **`loadRoomObjects`**) still mark the job failed without a step result row. Product stub vs rethrow behavior in the mapper is unchanged.

## Harness alignment (lambda-owned types)

**Segment** values in contracts align with routing keys such as **`candidates`**, **`planSelect`**, **`narrativeBeats`**. Verbose result payloads are **`unknown`** at the shared contract boundary; server code aligns them with harness inject shapes in [`../coyoteGame/generators/pipelines/hypothesis/coyoteHarnessInjectTypes.ts`](../coyoteGame/generators/pipelines/hypothesis/coyoteHarnessInjectTypes.ts) and related fixtures.

## Implementation status

Coyote hypothesis invokes **`finalizeHypothesisThinkingOnRunFailure`** on run failure after bootstrap. Client **API** and **EventBridge** replay for schedule remain in the task plan. This `AGENT.md` is the durable anchor for keys, lifecycle, and links; avoid duplicating full architecture here.
