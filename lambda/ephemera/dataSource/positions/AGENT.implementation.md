#### Adding a cross-host manipulation apply coordinator

Use when an atomic operator transfers an **`Object`** node between **membership hosts** (v1: room <-> character inventory). Cross-lane hub: [`../../diegeticLogic/AGENT.implementation.md`](../../diegeticLogic/AGENT.implementation.md). Actions egress playbook: [**Adding an atomic position-manipulation operator**](../actions/AGENT.implementation.md#adding-an-atomic-position-manipulation-operator).

1. **Authority** --- every object-lifecycle membership change (spawn/place/remove/drift-repair/take-hold/drop/give) reaches the kernel through **`positions/manipulation/membership/`** (`executeObjectMove`/`executeMembershipTransfer`), a single pipeline. Import shared primitives (**[`ludicGraph/`](ludicGraph/)**, **`buildObjectMovedFact`**, transact item builders).

2. **Ingress** --- register envelope guard in [`subscribedEvents.ts`](subscribedEvents.ts); route in [`index.ts`](index.ts). If the operator is a **membership move**, it very likely does **not** need a new execute module: name its host pair and route to [`commitAttempt`](manipulation/commitAttempt.ts). `give` is the worked example --- `(CHARACTER# -> CHARACTER#)` needs no new code below ingress.

3. **Post-persist bundle** --- do **not** write one. The kernel already streams **`Object Moved`** first, seeds **`internalCache.Positions`** on every committed graph, invalidates the affordance deliverable for Room hosts, and publishes **`RoomUpdate`**. Add only what is genuinely verb-specific. Contract: [Cross-host object membership-changed bundle](AGENT.contract.md#cross-host-object-membership-changed-bundle-object-move-takehold--drop--give).

4. **Graph transact** --- plan (shared adapter, or the Synthesize executor when the operator needs live grounding), then **`commitStepSequence`** only. **Must not** add `update*LudicGraphs` forks or a route-specific wrapper over the kernel.

5. **Fact shape** --- extend [`buildObjectMovedFact.ts`](manipulation/membership/buildObjectMovedFact.ts) for eligible host ids; **must not** introduce a parallel fact type for membership-only moves.

6. **Per-operator checklist**

| Operator | Host direction | Intent payload | Planning + kernel | `RoomUpdate` / affordance scope |
| --- | --- | --- | --- | --- |
| **`takeHold`** | room -> character | `objectIds`, `roomId`, `characterId` | the object-move route (`commitAttempt`) -> Synthesize executor -> `commitStepSequence` | Room hosts only |
| **`drop`** | character -> room | `objectIds`, `roomId`, `characterId` | the same, host pair reversed | destination room |

The **intent payload** column is the only per-operator row that genuinely varies. Everything right of it is shared, and the narration verb is derived from the host direction rather than declared --- so a new membership-move operator adds an ingress guard and a dispatch branch, and nothing else.

7. **Tests** --- ingress unit tests under **`manipulation/membership/*.test.ts`** and [`manipulation/commitAttempt.test.ts`](manipulation/commitAttempt.test.ts); routing in [`receivePaths.integration.test.ts`](receivePaths.integration.test.ts)'s **`Ludic Network Change Requested`** describe block.

### `ludicGraph/` (play manipulation model)

Host-bound **`EphemeraLudicGraph`** class --- membership + relational simulation; sole in-memory primitive for kernel, transact reducers, and read-only actions observation. Spec: [`ludicGraph/AGENT.md`](ludicGraph/AGENT.md).

**Boundary classifier.** [`expandValidate/interactionUnderTransfer.ts`](ludicGraph/expandValidate/interactionUnderTransfer.ts) answers what a move does to each relational edge it severs. Every peer edge defers, so its `dissolve` outcome has no producer. It is kept as the no-judgment class reserved for a future LLM tier, and a producer should not be added without that tier.

**`ConnectedTo` kind sites.** The kind is spelled in three module-private `HOST_RELATIONAL_EDGE_KINDS` Sets that must change together (`mtw-interfaces/ts/ephemeraMeta.ts`, [`ludicGraph/baseClasses.ts`](ludicGraph/baseClasses.ts), [`publishedEvents.ts`](publishedEvents.ts)); a Set literal has no exhaustiveness check against the union. Symmetry is one helper, `ephemeraEdgeEndpointsEqual` (used by `edgesMatch`), plus sorted endpoint keys in `collapsedEdgeIdentityKey` and `stubPortIdFromEdge`. `EphemeraLudicGraph.equals` stays positional on purpose: it compares edge lists, and a reversed edge in the same slot is a representational difference it does not erase. `applyDeparture` routes a deferred `ConnectedTo` to a `dissolveRelationalEdge` repair, as for any non-`Custom` defer.

**Shelved: a part leaving its whole has no challenge.** A `ConnectedTo` boundary edge defers, but `attemptActionsFromBoundaryOutcomes` ([`expandBoundaryChallenges.ts`](../actions/commandAttempt/expandBoundaryChallenges.ts)) has a challenge type only for `Custom`, so it throws on a deferred `ConnectedTo` (pinned by a test). Unreachable until a producer can tear a part out of its whole. **Trigger:** the first slice whose move can leave a `ConnectedTo` edge on a mover's boundary.

**Host serde.** `fromCharacterMeta` / `fromObjectMeta` / `fromFeatureMeta` / `fromAreaMeta` are thin, host-named wrappers over one shared `fromPlainHostMeta` body (direct `ludicGraph` field read, trivial empty default). `fromRoomMeta` is the one irregular case --- it layers the `seedFromActiveCharacters` absent-value fallback on top of the same decode. Rule: [Host storage: one shared serde, one documented exception](AGENT.contract.md#host-storage-one-shared-serde-one-documented-exception).

**Presence descent is unimplemented, and that is the entry.** Behavior lives **nowhere** today. The emitters --- [`resolvePresenceMoves.ts`](manipulation/membership/resolvePresenceMoves.ts) (a move reparents the mover's binding, and joins on a collision), [`containmentPopulationSteps.ts`](manipulation/containment/containmentPopulationSteps.ts) and the `createComponent` step (a component's hostless `PRESENCE#Base` at birth) --- write **one binding per rehost, facing one host, with no arity check**, and nothing cascades into a moved thing's interior. Depth in the presence structure comes from **graphs nesting** (a host's interior is its own shard, reached by external address), never from a traversal: a move names one entity, and its hosted contents travel with its shard.

**The presence structure is a DAG, and it is built.** A binding's parents are a stored set (`fromHostPresences`), so a thing that sits identically under several parents holds one binding, written once and seen from every parent. Upward walks (`hasPresenceAncestor`, `roomsForHost`, `presenceRooms`) are breadth-first with a visited set, so they cost what the forest walk did. Arity is the positive rule in [`AGENT.contract.md`](AGENT.contract.md#presence-nodes-cover-consolidation-and-the-single-write-path): each parent binding whose cover lists a node is named by exactly one of that node's bindings. Sharing is stored, never inferred from equal covers; the one caller that writes a share is the spread. A descent constructor (a child needing one binding per parent bucket it appears in, [PR-C1](../../../../taskPlanning/lambda/ephemera/dataSource/positions/AGENT.presence.corpus.planning.md#pr-c1-the-contraption-in-two-rooms-and-whether-covers-nest)'s *port arity descends*) is still unwritten, but it no longer has to copy a child's binding once per parent.

**A second, related prediction parked here for the same reason (presenceNodes Slice 5, PN-23 clause 2):** the emitters above mint no `Remainder` and the type no longer has one: a mint writes an empty cover, and the cover index (`addPresenceBinding`, `repairPresenceBinding` and the move) adds each child's entry to its parent's cover as the pointer is written. `ludicCache`'s fold copies a binding's explicit entries as written. **Computing a carve-out of explicit entries beside the room's empty Area carve-out is unbuilt, gates nothing today, and is owed by no current slice** --- the same posture as the descent prediction above, and for the same reason: no constructor needs a partial cover yet. Decided under PN-23 of `AGENT.presenceNodes.planning.md`, a presence-nodes migration plan closed and deleted 2026-09-18; this paragraph is its forwarding address.

**Producers and routing (monotone covers).** Every cover is explicit entries, and each producer writes the entries it means; none relies on a complement.

| Producer | Routes to | Writes |
| --- | --- | --- |
| `createComponent` (`applyStepSequenceCore.ts`) | the new host's own `PRESENCE#Base`, hostless | `{ members: [] }`: a new component has no members |
| `rootStep` (`containmentPopulationSteps.ts`) | a parent with no binding: mints its Base (a Room or Area without one, any other parent with none at all) | `{ members: [] }`; each child's placement writes its own entry through the cover index |
| Population placing a child | the parent's Base, via `childParentBindingIdOf`; a parent with several bindings and no Base is skipped with a warning | a child's first binding is Base; a non-first binding writes `[]`, like the room's Area carve-out |
| `addPresenceBinding` / `repairPresenceBinding` with `fromHostPresences` | every named parent binding (the step carries the binding's whole parent set after the write; `[]` is hostless) | the cover index (`writeCoverIndex`): an entry onto each parent's cover and off each parent the write drops; a repair that leaves another host names its parents there as `previousParents` so the entries come off |
| The planner's F steps (`resolvePresenceMoves`: `reparentPresenceBinding`, `joinPresenceBindings`, and `addPresenceBinding` for a minted Base; applied in `kernel/reparentPresenceBinding.ts`, `joinPresenceBindings.ts`, `splitPresenceBinding.ts`) | a destination parent binding, or no parent | a reparent writes entries onto each gained parent and off each lost one and leaves cover and children alone; a join unions the parents and covers of the bindings it merges, swaps them for the survivor in each child, and the planner writes the joins one level down for children that collide (`cascadeHosts` in the footprint). To no parent: the binding is left parentless and removed at the run's end (`settleParentless`, with the pieces in `kernel/endOfRunRules.ts`), Base becomes hostless, and children fall through to `PRESENCE#Unplaced` only if no other parent on the host covers them; empty Unplaced is removed |
| A mover with no binding at all (`resolvePresenceMoves`) | gets `PRESENCE#Base` minted ahead of its first reparent | an `addPresenceBinding` step; the id is always Base |

Bystanders write only the room's characters row, never a cover. `unpointedBindingOf` (`presenceParent.ts`) finds the binding with no parent pointer; the sensors are `coverageViolationsOf` and `lacksBase` (report-only, in the cover-drift sweep). Retired with the complement: the `Remainder` cover sentinel, `unclaimedComponentNodes`, the split, join and release steps, and the Base migration.

**Known residual, a multi-binding whole's contents (PR-12 obligation A).** A move names one binding and keeps its id, and a host holds a mover's node while any binding of it points there, so moving, scrubbing or destroying a multi-binding host no longer demints a binding or drops membership. A scrub reparents each binding to one destination and joins them into one, with the joined bindings' children re-pointed to the survivor. A child listed under two of them ends holding two bindings under the survivor, which the planner joins one level down (and names the hosts of that cascade as `cascadeHosts`; it no longer refuses it). Re-partitioning contents when a host's binding count changes is PR-12 obligation A in [`AGENT.presence.planning.md`](../../../../taskPlanning/lambda/ephemera/dataSource/positions/AGENT.presence.planning.md#open-decisions-design--plan-only); rules in [`AGENT.contract.md`](AGENT.contract.md)'s binding-addressed move rule.

**Shelved: authored placement into a multi-binding parent.** WML names a parent by component key and cannot name a binding, since bindings are ids ephemera mints. So when cache-time population places a child into a parent with several bindings (a Feature authored into two rooms, then a child authored into that Feature), there is no binding for the child to name. `fromHostPresence.presence` is required, so population refuses that placement: it logs a warning and writes nothing (`containmentPopulationSteps`). **Gate:** lifting [C2](../../../../taskPlanning/lambda/ephemera/dataSource/positions/AGENT.abstractionLayers.corpus.planning.md#c2-the-rope-in-two-rooms-refused-at-the-gate)'s refusal of authored multi-hosting. Whoever lifts it owes WML a way to say which part of a multi-hosted parent a child sits in (or a rule that picks one), then a population path that writes it. No authored component has more than one parent today.

**Shelved: a later move of a spread Object is crude.** A take (the destination is the acting character) of an Object held in several hosts is allowed unconditionally and lifts it out of every host (`alsoLeaving`); every other destination still refuses as `multiPresent` (`transferPreconditionFailure`, `attemptCandidates.ts`). The take does not ask whether the hosts came from a spread (one shared binding) or from drift (distinct bindings, which the take joins in hand), and there is no un-spread ("pull the rug off the table"). **Next refinement:** lift the refusal only when every host holds a parent of one shared binding. **Trigger:** the first play that needs to move a spread Object anywhere but into a hand, or the ConnectedTo plan's OD-3 (a rope across rooms), which meets the same gate by another representation.

**Shelved: open phrasing for a spread.** The front end is a closed phrase template (`matchContainmentTemplate.ts`) behind the `transferMembership` intent's optional spread field. Teaching the LLM fallback to produce the spread intent is later work, and the intent is shaped so the fallback can produce it unchanged. **Trigger:** a player phrasing the template misses.

**Shelved: the room header lists a spread Object twice.** `ludicCacheRoomObjectContents` reads each cover forward, and a spread Object's one binding sits in both parents' covers, so it appears as a room-level object and as the host's content. `objectSpreadPayoff.integration.test.ts` pins this. It is the user's call whether the header should dedupe or show the Object where it is spread; nothing is fixed. **Trigger:** the first render complaint, or the refinement of the take rule above.

**Shelved: where a removed authored object's contents go when its binding has several parents ([PR-26](../../../../taskPlanning/lambda/ephemera/dataSource/positions/AGENT.presence.planning.md#open-decisions-design--plan-only)).** `contentDestinations` (`manipulation/containment/removeAuthoredObject.ts`) reads each of the removed object's bindings with `parentOf`, which throws on a multi-parent binding, so de-authoring a spread Object throws. Not reachable today: it runs only when an authored object is de-authored, and CoyoteGame has no authored objects yet. **Trigger:** the first authored object that can be spread and de-authored; answer PR-26 first.

**Shelved: do Feature and Area bindings exist in the dev data, and does the drift path reach them?** Deferred by the user 2026-10-11, because Coyote Game uses neither Features nor Areas. The dev world held no presence nodes at all when this was asked, so either containment population never ran on it (its components predate population, and `cacheAsset` emits only for changed ones) or it ran and the bindings were never written. The cover heal finds children from the parent's stored `PartOf` edges, so if Area and Room graphs carry none, Room-in-Area and Feature-in-Room bindings stay unwritten and the heal would have to read each parent's authored children instead (ephemera can, through `internalCache`'s component data). **First check when it matters:** does a `Meta::Area` row's graph hold its Rooms and their `PartOf` edges? **Trigger:** whatever first uses Features or Areas in play.

**Two things already preserve that choice at no cost, and both must survive refactoring.** `EphemeraPresenceCoverEntry` is `{ host, presence }` ([`ephemeraMeta.ts`](../../../../packages/mtw-interfaces/ts/ephemeraMeta.ts)), so a cover entry **can** name a shared binding rather than only a bare node. And any integrity check must read *a host **one or more** of whose covers names this presence node* --- **written as *exactly one* it forecloses the DAG silently**, by making it fail validation rather than by anyone deciding against it.

### `ludicCache/` (the `ludicCache` prototype, Channel C)

The `ludicCache` prototype (Channel C): the types, the pairwise reducer pieces, and the whole-cache rebuild seeded at a host. A room-seeded consumer (the command referent pool, the room affordance header) reads the room's stored row, rebuilt once per change ([Stored row](#stored-row-read-mark-rebuild)); a non-room seed keeps the per-request cold rebuild. The rules are in [`AGENT.contract.md` --- Ludic cache staleness and rebuild](AGENT.contract.md#ludic-cache-staleness-and-rebuild). Fulfils the `EphemeraLudicCacheData` naming reservation in [`internalCache/AGENT.md`](../../internalCache/AGENT.md). Mental model: [`AGENT.ludicNetwork.md`](AGENT.ludicNetwork.md) section 5.

#### Stored row: read, mark, rebuild

The rules are in [`AGENT.contract.md`](AGENT.contract.md#ludic-cache-staleness-and-rebuild); this is how they are built.

- **Read.** One `getItems` (`BatchGetItem` over the two exact keys (three with `withCharacters`), `ConsistentRead`), not a prefix `Query`: a prefix would also match any future `LudicCache::<tenant>` row, which could be large. Results come back unordered (tell the rows apart by `DataCategory`) and `UnprocessedKeys` is not retried, so a throttled key reads as an absent or stale row and is rebuilt: slower, never wrong. The marker lives in its own small row because `UpdateItem` is billed on the larger of the item's before and after size, and the marker is bumped far more often than the cache is rewritten.
- **Rebuild.** `singleFlight` (`coalesce` mode) keyed on (`roomId`, marker version), so a request for N+1 is never pooled into a flight building N. The build step writes with `ephemeraDB.conditionalPutItem` and **catches its own condition failure, returning the newer row it finds**. Every caller, builder or follower, applies one rule to the flight's result: labelled with the version it read, return it; otherwise reread, bounded. `singleFlight` carries a build failure to followers as `SingleFlightFailedError` (with the lead's error summary), which the reader treats as a collision. `putItem` and `primitiveUpdate` swallow errors outside developer mode, so a refused monotonic write or a failed bump would go unreported; the stale-marking path uses `conditionalPutItem` and `strictPrimitiveUpdate`.
- **Fresh reads.** The rebuild drops the per-invocation name memos after reading the marker, and reads graphs through `getFreshLudicGraph` (the shared gateway read is eventually consistent and behind the `Positions` memo, so is not used). **Residual:** component reads are eventually consistent, so a rebuild inside the replication window of a rename could read the old name; the event hop between the asset write and the bump is longer than that window in practice.
- **Marking in the kernel.** `commitStepSequence` resolves the rooms before the transact from the non-capture footprint, against pre-commit graphs (a destroyed host's pre-commit graph still walks up to its former parents), and the bump items ride the existing `cascade`. A room set that cannot be resolved fails the commit rather than skipping the mark, and a transact that would exceed DynamoDB's 100 actions is refused with a clear error. `TransactWriteItems` conflicts per item, so concurrent commits in one room collide on its marker; the kernel's catch-all retry on `TransactionCanceledException` (its optimistic lock, which re-reads and re-validates) absorbs that. That retry only fires because `exponentialBackoffWrapper` matches `err.errorType ?? err.name`: SDK errors carry `name`, and matching `errorType` alone never retried live.
- **Name sources.** A `Component Updated` marks the component's rooms (not a character's: a rename marks nothing, since the cache holds no character name, and `onCharacterComponentUpdated` invalidates `CharacterMeta` and the room memos and publishes `RoomUpdate` per room); since `cacheAsset`/`decacheAsset` stream `Component Updated` for every component in their diff, a room's participating assets changing is covered by the room's own event. A zone change into or out of Canon marks every room using the asset. `Canon Updated` only reorders the global Canon list, which no room stack reads, so nothing subscribes to `CanonSet`/`CanonAdd`/`CanonRemove`. No path renames an improvised Object or Character after creation; if one is added, it is a new name source.
- **The completeness test and its gap.** [`invalidationCompleteness.integration.test.ts`](ludicCache/invalidationCompleteness.integration.test.ts) proves each *known* writer marks. A graph writer that bypasses both `commitStepSequence` and the known out-of-kernel callers, and is not added to the case list, is not caught. **When adding a writer, search by what the code does** (`optimisticUpdate` / `transactWrite` on a host `Meta::` row), not by name.
- **Characters row (the authority for a room's characters).** `ludicCache/charactersRow.ts` (shape and pure readers in `charactersRowShape.ts`). `charactersRowItemsFor` builds the kernel's `cascade` items from `membershipChangesOf` (which, for a bystander, reads the rooms from the mover's *own* bindings, not from room-graph nodes), **one `PrimitiveUpdate` per room** (a transaction may not name an item twice), with `#` placeholders passed through `PrimitiveUpdate.ExpressionAttributeNames`. The row is top-level attributes keyed by character id because a `SET` on a path into a missing map fails while `SET #id` creates the item. `readRoomCharacters` is a strongly consistent `getItem`; an absent row is an empty room. There is no rebuild: the adjacency index is a legacy projection and is not a source. **Readers:** `getRoomCharacterList` (`internalCache/hydrateRoomRoster.ts`, the seam for fan-outs, `publishMessage`, perception and Coyote collection) and `repairRoomOccupancyDrift` read it through `readRoomCharacters`; the room header reads it inside `readLudicCache`'s one `getItems` (`withCharacters: true`). **Existing data and healing:** `migrateRoomBystanders` (`manipulation/membership/`, called first by `repairRoomOccupancyDrift`) writes the row (`if_not_exists`) for each character whose own binding points at the room, drops ghosts, and strips the character nodes from a legacy room graph under a condition on the graph read, bumping the marker. The diagnostics `roomOccupancyDriftSweep` is row-forward: it queries the `LudicCache::Characters` rows and compares each character against session adjacency and membership containers. **Still on the graph, by design:** object hosts (`resolveHostedNodeWmlData`) and the `ludicGraph` class's own `characterIds` getter. **Deploy order for a legacy dev instance:** run the sweep (or `repairRoomOccupancyDrift` per room) before the new cache code serves traffic, then confirm the sweep reports clean.
- **Rollback.** Point the consumers back at `buildLudicCache` and stop reading the rows; they are droppable and nothing else reads them. Hit latency, rebuild cost and row size are measurements, not rollback triggers.

#### Rebuild mechanism: findings the fold implements

Graduated from the retired `ludicCache` rebuild plan. Where this text says *finding N*, it means the numbered items below; the plan's decision and slice labels that survive in the prose (D1, D2, LR-8, Slice 2b, PN-*, and similar) name decisions made in plans that no longer exist, and are kept only so a reader can trace the reasoning. Persistence of the cache (a stored row, rebuild on stale read) is described in [Stored row](#stored-row-read-mark-rebuild).

1. **Compose at crossing ports, never at nodes.** A merge may collapse two edges sharing a **crossing-port** terminal; never two sharing a **node** terminal. Crossing ports are not referents and nodes are, so composing across a port destroys nothing and composing across a node destroys something a player could have named. **A possible/impossible rule, not a preference.**

   **Its "required primitive" is already shipped, and the hazard it warned of is moot.** The finding demanded a port-aware terminal discriminator, on PQ-9's finding that `isEphemeraObjectId` would *crash* on a `#`-separated port address. Ports are structured values now: `EphemeraLudicPortAddress` is `{ owner, port }`, `EphemeraLudicTerminalId` is a union, `isEphemeraLudicPortAddress` exists, and [`ephemeraMeta.ts`](../../../../packages/mtw-interfaces/ts/ephemeraMeta.ts) states outright that *the parsed shape IS the stored shape --- no string form*. `mergeReducer.ts` already discriminates this way. **Do not re-import the string-parsing hazard.**
2. **General edge-merge contains edge-stitch, and the argument is not efficiency.** Stitch is merge over a chain of length two. The general form is arguably *less* code --- stitch carries a case split (append a crossing and rewrite the endpoint, versus prepend and rewrite the start) that composition does not, since direction falls out of which terminal is shared. **The narrow form is the same code with an unsettled premise baked in as a restriction.** This is the finding D1 turns on.
3. **Entitlement and retention are two questions, and only the first is load-bearing.** *May the reducer consult a graph it has already merged?* --- **yes, settled**, forced by [LC8](../../../../taskPlanning/lambda/ephemera/dataSource/positions/AGENT.abstractionLayers.ludicCache.corpus.planning.md#lc8-the-spring-in-the-box-and-in-the-contraption)'s sub-graphing argument. *In memory, or shard ids re-read on demand?* --- ~~same semantics, different cost~~ **one mechanism, decided 2026-10-13: re-read by shard id through `internalCache.Positions`, whose per-invocation memo is the in-memory retention** (D4).
4. **Do not drop anything during sub-graphing is rejected, recorded so it is not re-proposed.** It would make the cache self-describing and remove recovery entirely, and it fails for the reason the cache exists: **unbounded size is what the ragged frontier and `interiorConsolidated` are there to control.**
5. **Recovery is a keyed walk, not a scan.** Every terminal that becomes newly present is a trigger; look it up against retained graphs; follow the chain, possibly across several graphs, until it grounds. **Complete because an edge is recoverable only if at least one terminal is now present, and every such terminal is a trigger.** **No index and no new store is needed** --- the port record's egress list supplies the outward half and the interior graph's own edges supply the inward half. What remains is a **lookup discipline**: both halves must be consulted, and neither direction quietly implemented one-way. A one-way walk **silently returns nothing**, which is the failure mode to write a test against rather than to guard. **This is the *both-sides navigability constraint*** --- named here because [the presence corpus's PR-11 option (A)](../../../../taskPlanning/lambda/ephemera/dataSource/positions/AGENT.presence.corpus.planning.md) cites it by that name, and because it began life as a demand on [PQ-4](../../../../taskPlanning/lambda/ephemera/dataSource/positions/AGENT.abstractionLayers.planning.md) to *build* a field. It is no longer that: the shipped port record already satisfies it from both directions, so what PQ-4 would have owned is discharged and only the consumer discipline survives.
6. **Triggering on newly-present terminals collapses stitching and recovery into one mechanism.** Starting from *edges left dangling in the cache* under-covers, because an edge dropped while **both** terminals were ungrounded leaves no dangling trace. Triggering on **every terminal that becomes representable** covers it --- and extending a cache edge into a host that just consolidated and recovering an edge sub-graphing discarded become the same operation. **This is a simplification only if a terminal is looked up the same way in both stores**; if the cache is searched one way and retained graphs another, the two mechanisms are back wearing one name.

**What the shipped code already does with all of this.** [`collapseCrossingPorts`](ludicCache/mergeReducer.ts) implements findings 1 and 2 for the **pairwise** case: it composes at crossing ports only, excludes presence ports, asserts both legs agree on identity fields, rewrites the port terminal to the real interior node, and groups by identity so two ports collapsing to the same `(from, to, kind)` land on one record with two `chains` entries side by side. [`subGraphFromNodes`](ludicGraph/presenceSubGraph.ts) implements the cut, with stub ports minted transiently and never persisted. **Findings 3, 5 and 6 have no code at all** --- they are about the fold across many graphs, which is Slice 3.

#### How stub-port ids match --- a property of the construction, not a rule it obeys (recorded 2026-09-14)

**Read the status of this note before using it.** What follows is an **emergent property** of choices made elsewhere, not a design commitment anything is obliged to honour. It is written down because it is **demonstrably hard to reconstruct from the code** --- it took a wrong turn and three corrections to state it in the conversation that produced it --- and because working code now **relies on it as an assumption**. **If the decisions below change and this stops holding, that is a refactor cost, not a design regression**, and nobody should read this note as a veto on revisiting them.

**The property.** A stub port's id comes out **identical from both sides of the cut, computed independently, with neither side seeing the other**. [`subGraphFromNodes`](ludicGraph/presenceSubGraph.ts) gets there by minting from `stubPortIdFromEdge(edge)` on the edge **before** rewriting, so one bucket (`fromIn`) and the mirror bucket (`toIn`) still produce the same string. **That is the whole matching mechanism:** two buckets discover they hold halves of one edge not by comparing the halves but by both naming the port after the whole.

**What it is downstream of --- the list to check if it ever needs revisiting.** (i) Buckets are cut **independently**, each `subGraphFromNodes` call seeing only its own node set, with no shared state and no coordination; (ii) the id is **purely derived** from the edge's own fields and is **transient, never persisted** (LR-1); (iii) there is **no allocator** --- no central authority assigning port ids that both sides could instead consult. **The property is a consequence of those three together.** Change (i) to union-then-cut --- which Slice 2b already does for the cross-bucket-same-parent case --- and much of the matching problem does not arise, because nothing is severed. Introduce (iii) and side-dependent ids become available. **--- amendment (2026-09-14): the id's shape now has a *second* consumer, and a change to it has to satisfy both.** As of the `STUB-` prefix (see the standing-cleanup entry in Recommended order), a stub id is relied on to be **recognizable as a stub by inspection**, because a minted stub and an authored `EphemeraCrossingPort` are otherwise indistinguishable --- `isCrossingPort` narrows on `kind`, and a stub carries the severed edge's own `kind`. Before this, the only constraint on the id was that both sides derive it identically; now it must *also* be sniffable. **The two constraints are independent and can be broken separately**, so anyone revisiting the list above should check the prefix requirement too --- it is not downstream of (i)--(iii).

**What it rules out *while those choices stand*.** Any id component derived from *which side this bucket is on* breaks matching outright rather than degrading it --- the halves get different ids and never meet. **So a `STUB-${chainId}-${in|out}` scheme does not work here:** a tag that distinguishes the two halves destroys the match, and a tag both sides agree on is a constant that distinguishes nothing. **Proposed and set aside on this ground 2026-09-14 --- conditionally, and the condition is the list above**, not a judgement about the scheme itself.

**A related category distinction, since both mechanisms are called "ports."** Same-host severing splits **one** edge with two real terminals across two buckets of **one** host, and the halves must agree on a minted id --- `stubPortIdFromEdge`'s job. A chain crossing a host boundary is **two** legs in **two** hosts' graphs meeting at an **authored** `EphemeraCrossingPort`, whose `kind` is *"authored at mint time, never derived from an edge."* **`chainId` is a chain identity and belongs to the second; the key `stubPortIdFromEdge` derives is an edge identity serving the first.** ~~Keying one on the other is a category swap in either direction.~~ **--- amendment (2026-09-14, same day): the category distinction stands, the prohibition does not, and `stubPortIdFromEdge` now mints `STUB-${chainId}` when a `chainId` is present.** The two mechanisms really are different, and nothing above is retracted --- but *being different categories* does not make one unusable as a key for the other; it makes it usable only where the coarser identity is **injective at the scope the key must be unique over**. Both halves of that are already recorded in this note and were simply never put together: (1) this note's own chain-shape paragraph records, from the author, that doubling back through one host is neither required nor desirable, hence **at most one leg of a given chain per host** --- so within one cut the chain→leg map is injective; and (2) the `stubPortIdFromEdge` rename entry establishes that the requirement is uniqueness **among stub ports in this cut**, not global uniqueness --- *"nobody asks whether a stub port id is globally unique."* At that scope the chain names the leg unambiguously. **What the amendment does not do is make this an invariant:** it is admissible *because of* an unenforced property of construction, which is this note's whole subject. **So the violation is now made loud rather than trusted** --- `subGraphFromNodes` throws on two stubs minting one id in a single cut, because the failure would otherwise be silent (`fromFieldPayload` copies `ports` without deduping, unlike `addPort`, and the merge resolves legs with `.find`, so the second crossing would simply vanish). **Distinguish this from the scheme still rejected above:** that one was `STUB-${chainId}-${in|out}`, and the fatal component was the **side tag**, not the `chainId`. This scheme carries no side tag.

**Chain shape, from the author (2026-09-14), recorded as design input rather than as verified behaviour --- nothing mints a `chainId` yet.** A chain is *"the graph equivalent of a bezier-curve specification: two end-points, and a third *pick some points to route through* specification."* A chain-qualified leg within one host is one of three shapes: (a) it connects two **internal** terminals; (b) it connects an internal terminal to a **port on the host's boundary**; (c) it runs **port-to-port**, where a multi-present host is a useful mediating path between otherwise very distant nodes (a *Computer System* abstraction carrying network connections). **And doubling back --- routing through one host twice --- is neither required nor desirable**, which yields the uniqueness property the rejected scheme was reaching for: **at most one leg of a given chain per host.**

**Each shape meets the cut differently, and (c) is the one to check before relying on any of this.** (a) is severed normally and mints a stub --- **so chain-bearing edges do reach the stub path**, and `chainId`'s presence in the key is *not* vestigial. (b) is skipped by [the already-port-qualified branch](ludicGraph/presenceSubGraph.ts) --- *"nothing is minted, since that port's home graph is the other side"* --- and passes through whole. **(c) has no clearly-correct handling in the shipped cut:** `fromIn`/`toIn` test `ephemeraLudicTerminalOwner`, which returns `.owner` for a port address, so a port-to-port leg's membership turns on whether the host's own id is in the bucket's node set --- and the node set always contains the **root**. **If `hostId` and the root coincide the leg is kept whole in *every* bucket (duplicated); if they do not it is dropped from every bucket (lost).** Neither is obviously right, **this is LC10's shape exactly**, and it should be traced against real data rather than settled from this note. **--- amendment, 2026-09-14: both readings above are superseded by the endpoint-status rule** (see Recommended order). **(b) no longer passes through whole**, and the branch quoted here is gone: its justification --- that a port-qualified far endpoint means the far node belongs to a different graph --- was false, since a node of *this* graph can name a port on its own interior, and PR-C2 had already settled that a cross-host edge is two edges rather than one. **(c) is no longer contingent on whether `hostId` and the root coincide:** both are neutral by rule, so the leg is kept in every bucket deliberately. **The sentence to keep is the conditional one** --- under the old code (c) survived *only* because the two coincided, which is to say **LC10's shape was being preserved by the very collision that was about to be fixed**, and fixing classification without deciding LC10 would have dropped it silently from every bucket. That is why the three changes are coupled rather than sequential. **LC10 itself is still open.**

**What the shipped code already does about two routes, which decides nothing but narrows the question.** [`collapseCrossingPorts`](ludicCache/mergeReducer.ts) accumulates a `chains` entry per collapse and then groups by `collapsedEdgeIdentityKey` --- **which includes `chainId`**. So two routes that **share** a `chainId` merge into one record carrying both routes side by side, and two routes with **different** `chainId`s stay as two records. **Both branches of [LC11](../../../../taskPlanning/lambda/ephemera/dataSource/positions/AGENT.abstractionLayers.ludicCache.corpus.planning.md#lc11-the-same-contact-reached-two-ways)'s fork are therefore already implemented, selected by `chainId` equality** --- so that case's real question is not *what does the code do* but **whether one relationship reached two ways should be minted with one `chainId` or two**, which is a question about chain minting and has no code to read it off.

#### Shelved: incremental `ludicCache` maintenance

**Not built, and not on the roadmap until the persisted cache's measurements ask for it.** The cache is rebuilt whole on a stale read; nothing is stored per edge or per node to support incremental repair. If a later iteration builds incremental update, it builds its own maintenance structure **beside** the cache, never inside the reasoning record. The arguments below are the prior design for that structure, retired 2026-10-13 when `supportedBy` was removed from the cache edge. Labels such as D8, D9, D11 and PN-16 refer to the retired plan's decisions.

##### Support structure for composed edges (was D8)

**Does the cache edge's `chains` field keep its name?** It collides with P8's **chain** --- a chain is an addressing route across boundary crossings, named by `chainId`, which sits on **every leg** of it; `chains` is the renamed `crossings`, holding **one ordered host list per independently-consolidated route**. Unrelated concepts, same word, and **both can sit on one collapsed edge**. **Chronology, because it explains the collision rather than excusing it:** P8's leg/chain split settled 2026-08-28, the rename landed 2026-09-10 under LR-8, and PR-8's verdict cell documents the rename in detail without noting the clash. ~~**Rename (`consolidationRoutes`, `hopsEntered`) or document and live with it** --- but decide before Slices 3--6 add consumers. #### Shelved: participant characters

A participant is a character relationally entangled with its room (holding a rope tied to a post, or holding up a tent-pole). None can exist today: `takeHold` refuses any boundary edge the attempt does not dissolve, and `planCharacterMoveTransfer` does no chain sweep. Every character is a bystander, and the code names the rule for bystanders (`isBystanderMove`, `manipulation/kernel/bystander.ts`), so the participant work amends one predicate. Sketched so far:

- **Status from the graph.** A participant is a character whose shard holds a crossing or boundary edge to a host outside its own subtree.
- **Room-side representation.** A participant's node returns to the room graph, which carries its entanglement edges (a rope tied to a post is an edge between the room's graph and the character's, and needs the character's node on the room side to land on). Becoming a participant writes the room graph and marks the room; ceasing to be one removes the node. The characters row already lists every present character, participant or not, so the roster stays on one source.
- **Inclusion.** Expand the participant's whole shard rather than following edges, so the walk's "no edge is ever followed" rule holds.
- **Found vs available.** Decide per actor at read time, from the cover path: a node held by another character has `CHARACTER#other` on its path.
- **Prerequisites.** `takeHold` must be relaxed, and character moves need a chain sweep.

## Navigate orchestration (not in `membership/`)

| Concern | Location |
| --- | --- |
| Convergent character-route orchestration (plan, commit, present) | [`navigate/orchestrateCharacterMove.ts`](navigate/orchestrateCharacterMove.ts) (3g) --- one entry point for navigate/home/connect/disconnect, `repairRoomOccupancyDrift`'s ghost purge, and `repairCharacterLegalPlacement`'s relocation call; builds and compiles the plan via `planCharacterMoveTransfer` (which uses [`compilePositionKernelOp`](manipulation/kernel/compile/compilePositionKernelOp.ts)), then calls [`commitAndPresentStepSequence`](manipulation/kernel/commitAndPresentStepSequence.ts) |
| Presentation (arrival-room header, render kicks, **and leave/arrive narration**) | Inside `commitAndPresentStepSequence`, via [`presentStepSequence`](manipulation/kernel/presentStepSequence.ts): publishes narration and delivers the arrival header (a `describe` step) only when the compiled plan carries one (`to !== null`) |
| Player navigate ingress (stream only) | [`../actions/index.ts`](../actions/index.ts) emits `Character Navigate`; positions executes |
| Leave/arrive world copy | **Compiled and reported synchronously for every character route** --- there is no membership fan-in. Every route (navigate/home/connect/disconnect/ghost-purge) presents through `commitAndPresentStepSequence` above. Rules: [`AGENT.contract.md` --- Narration and presentation](AGENT.contract.md#narration-and-presentation). |

**Navigate compiles its op once, before commit** (3e) --- `planCharacterMoveTransfer` builds and compiles the full plan, including the header slot, since `to` and the character's assets (the only inputs the perspective-key lookup needs) are both known pre-commit. `orchestrateCharacterMove` commits and presents that same compiled plan rather than rebuilding it.

**Object moves compile once**, because they have no header slot and carry no narration: a second compile would be two chances to disagree in exchange for nothing. The plan holds mutation steps only; the attempt's audiences are captured by `commitAttempt`'s own steps, and its lines delivered by `deliverNarrationUnits`.
