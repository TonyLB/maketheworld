# `mtw.ephemera.messageOrchestration`

**Status:** Scaffolded 2026-07-26 --- bus-only, non-replayable `EphemeraDataSource`. Registered from [`../../app.ts`](../../app.ts) via `import './dataSource/messageOrchestration'`. Mechanism only: no real producer or consumer is wired onto it yet. See [`taskPlanning/lambda/ephemera/AGENT.messageOrchestrationConsolidation.planning.md`](../../../../taskPlanning/lambda/ephemera/AGENT.messageOrchestrationConsolidation.planning.md) for the full migration this DataSource is Phase 2 of.

## Role

Ordered-array/settle-then-flush replacement for `OrchestrateMessagesData`'s before/during/after tree (`internalCache/orchestrateMessages.ts`): Plan/Synthesize's compiler declares a bundle's slots up front, in compiled order; each slot is resolved independently and reports its content; once every slot has reported (or the bundle settles with some slots unresolved), the resolved subset flushes to `messageBus.publish` in the original compiled order. Decouples resolution order from delivery order without a graph/tree abstraction.

| Layer | Owner |
| --- | --- |
| Instruction compile (produces the ordered slot list) | Plan/Synthesize |
| Slot resolution (a mutation's fact-streaming, the perception kernel's per-step render) | Whichever component owns that slot |
| Bundle correlation, settle, ordered flush | **`mtw.ephemera.messageOrchestration`** (this package) |
| Terminal WebSocket delivery | `messageBus.publish` (`PublishMessage`), called directly from this DataSource's fan-in handler |

## Ingress

Two `api.ephemera` command kinds, both in-process only (no EventBridge --- see [`../localApiEvents.ts`](../localApiEvents.ts)'s header comment on the pattern this reuses):

- **`Message Bundle Declared`** (`MessageBundleDeclareCommand`, [`localApiEvents.ts`](localApiEvents.ts)): `{ bundleId, slots: [{ slotId, expectedPublishType, componentId?, perspectiveKey?, targets?, threadKind? }] }` --- the full, compiled-order slot list, emitted once per bundle. The four optional fields are the slot's **match key** (MO-9, see below); only slots a render-completion handler needs to self-match against populate them (e.g. navigate's header slot) --- slots resolved by a producer that already knows its own `bundleId`/`slotId` statically (navigate's leave/arrive slots) leave them unset.
- **`Message Slot Reported`** (`MessageSlotReportCommand`, [`localApiEvents.ts`](localApiEvents.ts)): `{ bundleId, slotId, message }` where `message` is a `PublishMessage` (`../../messageBus/baseClasses.ts`) --- the eventual bus-publish payload, held until the bundle settles rather than published immediately.

Envelope guards + typed send-helpers (`sendMessageBundleDeclared`, `sendMessageSlotReported`): [`subscribedEvents.ts`](subscribedEvents.ts), mirroring `dataSource/perception/subscribedEvents.ts`'s `sendCharacterPerceptionRequested` shape. **No caller invokes these yet** --- Phase 3 (navigate) and Phase 5 (object-look kernel) wire producers in.

## Fan-in / settle mechanics

[`messageOrchestrationFanIn.ts`](messageOrchestrationFanIn.ts) is a `FanInCluster` spec on the shipped `FanInCluster`/`FanInClusterStore` framework (`packages/mtw-lambda-patterns/ts/dataSource/AGENT.implementation.md`'s fan-in section; concrete precedent `dataSource/perception/membershipPresentationFanIn.ts`). Cluster identity is `bundleId`, known on every leg --- **unlike** membership presentation's provisional/unify case, **either** leg kind (`bundle-declare` or `slot-report`) may seed the cluster, so a slot-report that arrives before its bundle-declare still joins the same cluster instead of being silently dropped. `completed` is "the bundle has been declared and every declared `slotId` has a registered leg." Settle is `messageBus`'s existing deferral tail (`registerDeferral`/`flushAndSettle`/`settleDeferrals()`), the same mechanism membership presentation and object manipulation presentation fan-in already use for "optional leg never arrives" --- registered here via a manual `messageBus.registerDeferral('fanIn-mtw.ephemera.messageOrchestration', { onClear, afterSettled })` ([`index.ts`](index.ts)), mirroring `dataSource/perception/index.ts`'s pattern rather than `FanInClusterStore`'s own `registerDeferral` convenience method --- the convenience method calls `settleDeferrals()` unconditionally, which throws if `setHandlerContext` was never called (i.e. no event has reached `receiveEvents` yet); the manual form guards on `getOpenPartialCount() > 0` first, same as perception's two-store wiring.

## Publish behavior

On completion (all slots reported) or settle (deferral tail fires with some slots still unresolved), the cluster's `handler` iterates the declared slot list **in compiled order** and calls `messageBus.publish` for each slot that has a report, skipping any that never resolved ("tolerantly failed" --- Phase 1's design). **`CreatedTime` assignment (shipped, Phase 4):** the handler assigns each published message's `createdTime` itself --- `baseTime + offset`, `offset` incrementing only over slots that actually resolved (so a skipped slot leaves no gap) --- **overwriting** whatever `createdTime` the reported `PublishMessage` already carried. This is deliberate, not a placeholder for later work: the bundle is the one place that knows the full, correctly-ordered resolved set at flush time, so it is the right layer to assign relative ordering, rather than requiring every producer to compute a mutually-consistent time independently (that degenerates into beat-anchor/clamp arithmetic --- tried and reverted this same session, see [`AGENT.messageOrchestrationConsolidation.planning.md`](../../../../taskPlanning/lambda/ephemera/AGENT.messageOrchestrationConsolidation.planning.md) Phase 4's second follow-up note). This does **not** yet replace `publishMessage/index.ts`'s separate `allOffsets()`-based `CreatedTime` computation for non-bundled `messageGroupId` traffic --- that migration is still Phase 6.

`expectedPublishType` on each declared slot is carried through but **not validated** against the reported message's `displayProtocol` in this slice --- there is no caller yet that could violate it; deferred, not silently dropped.

## Slot match index (MO-9)

Before this, correlating a render completion (`Render Pertains` / `Generation Started` / error-deferred) to its bundle slot ran entirely through `internalCache/perceptionThreads.ts`: the `characterMove` thread row carried `bundleId`/`slotId` as passthrough fields, stamped on at `register()` time, and `messageOrchestration` itself never recognized anything --- it was a passive receiver. [`slotMatchIndex.ts`](slotMatchIndex.ts) fixes this: `SlotMatchIndex` is a bucket-per-`(componentId, perspectiveKey)` index, populated from each declared slot's match key when a bundle-declare leg routes (`index.ts`'s `receiveEvents` calls `registerSlot` per slot), mirroring `PerceptionThreads.list`'s own "bucket of candidates, caller disambiguates" shape rather than being folded into `FanInCluster`'s `canAcceptLeg` (there is no precedent in this codebase for matching a leg against several structurally-compatible candidates by secondary criteria inside `FanInCluster` --- every existing cluster gates on one strict scalar identity field).

- `findDeclaredSlotMatch(componentId, perspectiveKey, threadKind)` (exported from [`index.ts`](index.ts)): returns every declared slot matching the key, each entry wrapping the actual declared `MessageOrchestrationSlotSpec` (`{ bundleId, spec }` --- not a hand-copied subset, so nothing can drift out of sync with what was declared). The caller (`dataSource/perception/orchestrate.ts`'s `deliverCharacterMoveMessage`) disambiguates further by exact `targets` equality when more than one candidate comes back --- two movers can race into the same room with the same `perspectiveKey` (perspectiveKey is derived from room-asset visibility, not the character) in one invocation, so `targets` is the only field that still tells them apart.
- `consumeSlotMatch(componentId, perspectiveKey, bundleId, slotId)`: removes a matched entry once its slot has been reported, so a later render event for the same key can't re-match an already-resolved slot. Called explicitly by the caller, not hooked into `sendMessageSlotReported` (a generic helper also used by `publishMembershipPresentation.ts`, which never touches this index).
- Cleared via the same `onClear` callback `index.ts` already registers for `messageOrchestrationFanInStore`.
- **Iteration-1 scoping, deliberate bridge:** matching stays *pull* --- the render-completion handler queries this index --- rather than `messageOrchestration` subscribing to the render stream itself. Whether it ever should is MO-5's separate, later concern, not resolved here.
- `bundleId`/`slotId` were removed from `PerceptionThreads`' `CharacterMovePerceptionThread` row once this shipped --- `PerceptionThreads` no longer carries any messageOrchestration correlation data.

## Content ingress / delivery seam (MO-10)

MO-10's fan-out fix (single-flight kickoff; shared *content* reported once, each listener building its own addressed *envelope*) turned out to need two loosely-coupled state machines, not one mechanism bolted onto `SlotMatchIndex`. Reviewing the "who does what" surfaced that MO-7's symmetric placeholder/terminal fill is actually two separate resolve waves against the same key --- if the first wave drained the match bucket (as `SlotMatchIndex`'s single-match design does), the second wave would have nothing left to stand on. Splitting the concern in two removes the assumption that a drain was ever necessary:

- **Ingress** ([`contentIngress.ts`](contentIngress.ts), `ContentIngressIndex`): owns content resolution, kickoff single-flight, and replay. Bucket-per-`(componentId, perspectiveKey, threadKind)` (a three-part key, since Ingress buckets are already disambiguated by `threadKind` rather than filtering at read time the way `SlotMatchIndex` does). `registerSlot(bundleId, spec)` returns `{ shouldKickoff: true }` the first time a bucket is touched (the caller is responsible for invoking its own kickoff) or `{ shouldKickoff: false, replay }` on every later registration against a still-live bucket, where `replay` is every event recorded so far --- the "current in-memory concurrent render, handled ad hoc" case (a second same-invocation listener registering after content has already started resolving) made coherent. `reportContent(componentId, perspectiveKey, threadKind, content)` records the event and returns every currently-registered listener --- it never removes a listener, so a placeholder wave and a later terminal wave for the same key both see the same, full listener list. `RenderContent = Omit<PublishMessage, 'targets' | 'messageId'>` is the concrete type encoding the content-vs-envelope split: Ingress only ever deals in content, never in an addressed `PublishMessage`. Deliberately has no `messageBus` dependency --- it returns data; the caller decides what to do with it.
- **Delivery** (the existing [`messageOrchestrationFanIn.ts`](messageOrchestrationFanIn.ts) plus the new [`deliveredSlotIndex.ts`](deliveredSlotIndex.ts), `DeliveredSlotIndex`): owns bundle waiting/delivered state. Waiting-stage consolidation ("if both a placeholder and a terminal report land on one slot before the bundle completes, only the latest is delivered") needed no new code --- `MessageOrchestrationFanInCluster.registerLeg`'s `this.reports.set(leg.slotId, message)` is a plain `Map` overwrite, already doing this. The one real gap: `FanInClusterStore.completeReadyPartials` (`packages/mtw-lambda-patterns/ts/dataSource/fanInClusterStore.ts`) permanently drops a cluster once `completed`, so a slot-report leg arriving after a bundle has already flushed (the terminal, once the placeholder already completed the bundle) has nothing to standalone-deliver against and would silently orphan. `DeliveredSlotIndex` closes this: `MessageOrchestrationFanInCluster.handler()` --- via the `deliveredSlotIndex` field on `MessageOrchestrationFanInHandlerContext`, now required alongside `messageBus` --- snapshots `{ slotId, targets, messageId }` for every slot that actually resolved by flush time (not for a slot that never reported --- "tolerantly failed", nothing to standalone against) at the moment it publishes. A later slot-report leg for the same `(bundleId, slotId)` can be checked against `deliveredSlotIndex.find(bundleId, slotId)` before being routed into `FanInClusterStore.route()`: a hit means standalone delivery, a miss means route normally.
- **One-way call direction**: Ingress calls into Delivery (reporting content as it resolves); Delivery never reaches back into Ingress.
- **Not yet wired to a real caller.** `orchestrateNavigate.ts`'s `PerceptionThreads.register` call and `orchestrate.ts`'s `PerceptionThreads.list`-driven `characterMove` loops still run the old single-match path (`SlotMatchIndex`/`findDeclaredSlotMatch`/`consumeSlotMatch`, still present and still the only production mechanism in use). Migrating those call sites onto `ContentIngressIndex`/`DeliveredSlotIndex` --- retiring `PerceptionThreads`' `characterMove` role entirely, not just its `bundleId`/`slotId` passthrough fields --- is the next slice ("Expanded scope, per MO-10" in the planning doc below).

## Explicit non-goals (this slice)

- No real producer or consumer wired onto `ContentIngressIndex`/`DeliveredSlotIndex` yet --- see "Content ingress / delivery seam (MO-10)" above; the migration is the next planning-doc sub-item.
- No real producer or consumer wired in --- Phase 3 (navigate's tail), Phase 4 (`publishMessage`'s `CreatedTime` computation), and Phase 5 (object-look's perception kernel) migrate existing call sites onto this DataSource later.
- No `CreatedTime`/offset computation (Phase 4).
- No EventBridge / DataSource-to-DataSource subscription --- API Ingress only for this iteration (MO-5 in the planning doc, deliberately deferred).
- No outbound stream events --- output is a direct `messageBus.publish` call, not a further stream republish ([`publishedEvents.ts`](publishedEvents.ts) is a `busOnly` placeholder).
