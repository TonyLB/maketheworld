# `mtw.ephemera.messageOrchestration`

**Status:** Scaffolded 2026-07-26 --- bus-only, non-replayable `EphemeraDataSource`. Registered from [`../../app.ts`](../../app.ts) via `import './dataSource/messageOrchestration'`. **`characterMove` fully migrated onto this DataSource (2026-07-27, MO-10):** `orchestrateNavigate.ts` and `dataSource/perception/orchestrate.ts`'s three render-completion handlers no longer touch `PerceptionThreads` for `characterMove` at all --- see "Content ingress / delivery seam (MO-10)" below. Other threadKinds (`roomDescription`, `roomHeaderBroadcast`, etc., Phase 7) still go through `PerceptionThreads` directly. See [`taskPlanning/lambda/ephemera/AGENT.messageOrchestrationConsolidation.planning.md`](../../../../taskPlanning/lambda/ephemera/AGENT.messageOrchestrationConsolidation.planning.md) for the full migration this DataSource is Phase 2 of.

## Role

Ordered-array/settle-then-flush replacement for `OrchestrateMessagesData`'s before/during/after tree (`internalCache/orchestrateMessages.ts`): Plan/Synthesize's compiler declares a bundle's slots up front, in compiled order; each slot is resolved independently and reports its content; once every slot has reported (or the bundle settles with some slots unresolved), the resolved subset flushes to `messageBus.publish` in the original compiled order. Decouples resolution order from delivery order without a graph/tree abstraction.

| Layer | Owner |
| --- | --- |
| Instruction compile (produces the ordered slot list) | Plan/Synthesize |
| Slot resolution (a mutation's fact-streaming, the perception kernel's per-step render) | Whichever component owns that slot |
| Bundle correlation, settle, ordered flush | **`mtw.ephemera.messageOrchestration`** (this package) |
| Terminal WebSocket delivery | `messageBus.publish` (`PublishMessage`), called directly from this DataSource's fan-in handler |

## Ingress

Two `api.ephemera` command kinds, both in-process only (no EventBridge --- see [`../localApiEvents.ts`](../localApiEvents.ts)'s header comment on the pattern this reuses):

- **`Message Bundle Declared`** (`MessageBundleDeclareCommand`, [`localApiEvents.ts`](localApiEvents.ts)): `{ bundleId, slots: [{ slotId, expectedPublishType, componentId?, perspectiveKey?, targets?, threadKind? }] }` --- the full, compiled-order slot list, emitted once per bundle. The four optional fields are the slot's **match key** (MO-9, see below); only slots a render-completion handler needs to self-match against populate them (e.g. navigate's header slot) --- slots resolved by a producer that already knows its own `bundleId`/`slotId` statically (navigate's leave/arrive slots) leave them unset.
- **`Message Slot Reported`** (`MessageSlotReportCommand`, [`localApiEvents.ts`](localApiEvents.ts)): `{ bundleId, slotId, message }` where `message` is a `PublishMessage` (`../../messageBus/baseClasses.ts`) --- the eventual bus-publish payload, held until the bundle settles rather than published immediately.

Envelope guards + typed send-helpers (`sendMessageBundleDeclared`, `sendMessageSlotReported`): [`subscribedEvents.ts`](subscribedEvents.ts), mirroring `dataSource/perception/subscribedEvents.ts`'s `sendCharacterPerceptionRequested` shape. **No caller invokes these yet** --- Phase 3 (navigate) and Phase 5 (object-look kernel) wire producers in.

## Fan-in / settle mechanics

[`messageOrchestrationFanIn.ts`](messageOrchestrationFanIn.ts) is a `FanInCluster` spec on the shipped `FanInCluster`/`FanInClusterStore` framework (`packages/mtw-lambda-patterns/ts/dataSource/AGENT.implementation.md`'s fan-in section; concrete precedent `dataSource/perception/membershipPresentationFanIn.ts`). Cluster identity is `bundleId`, known on every leg --- **unlike** membership presentation's provisional/unify case, **either** leg kind (`bundle-declare` or `slot-report`) may seed the cluster, so a slot-report that arrives before its bundle-declare still joins the same cluster instead of being silently dropped. `completed` is "the bundle has been declared and every declared `slotId` has a registered leg." Settle is `messageBus`'s existing deferral tail (`registerDeferral`/`flushAndSettle`/`settleDeferrals()`), the same mechanism membership presentation and object manipulation presentation fan-in already use for "optional leg never arrives" --- registered here via a manual `messageBus.registerDeferral('fanIn-mtw.ephemera.messageOrchestration', { onClear, afterSettled })` ([`index.ts`](index.ts)), mirroring `dataSource/perception/index.ts`'s pattern rather than `FanInClusterStore`'s own `registerDeferral` convenience method --- the convenience method calls `settleDeferrals()` unconditionally, which throws if `setHandlerContext` was never called (i.e. no event has reached `receiveEvents` yet); the manual form guards on `getOpenPartialCount() > 0` first, same as perception's two-store wiring.

## Publish behavior

On completion (all slots reported) or settle (deferral tail fires with some slots still unresolved), the cluster's `handler` iterates the declared slot list **in compiled order** and calls `messageBus.publish` for each slot that has a report, skipping any that never resolved ("tolerantly failed" --- Phase 1's design). **`CreatedTime` assignment (shipped, Phase 4):** the handler assigns each published message's `createdTime` itself --- `baseTime + offset`, `offset` incrementing only over slots that actually resolved (so a skipped slot leaves no gap) --- **overwriting** whatever `createdTime` the reported `PublishMessage` already carried. This is deliberate, not a placeholder for later work: the bundle is the one place that knows the full, correctly-ordered resolved set at flush time, so it is the right layer to assign relative ordering, rather than requiring every producer to compute a mutually-consistent time independently (that degenerates into beat-anchor/clamp arithmetic --- tried and reverted this same session, see [`AGENT.messageOrchestrationConsolidation.planning.md`](../../../../taskPlanning/lambda/ephemera/AGENT.messageOrchestrationConsolidation.planning.md) Phase 4's second follow-up note). **Phase 6 shipped (2026-07-27):** `publishMessage/index.ts`'s separate `allOffsets()`-based `CreatedTime` computation for `messageGroupId` traffic is removed --- `messageGroupId` had zero production producers left (`OrchestrateMessagesData.newMessageGroup()` has no callers outside its own test/`clear()`), so the branch was dead code; `computedCreatedTime` is now always `baseTime + index` in payload-array order for any payload that doesn't carry its own explicit `createdTime`. `publishMessage/index.ts` is now the last thing that would need touching before `OrchestrateMessagesData` itself can be deleted (Phase 8).

`expectedPublishType` on each declared slot is carried through but **not validated** against the reported message's `displayProtocol` in this slice --- there is no caller yet that could violate it; deferred, not silently dropped.

## Slot match index (MO-9, removed)

`SlotMatchIndex` (`slotMatchIndex.ts`, bucket-per-`(componentId, perspectiveKey)`, `findDeclaredSlotMatch`/`consumeSlotMatch` exported from `index.ts`) was the original MO-9 single-match mechanism: a render-completion handler queried it for one declared slot, disambiguating multiple candidates by exact `targets` equality. MO-10 superseded it for `characterMove` with `ContentIngressIndex`'s fan-out-to-every-listener model (below); once that migration shipped, nothing called `findDeclaredSlotMatch`/`consumeSlotMatch` any more, and `index.ts`'s `receiveEvents` only kept populating the index on every bundle-declare as unused dead work. **Removed entirely** (2026-07-27, the "Retreat `PerceptionThreads` to reactive-broadcast-only" slice): `slotMatchIndex.ts` deleted, along with its import, instantiation, the two exported query functions, the bundle-declare population call, and its `onClear` entry in `index.ts`. Whichever Phase 7 threadKind migrates next builds against the `ContentIngressIndex`/`DeliveredSlotIndex` seam (below) directly, not this retired mechanism.

## Content ingress / delivery seam (MO-10)

MO-10's fan-out fix (single-flight kickoff; shared *content* reported once, each listener building its own addressed *envelope*) needed two loosely-coupled state machines, not one mechanism bolted onto `SlotMatchIndex`. Reviewing the "who does what" surfaced that MO-7's symmetric placeholder/terminal fill is actually two separate resolve waves against the same key --- if the first wave drained the match bucket (as `SlotMatchIndex`'s single-match design does), the second wave would have nothing left to stand on. Splitting the concern in two removes the assumption that a drain was ever necessary:

- **Ingress** ([`contentIngress.ts`](contentIngress.ts), `ContentIngressIndex`): owns content resolution, kickoff single-flight, and replay. Bucket-per-`(componentId, perspectiveKey, threadKind)` (a three-part key, since Ingress buckets are already disambiguated by `threadKind` rather than filtering at read time the way `SlotMatchIndex` does). `registerSlot(bundleId, spec)` returns `{ shouldKickoff: true }` the first time a bucket is touched (the caller is responsible for invoking its own kickoff) or `{ shouldKickoff: false, replay }` on every later registration against a still-live bucket, where `replay` is every event recorded so far --- the "current in-memory concurrent render, handled ad hoc" case (a second same-invocation listener registering after content has already started resolving) made coherent. `reportContent(componentId, perspectiveKey, threadKind, content)` records the event and returns every currently-registered listener --- it never removes a listener, so a placeholder wave and a later terminal wave for the same key both see the same, full listener list. `RenderContent` (a distributive `Omit<PublishMessage, 'targets' | 'messageId'>` --- a plain `Omit` over a union type collapses to only the fields common to every member, so this needed the standard naked-type-parameter conditional idiom to distribute properly) is the concrete type encoding the content-vs-envelope split: Ingress only ever deals in content, never in an addressed `PublishMessage`. Deliberately has no `messageBus` dependency --- it returns data; the caller decides what to do with it.
- **Delivery** (the existing [`messageOrchestrationFanIn.ts`](messageOrchestrationFanIn.ts) plus [`deliveredSlotIndex.ts`](deliveredSlotIndex.ts), `DeliveredSlotIndex`): owns bundle waiting/delivered state. Waiting-stage consolidation ("if both a placeholder and a terminal report land on one slot before the bundle completes, only the latest is delivered") needed no new code --- `MessageOrchestrationFanInCluster.registerLeg`'s `this.reports.set(leg.slotId, message)` is a plain `Map` overwrite, already doing this. The one real gap: `FanInClusterStore.completeReadyPartials` (`packages/mtw-lambda-patterns/ts/dataSource/fanInClusterStore.ts`) permanently drops a cluster once `completed`, so a slot-report leg arriving after a bundle has already flushed (the terminal, once the placeholder already completed the bundle) has nothing to standalone-deliver against and would silently orphan. `DeliveredSlotIndex` closes this: `MessageOrchestrationFanInCluster.handler()` --- via the `deliveredSlotIndex` field on `MessageOrchestrationFanInHandlerContext`, required alongside `messageBus` --- snapshots `{ slotId, targets, messageId, createdTime }` for every slot that actually resolved by flush time (not for a slot that never reported --- "tolerantly failed", nothing to standalone against) at the moment it publishes. A later slot-report leg for the same `(bundleId, slotId)` is checked against `deliveredSlotIndex.find(bundleId, slotId)` **before** being routed into `FanInClusterStore.route()` (`index.ts`'s `receiveEvents`): a hit publishes standalone (reused `targets`/`messageId`; `createdTime` is `Math.max(already.createdTime + 1, getCurrentTimestamp())` --- the same clamp shape as `orchestrate.ts`'s `terminalCreatedTime`, but anchored to the placeholder's exact bundle-assigned time rather than an unrelated wall-clock/thread estimate, since the standalone terminal is a genuinely later, distinct transcript event, not a reuse of the placeholder's own `CreatedTime` --- **shipped Phase 6, 2026-07-27**), a miss routes normally.
- **`MessageId` stability is the Delivery layer's job, assigned lazily, not pre-declared.** `MessageOrchestrationFanInCluster.registerLeg` mints a messageId on a slot's *first* report (`supplied ?? mint()`) and carries it forward on every later overwriting report for the same slot (`supplied ?? existing?.messageId ?? mint()`) --- a general improvement to the cluster itself (every bundled slot gets this, not just `characterMove`), and it means `MessageOrchestrationSlotSpec` needs no `messageId`/`createdTime` fields at all. (An earlier design draft considered pre-assigning `messageId` at declare time; reviewing it against the cluster's own `reports: Map<slotId, PublishMessage>` --- already the single source of truth for a slot across however many waves report before flush --- showed the cluster is the more robust, simpler home for this.)
- **One-way call direction**: Ingress calls into Delivery (reporting content as it resolves); Delivery never reaches back into Ingress.
- **Wired to `characterMove` (2026-07-27).** `orchestrateNavigate.ts` calls `registerIngressSlot(bus, bundleId, headerSlotSpec, kickoff)` in place of `internalCache.PerceptionThreads.register(...)`, with `kickoff` wrapping `kickPassiveRenderRequestedForCharacterInRoom`. `dataSource/perception/orchestrate.ts`'s three render-completion handlers call `reportIngressContent(bus, componentId, perspectiveKey, 'characterMove', content)` in place of their `PerceptionThreads.list(...)`-driven loops; the four MO-9-era helpers (`disambiguateCharacterMoveMatch`, `deliverCharacterMoveMessage`, `deliverCharacterMoveTerminal`, `publishCharacterMoveGeneratingHeader`) are deleted. `orchestrateCharacterNavigate`'s `beatAnchorTime` parameter was removed (used only for the now-obsolete declare-time `messageId`/`createdTime` pre-assignment --- confirmed via grep it had no other use in that function; its caller, `afterCharacterMembershipNavigateChanged.ts`, still uses `result.beatAnchorTime` independently for `persistRoomStackNavigate`).
- **A real regression found and fixed during the migration:** `handleRenderPertains`'s roster-broadcast fallback (`dataSource/perception/orchestrate.ts`) fired whenever `internalCache.PerceptionThreads.list(...)` returned zero entries. Once `characterMove` stopped registering with `PerceptionThreads`, that would be true for *every* navigate header render, spuriously broadcasting to the whole room roster. Fixed by gating the fallback on `entries.length === 0 && publishedCharacterMove === 0` (the count `reportIngressContent` returns).
- **A confirmed, accepted behavior difference from the old design:** a 3rd+ event for an already-fully-delivered slot (e.g. a duplicated/out-of-order bus event) now gets a redundant standalone re-publish (same `messageId`, a `createdTime` anchored strictly after the original recorded slot's time --- note this is the original `record()`ed value each time, not a chain off the prior standalone's own publish, since a standalone doesn't re-record itself) rather than the old `PerceptionThreads.remove()`-then-nothing-matches silent drop --- `DeliveredSlotIndex` has no "already stood alone once" flag, deliberately, per user confirmation.
- **A pre-existing race condition in the shared `FanInClusterStore` (`packages/mtw-lambda-patterns/ts/dataSource/fanInClusterStore.ts`), exposed and fixed by this migration:** `completeReadyPartials` used to compute `stillOpen` by iterating `this.openPartials` and `await`-ing each ready partial's `handler()` inline, only reassigning `this.openPartials` after the whole loop finished. Two `route()` calls can interleave at that `await` (exactly what happens when Ingress fans the same content out to two listeners, each triggering its own nested `bus.publish()` --- MO-10's own core scenario): both see the same partial as "ready" in `openPartials` before either removes it, so both flush it, duplicating the wire message. Fixed by splitting ready-vs-still-open and reassigning `openPartials` **synchronously**, before awaiting any handler --- the same pattern `settleDeferrals()` already used. This is a shared-library fix, benefiting every `FanInClusterStore` consumer (membership presentation, object manipulation presentation), not just this DataSource.

## Explicit non-goals (this slice)

- `characterMove` is the only threadKind wired through Ingress/Delivery so far --- Phase 7 (object-look's perception kernel and the other directed-consequence threadKinds: `roomDescription`, `featureDescription`, `knowledgeDescription`, `objectDescription`, `sessionOrientationRender`, `sessionOrientationAffordances`) migrates the rest later. Those threadKinds still register/list/update/remove directly on `internalCache.PerceptionThreads`, unchanged by this slice --- migrating them is Phase 7's job, not a gap here.
- `PerceptionThreads`' `CharacterMovePerceptionThread` type and its `register`/`list`/`update`/`remove` support for `characterMove` are removed (2026-07-27, this slice) --- `PerceptionThreads` now serves only the still-unmigrated directed-consequence threadKinds above plus its permanent reactive-broadcast role (`roomHeaderBroadcast`, the `entries.length === 0` roster fallback).
- No `CreatedTime`/offset computation for `publishMessage`'s separate `allOffsets()`-based non-bundled traffic (Phase 6).
- No EventBridge / DataSource-to-DataSource subscription --- API Ingress only for this iteration (MO-5 in the planning doc, deliberately deferred).
- No outbound stream events --- output is a direct `messageBus.publish` call, not a further stream republish ([`publishedEvents.ts`](publishedEvents.ts) is a `busOnly` placeholder).
