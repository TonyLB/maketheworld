# `mtw.ephemera.actions` --- object manipulation pipeline contract

This file records **contracts** only. Mental models: [`AGENT.concepts.md`](./AGENT.concepts.md). Code map: [`AGENT.implementation.md`](./AGENT.implementation.md). The Acme `stableKey` contract still lives in [`AGENT.md`](./AGENT.md#acme-catalog-lines-and-stablekey-normative-contract).

---

## Grounding

- **Grounding is total.** It **must** be handed a complete `ReferentAssignment`. A referent with no `groundedId` and no entry in the namespace it needs **must** throw, as a construction bug; callers **must not** branch on it as a runtime outcome. (A derived referent the world cannot resolve is the assignment builder's to report, before Grounding runs.)
- **Identify matches a span by its forms, and never rewrites it.** A span names a catalog entry exactly when its normalized text, as given or else with a leading article (`a`, `an`, `the`, `some`) peeled, equals the entry's short name; the first form with a match decides, so a name that starts with an article ("the thing") still matches whole. A span with no exact match ranks with its article peeled, in both the lexical and embedding channels. The span itself (in the skeleton, the pool, and every message) stays as written, so neither route peels before Identify ([`enrich/objectManipulation/spanMatchForms.ts`](enrich/objectManipulation/spanMatchForms.ts)).
- **Identify embeds a trimmed span at most once per invocation.** Spans that differ only by a leading article or by case or spacing share one Bedrock embed, even when requested concurrently ([`internalCache/spanEmbeddings/index.test.ts`](../../internalCache/spanEmbeddings/index.test.ts), [`compileAttemptsFromSkeleton.concurrency.test.ts`](enrich/objectManipulation/compileAttemptsFromSkeleton.concurrency.test.ts)).
- **Enumerate owns the joint candidate space.** The product across an attempt's referents **must** be formed before Grounding, and a relation joining an object to itself **must** be dropped there. Grounding and Validation never see one.

## Plan

- **Plan's output is a set of ungrounded attempts, and every fallback emits that same type.** Plan never reads world state: its attempts carry no ids. Every fallback (identity-only, plan-only and joint) takes or proposes attempts, not families, so one producer handles them all.

## Outcomes climb the ladder

- **Abstain hands the command on; every other outcome answers.** The producers are a ladder ordered by cost ([`parseCommand.ts`](parseCommand.ts)): the fast path (the intent rows, then Plan's templates over the command's own tokens and the producer), then classify, then Acme. Plan runs once, on the fast path: no LLM segments the command (the Parse LLM is retired), so classify adds no reading, only realness and shape. A rung's **Abstain** (not understood, FT-3.2) sends the command to the next rung. An **Error** (understood, but forbidden), a **Consult** or an attempt is the answer on whichever rung produced it, and never climbs. Only the top rung's Abstain reaches the player ("I couldn't understand that command."). The Plan LLM fallback takes a slot on this ladder when it is built ([proposal](../../../../taskPlanning/lambda/ephemera/dataSource/actions/AGENT.objectManipulationIterations.planning.md#proposal-deterministic-first-then-an-orchestration-loop-2026-10-25)).
- **The producer maps an outcome by its reason, never by attempt kind** ([`compileAttemptsFromSkeleton.ts`](enrich/objectManipulation/compileAttemptsFromSkeleton.ts)). Not understood is an Abstain: nothing grounds (no catalog, no assignment), no reading survives Identify or the entry checks, or selection is below the floor. A refusal the world gives (the dry run's `illegal`, such as "The table has no cup.") is an Error with its reason, as is the actor's own state (no room, no character) and a stale answer. A pending challenge (`defer`) is an Abstain until the deferred tier judges it. When every attempt is refused, an Error refusal wins over an Abstain one, and an attempt's own Error refusal wins over a pool that only abstains (a take with no room answers its Error, though the bare exit reading beside it survives its entry checks and then grounds nothing).
- **Selection abstains when it has nothing to say.** `selectPlanTuple` returns `error` only with an illegal candidate's reason; no candidates, or nothing legal and no reason, is `abstain`.
- **Plan reading nothing is an Abstain too.** Zero attempts on the fast path climbs (only an empty command, or one over the guard cap); after classify it goes to Acme, then `Unimplemented`. The bare exit reading fits every command, so it is no evidence that a template read one: a command no other template reads goes to Acme, then `Unimplemented`, whatever that reading's Abstain. One a template did read, and Acme does not take, ends at the fast path's Abstain, at classify's confidence.
- **What no template reads, nothing reads until the Plan LLM exists.** A manner word (`carefully get the cup`) or a typo beyond the lexical channel's tolerance makes a command no template fits, and it ends at `Unimplemented` (accepted, user, 2026-10-27: Parse dropped such words, but every command the characterization corpus pins reads the same without it). The Plan LLM, when built, reads what the deterministic rungs hand up (tokens, readings, Identify pools, abstain reasons), not a second segmentation.

## Qualifier

A qualifier is a phrase that names where an object is: "get the cup on the table", "get bag from table".

- **A qualifier restricts; an argument places.** A phrase that describes where something is now restricts which object, and which of its bindings (`view`), a referent means. A phrase that names where something goes ("put cup on table") is an argument, the destination. The preposition is a hint, not a role: "from" can only restrict, while "on" and "in" can do either.
- **Segmentation and attachment are decided in one place: Plan's one match of the templates over the command's tokens** ([`plan/planSkeleton.ts`](enrich/objectManipulation/plan/planSkeleton.ts) `planTokens`, engine [`deterministicTemplate/patternTemplate.ts`](deterministicTemplate/patternTemplate.ts) `matchPattern`). Plan reads the command's own **tokens**, and nothing upstream decides how the command is cut or which span a phrase belongs to.
  - **Tokens are cut at every fixed word a template reads** ([`deterministicTemplate/granuleTokens.ts`](deterministicTemplate/granuleTokens.ts)). The fixed words are first cut into **granules**: two adjacent words of an option stay joined only if they are adjacent in every option where either appears, so each fixed word is in exactly one granule. A command's tokens are its granules where the whole granule appears (never inside a longer word: `on` in `onto`), each punctuation mark on its own, and every other run of words one span token. A word is a run of letters and digits, with an apostrophe or hyphen only between two of them. An option that repeats a word or holds a mark is rejected when the granules are built.
  - **The matcher merges.** A fixed word matches a run of granule tokens equal to one of its options. A span takes any run of one or more tokens holding a word, a template's own fixed words and punctuation marks included (`look at cup` read by the plain look template has the span `at cup`; `take cup.` has `cup .`), its text the tokens re-joined with single spaces. So adding a template changes no reading of a command it does not read completely: its words only cut spans that a merge rebuilds.
  - A template's object and destination are **object phrases**: a span, optionally a closed-set preposition and another object phrase, right-nested ("the cup on the saucer on the table" is the cup on (the saucer on the table)). Each way the template fits is a **reading**: a phrase the object phrase reads is nested onto its span (`ObjectSpanToken.qualifier`, "modifies the referent"); a phrase a fixed word reads is an argument ("modifies the verb"); a preposition inside a span is read by nothing, as part of a name. Each preposition is a link or inside a span, so an object phrase with k prepositions has 2^k readings. Every reading becomes its own attempt, whatever the verb, and the dry run and selection choose. Lowering reads only the qualifier, never which reading produced it.
  - **No pattern leaves a tail unread.** Words outside the closed set stay in a span (`get cup under table` reads the one span `cup under table`), which Identify judges at the ordinary rate.
- **The guard cap: a command holding more than six closed-set prepositions gets no deterministic reading** (`exceedsQualifierCap`, [`plan/qualifierPrepositions.ts`](enrich/objectManipulation/plan/qualifierPrepositions.ts)). The fast path does not claim it and Plan reads nothing from it, so it climbs. Readings multiply with the prepositions (a containment command with k of them has k * 2^(k-1)), so the cap is for pathological input only.
- **A qualifier is an assertion, not a referent field.** Lowering puts an action whose step is `containedBy(subject, qualifyingSpan)` ahead of the action whose referent carries it. No narration unit covers it, and the qualifying span is that action's referent, so Identify resolves it unchanged. Referents and attempts carry no qualifier.
- **The dry run judges it; commit does not.** It is satisfied when **every** binding of the subject's view sits **directly** under the object, whatever the relation. So the whole of a draped cloth fails "on the table" while its table part passes, and a cup on a saucer on the table is not "from table". A candidate that fails it is illegal, so the check removes candidates and disambiguates through ordinary selection. The step's `relation` (`On`, `In`, or absent) is recorded from the closed lexicon (`on`, `on top of`, `off` give `On`; `in`, `inside`, `out of` give `In`, as does a bare `out` from either route; `from` gives none) but is not yet judged. Motion words (`onto`, `into`), spatial words the bindings do not hold (`under`, `behind`, `next to`) and name words (`of`, `with`) are outside the set, and stay inside a span.
- **An unmet qualifier refuses; it is never dropped.** When the subject and the qualifier each resolve but every candidate fails the assertion, the command refuses with "The <host> has no <subject>." (`qualifierErrorMessages`), which claims no relation. A qualifier is never dropped to rescue a take. This governs the qualifiers the matcher reads; surplus text a span absorbs (`hold of the cup`) is priced by Identify, not a qualifier, and can be dropped by a cheaper reading. A qualifying span that matches nothing is the ordinary unknown-span outcome.
- **Every reading reads every span of its fill.** A take or drop names its object, and each qualifier's host through the assertion lowered from it, so no attempt is dropped for a span it leaves unread. A chain (`take cup on saucer on table`) is read by its reading of every span. A drop's tail is read both ways: as where the cup goes ("drop the cup in the box": `drop` is a containment verb, and its move starts at the actor, since a drop releases only what is held), and as a qualifier on what is dropped (the cup that is in the box). The dry run judges both, so a held cup refuses the qualifier reading ("The box has no cup.") and the move into the box is the one left, and a cup not held refuses both as not carried.
- **What the fast path claims** ([`discriminateIntent/deterministicChecks.ts`](discriminateIntent/deterministicChecks.ts)): first, every command an intent row reads whole (`look`, `help`, `home`, `predict`, `wait` and their closed paraphrases, `deterministicTemplate/intentTemplates.ts`), answered by that row's result, never an attempt; the rows run ahead of Plan's templates, so `go home` is `Home` even where an exit is named "home". Then every command one of Plan's templates fits, and since the bare exit template fits any, that is every non-empty command under the guard cap: looks, spreads and navigations are read before classify as takes and puts are. The fast path cuts the command into tokens once, at every deterministic template's fixed words as Plan does. **No gate:** matching reads only tokens, and what the world must make true is Identify's and the dry run's to judge, so a `get` of something absent (`get up`) is Identify's question and a fast-path Abstain climbs. A claim hands the tokens up, and Plan reads every template over them; pieces pass through as typed. A template Plan learns, the fast path learns with it.
- **Every fill is a reading** (user, 2026-10-25). Plan groups the readings by segmentation, the token ranges they cut (two attachments of `put cup on saucer on table` with the same cuts are one fill, and so is the same cut of `drop the cup in the box` from two templates), and the producer takes every fill together (`SkeletonFill`, one per segmentation, on either route). A segmentation is a reading, like an attachment: Identify, the dry run and selection choose among them with real evidence, so nothing picks a fill before that evidence exists. Each attempt reads, and is judged against, its own fill's spans. A `stableRefKey` names a span occurrence (its token range), so one occurrence has the same key in every fill; two occurrences of one text are numbered (`benchRef1`, `benchRef2`). One Identify serves every fill, and identifies each distinct span text once. A resumed answer keeps the fills that hold its keys. The frozen root holds every fill.
- **Exact-fill precedence is a temporary bridge** ([`compileAttemptsFromSkeleton.ts`](enrich/objectManipulation/compileAttemptsFromSkeleton.ts); ladder rung 14 reconsiders it). When some fill has every span matched exactly by Identify, the fills that don't are dropped before the producer. The lexical rank forgives words around a name, so a longer span ("cup from table") would otherwise compete with the exact segmentation, and win when that one is illegal ("take cup from table" must still answer "The table has no cup."). With no fully exact fill, every fill competes, and the thin race asks the player how to cut the command: an accepted limitation until rung 14.
- **The pure pass: a literal name match the world accepts beats a semantic one.** The producer ([`compileAttemptsFromSkeleton.ts`](enrich/objectManipulation/compileAttemptsFromSkeleton.ts) `compileReadings`) tries a **pure pass** before the **full pass**. The pure pass keeps only the fills whose every object span matches a candidate's name by **ordered word subsequence**: the span's words (a leading article peeled, normalized as `SpanEmbeddings` keys are) appear among the name's words in the same order, gaps allowed, whole words only (`cup` and `big cup` match "big red cup"; `cup red` does not match "red cup"; `cup` matches neither "cupboard" nor "teacup"), and the normalized span is at least 3 characters. An exact match is the case where the subsequence is the whole name; exit spans are always eligible. A span no candidate matches is ineligible, and a fill holding one is not in the pure pass. The pure pass grounds its spans by the lexical channel alone over the matching candidates (so every pure fill is on one scale, and no span embeds), then runs the shared dry run and selection. **It succeeds on `CommandAttempt` or `Consult`**, and that is the result (a Consult among pure candidates is accepted: embeddings would not separate them, and a semantic-only candidate is not offered). `Abstain` or `Error` falls through to the full pass on all fills, exactly as without a pure pass, embeddings included; only the returned pass's refusals surface. So `get light` with a "light switch" and a "lamp" takes the light switch without embedding. Exact-fill precedence applies within each pass. A Consult records its `pass` (`'pure' | 'full'`), and a resume starts there: `full` runs the full pass only, so a resume sees the pools that built its Consult; `pure` retries the pure pass and falls through if the world no longer lets it succeed; a row without the field resumes as `full`.
- **Surplus another reading could explain costs more (a score, never a prune).** Each object span carries `structure` (`ObjectSpanToken.structure`): its tokens and the proper sub-runs of them that some complete reading of the command reads as a span of its own, the union across every template and fill (`readFills`). A template that fails to read the command completely contributes nothing, so adding a template changes scores only for commands it reads completely. Identify's lexical channel (only) prices the span's surplus outside the smallest sub-run that holds the whole match at a heavier rate, on top of the ordinary span-side cost: against "pig", `pig in a blanket` scores below `piggy pig piggy`. It applies to the span's surplus only, never a catalog name's extra words (`pig` against "pig in a blanket" takes none). A match whose word pairs cross a sub-run's edge (`man in teh moon` against "man in the moon") takes none, and a name merged across a cut pays a heavier boundary cost in the alignment. Whether the alternative's other spans ground is not consulted, so a merged reading whose alternative fails (`take pig in xyzzy`) stays in the pool and can win. Every candidate stays in the pool with its score.
- **A look reads an object phrase.** The look's object is an object phrase like any template's, so "look at the cup on the table" (and "look cup on table") checks the qualifier before it describes; `look at` / `l at` is a second pattern sharing the builder, so `at` is read as a fixed word in one reading and inside the span in the other. A look is an attempt of kind `look`, so a qualified look's assertions ride beside its narration and are judged by the dry run; the dispatch describes the referent the narration names (`commandAttempt/lookedAtObjectId.ts`).

- **A navigation is an attempt, and its exit a span grounded against the room's exits** ([`plan/matchNavigationTemplate.ts`](enrich/objectManipulation/plan/matchNavigationTemplate.ts)). A movement verb and an exit (`go`, `head`, `walk`, `move`, `travel`, `enter`), or a bare exit name alone, is a template whose span slot declares the exits as its catalog; Identify grounds that span by the exits' exact names, to the room each leads to ([`exitSpanPool.ts`](enrich/objectManipulation/exitSpanPool.ts)), and never against objects, and an object span never against exits. A range read against exits is keyed, and cut, apart from the same range read against objects, so a key names one pool. The reading is an attempt of kind `navigation`, one navigate action whose referent is the exit, pooled and selected with every other reading; a reading whose span grounds nothing drops out alone, so the bare reading that every command carries never sinks another. The dry run judges that the exit is here and leads to that room alone: an exit name two exits here share, to two rooms, refuses every reading of it with the ambiguity (an Error, never a Consult; asking which is shelved). The dispatch sends a navigation through the exit's own stream (`Character Navigate`, `commandAttempt/navigationTarget.ts`), rechecking the exit as the UI's exit click is rechecked, never through the ludic network.

## Validation

- **Validation never grows a candidate.** It checks a complete grounded candidate against what the world forbids, and **must not** re-check what Expansion just built.

## Command attempt

- **The result is derived, never stored.** An attempt's `result` (`pending` / `succeeded` / `impossible`) **must** be computed from its challenges' verdicts, and recording a verdict (`recordVerdict`, pure, addressed by challenge id) **must** be the only way it changes.
- **One impossible challenge refuses the whole attempt**, regardless of any other challenge's state.
- **A challenge propagates nothing.** What a met verdict permits is its own action's desired result; no verdict may widen another action.
- **Adjudicate runs actions-side, per candidate, before the dry run.** Verdicts **must** ride the published attempt. Positions honors them at commit and never judges --- that half of the rule is [`../positions/AGENT.contract.md`](../positions/AGENT.contract.md)'s (the `attempt` paragraph under the `mtw.ephemera.actions` ingress).
- **Every `transferMembership` carries its own preconditions and boundary expansion, whatever template produced it.** A transfer's moved object must sit in exactly one host, its `from` must be that host, and `from` must differ from `to`; a failed precondition is illegal, never a defer. Expansion adds the boundary dissolves and the exit-contact challenge from the object's source host, for take, drop and containment alike (ISS8203 slice 3).
- **Whoever creates an action authors the narration unit over it.** Plan's templates author units over the actions they build, Expansion over each facilitating action it adds; positions **must not** author or synthesize one (its half of the rule is [`../positions/AGENT.contract.md`](../positions/AGENT.contract.md#positions-derives-no-narration-copy)). An action no unit covers narrates nothing.
- **A unit covers actions by minted id, never by position**, and its variants carry **unfilled** parts: the actor and every referent are slots, filled at delivery, since an author upstream of commit cannot know display names.
- **A deterministic template narrates only from closed sets.** It conjugates the verb from its own closed verb map, keyed by the verbs it matches, and writes the closed phrase it matched (`into`, `on top of`), never the raw text of the command. Open verbs and manner belong to the LLM Plan fallback, which writes its own line.
- **A plan step may name a later step's referent before it exists.** An `extend` mints its new binding's `presenceUuid` at Plan time, and the move that follows names that binding as a one-binding `view` on the moved referent (`PresenceKey(presenceUuid)`); whether the binding exists yet is read off the attempt's earlier extend step (`viewMintedByExtend`), not flagged on the referent. A referent's `view` is the part meant, bare ids of the object's own bindings (the host being its `groundedId`). It is distinct from `groundedPresence`, which is everywhere the object is seen and is what an audience walks up from. **A transfer moves exactly the bindings of its object's view, and leaves every host they sit under**: a take of the whole of an object in several hosts leaves them all, a take of one part leaves one and the rest stays where it was with its `ConnectedTo` edge (PR-5). For an object in several hosts, a `from` grounds only when the referent names a view (in the dry run, the first host the view sits under per the catalog's placement; at commit, a live host of it), and the move starts from the hosts the view's bindings sit under, which the planner reads off the mover's graph; an object in several hosts with no view has no `from` and the step is refused (`noMembershipHost`). An object in one host is judged by that host, as ever. No layer reads an object's own graph to learn where a part is beyond the one it already reads. A put on an object with several parts lands under the one part its `view` names (`toBinding`), never the deepest. A view the world has moved past (a binding the object no longer has) refuses, in the dry run and again at commit. An object with no position to name (no placement, or no own binding) carries no view. A catalog entry carries the structure behind `groundedPresence` (`placement`, see [`positions/AGENT.contract.md`](../positions/AGENT.contract.md)); `readingsOf` groups an object's own bindings into readings (bindings under the same parents are one) and `defaultReading` is PR-2's rule: the one reading at the actor's position, else none. A reading is at the actor's position when its parents reach the actor's room without passing through another room, or when it sits under the actor itself (a room's cache holds no character, so a held part's walk upward reaches no room; the actor is known by id). **Only readings at the actor's position are ever meant or offered**: a part in another room is never an option. A unique one is stamped as the view without being asked (and without being an answer, so the row, resume and labels never see it), whether or not the object has other parts elsewhere. Several are offered as one candidate each plus all of them together ("both parts of the cloth"), and the dry run keeps only those the verb can act on: with one end of a rope held and the other on the floor, `take rope` can only take the floor end and `drop rope` can only drop the end in hand, so neither asks. Where two or more survive, the Consult asks and the answer is stamped on the referent's `view`. The "all together" choice is not offered for the object a mover lands on (a `transferMembership`'s `to`), which takes one part only. An answer that matches no current reading refuses as stale. A stamped view never overwrites a view the Plan already named (a spread's minted binding). A held entry's `placement` names only the part in hand, read from the character's own graph (the object's bindings its bindings cover); an object with a part in the room takes the room entry, whose placement already holds every binding of the object, the held one included. Extend's precondition, that the object has extent, is assumed for anything it is applied to; the dry run leaves extend out of the executor's worklist.
- **Expansion words a facilitating dissolve from the moved end**, not from edge direction ("frees the rope from the post", whichever end the edge names first), with one audience over both ends, *before* the dissolve.
- **Every copy of an attempt carries its narration units and its kind.** A stage that rebuilds an attempt (Grounding, Expansion, adjudication) must pass them through, adding its own units after Plan's.
- **An attempt's kind is set by its author, never inferred.** A Plan template's name is the kind of every attempt it builds (`look`, `membership`, `containment`, `spread`, `navigation`; a peer relation is `relation`, whether built by the LLM fallback or by the closed `tie`/`untie` templates), and a stage asking what an attempt is reads `kind`, not its actions.
- **Defer has one meaning: a challenge left pending.** A route may not add a defer reason of its own (a complexity LLM, an exit-edge flag). The deferred adjudication tier is the only place a pending challenge is judged, and until it has a judge the candidate abstains.

## Persistent command

- **One row per character per session, holding one pending command.** The key is `CHARACTER#<characterId>` / `SESSION#<sessionId>`; a new command either answers the pending one or replaces it. A session's rows are deleted on `Session Disconnect`, found by a query on the session, never from the event's `characterIds`. Every write sets `deleteAt`, and a read **must** treat a row past its `deleteAt` as absent (DynamoDB may keep it for up to about 48 hours).
- **The row stores plain data and no world fact.** It holds the frozen root (every fill: its stamped skeleton and Plan's ungrounded attempts from it; the classify confidence), `selectedAttempt` (the primary action's Plan-minted id), `referentAnswers` (`stableRefKey` to thing id), `viewAnswers` (`stableRefKey` to the part of that object chosen, a list of its own binding ids or `'whole'`; absent where no object was asked about by position) and `challengeAnswers` (structural challenge id to `{ verdict, source: 'player' | 'process', askedAs? }`), and beside the frozen root (never inside it, since the root is Plan's output) the Consult's producer `pass`. It **must not** store a grounding, a catalog or any pipeline state. A row that fails the payload guard is absent, never an error.
- **A resume restarts at `compileAttemptsFromSkeleton`.** It **must not** rerun classify or Plan, and it reads the character, room and catalogs fresh. Referent answers narrow the answered span's freshly built pool and view answers narrow that object's readings; a challenge answer is recorded as that challenge's verdict directly; a stored key the rerun does not regenerate is ignored.
- **A stale answer refuses.** A chosen attempt no longer among the frozen attempts, or a chosen thing no longer in its pool, returns `Error` with the reason on every route. A resume **must not** act on a stale id.
- **An open question lives in `pending`.** `pending.options` maps fresh per-question `optionId`s to `referentAnswers` (and `pending.views`, where an option also fixes a part, to `viewAnswers`); `pending.answer` is set when one is chosen. The `optionId`s are the nonce (every Select revision shares the bubble's `messageId`, so `messageId` cannot tell questions apart). A typed command's `put` overwrites the row, replacing any open question.
- **An answer is a conditional update in place.** The reducer sets `pending.answer` only when the option exists, the question is unanswered and the row is unexpired, and the write is conditional on `pending` being unchanged, so of two racing answers (or an answer racing a new question) at most one wins. The winner resumes from the pre-answer row with the option's answers merged in. A terminal result leaves the answered row to its TTL.
- **A duplicate answer is a silent no-op.** The first answer's outcome owns the bubble, and an `Error` there would overwrite it.
- **A stale answer refuses on the bubble only for the bubble's own id.** A missing or expired row, an overwritten question or an unknown `optionId` gets the stale-answer `Error` on the row's bubble when the client's `messageId` equals the row's `transcript.messageId`; otherwise it goes out as `WorldOOCMessage`, because the client-supplied id is untrusted.
- **The row is the single place a command waits,** on the player or on another process. Waiting is not a verdict: an unanswered challenge has no verdict yet (`pending`), and an unanswered referent question comes before any attempt exists.
- **Plan stays blind to the world, or its output is frozen whole.** The freeze line is exactly `compileAttemptsFromSkeleton`'s input. A future LLM Plan fallback that proposes identities has read the world: either it proposes attempts only, or its whole output is frozen and its identity half is treated as a hint that is rechecked. Context outside the command text (a reading of "take it") would belong in the frozen root.

## Command outcome

- **An outcome rides the command's own bubble.** `handleParseRequested` mints the echo's `messageId` and `createdTime` when the request carries a `sessionId`, and carries them (with the trimmed command text and the session) on `ResponseContext.transcript`. Every line that answers a parsed command goes through `reportCommandOutcome(context, 'Error' | 'Info', lines)`, which republishes the echo under that id with `Outcome`.
- **A revision resends the whole body.** The client replaces, never merges, so the republish carries `Message` (the command text) and `SessionId` again; the echo's position comes from the first publish's `createdTime`.
- **No echo, no bubble.** With no `transcript` (no `sessionId`, or an `Action Assessed` entry that never had an echo) the helper falls back to a standalone `WorldOOCMessage`. Notices with no originating command stay `WorldOOCMessage`.
- **The test harnesses stay OOC.** `runCoyoteEngineTestHarness` and `runAcmeOrderAffinitiesHarness` publish multi-line, dev-only reports straight through `messageBus`; they are output, not the outcome of a command, so they do not take `reportCommandOutcome`.
- **The row remembers its bubble.** `transcript` (`messageId`, `createdTime`, `command`) sits beside `root`, not inside it: it describes this attempt, not Plan's output. It is optional (no session means no echo; older rows lack it), and the session comes from the row's key. `transcriptContextForResume` turns it into the `ResponseContext.transcript` a resumed command's outcome is reported through, so that outcome lands on the original bubble. A late revision updates the bubble in place wherever it sits in the log.
- **A Select is one more revision of the command's own bubble.** `Outcome` can be `{ Kind: 'Select'; Message; Options: { OptionId; Label }[] }`: a question the player answers by choosing an option. It resends the whole body like any revision, and it is replaced by the resumed command's own outcome (or by the next Select if still ambiguous). Nothing echoes the choice.
- **Ask only when the answer would differ.** A Consult becomes a Select only when its alternatives differ in `referentAnswers` (alternatives that differ only by plan stay an `Error`) and the context has a `transcript`; otherwise the `Error` line stands, as it does when the row write fails.
- **The client never supplies an answer.** It sends `{ messageId, optionId }`; the server looks the option up in the row. Re-parsing the chosen text is not an answer path, because it redoes Plan and may resolve differently.
