## Worklist execution model

A live route seeds an ordered list of `Change`/`Assertion` instructions (one per grounded candidate, per BD-32's scope --- multi-candidate fan-out and selection stay in the caller), then `runExecutor` drives them to fixpoint by priority: ground the first `ungrounded` instruction; else fire command-expansion on the frontmost `grounded` instruction, which either retires it directly into the output list (an atomic effect: `transferMembership`, `establishRelation`, `dissolveRelation`) or retires it having minted zero or more child instructions pushed to the front (a generator: `sameHost`). A move's boundary dissolves are not the executor's to find: Expansion adds them to the command attempt as facilitating actions, and the membership dry run seeds them grounded, ahead of the move (BD-28's order).

Two invariants worth knowing before touching this, both enforced by `runExecutor`'s priority order rather than any per-instruction bookkeeping: every seeded instruction is grounded before any command-expansion fires, so a generator never sees a half-grounded sibling; and a command-expansion's minted children are causally downstream (they didn't exist when their parent fired) and already grounded, so pushing them to the front is always sound. No phase widens an operand set: an object's hosted contents live in its own shard and travel with it. The per-primitive dispatch table is documented where it's implemented, not restated here.

| [`groundReferent.ts`](groundReferent.ts) | Grounding for a single `Referent`: a referent whose `groundedId` is known is its own candidate; otherwise ranked candidate pools per `stableRefKey` into a settled id (or the joint candidate space `groundChange` fans out over) |
| [`groundChange.ts`](groundChange.ts) | Grounding for a `Change`: Cartesian product across its `Referent`s, same-object combinations kept (BD-23) |
| [`groundAssertion.ts`](groundAssertion.ts) | Grounding for an `Assertion` (`sameHost`/`containedBy`) |
| [`expandSameHost.ts`](expandSameHost.ts) | BD-16's `sameHost` command-expansion: resolves where a relational `Change` goes --- confirms an already-shared host, expresses a shard boundary as crossing legs plus a port, or declines; it never relocates an endpoint. `establishRelation` and `dissolveRelation` call different discovery primitives, matching the different question each asks --- establish calls `findShardBoundary.ts`/`buildCrossingLegs.ts` (containment ancestry); dissolve calls `findRelationalChain.ts`/`buildCrossingDissolveLegs` (existing relational edges/ports), which also subsumes the old portless case correctly instead of via ancestry coincidence. Takes an `env` slice (`getMembershipContainers`/`getGraph`/`getCurrentHost`, all optional) rather than a bare `getMembershipContainers` callback, to carry what `findRelationalChain` needs. Both establish and dissolve now land live end to end, through the shared `executeEstablishEdgeChain` commit path. |
| [`findRelationalChain.ts`](findRelationalChain.ts) | The dissolve-side discovery primitive, `findShardBoundary.ts`'s mirror image: walks existing relational edges/ports outward from a subject (not containment ancestry) to find the chain a prior `establishRelation` already built, so a `dissolveRelation` can remove it. `found` / `notFound` (decline) / `ambiguous` (decline, more than one qualifying chain). Wired into `expandSameHost.ts`'s `dissolveRelation` branch. |
| [`buildCrossingLegs.ts`](buildCrossingLegs.ts) | `findShardBoundary.ts`'s `'crossed'` verdict into establish-side legs/port (`buildCrossingLegs`), and `findRelationalChain.ts`'s `'found'` result into dissolve-side removal steps (`buildCrossingDissolveLegs`) --- one `dissolveRelation` per discovered edge, one `removeCrossingPort` per discovered port, in the chain's own discovery order (no data dependency between the two step kinds, unlike establish's port-before-leg requirement, and no hop cap --- it only maps already-stored ids). Both wired into `expandSameHost.ts`; the dissolve side now has a commit path too, through the shared `executeEstablishEdgeChain`. |
| [`filterLegalRelationalCandidates.ts`](filterLegalRelationalCandidates.ts) | Validation for the relational route: `evaluateRelationalLegality.ts`'s checks plus cycle detection over `groundChange`'s joint candidate space |
| [`detectRelationalCycle.ts`](detectRelationalCycle.ts) | Directed-cycle check one relation kind's edges, simulated post-candidate --- catches a self-relation as a one-node cycle rather than a bespoke `subjectId === targetId` rule |

Kernel-layer step vocabulary (`KernelStep`, entity-kind-general `transferMembership`) and the `fromExecutorStep` adapter bridging this folder's `ExecutorParsePlanStep` to it live in [`../../../../positions/manipulation/kernel/kernelStep.ts`](../../../../positions/manipulation/kernel/kernelStep.ts) --- outside this folder, since the kernel serves every membership-transfer route, not just the two that reach it through this executor.

## Follow-up: one grounded step vocabulary (no owning plan)

Grounded ids are needed in only two places: Expansion, which reads a real graph, and the kernel's step vocabulary. Everywhere upstream holds `plan/planStep.ts`'s `PlanStep`, whose referents are grounded or not by what is known (`groundedId`). Three grounded shapes still exist beside `PlanStep<GroundedReferent>`: `ParsePlanStep` (with its Room-only `hostRoomId`, `groundChange`'s output), this folder's `ExecutorParsePlanStep`, and `GroundedAssertion`. They could collapse into `PlanStep<GroundedReferent>`, which would reach the relational route, `sameHost`'s crossing legs, and `kernelStep.ts`'s reuse of the executor's relational step types. Nothing is blocked on it, and no plan owns it; pick it up when a change next touches all three.
