# Foundational Concepts

This is a passably brief glossary of some of the basic concepts with which you should be familiar before you attempt
to change (or, really, even to understand) the Make The World codebase.

## Scale to Zero services

A cloud service that *scales to zero* is one that has minimal costs (on the order of pennies) when it is not in use at
all. I also sometimes think of the converse of "carrying costs" ... the costs of a non-scale-to-zero service even
when it's doing nothing.

Make the World uses the following scale-to-zero services extensively:

- Lambda
- EventBridge
- DynamoDB
- S3
- API Gateway

The following services would make many things much simpler, but they have (often substantial) carrying costs, so
I've figured out ways to approximate the same things in other ways:

- OpenSearch would give vector search for *retrieval augmented generation*
- Neptune would give a strong graph database
- ElastiCache would make the active-set of data massively more performant

There are all sorts of shiny toys in AWS-world, but we're on a philosophically motivated budget here, so
*don't touch* unless it scales to zero.

## Infrastructure as Code

*Infrastructure as Code* means basically "I write some code *describing* what a set of cloud resources should look
like, then some system (CloudFormation with the Serverless Application Model extensions, in our case)
*changes my cloud* to make it look like that description, whenI tell it to do so."  Make The World is entirely
deployed through Infrastructure as Code. This offers two big advantages:

- For a developer (i.e., me, and maybe you), Infrastructre as Code offers better maintainability and resilience:
If you *really* mess up your system, it's always simple to burn it to the ground and create a new instance just
like it.
- For a more casual user, AWS offers the *Serverless Application Repository* which allows push-button installation
of CloudFormation templates into your AWS repository. This is ideal for MTW's intended model of "Install your own rather than renting time on anyone else's."

## Service Oriented Architecture

A *service oriented architecture* is one in which complex overall behaviors are created by the aggregate action of
smaller blocks of code ("services"), each of which:

- Have sole authority over some functional area, and all data pertaining to that area, and
- Offer a specific set of functions regarding that data to other services in the software ecosystem

SOA is a good mix with scale-to-zero services, both because the granular grouping of functions helps reduce costs by
allowing only the relevant code to run at any particular time, **and** because independent chunks of code with clearly
delineated authority make for a more maintainable overall code-base.

## Event-driven programming

An *event-driven* program or service is, as the name suggest, one where the action is in *response* to an external
event of some sort. Event-driven programming is needed to leverage scale-to-zero services: It doesn't help that your
Lambda functions only charge you when they are called, if your system is *calling* those functions all the time even
when nobody is on-line. The benefits happen when you have a system that only makes calls when they're needed, combined
with services that only accrue costs during the times they've been called.

Each of the services in the MTW architecture is event-driven. Frequently the events to which one service is responding
are generated by some other service or services, and similarly the end result of execution may be to create yet more
events to which other services can respond.

## Loose Coupling

The constellation of concepts above all depend upon *loose coupling* between services. Roughly, this means that each
service should expect that any other service will respond to work with the attitude "I'll get to it when I get to it,
maybe, if I feel like it." Loose coupling is the opposite of *tight coupling*, in which service A might send a message
to service B and then **wait** expectantly for service B to return results.

The siren call of tight coupling is that it is (a) easier to conceptualize, and (b) performant. But don't. Systems
built around tight coupling have a great deal of trouble being resilient and recovering from transient shocks, and
they have *even more* trouble scaling smoothly to unexpected traffic. Make The World builds for loose coupling, and
unless you have an exceptionally good reason to do otherwise, so should you.

## Bi-directional client connections

To be a a part of this ecosystem, a web client (like the ones that players use to take part in MTW) must also be
loosely coupled: It can't be hanging there waiting for results from a service that is in "I'll get to it when I
get to it" mode. Loose coupling for clients is achieved with bi-directional connections (WebSockets, in fact) that
let the client hold connections open and receive results from the ecosystem as and when they are generated.

In many ways, this makes web-clients another service, just like anything else in the ecosystem:  The client
occasionally publishes its own messages (when the user does something), and in turn subscribes to a subset of the
events being published by other services (i.e., the things the user should see).
