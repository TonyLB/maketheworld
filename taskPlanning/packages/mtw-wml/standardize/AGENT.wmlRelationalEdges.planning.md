# WML relational edges: a written form for every edge kind

**Status: opened 2026-10-15, not started. Next step: [Slice 0](#recommended-order), then [Slice 1](#recommended-order) ([OD-9](#open-decisions-implementation--plan-only) decided 2026-10-16), and [OD-1](#open-decisions-implementation--plan-only)--[OD-3](#open-decisions-implementation--plan-only) before Slice 2.** An implementation plan, per [`taskPlanning/AGENT.md`](../../../AGENT.md). It expects to grow a lot of open decisions as the work is dug into; the ones below are the ones visible on day one.

## Goal

Give WML text a way to write **relational edges**: every `LudicEdgeKind` other than `Navigation`, which already has `<Exit>`. First on the **wire** (ephemera's deliveries to the client), then for **authoring**.

**Why now: the wire loses edges, silently.** Every delivery is WML text: the server builds a `StandardForm` and prints it with `schemaToWML` (for example [`objectRenderWmlFromCacheRecord.ts`](../../../../lambda/ephemera/dataSource/perception/objectRenderWmlFromCacheRecord.ts)). The graph handed to it carries relational edges (`toWireLudicGraphFull` in [`wireProjection.ts`](../../../../lambda/ephemera/dataSource/positions/ludicGraph/wireProjection.ts) maps them), but `StandardLudicRelationalEdge.schemaNode()` returns `undefined` ([`ludicEdge.ts`](../../../../packages/mtw-wml/ts/standardize/keys/edges/ludicEdge.ts)), so they are dropped at print, with no error. What survives:

- **Membership**, because membership is the node list ([primer section 1, clause 2](../../../../lambda/ephemera/dataSource/positions/AGENT.ludicNetwork.md)), printed as nested references.
- **`Navigation`**, as `<Exit>`.

What is lost: every `Custom` edge, and every **hosting kind**. `Cup -On-> Tray` is an edge, not a node, so the client cannot tell a cup on a tray from a cup in it. Ports and presence nodes are not printed either, and WML has no syntax for either: no tag, attribute or value type in `mtw-base` or `mtw-wml/ts/schema` (checked 2026-10-16). That matters for edges because an edge may land on a presence binding ([PR-15](../../../lambda/ephemera/dataSource/positions/AGENT.presence.planning.md#settled-register)), and `ConnectedTo`'s span-to-span edges always do. So this plan also prints **binding identity** ([Slice 1](#recommended-order)); ports and covers stay unprinted. Each new kind widens the hole; [`ConnectedTo`](../../../lambda/ephemera/dataSource/positions/AGENT.connectedTo.planning.md) is the next one.

**Why for authoring too:** all authoring goes through WML, and authors will need to state relations nesting cannot (a lamp under a table, a rope's two ends).

**Payoff, stated at the observable output:** ephemera delivers a room in which a cup is `On` a tray and a lamp is `Custom('under')` a table. The client parses the delivered WML text and its `StandardForm` holds both edges, kind and label intact. Then (Slice 6) one client surface shows something it could not show before.

### Phase B: authoring (unsliced)

Sliced once Phase A ships. Its known questions are [OD-6](#open-decisions-implementation--plan-only)--[OD-8](#open-decisions-implementation--plan-only). The primer names the cost: author-lift drags in asset-stack merge, identity across cache runs, and retraction.

## Not in scope

- **Printing ports.** No whole relation needs a crossing-port terminal: a crossing port exists only where a relation is cut into legs, and authors write the whole relation. Stub ports are Slice 0's check.
- **Printing a binding's cover.** Slice 1 prints identity only (see above).
- **Presence semantics.** What a binding *means* belongs to [`AGENT.presence.planning.md`](../../../lambda/ephemera/dataSource/positions/AGENT.presence.planning.md). A semantic question this plan hits goes there as a row, linked from here, rather than being decided by a syntax choice.
- **Changing `<Exit>`.** `Navigation` keeps its tag and its Area-scoped rules.
- **Removing server-side workarounds** (`hostedNodeNameStubs`, precomputed contents). Slice 0 lists them; their removal belongs to whichever consumer replaces them.

**Coordination with the ConnectedTo plan.** Its Slice 0 adds `ConnectedTo` to WML's kind union, which `edgeToWire`'s types require; it needs nothing printed. Once both plans ship, the printer here is kind-agnostic and would carry `ConnectedTo` too. That is a wire-lift of a **Prototype** kind, which the lift rule forbids for an unsettled layer. Carrying it on the wire is transient, so retracting it later costs nothing; **authoring** `ConnectedTo` waits until that plan graduates.

## Open decisions (implementation --- plan only)

Plan-only: decisions made in order to implement the next slice(s). Do not copy into package `AGENT.concepts.md`. When a decision ships, record it in the WML docs ([`AGENT.edges.md`](../../../../packages/mtw-wml/ts/standardize/keys/edges/AGENT.edges.md), [`components/AGENT.implementation.md`](../../../../packages/mtw-wml/ts/standardize/components/AGENT.implementation.md)) and remove the row here.

| ID | Decision | Blocks | Status |
| --- | --- | --- | --- |
| **OD-1** | **How hosting kinds are written: on the nested reference, or as edge tags.** The user's call. Membership is already written by nesting, and the contract stores a hosting edge only as the member's own edge to its host's **root**. So the kind can be a property of the nested reference (`<Object key=(cup) on />`-like), giving one spelling per fact, with no mark meaning `In`. The alternative is explicit edge tags, with nesting as sugar for `-In->`, giving two spellings of one fact. A third option, edge tags only, would retire nesting as the authoring fast path. Leaning the nested reference, pending a check that no stored hosting edge ever lands on a port rather than the root. Under [OD-9](#open-decisions-implementation--plan-only) a member with two bindings into one host is written twice (once inside each `<Presence>`), so a kind on the reference is written twice and the copies could disagree. The contract stores one hosting edge per member, not per binding: either the parser requires the copies to agree, or the kind moves somewhere written once | Slice 4 | Open, the user's call |
| **OD-2** | **Tag shape for non-hosting kinds:** one generic tag with a `kind` (and `Custom`'s label), or one tag per kind as `<Exit>` is for `Navigation`. Per-kind tags make every new kind a schema change in `mtw-base`; a generic tag makes kind a string the parser must validate against the union | Slice 2 | Open |
| **OD-3** | **Terminal syntax. Narrowed 2026-10-16 to two forms: a component key, or a host plus a binding.** A component reference can reuse `<From>`/`<To>` string bodies (legal key or universal id), per *Endpoint wrapper (planned abstraction)* in `AGENT.edges.md`. The `{owner, port}` arm is only ever needed for a binding (`port: 'PRESENCE#...'`): crossing-port terminals are leg ends, and WML writes whole relations. **An edge onto a binding names both the binding's host and its presence id (the user, 2026-10-16).** The contract qualifies every reference to a binding with its host and never promises a presence id unique beyond it, so a presence id alone does not name a binding. Unsettled: the written form of the pair (two attributes or one compound value), and stub ports if Slice 0 finds one in a delivery. **Do not default a bare component terminal to its remainder binding:** under PR-15, an edge onto a binding means the part present via that binding, which is not the same claim as an edge onto the whole. If [PR-23](../../../lambda/ephemera/dataSource/positions/AGENT.presence.planning.md#open-decisions-design--plan-only) lands, an edge onto the remainder is written `(rope, REMAINDER)`-like, explicitly | Slice 2 | Open: pair syntax, and Slice 0's stub check |
| **OD-4** | **The bare `{presence}` terminal**, a graph's self-reference to one of its own bindings (PR-15 clause (c)). With bindings printed (Slice 1), it has a target. **Leaning:** the printer writes it in the same key-plus-binding form as an exterior reference, with the graph's root as owner, so WML has one written form for "an edge onto a binding". This is what the contract already requires inside `ludicCache`, where a bare `{presence}` is corruption. Check that parsing it back as `{owner, port}` on the client loses nothing a reader needs | Slice 2 | Open, leaning one form |
| **OD-5** | **Which client surface reads a delivered edge first.** Candidates: an object's contents line that distinguishes `On` from `In` ("a tray, with a cup on it"); a room header line for a `Custom` relation ("a lamp, under the table"). Pick the one whose server-side workaround Slice 0 finds costliest | Slice 6 | Open |
| **OD-6** | **Which kinds are authorable.** The contract has no deterministic authoring for `PartOf`, and `Custom` comes only from the LLM Plan fallback at play time. Authoring is a different path, so neither fact settles it | Phase B | Open |
| **OD-7** | **Edge identity across asset-stack merge.** Today non-`Navigation` edges match structurally (kind, endpoints, label). An author editing a label with `Replace` needs an identity that survives the edit, as `<Exit uuid=(...)>`'s does. Candidates: an authored `edgeId`, or structural identity with Remove-then-add for edits | Phase B | Open |
| **OD-8** | **Authored edges onto play-time structure.** An author cannot name a presence binding or a minted port: their identities are minted at play time, and the primer warns that minting at merge time doubles them. Whether authored edges are limited to component terminals, or need a stable derived identity for the others. LG-6 in [`standardize/AGENT.md`](../../../../packages/mtw-wml/ts/standardize/AGENT.md) suggests one for bindings, derived from `(hostedThing, parent host)`. Arity complicates that: two bindings into one host share that pair. **[PR-23](../../../lambda/ephemera/dataSource/positions/AGENT.presence.planning.md#open-decisions-design--plan-only) would answer it for the common case:** a fixed `REMAINDER` id lets an author name "the rope as it is here" as `(rope, REMAINDER)` without play-time minting, and survives arity because a whole has one remainder. Minted ids would remain only on explicit carve-outs, which only play-time split creates | Phase B | Open |
| **OD-9** | **Where and how a binding's identity is written. Decided 2026-10-16 (the user): a `<Presence key=(...) />` tag, identity only, with presence parentage written as nesting.** `<Room key=(lab)><Presence key=(labRoom)><Object key=(rope)><Presence key=(labEnd) /></Object></Presence></Room>` gives `labEnd` the parent pointer `{ host: lab, presence: labRoom }`: the stored shape (`fromHostPresence`, PR-21, [`ephemeraMeta.ts`](../../../../packages/mtw-interfaces/ts/ephemeraMeta.ts)) names the parent **binding**, and a host's own `<Presence>` is that binding. `labRoom` has no pointer: a room's binding is a hostless remainder. **The rules.** (1) A `<Presence>` may contain member references; a member inside it is an explicit cover entry of that binding, and the member's own `<Presence>` takes it as parent. (2) A member placed **directly** under a host element is covered by that host's **remainder** binding (the `Remainder` cover sentinel: every member no binding lists explicitly) and points at it. This mirrors the cover type, keeps the explicit/remainder distinction the cover heal depends on (contract, *Presence nodes*), and leaves authored WML's direct placement meaning the same thing in every mode. (3) The wire therefore does **not** wrap every member: remainder members print directly under the host. Why nesting rather than pointers: presence parentage is a tree (one pointer per binding), it refines membership (a member under a binding is a member of that binding's host), and inherited arity needs no special case: a contraption bound twice writes two `<Presence>` children, each holding its own members, so no key repeats under one parent element. Named for the model's node (`tag: 'Presence'`) rather than a generic `<Endpoint>`, because a binding exists whether or not an edge lands on it and the model has no free-standing positions. **Rejected:** a `presence=(...)` attribute on the nested reference (needs a repeated key or a list for arity); and an explicit `parent=(key)` pointer for multi-binding hosts (added on first recording, superseded by nesting the same day). **Depends on [PR-23](../../../lambda/ephemera/dataSource/positions/AGENT.presence.planning.md#open-decisions-design--plan-only)** (a fixed `REMAINDER` presence id per whole): if it lands, the remainder binding needs no printed id and no mark, and rule (2) points at `(host, REMAINDER)`; if not, the printer writes the remainder binding's minted id with a `remainder` mark (Slice 1 check (c)). **Open sub-question:** a whole with **several** `Remainder`-holding bindings, which the type permits; a directly placed member then has one binding per such binding and nesting cannot say which is which. Nothing writes this today (population refuses multi-binding parents; the carve-out writer is not built), and PR-23 would rule it out. Not a cover: printed nesting may let the client rebuild cover entries, but this plan does not promise it. Authoring an explicit `<Presence>` mints a binding, which is [OD-8](#open-decisions-implementation--plan-only)'s hazard. The word has two senses in this project ([*Two things are called presence*](../../../lambda/ephemera/dataSource/positions/AGENT.presence.planning.md#two-things-are-called-presence-and-whether-they-are-one-thing-is-pr-2)); authoring docs should say this tag means a binding | Slice 1 | **Decided 2026-10-16**; remainder form waits on PR-23; record in WML docs when Slice 1 ships |
