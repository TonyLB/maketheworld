# Intent-centric Plan: Plan emits ungrounded attempts, not a family

**Status:** Slices 0 through 3 done 2026-10-05 (slice 1: Plan emits ungrounded attempts; slice 2: one shared producer for the skeleton routes; slice 3: membership joins the shared producer, transfer preconditions and boundary expansion for every `transferMembership`, the complexity-LLM hop retired, see its checklist). Next: slice 4. Every remaining decision row is decided.

Task-planning conventions: [`taskPlanning/AGENT.md`](../../../../AGENT.md). Ladder position: [`AGENT.objectManipulationIterations.planning.md`](AGENT.objectManipulationIterations.planning.md), iteration 11.

## Why

The pipeline after Plan already works on intents. A `CommandAttempt` is a list of actions keyed by outcome class. The shared stage expands, adjudicates and selects without caring which route produced the candidate. [`commitAttempt`](../../../../../lambda/ephemera/dataSource/positions/manipulation/commitAttempt.ts) handles each action by its `desiredResult.primitive`, and there is one hand-off event per attempt.

Plan is the one stage still built around families. `classifySkeletonFamily` returns a closed union (`membership | relational | relationalDefer | look | none`). [`parseCommand.ts`](../../../../../lambda/ephemera/dataSource/actions/parseCommand.ts) sends each arm to its own producer. Each producer builds the plan step itself, then repeats the shared work. Plan therefore produces a family tag, not the ungrounded attempt that [`actions/AGENT.concepts.md`](../../../../../lambda/ephemera/dataSource/actions/AGENT.concepts.md)'s `CommandAttempt` section says it emits.

Evidence in today's code:

- **`relationalDefer` is the family list leaking.** On "put X on Y", `matchRelationalTemplate` already knows the intent (a `transferMembership` with `containment: 'On'`), but its output type belongs to the relational family. So it returns `nestingDefer`, and `parseCommand` reroutes it.
- **Containment skips boundary-edge Expansion because of how commands are routed.** "Connected to nothing outside itself" is a precondition of whole-object transfer, and containment is a `transferMembership`. But `compileObjectContainmentFromSkeleton.ts` expands nothing, so `commitAttempt` refuses to put a lashed rope on the table, even though the same rope can be taken.
- **Plan runs twice.** `classifySkeletonFamily` matches the skeleton, then `compileRelationalFromSkeleton` and `compileDescribeFromSkeleton` match it again.
- **Four producers repeat the same work.** Each does its own catalog merge, Identify, keyed pools, `enumerateIdentityAssignments`, self-relation filter, attempt referents, Consult wording and result mapping. `keyedPool` exists twice, nearly verbatim.
- **The LLM fallback is typed as a family picker.** `PlanOnlyFallbackCandidate.plan` is `RelationalPlanStub | MembershipPlanStub` ([`fallback/planOnlyFallback.ts`](../../../../../lambda/ephemera/dataSource/actions/enrich/objectManipulation/fallback/planOnlyFallback.ts)). An LLM given the attempt vocabulary can compose an answer; an LLM given families can only pick one. This plan exists mainly to get the type right before iteration 2 builds the plan-only and joint prompts.

## Target shape

```text
Parse -> Plan: skeleton -> set of ungrounded attempts (templates today; an LLM fallback later, same type)
      || Identify: one candidate pool per stableRefKey named in any attempt's steps
   -> Enumerate: each attempt x each joint identity assignment (one id per stableRefKey) = the candidates
   -> Grounding: stamp each candidate's ids, short names and glosses onto its steps' referents
   -> shared stage: expand (satisfy each desired result's preconditions) -> adjudicate -> dry run (one executor seed) -> select
   -> one attempt-carrying result -> one exit (bus hand-off, or in-process for narration)
```

Plan still never reads world state. Only its output type changes.

**Terms.** This plan uses `actions/AGENT.concepts.md`'s attempt vocabulary: an action's **desired result** and its kind (a position step, or narration); a desired result's **preconditions**; the **challenges** a facilitating action carries; and a candidate's **defer reason**. `primitive` appears only as the name of the `Change.primitive` field. Dispatch in this plan is keyed on one of those four things, never on a route.

## Scope

**In:** the four object-manipulation routes (membership, relational, containment, describe), including the deterministic take/drop/get fast path; the BD-19 fallback stubs' output type.

**Out (each named so it isn't mistaken for a gap):**

- **Non-object families.** Help, Home, LookRoom, Navigation and AcmeOrder still go through `DeterministicTemplate` -> `ParseCommandResult`. Navigation is arguably a `transferMembership` of `actingCharacter`, but nothing in this plan needs it.
- **Multi-action intents from the player's words** (corpus row 6, "take the entire coil of rope"). The type will admit them, but no template emits one.
- **The LLM plan fallback itself, and confidence calibration across plans.** Those are iteration 2 (BD-19 (3)), [`AGENT.manipulationFrameAndRelational.planning.md`](AGENT.manipulationFrameAndRelational.planning.md).
- **The relational-complexity LLM adjudicator.** Slice 3 builds the deferred adjudication tier it plugs into, with a naive implementation that judges nothing; the LLM itself is ladder layer 1's unowned remainder.
- **`Assertion` emission** (iteration 6). Templates that emit attempts can carry `Assertion` steps later; this plan adds none.

### PI-9 discussion: what a read step would change

The question is not whether a look changes the world (it doesn't), but whether `PlanStep` should be the vocabulary of what an attempt intends, or only of graph mutations. Three options:

- **A. Keep it (current).** A look is a step-less `NarrateAttemptAction` carrying its own `referents`. Consequences, good: every plan step has an applier, so Plan's output is always executable. The shared stage needs two arms, one for steps and one for step-less narration. The look's referents are a special case that slice 1 had to add.
- **B. Add a read predicate on the existing `Assertion` arm** (or a read primitive beside it). A look becomes a read step with a referent and no graph change. Its applier would return the prose and write nothing. Consequences, good: every attempt's intent is a `PlanStep`, so one describer per kind (PI-2) covers looks; a look's referents come from its steps, and the step-less referent exception goes away; the attempt vocabulary is uniform. Consequences, bad: (1) **Type shape.** Code that reads `object`, `from` or `to` from every `Change` arm would have to narrow, which the compiler finds site by site. (2) **Silent no-ops.** A read arm that is a flag on `Change` could swallow a mutation that was meant but built as a read, so the read primitive should be its own kind, not a flag on `Change`. (3) **Scope.** Nothing bounds what a read step may ask. Without a written scope in [`AGENT.concepts.md`](../../../../../lambda/ephemera/dataSource/actions/AGENT.concepts.md), read steps invite every future query into the plan's output, so the scope must be fixed in writing before one is added. `commitAttempt`, Expansion, Adjudication and the dry run each gain one more arm of the kind-dispatch they already do; a no-op there is the same as a satisfied precondition, not a special path.
- **C. Keep narration step-less, but rename the class to what it is** (describe-only, no world change). This settles the naming confusion without changing `PlanStep`. It does not decide whether looks are steps; it only stops the name from implying they are.

### What the kernel already has (checked 2026-10-05)

Three things share the word "narration" or "describe", and they sit at different layers:

- **Describe step (read).** `ExecutorDescribeStep` (`synthesize/executorTypes.ts`, `kind: 'describe'`, `referentKind` including `'room'`) is the executor's read-only step. The presentation kernel reuses it verbatim. A UI-triggered look already runs it: `actions/index.ts` builds `{ kind: 'describe', referentId, referentKind: 'object' }` and runs it through `commitAndPresentStepSequence`. So a look has a kernel step today. The attempt pipeline's describe doesn't use it, and returns `LookComponent` instead (PI-6, slice 4).
- **Narrate step (consequence prose).** `PresentationKernelNarrateStep` (`kernel/kernelStep.ts`) is compiled from committed mutations, such as "Tanya picks up the Orb of Mystery". It runs only on `commitStepSequence`'s `ok: true`. This is the "consequence of plan steps" rule, already built.
- **Room header (delivery, not a step).** The arrival header is a message-orchestration slot. `compilePositionKernelOp` passes a caller-supplied `headerSlot` through, and the caller renders it (`resolveHeaderSlot` in `navigate/orchestrateCharacterMove.ts`, then `presentCharacterMove.ts`). The kernel does not decide whether a header exists, so headers stay outside its step vocabulary by design.

**Two questions, not one.** (1) **Plan vocabulary:** should a look's desired result be a `PlanStep`, so Plan's output carries it? This is still open, and it decides what Plan emits. (2) **Execution route:** once a look is in an attempt, should `commitAttempt` lower it to the kernel's existing describe step? This is also open, and it is separate from (1). The answers can differ: a look can stay a step-less attempt action while commit lowers it to a describe step, or it can be a `PlanStep` that the kernel never needs to execute. The kernel finding answers (2)'s "is there a place for it" question and leaves (1) untouched.

### Decision (2026-10-05)

A look is an **action** that goes through the shared pipeline like any other, and it is **not built from `PlanStep`s**. The bridge is the `referents()` accessor that every `AttemptActionMember` already has: each action type implements it differently. `PositionAttemptAction` derives its referents from its steps. `NarrateAttemptAction` returns the referents it holds. Identify, Enumerate and Consult read referents through `action.referents()`, so "look cup" and "get cup" share one grounding path with no step in the look.

What this settles and what it doesn't:

- **Settles question 2 in part.** The look reaches Identify, Enumerate and Consult through the shared path, and commit lowers it to the kernel's describe step.
- **Leaves question 1 open.** Whether a look's desired result is a `PlanStep` is still a vocabulary question, and this resolution doesn't need an answer to it.
- **Grounding is a second per-kind accessor, not a second pipeline.** Identify and Enumerate need only `referents()`. Grounding writes an assignment back onto the action, and today that write is `stampCandidateReferents`, which takes a `PlanStep`. A narration has no steps, so it has nothing for that stamp to write to. The resolution needs a method alongside `referents()`, in the shape of `withChallenges`: pure, returning a new action of the same kind with the assignment applied. `PositionAttemptAction` stamps its steps, and `NarrateAttemptAction` stamps its referent array. Each kind owns how its referents take ids, and the shared stage calls the method without knowing the kind.
- **The shared stage's step passes ask each action what it needs.** Expansion, the dry run and the executor read steps. A look has no preconditions and no mutation, so those passes are no-ops for it. This is the kind-dispatch already used at commit, and it is the reason the "bad" bullet above is about one more arm, not a special path.
- **Changes slice 2.** Done in the slice text (2026-10-05): Identify reads `action.referents()`, and grounding goes through the per-kind method.

Decided against a `PlanStep` for a look, which is option A's vocabulary (step-less action) reached through the shared pipeline rather than through a rename. Option C's rename (describe-only, not narration) is still wanted for naming, and it lands in slice 5's docs item, not in code.
