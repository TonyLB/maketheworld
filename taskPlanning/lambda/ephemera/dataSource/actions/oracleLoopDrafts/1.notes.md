# Oracle draft 1: notes and reading rubric

For [Slice 2.5](../AGENT.oracleLoop.planning.md#recommended-order): can a candidate, shown this way, be read by a model we could use? The instructions are [`1.txt`](1.txt), passed as `instructions`.

## What the draft is

- `Reading the scene`, `Relations and frames`, `Reading player intent` and `Improvising` are v45's, byte for byte, taken from the constants in `frameJudge.ts` when the file was assembled.
- `Role` and `Task` are new, and mine. `Task` borrows three things from v45: a step that starts by copying from a literal place (`Moves`, as `Mentions` did), a `Picture` step with the motorcycle and shoebox, and `Tests` as bare yes/no lines, each starting with "Given what X said", with the verdict last.
- The answer-to-beat is called "the best answer so far", in plain words. For this draft it is always the floor, and `Role` says that a candidate that works beats it.
- `Improve` is the direction, written as one improvement request. Draft 1 doesn't say whether it goes to the engine or the player: that depends on the method dial, which these cases leave unset, and it isn't what this slice tests.
- `Answer` gives `better` or `not better` plus one sentence. The probe will grade it as having no label. Ignore that grade; the form check is the only check that applies.

## How it is probed

A departure from the plan's wording, mine: the candidate goes in through `proposedOutcome` and not in `sceneText` written by hand. `sceneText` is set once per invoke, while `proposedOutcome` is worked out for each request. That lets OC-1 and OC-6 share an invoke. It also keeps the candidate's text identical to what v45 failed to read (0 of 9), so the comparison holds. The block's framing is `Candidate`, and its explanation is the built default. `sceneText` is the fixture's judge render plus one line after `End of scene.`: `Best answer so far: I don't see how.`

The prompt, in order: instructions, scene, best answer, `Candidate:` block (moves, then the fiction after), `Request:`.

| Invoke | Fixture | `only` | Cases | Calls |
| --- | --- | --- | --- | --- |
| 1, 2 | `teaTable` | `[0, 4]` | OC-1 (pick up the table), OC-6 (pour) | 6 each |
| 3, 4 | `teaTableCupOnFloor` | `[0]` | OC-11 (table in cup) | 3 each |

Run each pair on `NovaMicro` and `Nova2Lite`, 3 repeats, for 18 calls in all.

## Rubric (written before the batch)

**A reply reads the candidate** if a line after `Moves` uses something only the candidate says. `Moves` itself is copying, so it doesn't count.

- **OC-6, pour.** Only the candidate says the tea goes into `[cup1]`, since the request names no destination. *Reads:* `Changes` or `Picture` puts `[tea2]` in `[cup1]`. *Good:* `Picture` has the teapot tipping, and `Rules` gives `Conflict`, or `Missing` names the tilt. Then `works: no`, and `Improve` names a way to tip it (the table tipped, the glue freed). *End result:* `not better`. A `better` here is the wrong `simple` again.
- **OC-11, table in cup.** The request says as much as the moves do, so reading shows in the after: the saucer and teapot ride into the cup on the table, and the table sits with `[tea1]`. *Reads:* `Changes` or `Picture` uses either of those. *Good:* `fits: no` on size, and `Improve` says `nothing`. *End result:* `not better`, with size as the sentence.
- **OC-1, the guard.** *Reads:* the saucer, cup and teapot held along with the table. *Good:* the glue gets `No consequence`, and `works: yes`. *End result:* `better`. A `not better` that cites the glue is the old false refusal.

**For each reply, record:** reads, yes or no; the end result; and anything a line got wrong on the way. Then read the outcome against the slice's exits (both models read it, only Lite does, or neither does).

## Results (2026-11-09, first batch)

18 calls, instructions hash `5cfa2023`. Every reply had all eight steps, in order, and none hit the 512-token cap.

| Case | Micro | Lite | End result |
| --- | --- | --- | --- |
| OC-1, pick up the table | `better` ×3 | `better` ×3 | Right on both |
| OC-6, pour | `better` ×3 | `better` ×3 | Wrong on both |
| OC-11, table in cup | `better` ×3 | `not better` ×3, on size | Right on Lite only |

- **Reading: yes on both models, for the move lines.** On OC-6, every reply carries the candidate's `[tea2]` into `[cup1]` into `Changes`, and most carry it into `Picture` too. The request names no cup. One caveat: `Changes` matches `Moves` word for word, so it may reword the move rather than compare the after-state with the scene. On OC-1 and OC-11 the request already says nearly everything the moves do, so those cases show little either way.
- **The after-state wasn't read, on either model.** No reply uses anything only `After:` says: the room empty after picking up the table, the saucer riding along, the saucer and teapot going into the cup.
- **Pour fails on both, so the fault is the prompt.** Both models read the glue rule as being about the table's frame, or about the teapot-to-table relation staying intact, never as about tipping the teapot. Lite, repeat 3: "pouring does not require moving the teapot itself, only the liquid inside it." Micro's `Picture` lifted or tilted the teapot in 2 of 3 replies, and `Rules` still gave `No consequence`. Lite's `Picture` never tilted it.
- **Size fails on Micro only, and the cause is open.** Micro says "fits: yes" 3 of 3, and one reply took "small round tea table" as a reason it would fit. Against blaming Micro: v45 on Micro gave `impossible` ×3 on OC-3, the same request in the original scene. And this draft's `Picture` ("lifted, tipped, carried or fitted") asks how a thing moves, not whether it fits.
- **`Improve` on Lite's OC-11:** shrink the table by magic, or establish that the cup is large. Both change how things really are, where the rubric wanted "nothing".
- **Every wrong end result was a false `better`,** the error with no recovery.
