# Object manipulation: iteration roadmap

**Status:** Standing index for a multi-iteration initiative, not a normal disposable task plan --- see [Lifecycle](#lifecycle) below. Split out 2026-07-18 from the original single planning doc (`AGENT.manipulationFrameAndRelational.planning.md`), which had grown to mix a finished deterministic vertical, an in-flight LLM-fallback build, and two not-yet-started future-iteration design threads in one file. Honestly-scoped "not built yet" stubs for later iterations were reading as failures because there was no visible boundary saying which iteration was actually active.

Task-planning conventions: [`taskPlanning/AGENT.md`](../../../../AGENT.md).

## Purpose

Object manipulation parse (take / drop / relate) is being built as a sequence of iterations, each with its own definition of done. This doc is the index: it names the ladder, states what "done" means for each rung, and points at the plan that owns each one. A `NotYetImplemented` stub for a later iteration is expected and correct while an earlier iteration is still active --- that's the thing this doc exists to make legible.

**Correction (2026-07-18): 3 and 2 are *buildable* in parallel, but not fully independent --- an earlier version of this note claimed the fallback LLMs "don't consume Parse's tokenized skeleton," which conflated "can be worked on concurrently" with "has no data relationship." They're not the same claim, and the second one was wrong.** The plan-only and joint fallbacks' actual job --- Plan's deterministic template match failed against the skeleton, ask an LLM to interpret intent instead --- is better served by handing that LLM the skeleton (referents already segmented, and for plan-only, already resolved to real objects) than by having it re-derive referent boundaries from raw command text, work Parse (and Identity) has already done reliably. **Sequencing implication:** iteration 2's steps 4-5 (plan-only, joint fallback real implementations) are **paused** until iteration 3's consolidated Parse hop produces a stable skeleton shape to design their prompts against --- building them now, against raw text, would mean reworking them once Parse exists, the exact cost the "don't build ahead of need" discipline elsewhere in this doc exists to avoid. **Update (2026-07-19):** iteration 3's Step 2a wired Parse into the live *membership* route --- real progress, but only a *partial* unblock, since plan-only and joint fallback need a stable skeleton for both membership and relational commands. The pause on steps 4-5 remains in effect until Step 2b (relational wiring) ships. **Update (2026-07-19, later the same day): the pause is lifted.** Iteration 2's own per-fallback prerequisite lists (plan-only: Step 2b's steps 1, 3, 4; joint: steps 1, 3 only) were satisfied by Step 2b's shipped work before Step 2b's final sub-step (step 6, live wiring) even landed --- so plan-only and joint fallback's own design/build can proceed now, as their own separate, not-yet-started effort tracked in `AGENT.manipulationFrameAndRelational.planning.md`. Step 2b went on to ship in full on 2026-07-19, and iteration 3's Step 3 (legacy retirement) shipped 2026-07-20 --- neither changes this unblock, already in effect before either landed. Step 3 (identity-only fallback, already shipped) needed no such pause and needs no rework: its `rawObjectSpan: string` input already carries exactly what a Parse `{ type: 'objectSpan', span }` token's `.span` field would --- Parse's eventual completion is a *source* change for that fallback (where the string comes from), not a *shape* change. Iteration 4 (backtrack) still doesn't need iteration 3 finished first, per the note below --- only iteration 2's two remaining fallback steps do.

**Why 4 doesn't strictly need 3 first:** BD-18's open sub-questions (addressable resume points, bounded retry, cost/latency) are generic to any stage, not specific to Parse. Iteration 3 gives Parse a fourth thing worth backtracking *to*; it's not a hard prerequisite for building the backtrack structure itself.

## Iteration 1, remaining

When this lands, revisit whether the cardinality check should move to gate apply instead of Identify, or be removed entirely once N-object apply is real.

## Getting started

1. Skim [`taskPlanning/AGENT.md`](../../../../AGENT.md).
2. Identify which iteration your task belongs to using the ladder above, then open that iteration's owning plan --- this doc is the index, not where the work is tracked.
3. If you're not sure which iteration a change belongs to, check the BD-N index above for the closest-matching existing decision before starting new design work.
4. Testing authority: [`lambda/ephemera/AGENT.testing.md`](../../../../../lambda/ephemera/AGENT.testing.md).

## Lifecycle

This doc is **not** disposed when any single iteration finishes --- it's the standing index for as long as more than one iteration is either active or not-yet-started. Dispose (or fold into a durable `AGENT.md`) only once the whole ladder reaches steady-state and there's no longer a "which iteration are we on" question worth answering.
