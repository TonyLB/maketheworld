# Object manipulation: iteration roadmap

**Status:** Standing index for a multi-iteration initiative, not a normal disposable task plan --- see [Lifecycle](#lifecycle) below. Split out 2026-07-18 from the original single planning doc (`AGENT.manipulationFrameAndRelational.planning.md`), which had grown to mix a finished deterministic vertical, an in-flight LLM-fallback build, and two not-yet-started future-iteration design threads in one file. Honestly-scoped "not built yet" stubs for later iterations were reading as failures because there was no visible boundary saying which iteration was actually active.

Task-planning conventions: [`taskPlanning/AGENT.md`](../../../../AGENT.md).

## Purpose

Object manipulation parse (take / drop / relate) is being built as a sequence of iterations, each with its own definition of done. This doc is the index: it names the ladder, states what "done" means for each rung, and points at the plan that owns each one. A `NotYetImplemented` stub for a later iteration is expected and correct while an earlier iteration is still active --- that's the thing this doc exists to make legible.

**Correction (2026-07-18): 3 and 2 are *buildable* in parallel, but not fully independent --- an earlier version of this note claimed the fallback LLMs "don't consume Parse's tokenized skeleton," which conflated "can be worked on concurrently" with "has no data relationship." They're not the same claim, and the second one was wrong.** The plan-only and joint fallbacks' actual job --- Plan's deterministic template match failed against the skeleton, ask an LLM to interpret intent instead --- is better served by handing that LLM the skeleton (referents already segmented, and for plan-only, already resolved to real objects) than by having it re-derive referent boundaries from raw command text, work Parse (and Identity) has already done reliably. **Sequencing implication:** iteration 2's steps 4-5 (plan-only, joint fallback real implementations) are **paused** until iteration 3's consolidated Parse hop produces a stable skeleton shape to design their prompts against --- building them now, against raw text, would mean reworking them once Parse exists, the exact cost the "don't build ahead of need" discipline elsewhere in this doc exists to avoid. **Update (2026-07-19):** iteration 3's Step 2a wired Parse into the live *membership* route --- real progress, but only a *partial* unblock, since plan-only and joint fallback need a stable skeleton for both membership and relational commands.
