## Why

The membership route runs every candidate through one chain: ground + expand + adjudicate, dry run, then select by confidence with a floor and a margin. The relational route runs a different chain and takes its first legal candidate. The containment route (`put X on/in Y`) has no candidate pool at all. So only membership can choose among several readings of a command, or ask the player when two are close.

This is the structural half of [BD-25](AGENT.manipulationFrameAndRelational.planning.md#bd-25), pulled forward. The iterations plan put it at [iteration 2 step 2](AGENT.objectManipulationIterations.planning.md#resuming-iteration-2-2026-09-23), after the plan-only fallback (step 1). It now comes first (decided 2026-10-01): a plan-only fallback that proposes N ranked plans of any family needs one selector to send them through, and today two of the three routes have none.

## Target shape

The [attempt plan's Target shape](AGENT.commandAttemptPhase.planning.md#target-shape) is route-agnostic, and this plan builds it for relational:

**plans × identity candidates -> ground -> expand -> adjudicate -> dry run -> select**

- **One shared stage, agnostic to plan kind** (AP-1). Plans are sequences of steps and have no kind; dispatch per step stays in the executor. Routes differ only in how they produce candidates. Membership is the first producer and relational the second. BD-25 recorded that this is built by extraction, not as a parallel selector.
- **The dry run carries its validated expanded plan out**, and the exit publishes the selected candidate's plan instead of recomputing it (AP-1).
- **The selection unit is a grounded candidate carrying its attempt**, as on the membership route since [attempt plan slice 2.6](AGENT.commandAttemptPhase.planning.md#recommended-order). The selected candidate's attempt is the one published.
- **The attempt is grounded by substitution** ([slice 2.8](AGENT.commandAttemptPhase.planning.md#recommended-order)): Plan's `Change` keeps its referents' `stableRefKey`s, and grounding adds `groundedId`s.
- **Selection is `selectPlanTuple`, unchanged.** Calibrated ranking (BD-19 (3), then BD-25's rubric) later swaps in through `getConfidence` without changing the stage's shape.
- **Membership-specific names are renamed during the extraction**, not before (BD-25).

## Stage sketch

Slice 0's output (AP-1). Field shapes, not final code.

```ts
// selectPlanCandidate.ts (renamed from selectIdentityPlanTuple.ts; holds selectPlanTuple too)
type PlanCandidate = {
    identities: ReadonlyMap<string, IdentityPlanIdentity> // the joint assignment, one per stableRefKey
    confidence: number                                     // AP-2: min over the identities' jointRelevance
    attempt: CommandAttempt                                // grounded by substitution; its primary actions are the proposed plan
}
type ValidatedPlan = { steps: readonly ExecutorParsePlanStep[]; extraKernelSteps?: readonly MutationKernelStep[] }
// DryRunOutcome's legal arm carries `plan: ValidatedPlan` in place of objectIds/hostId
type ConsultAlternative = { proposedCommand: string; label?: string; objectId?: EphemeraObjectId } // replaces SpanResolutionConsultAlternative
type PlanStageEnvironment = { expansion: ExpansionEnvironment; grounding: Pick<GroundingContext, 'actingCharacterId' | 'getCurrentHost'> }

function selectPlanCandidate<T extends PlanCandidate>(input: {
    candidates: readonly T[]           // a producer's output, already grounded by substitution
    environment: PlanStageEnvironment  // built by the route (sandbox state, prefetch)
    toConsultAlternative: (candidate: T) => ConsultAlternative
}): SelectPlanTupleResult<T>
// body: Expand + Adjudicate (per step) -> dry run (pending -> defer, impossible -> illegal,
// lower the actions, runExecutor, validation per step) -> selectPlanTuple
```

- A producer extends `PlanCandidate` with what its exit needs: membership's candidate is `PlanCandidate & { identity; plan: MembershipPlanStub }`.
- `ConsultAlternative` keeps `objectId` optional so membership's wire payload does not change (AP-3).
- **Names:** `selectPlanCandidate.ts` for the stage; producers are `propose<Route>Candidates` (`proposeMembershipCandidates` merges `proposeMembershipTuples` and `groundMembershipCandidates`; then `proposeRelationalCandidates`, `proposeContainmentCandidates`, `proposeDescribeCandidates`). `selectIdentityPlanTuple` and `GroundedMembershipCandidate` retire.

## Scope

- **In:** extracting the chain; moving relational, containment (AP-4) and Describe (AP-5) onto it; relational's attempt built per candidate, before selection; the hand-off to positions as one event per attempt (AP-9).
- **Out:** calibrated ranking (BD-19 (3), BD-25's rubric); any LLM fallback (iteration 2 steps 1 and 3); a sibling-attempt producer (the stage stays a `map`, per slice 2.6).
