## Crossing the seam now (JF-18, 2026-11-07)

**The user's question:** the Recommended order as first written seemed to aim at an apples-to-apples comparison of the loop against the single judge. Is that worth its cost? Measurements built on the old structure are path-dependent, the seam has to be crossed some day, and metrics won't carry across it, so the question is only how long to put it off.

**Mine, agreed:** not worth it. The grader scores the label after `Answer:`, and the oracle's product is a verdict and a direction, so a comparison would be by reading on both sides, which needs no v45 baseline. Nothing in production reads v45, so there is no live behaviour a baseline would guard. What v45 taught (the Micro writing findings, the reusable modules, the noticing failures) carries across as cases and wording, not numbers. Where the order leaned on the old structure: the corpus's "against today's model", which the design variant means as the limit a case hits and not a baseline; Phase 2's "with the instructions constant", which would have tuned the oracle inside v45's prompt; and Phase 1, a question that doesn't depend on the seam, asked through v45's proposal block. So Phases 1 and 2 merged into oracle drafts, with draft 1 written fresh from the modules. The cost named at the time: if draft 1 does badly, structure and wording can't be told apart. Reusing the modules word for word narrows that.

**The user's proposal for the corpus:** classify the measured cases as oracle cases, improvisation cases or both, rewrite them accordingly, and accumulate two corpora. That keeps continuity of cases, the same scenes and requests read across the seam, without the labels and tallies. **Mine, agreed:** one file with a part per function, since half the measured cases are both and two copies would drift; loop cases as a third kind, since what passes between the phases belongs to neither; oracle cases carry hand-written candidates as inputs, engine cases a rubric written before any run. The rewrite is the corpus's [How a case is written](AGENT.oracleLoop.corpus.planning.md#how-a-case-is-written).

## The order reshaped around fixtures (2026-11-07)

**The user's points:** the oracle's inputs need fixture handlers before its drafts, so the harness comes before draft 1; the engine's fixtures can wait until about the engine stub, or be deferred to a later plan that drafts the engine's prompts; and a step defining the oracle's input types comes before the harness. **Mine, agreed:** the engine's fixtures stay in this plan at the stub, since the loop by hand needs none and this plan owns the stub; deferring them would want a durable home only if the stub moved out too. A case isn't a request (OC-6 and OC-30 share one), so fixture cases are keyed by case ID. The harness can't grade a reply format no draft has written, so it starts read-only and comparative grading follows the drafts. The inputs' wording is prompt text, so the harness renders them with a framing a draft can override. The types step splits into a requirement half, swept from the corpus, and a representation half at the Prototype tier, with fields on open rows in their simplest form and marked, so no row becomes a gate. The old Prototype phase dissolved into the harness and the engine stub.

## A fixture builder before the input types (2026-11-08)

**The user's points:** OC-10's hammer conflict (the fixture holds it, JF-11's example has it on a table) is better met by tunable fixtures than by picking one; a builder, not override flags in the probe payload; the builder founded on the existing instruction set for placement and creation; and population should accept a `hostingKind`. The user also separated two shapes I had blurred: a full default patched into variants, against an invariant core with the rest built by instructions. **Mine, agreed:** payload flags break the closed fixture set, and the tests never see a variant. The move dry run (`dryRunProposedMoves`) is async because the move planner's graph walks await `getGraph`, which in production reads the internal cache and learns which host to read next from the last; JavaScript can't make that synchronous, so a patched default resolves only through an async step, and every reader of `graphs` would go through it. Authored population (`rootStep`, `containmentPopulationSteps`) is synchronous over graphs passed in, so the user's core-plus-instructions shape builds each variant as plain data at module load, places each thing where its dial says rather than moving it, and lets dials touching one host compose in the kernel. The hand-written fixtures stay, since they pin the fold independently of population. Placed first, as step 1, since neither it nor the input types depends on the other.

## Population takes a kind (2026-11-08)

**Finding, mine:** `authoredHostingKind` gave an Object under a Character `In`, which `admissibleHostingKinds` refuses on a Character host (only `On` and `Held`), so applying those steps would throw at `setHostingKind`. A unit test pinned the `In` ("no character branch", 2026-10-11); production never reached it, since authored WML places no Object under a Character. `defaultHostingKind` in `settleMembership.ts`, the kind a move's arrival gives, matched it everywhere else and gives `Held` there. **The user's call:** the default becomes `defaultHostingKind`'s and `authoredHostingKind` is deleted, which answers the kind half of step 1's `Held` check. **Mine:** an inadmissible kind throws rather than warning and writing nothing, as a parent with no Base does, since only code chooses a kind.

## Held placement needs a Base (2026-11-08)

**Finding, mine:** population names the parent's binding through `childParentBindingIdOf`, which finds `PRESENCE#Base` and nothing else. Every hand-written fixture's actor holds one binding called `inRoom`, so population into its hand warns and writes nothing. The contract puts the defect in the fixtures, not in population. Its rule "Base and Unplaced" ([positions contract](../../../../../lambda/ephemera/dataSource/positions/AGENT.contract.md)) says every host holds Base from birth, Base is the stable lookup for a context-free add, and a host with no Base is a defect that `lacksBase` reports. A character also holds exactly one binding (the single-hosted check in `applyStepSequenceCore`), so the builder's core cannot add a Base beside `inRoom`; it must write the actor's one binding *as* Base, pointed at the room's Base. Population then places `Held` under it, and a unit test applies that shape. Held placement needs no step of its own. **Corrected in passing:** the inline comment in `containmentPopulationSteps` said the parent binding is "else the parent's only binding", and that a parent with several bindings names none. That is the move planner's `destinationBindingOf` rule. The code took Base and only Base, and the contract agrees with the code, so the comment and the warn message were fixed. The behaviour is unchanged.

## Hand-written bindings renamed to Base (2026-11-08)

**Finding, mine:** Slice 1's acceptance test, that `teaTable` built through the builder comes out identical to its hand-written graphs, could not pass as written. Population names a host's first binding `PRESENCE#Base` by rule, while no non-room host in a hand-written fixture holds one: their bindings have descriptive names (`onFloor`, `onTable`, `inRoom`), so every own key, pointer and cover entry would differ. Sub-item 3's IDs cannot match them either, since they name only a second binding. Binding names do not reach the rendered prose. **The user's call:** rename the hand-written bindings to what population writes, so a host's first binding is Base; a second binding is written with a descriptive name, not an invented UUID. The acceptance stays graph identity, against the renamed graphs. **Scope:** the two acceptance fixtures are renamed now (mine), and the rest is cleanup left to a later slice (the user's agreement).

## Fixture builder built (2026-11-08)

**Findings, mine, from building it:** edge IDs were already the caller's. Production's tie sends `establishRelation` for the two edges between things, `assignEdgeId` with IDs from `mintedEdgeIds`, then the `Justifies` edge, which never gets an ID, so the builder writes relations in that order and the hand-written `teaTable`'s `e3` on its `Justifies` edge was a shape production cannot produce; it was dropped. The kernel's cover index fills a parent's cover as each child is placed, in placement order, so a description writes no covers. Node order matters to the comparison: population puts a host's binding right after its root, ahead of the members, so the renamed graphs were reordered to match. The goldens did not move, so the fold reads neither binding names nor where a binding sits among members. A graph that never held an edge stores no `edges` key, so `hostGraph` now writes none when given none. **The user's call:** the hammer dial's second position is on the floor, not on the table: with the hammer already on the table, "put [hammer1] on [table1]" does nothing, so JF-11's example needs it elsewhere.

## Asking the player is a move of the loop (JF-19, 2026-11-08)

**The user's corrections, in order, on the first type sketch.** First: the oracle doesn't decide to ask the player a question; it can judge that the best we can do is to highlight that there is a question to be asked. Second: a question for the player is still an output where it differs from plain text, when it can offer options ("Do you mean the red cup or the blue cup?", now OC-32), and not for "But how?". Third, a reframing: if the oracle records ways to make things better, and candidates are attempts to improve the request, the question becomes whether "save the state, ask a question, then resume or restart the loop with the added information" is a legitimate part of the loop. **Mine, on it:** yes, and it dissolves the fork I had posed (whether a plain question is the floor's sentence or a candidate); a direction says where better information comes from, the engine or the player, with the player's costing a turn; asking is a third exit from the round loop beside the turn limit and the default winning; and OC-31's turn 2 is the same loop restarted, which is most of JF-12. Production already has the move: a Consult saves Plan's frozen output, asks, and reruns with `ResumeAnswers`. Resume and restart differ against the actions contract, whose persistent row stores no pipeline state: restart fits it and rediscovers what earlier rounds found, while resume keeps that and needs the contract amended. **The user's call:** restart, at least until something shows old reasoning materially better than starting fresh with more information; a little expense of reasoning from scratch is likely worth it. The refused-move row first proposed as JF-19 is now proposed as JF-20, still not opened.

## A stretch is a judgment of an improvisation (2026-11-08)

**The user's corrections, in order, on the sketch's stretches.** First: stretches are a named subset of what would improve a candidate, so there is one list of improvements, with no need-to-have tag; a candidate that loses now and would win with an improvement sits on the frontier. Second: "stretch" was used for two things, an act of improvising that strains plausibility and the item it produced, and pre-judging a stretch when asking for it side-tracked the division of labour. So an improvement request carries no price, an improvisation is what comes back, and a stretch is the oracle's judgment of how far the improviser went out on a limb, given the scene. Third: a candidate with a slot unfilled doesn't work, a fact separate from its score: a hard divide as a product, a soft malus for potential.

**Mine, along the way.** The oracle can know before asking whether there is an open fact, the hard limits and the dials, which are constraints and not a price; where it seems to pre-judge (OC-3's shrinking spell) it has imagined the item itself. The engine can list what it introduced as a hint, but only the oracle prices, since pricing compares against the answer-to-beat and the engine is the one under convenience pressure. An improvisation is an improvised fact, with an object the common case (accepted by the user). Not yet taken up: rereading OC-3's expected outcome and the corpus rubric's "how much it may stretch" as constraints, and the corpus outcomes that judge an unfilled slot as beating the floor (OC-7, OC-8; OC-31's turn 2 perhaps). OC-18 already expects the floor.

### The user's notes

1. Sections get specifiers, such as `Role:`.
2. What the data is and what the role should do are separate, in this order: `Role`, `Reading the scene`, `Task`.
3. `Reading the scene` and `Reading player intent` are reusable modules, tuned more broadly than one task. `Reading player intent` is likely global to the system. `Reading the scene` can vary somewhat with the render format.
4. `Reading player intent` carries the expectation that moving an object moves everything on or in it, and that moving a container away from its contents is considered only when the player specifies it or context makes it obvious ("yank the saucer out from under the cup" is a move of the saucer and of the cup's containment on the saucer).
5. `Reading the scene` explains the two registers, and headers make them obvious.
6. The graph representation is probably better wrapped in a Markdown code fence.
7. `Task` says how to use Rules. `Reading the scene` says what they mean, fictionally.
8. Rules is a section the earlier instructions anticipate, with no ad-hoc instructions of its own.
9. Anything after the question must be an explicit callback to the task instructions. It may not be needed: instructions up front, data and input last.
10. The two registers are a fictional description and a graph representation. v1 lost that distinction, so the sections are renamed and `Reading the scene` reinforces it (on v1).
11. Rules is a non-exhaustive list of fictional constraints derived from the graph: a rule's presence constrains explicitly, and its absence defers to the logic of the scene (on v2, reworded on v3).
12. Four labels, with `incomplete` and `impossible` as in JP-10: the reality is agreed and in the way, against the request suggesting the reality is not agreed. v5 uses the label wording I offered, which the user accepted as a direction (2026-11-04).
13. `Role`'s goal is the next step in communication: completing the request, aligning player understanding, or bouncing the question back as a puzzle (on v5).
14. The labels are four distinct categories, not a spectrum, so they have no inherent order; `Task` lists them in the order of `Role`'s next steps (on v6).
15. Fiction is not a simulation (2026-11-05). A simulation gives positions and derives relations from them. Fiction establishes the relations and leaves positions undefined, because they don't matter. Pulling the rug out establishes nothing about where the rug is; it revises the fact that the crate is on the rug.
16. People reason about fiction with a twist of register (2026-11-05): they briefly imagine a scene framed by what is established, check it against real-world physics, then abstract back to what is established. Sliding a cup across a table is thought about as motion when judging whether it can be done, yet it establishes no new fact: the cup goes from an unspecified spot on the table to an unspecified spot on the table.
17. Reasoning about fiction is lazy, not exhaustive (2026-11-05). Exhaustive reasoning concludes that the teapot comes with the table; lazy reasoning declines to modify the fact that the teapot is on the table. A secret door in a bookshelf does not have to imagine fifty books moving: the books remain as established. "It's a sort of compression." The working question is "If I move this table, which of these established facts need to be reconsidered?" A pyramid of wine-glasses stacked precariously on the table jumps out, and the glued teapot gets to be ignored.
18. `Reading player intent` and the rule's "defaults to moving" are the old voice, and should describe fictional inertia instead (on v8).
19. It is permissible for the LLM to be a little dumb, so long as it is not recalcitrant (2026-11-05). Users understand that they sometimes said too little for a system to parse their intent, but they get rightly frustrated when the system resists a legitimate intent.
20. Be skeptical of negative instructions that modify positive instructions: LLMs don't seem to deal well with that structure, so state the test positively (2026-11-05, on the chasm sentence).
21. Rules state the constraint plainly, as a rule, in a context that has already explained that rules can be dissolved through action (2026-11-05, on JP-1). "Cannot leave ... until freed" was awkward because it embedded the puzzle-solving mindset, that rules are meant to be bent or broken, in the rule itself.
22. `contingent`, `incomplete` and `complex` may be independent gates, of which we recognize only the first to fire (2026-11-05): an attempt to pry the teapot off with a screwdriver could be all three.
23. The one-word judgment is used for deterministic routing, and any more capable LLM that gets deferred to receives the whole output, including `Needs` and `Revises` (2026-11-05). This was the user's condition for the gates direction.
24. `Reading the scene` aligns with established against unestablished, not present against absent (2026-11-05, on v18). The prompt does not affirm that an unstated thing is neither present nor absent, only that it is not established as either. `Fiction` describes what has been established, since what the place "really is" can change through minting. `Graph` "adds no facts of its own but can help disambiguate the language of the fiction section" (the user's wording).
25. The `Fiction` part is tiny, with the details of established against exhaustive added later as clarifications and exceptions. Migrate them earlier, into `Fiction`, so they frame the later sections immediately (2026-11-05, on v19).
26. Don't tie the scene render to player perception (2026-11-05, on v20). "Reasoning is grounded in this established fiction" replaces "This is the story you are reasoning about" (the user's wording).
27. The lazy view does not need calling out against the graph in the prompt: building lazy-change expectations into `Fiction` and then listing the graph is enough to draw the parallels functionally (2026-11-05, closing JP-11).
28. `incomplete` is renamed `obstructed` from v24 (my suggestion, the user agreed, 2026-11-05). Earlier notes and rows keep the old name where they record what was said at the time.
29. JP-14 may be mixing two types of challenge (2026-11-05): can you do this thing you attempt, against do you even have a plan for the attempt? In the Coyote Game, "Wire the cloud-machine to the tesla coil to make a lightning-storm generator" is an insanely difficult skill challenge that the genre says the Coyote passes without issue, and "Catch the Road-Runner" is a challenge where plan after plan fails to be the right plan.

### Settled

Decisions a fix must not undo without saying so. A "was JP-n" label resolves any older reference.

- **The replacement rule (was JF-1):** it stands, as [When a candidate replaces the baseline](../../../../../lambda/ephemera/calibration/AGENT.md#the-built-judge-prompt-v45) now words it. A label the fixture tolerates is a border, not a lost pass. The `teaTable` table tolerates `complex` (user, 2026-11-06), since that division waits for the planner and `complex` fails safe, as the `tavern` table already does.
- **Two uses of "you" (was JP-3):** a sentence in `Reading the scene`: 'In the scene, "you" is the player'. The render stays as it is.
- **The user's `SECURED` passage (was JP-5):** it stays out. Its removal was mine, and this is its explicit decision. A code comment in `sceneRules.ts` records that it made things worse, and the rule and the inertia framing now cover its job. It is the first thing to try if the table refusal survives Slice 4.
- **"Text adventure" (was JP-7):** not named. The genre may suggest things are fixed in place, which could feed the table refusal. The text-adventure reading stays a requirement of the behaviour, and `game master` stays.
- **Lazy view and the graph (was JP-11):** no further prompt text (note 27). `Fiction` is the framing that replaced the old `LADDER` steps and the "what goes with what" wording of `PRECEDENCE`.
- **Transitory against established (was JP-12):** no further text. Only what the action depends on can change the label: `Needs` ("could not work without") and `Revises` ("established facts") leave a detail the action merely produces, such as a slick of moisture, to the narration. - **Rule wording (was JP-1), replaced by M28 to M30:** a rule states an invariant under a handle, and the judge gives each relevant rule a verdict. When [table1]'s frame moves, [teapot1] travels along with [table1].` (user's first sentence; second mine, with the user's "implies no restriction" as the fallback). - **Open world (was JP-9):** what is unstated is not established as either present or absent. Details get established because they are newly relevant, not because they newly occurred. Plausible improvisation is wanted, and improvisation for convenience is not. Silence can count as evidence: a bridge over a yawning chasm "would have been mentioned if it were there", so it leaves `contingent` for `incomplete`.
- **Improvised details (was JP-13):** the `contingent` label, with sure and unsure suggestions going to the same place. Whether to mint is decided by a more capable engine, which is for CA-6; a new established fact reaching the graph leaves a note there too. Fault tolerance: most border errors recover, through another turn or the engine's second look. A wrong `simple` has no recovery, and a wrong `impossible` recovers only if the player has something to add, so it does not excuse the table refusal.
- **Independent gates (was JP-15):** `Answer` is one word, the first gate that fires, with the obstacle before `Needs`, and code routes on that word alone. `contingent`'s and `incomplete`'s sentences stay for the first probe. `complex` stays a judgment, since `Revises` alone can't decide it. For CA-6: a deferred LLM gets the whole output as a first pass's notes, not as established facts, and its prompt has to say so, or a wrong `Needs` could anchor it.
- **The judgment schema (was JP-6):** five labels for this iteration, with `confusing` added at v37 (user) as a fall-through when no test says "yes". - **`obstructed`, and `impossible` (was JP-10, under the name `incomplete`):** the touchstone is respect for player ingenuity (user, from GMing indie RPGs): going from "It's an adamantium door... No man. Didn't you listen?" to "Well, I don't know. Can you? What do you want to try?". It differs from `Consult`, which asks the player to clarify and sets no puzzle. Freeing is not the only way past an obstacle (tipping the table to pour), so the judge names the obstacle and no way past it. The tone of the invitation is the whole system's, not this check's. `impossible` is a mismatch of shared reality, not "stop trying": "I don't think you and I have the same idea of the size of shoeboxes or motorcycles." For CA-6: an `obstructed` entry will at some point go to an LLM that decides how to present the possibilities to the player, and which will sometimes describe it as impossible if the player has no clue a path exists, so the judge need not draw that line. `obstructed` still says "getting past it is up to the player" as a placeholder (JP-14).
