## Crossing the seam now (JF-18, 2026-11-07)

**The user's question:** the Recommended order as first written seemed to aim at an apples-to-apples comparison of the loop against the single judge. Is that worth its cost? Measurements built on the old structure are path-dependent, the seam has to be crossed some day, and metrics won't carry across it, so the question is only how long to put it off.

**Mine, agreed:** not worth it. The grader scores the label after `Answer:`, and the oracle's product is a verdict and a direction, so a comparison would be by reading on both sides, which needs no v45 baseline. Nothing in production reads v45, so there is no live behaviour a baseline would guard. What v45 taught (the Micro writing findings, the reusable modules, the noticing failures) carries across as cases and wording, not numbers. Where the order leaned on the old structure: the corpus's "against today's model", which the design variant means as the limit a case hits and not a baseline; Phase 2's "with the instructions constant", which would have tuned the oracle inside v45's prompt; and Phase 1, a question that doesn't depend on the seam, asked through v45's proposal block. So Phases 1 and 2 merged into oracle drafts, with draft 1 written fresh from the modules. The cost named at the time: if draft 1 does badly, structure and wording can't be told apart. Reusing the modules word for word narrows that.

**The user's proposal for the corpus:** classify the measured cases as oracle cases, improvisation cases or both, rewrite them accordingly, and accumulate two corpora. That keeps continuity of cases, the same scenes and requests read across the seam, without the labels and tallies. **Mine, agreed:** one file with a part per function, since half the measured cases are both and two copies would drift; loop cases as a third kind, since what passes between the phases belongs to neither; oracle cases carry hand-written candidates as inputs, engine cases a rubric written before any run. The rewrite is the corpus's [How a case is written](AGENT.oracleLoop.corpus.planning.md#how-a-case-is-written).

## A fixture builder before the input types (2026-11-08)

**The user's points:** OC-10's hammer conflict (the fixture holds it, JF-11's example has it on a table) is better met by tunable fixtures than by picking one; a builder, not override flags in the probe payload; the builder founded on the existing instruction set for placement and creation; and population should accept a `hostingKind`. The user also separated two shapes I had blurred: a full default patched into variants, against an invariant core with the rest built by instructions. **Mine, agreed:** payload flags break the closed fixture set, and the tests never see a variant. Authored population (`rootStep`, `containmentPopulationSteps`) is synchronous over graphs passed in, so the user's core-plus-instructions shape builds each variant as plain data at module load, places each thing where its dial says rather than moving it, and lets dials touching one host compose in the kernel. The hand-written fixtures stay, since they pin the fold independently of population. Placed first, as step 1, since neither it nor the input types depends on the other.

## Population takes a kind (2026-11-08)

**Finding, mine:** `authoredHostingKind` gave an Object under a Character `In`, which `admissibleHostingKinds` refuses on a Character host (only `On` and `Held`), so applying those steps would throw at `setHostingKind`. A unit test pinned the `In` ("no character branch", 2026-10-11); production never reached it, since authored WML places no Object under a Character. `defaultHostingKind` in `settleMembership.ts`, the kind a move's arrival gives, matched it everywhere else and gives `Held` there. **The user's call:** the default becomes `defaultHostingKind`'s and `authoredHostingKind` is deleted, which answers the kind half of step 1's `Held` check. **Mine:** an inadmissible kind throws rather than warning and writing nothing, as a parent with no Base does, since only code chooses a kind.

## Held placement needs a Base (2026-11-08)

**Finding, mine:** population names the parent's binding through `childParentBindingIdOf`, which finds `PRESENCE#Base` and nothing else. Every hand-written fixture's actor holds one binding called `inRoom`, so population into its hand warns and writes nothing. The contract puts the defect in the fixtures, not in population. Its rule "Base and Unplaced" ([positions contract](../../../../../lambda/ephemera/dataSource/positions/AGENT.contract.md)) says every host holds Base from birth, Base is the stable lookup for a context-free add, and a host with no Base is a defect that `lacksBase` reports. A character also holds exactly one binding (the single-hosted check in `applyStepSequenceCore`), so the builder's core cannot add a Base beside `inRoom`; it must write the actor's one binding *as* Base, pointed at the room's Base. Population then places `Held` under it, and a unit test applies that shape. Held placement needs no step of its own. **Corrected in passing:** the inline comment in `containmentPopulationSteps` said the parent binding is "else the parent's only binding", and that a parent with several bindings names none. That is the move planner's `destinationBindingOf` rule. The code took Base and only Base, and the contract agrees with the code, so the comment and the warn message were fixed. The behaviour is unchanged.

## Fixture builder built (2026-11-08)

## Asking the player is a move of the loop (JF-19, 2026-11-08)

**The user's corrections, in order, on the first type sketch.** First: the oracle doesn't decide to ask the player a question; it can judge that the best we can do is to highlight that there is a question to be asked. Second: a question for the player is still an output where it differs from plain text, when it can offer options ("Do you mean the red cup or the blue cup?", now OC-32), and not for "But how?". Third, a reframing: if the oracle records ways to make things better, and candidates are attempts to improve the request, the question becomes whether "save the state, ask a question, then resume or restart the loop with the added information" is a legitimate part of the loop. **Mine, on it:** yes, and it dissolves the fork I had posed (whether a plain question is the floor's sentence or a candidate); a direction says where better information comes from, the engine or the player, with the player's costing a turn; asking is a third exit from the round loop beside the turn limit and the default winning; and OC-31's turn 2 is the same loop restarted, which is most of JF-12. Production already has the move: a Consult saves Plan's frozen output, asks, and reruns with `ResumeAnswers`. Resume and restart differ against the actions contract, whose persistent row stores no pipeline state: restart fits it and rediscovers what earlier rounds found, while resume keeps that and needs the contract amended. **The user's call:** restart, at least until something shows old reasoning materially better than starting fresh with more information; a little expense of reasoning from scratch is likely worth it. The refused-move row first proposed as JF-19 is now proposed as JF-20, still not opened.

## A stretch is a judgment of an improvisation (2026-11-08)

**The user's corrections, in order, on the sketch's stretches.** First: stretches are a named subset of what would improve a candidate, so there is one list of improvements, with no need-to-have tag; a candidate that loses now and would win with an improvement sits on the frontier. Second: "stretch" was used for two things, an act of improvising that strains plausibility and the item it produced, and pre-judging a stretch when asking for it side-tracked the division of labour. So an improvement request carries no price, an improvisation is what comes back, and a stretch is the oracle's judgment of how far the improviser went out on a limb, given the scene. Third: a candidate with a slot unfilled doesn't work, a fact separate from its score: a hard divide as a product, a soft malus for potential.

**Mine, along the way.** The oracle can know before asking whether there is an open fact, the hard limits and the dials, which are constraints and not a price; where it seems to pre-judge (OC-3's shrinking spell) it has imagined the item itself. The engine can list what it introduced as a hint, but only the oracle prices, since pricing compares against the answer-to-beat and the engine is the one under convenience pressure. An improvisation is an improvised fact, with an object the common case (accepted by the user). Not yet taken up: rereading OC-3's expected outcome and the corpus rubric's "how much it may stretch" as constraints, and the corpus outcomes that judge an unfilled slot as beating the floor (OC-7, OC-8; OC-31's turn 2 perhaps). OC-18 already expects the floor.

## The oracle decomposes (Slice 4's exit (c), 2026-11-10)

**What the drafts showed.** Twelve drafts and sixteen batches on Micro ([`iterations.md`](oracleLoopDrafts/iterations.md)). Nearly every fault left at the end was a loop or a look-back inside the one prompt:
- a filter on a loop dropped: "for each action with a line" was answered for each rule (PR-13);
- a join over earlier steps not computed: the window (PR-14);
- a later step reading the wrong earlier one: `Tests` answering from `Attempts` against `Rules`;
- several yes/no questions under one rule leaking into each other (PR-9, PR-11);
- the nearest text copied in place of an answer: step instructions (PR-10), and the rule's clause as what the play-by-play says (L-29).

What worked best was the single generative judgment: the play-by-play tilted OC-6's teapot 3 of 3 once the step was an action (draft 6).

**The user's call (2026-11-10).** The oracle decomposes into smaller pieces. The user's research else-thread found the same pattern in prior art: decomposed prompting, checklist evaluation, and LLM+P's split between translation into a formal form and deterministic checking. The general rule from it is one judgment per call, with loops, filters and joins done in code. The user chose to take the exit now and leave "which pieces work?" to follow-up plans, each building one small proven piece that composes. The other option was to investigate the pieces inside this episode first. A rules-blocking oracle is the user's example of a first piece: it takes a play-by-play, one rule, and the steps before the rule is voided (if any).

**Mine, agreed in direction:**
- Code already holds part of the formal side: the dry run, the generated rules with their handles and the things they name, and the candidate's `voids` lines. The relevance filter, the window, `works` and the verdict can all be code.
- A per-entity vocabulary ("teapot: forbids tilt") gets OC-1 wrong, since the glue allows the teapot to move with the table. The rule side's kinds come from the graph and can be listed in full. The motion side can't, so the smallest LLM judgment is a cell with one rule and the motions of its two things.
- Micro stays the target for every piece, the decomposition included.
- A pipeline costs more calls per round, and the 12-call cap means fewer cases per batch.

**The oracle-or-engine question becomes moot (user, 2026-11-10).** Whether the play-by-play is generated in the oracle or in the improvisation engine (L-17's question, L-23's shelved form) was a question about which prompt a piece belongs in. With one judgment per call, the groupings "oracle" and "engine" were a sign of composing too much into one prompt. The play-by-play becomes a stage that code calls and feeds forward, and which side it sits on is no longer a design question.

## The imagination answers the oracle's asks (the play-by-play's exit (c), 2026-11-11)

**What the drafts showed.** Ten drafts and eleven batches on Micro ([`oracleLoopDrafts/playByPlay/`](oracleLoopDrafts/playByPlay/iterations.md)). Asked for the whole scene at once (drafts 1 to 6), the play-by-play could make the action succeed (OC-6's teapot tilted, OC-20's table lifted) or report the knock-on (OC-30/2's saucer and cup sliding off), and never both for long. One reply reasoned that an unsecured thing slides on a tipping table, then kept the cup in place for the pour.

**The user's hypothesis and reversal (2026-11-11).** The failures come from asking every question at once: with "provide everything" and no direction, the reply finds its own direction and makes spurious connections (a saucer held still because the teapot is glued). So reverse the order: build the iterative engine first, with focused asks, and a general play-by-play later, if at all. "More loops of a process we can _create_ are better than fewer loops of a process that will elude us." The user's loop sketch: the oracle asks for more detail; the imagination gives the ordinary method (lift the teapot, tilt it) and "possible problem: glued"; the oracle asks for an alternate method; "tilt the table"; the oracle asks what happens to the other things; the saucer and cup slide, "possible problem: hard to pour into a falling cup"; the oracle asks for a mitigation; and so on, until "Possible!".

**The user's design along the way:**
- **The scene in full, problems in their own bucket.** Should a plain "expand" even be told about the glue? Told, but given a separate place for possible problems. That took PR-1 off OC-6 and OC-20 (0 of 3 to 3 of 3, batch 9).
- **Examples for grain.** "Delving into details at an 11, I need you at a 6." The examples keep the original rug ("may be too heavy"), and a plain book example at the same grain as the others, so simpler examples don't get coarser grain.
- **Intent is the original full command,** not derived from the action ("pull rug out from under crate" doesn't tell you why), and carried through the rounds.
- **Collateral consequences** go in the consequence listing, not the problems, since they don't violate the stated intent. The non-rule oracle judges them and may highlight them as undesirable. "Yes, they get highlighted, but No it's not by the imagine engine."
- **A possible problem is a deferral.** In the abstract: "Imagination: I've thought of something that might be a problem. Should I think about it as a problem? Oracle: Yes, it's a problem. I'm classifying it that way, and requesting you to imagine mitigations. Imagination: Very good! Imagining mitigations now." So a flag doesn't take over the oracle's job of posing the questions.
- **A prompt per ask** (mine, the user's mirror agreed): a tailored prompt per ask buys instructions and examples suited to it, but a shared core has to be deliberate, and testing a change to it takes more runs than testing one ask's part.
- **Families, not stages** (user). The 2026-11-10 entry set the oracle-or-engine question aside. The user's revision: "Oracle" and "Engine" will be families of prompts, with the rules-block and non-rules-block judgments already under the oracle's. The broad term for the generating family is **imagination**, and what was called the improvisation engine is one of its asks: "improve 'wipe [table1] with cloth' by improvising a cloth". Mine, the correction the user took: the imagination proposes the cloth, and the oracle judges whether it will do, the stretch included, as the 2026-11-08 entry has it.

**Mine, agreed:**
- **The tension sits in one sentence.** The premise ("what each … has to do physically for the action to happen") kept the method ordinary and the action succeeding (batch 11). "How each of the things … moves" freed the knock-on (batch 10, 2 of 3, flagged as a problem). So the knock-on is a later ask's, with its own wording.
- **Exit (c), now.** The play-by-play plan's premises no longer stood (a stage feeding the rule cell as is, a piece that never sees the request, an iterative generator as later work), and its names would carry into every later ask by path dependency (user). So the episode ends with its findings, and the [imagination plan](AGENT.imagination.planning.md) renames the piece before a second ask is built. Revised the same day (user): the probe's folder splits by family instead (`pieceProbe/`, `oraclePieces/`, `imaginationPieces/`), and each ask is its own read piece named for what it returns, so `playByPlay` keeps its name and ask 2 is `consequences`.
- **The family test:** a prompt that picks from a closed answer set is the oracle's (an answered piece); one that produces something to read is the imagination's (a read piece).

## An oracle piece answers with a verdict or a request (2026-11-12)

**Where it came from.** With the imagination plan held for the judging pieces (its IM-4, settled by the user), the next piece is the rule cell adjusted to the split asks. As first booked, the adjustment ran one way: the rule cell reading `playByPlay`'s lines. The user: it runs two ways, since something has to send the more-detail ask in the first place. That was the imagination plan's IM-2, "a 'not enough detail to judge' piece", which was mine.

**The user's design:**
- **The answers say what is called for.** `blocks` was never absolute. It means "void the rule, or find an alternate method around it", and both of those are asks for the imagination. So "needs detail" is one more answer of the same kind, and so is the path to `consequences`, perhaps a fourth. More will come.
- **Two kinds of output.** An oracle piece that knows it can ask for more says one of two things:
  - "I have what I need, and here is my judgment";
  - "my judgment is that this isn't enough for a judgment, in the following way(s)".
- **The vocabulary of requests is in flux,** but there will be many kinds to accommodate. They grow on two sides: the imagination's library of asks, and the oracle pieces' ability to say how more information would improve their read.

**Mine, agreed:**
- **Sufficiency is entangled with the judgment, so the two share a call.** What is missing shows up only when the judgment is tried: seeing that "tilts" and "tilts" doesn't settle the glue means knowing the glue turns on whether the teapot moves relative to the table. A separate sufficiency piece would:
  - do the judgment twice;
  - sometimes disagree with the piece that judges;
  - lose the request's "in the following way(s)", which only the judging call knows.

  So IM-2's piece of its own is superseded. The exception is a structural gap, such as a rule's end with no line or an action with no motions, which code catches before any call.
- **A verdict and a request differ in what code does next.** A verdict, `blocks` included, is a known answer about the plan as written, so code may change the plan. A request is "can't judge yet", so code keeps the plan and asks for more description.
- **The requests are typed by the imagination's asks,** with parameters: more detail on which step, which thing and which question; what happens to which unnamed thing; and the later asks.
- **The over-asking risk:** a piece that can ask has an easy way out, the oracle's counterpart of the imagination's over-flagging. The settled rule cell judges "tilts" and "tilts" rather than deferring it. So the corpus needs cells where asking is wrong as well as where it is right, and the loop's cap (the imagination plan's IM-3) is the backstop. Refined below: it is read per hop, not from the count of rounds.

**Tool calls, considered and set aside.**
- **Mine:** a request is a parameterised call addressed to someone else, so tool calls would carry it, with typed arguments, several requests in a turn, and dispatch that maps directly onto asks.
- **The user's counter:** a tool's result comes back into the same context. The oracle gets the new information together with its own reasoning for asking, which may help it follow its thread, but leaves it **more open to compounding errors and confirmation bias**.
- **Agreed:** the format and the conversation separate, and the conversation is the cost.
  - A fresh call keeps one judgment per call, with the loop in code (user, 2026-11-10).
  - It judges the new detail against the scene, not against the earlier call's expectation.
  - It is a function of its inputs, so it can be a probe cell.
  - Most of the benefit can be kept by passing the **question** the oracle asked into the fresh call, without its reasoning. Whether to pass it is a probe question.
  - Once every call is fresh, a tool call is only another output syntax, so a fenced JSON block, which the probe already reads, carries the two kinds as well. This design doesn't depend on Micro's tool use, so Slice 6's tool-call check keeps its own reasons.

**The direction:**
1. Each oracle piece answers in one fenced JSON block, with either a verdict from its own closed set or one or more requests typed by the imagination's asks.
2. Code checks structural gaps before the call, carries each request to the imagination, and calls the piece again fresh, with the richer inputs and perhaps the question asked.

**Open:**
- the request vocabulary, in flux by design;
- where the line falls between judging and asking, such as whether "tilts" and "tilts" stays `allows`, which is a corpus call;
- whether adding answers costs the settled cell's accuracy on Micro (46 of 48 with two);
- passing the question, or not.

**The composition probe moves up** (the user's question, agreed). Its first placing, after the non-rule blocker, rested on "composing one piece with code tests nothing new". Now the rule cell and `playByPlay` meet across a real seam, and a request's worth shows only in what comes back: whether the detail lets the cell judge, and whether the loop settles. So it is built alongside the rule cell's adjustment, starting with that pair of hops (mine), and is where the imagination's held flags and form get a consumer's reactions.

**Rounds are not the signal** (user). A hard case takes many rounds, each warranted. The user's sketch of the tilted-table pour:
1. The oracle needs detail on what tilting the table does to the teapot; `playByPlay` answers that it tilts with the table, and the tea pours.
2. The oracle *now* needs detail on the other things on the table; `consequences` answers that they slide off and fall.
3. The oracle: "That's a problem … need an attempted mitigation"; the mitigation answers "pick up the saucer *first*, then tilt the table".
4. The oracle: "That will work. Approved."

So the grading is per hop (mine, agreed):
- **An unwarranted request** asks for what the inputs already establish, repeats one already answered, or comes where the corpus says judge. An answer that changes nothing in the next judgment is a weaker sign, since confirming can be fair.
- **Under-asking,** judging where something is missing, is the mirror fault.
- **The cap** is a backstop sized for chains like this one, not a limit on rounds.

**The sketch is a corpus chain already:** OC-30 (A, the glued pour), OC-30/2 (B, tip the table, the saucer and cup slide) and OC-30/3 (C, B repaired, the saucer off first). It is the composition probe's target. Its hops need pieces not built yet: a request type for `consequences`, a judgment of a consequence against the intent, and the mitigation ask. So hops join as their pieces land, and a hop with no piece yet can be played by hand, as Slice 5 had it (mine). "That's a problem, need a mitigation" is a **verdict with an implied ask**, like `blocks`, not a request for information, so the two kinds hold (mine).

**Overlap** (mine): the composition probe takes up much of Slice 5 (the loop by hand on OC-30 and OC-31), and its rounds are Slice 6's multi-turn probe as fresh calls looped in code. Whether those slices fold in is the user's call.

## The non-rule blocker first, the rule cell later (2026-11-13)

**The user's question:** the responses beyond `allows` and `blocks` need prototyping, but should that be done while drafting the non-rule blocker, returning to refactor the rule cell once the design is more mature? The 2026-11-12 entry had the rule cell adjusted next.

**Mine, agreed by the user:**
- **The blocker is new,** so the verdict-or-request contract costs nothing extra there. On the rule cell it means redrafting a settled prompt (46 of 48) against a contract still in flux.
- **The blocker will press the request vocabulary harder.** The rule cell needs only how a rule's two ends move. The blocker judges impossibility for reasons no rule names, so its requests are open-ended, a fact such as a size as well as a method. The vocabulary is then shaped to serve both pieces, and the rule cell adopts it rather than sets it.
- **The rule cell can wait unrefactored.** Code asks `playByPlay` before calling it, so it never needs to ask. Reading `playByPlay`'s lines is adapter code: the lines for the named things, and the silence contract for a rule's other end.
- **The argument the other way,** and why it waits: the rule cell is the only piece with a known baseline, so it alone can measure what a third answer costs on Micro. That measurement is worth more once the vocabulary has settled, so it comes with the refactor.

**The order:**
1. the non-rule blocker, verdict-or-request from the start;
2. a composition probe alongside it, first composing what exists (`playByPlay` into the settled rule cell, through the adapter), then the blocker as it is built;
3. the rule cell refactored to the matured contract.

### The user's notes

1. Sections get specifiers, such as `Role:`.
2. What the data is and what the role should do are separate, in this order: `Role`, `Reading the scene`, `Task`.
3. `Reading the scene` and `Reading player intent` are reusable modules, tuned more broadly than one task. `Reading player intent` is likely global to the system. `Reading the scene` can vary somewhat with the render format.
4. `Reading player intent` carries the expectation that moving an object moves everything on or in it, and that moving a container away from its contents is considered only when the player specifies it or context makes it obvious ("yank the saucer out from under the cup" is a move of the saucer and of the cup's containment on the saucer).
5. `Reading the scene` explains the two registers, and headers make them obvious.
6. The graph representation is probably better wrapped in a Markdown code fence.
7. `Task` says how to use Rules. `Reading the scene` says what they mean, fictionally.
8. Rules is a section the earlier instructions anticipate, with no ad-hoc instructions of its own.
9. Anything after the question must be an explicit callback to the task instructions. It may not be needed: instructions up front, data and input last.
10. The two registers are a fictional description and a graph representation. v1 lost that distinction, so the sections are renamed and `Reading the scene` reinforces it (on v1).
11. Rules is a non-exhaustive list of fictional constraints derived from the graph: a rule's presence constrains explicitly, and its absence defers to the logic of the scene (on v2, reworded on v3).
12. Four labels, with `incomplete` and `impossible` as in JP-10: the reality is agreed and in the way, against the request suggesting the reality is not agreed. v5 uses the label wording I offered, which the user accepted as a direction (2026-11-04).
13. `Role`'s goal is the next step in communication: completing the request, aligning player understanding, or bouncing the question back as a puzzle (on v5).
14. The labels are four distinct categories, not a spectrum, so they have no inherent order; `Task` lists them in the order of `Role`'s next steps (on v6).
15. Fiction is not a simulation (2026-11-05). A simulation gives positions and derives relations from them. Fiction establishes the relations and leaves positions undefined, because they don't matter. Pulling the rug out establishes nothing about where the rug is; it revises the fact that the crate is on the rug.
16. People reason about fiction with a twist of register (2026-11-05): they briefly imagine a scene framed by what is established, check it against real-world physics, then abstract back to what is established. Sliding a cup across a table is thought about as motion when judging whether it can be done, yet it establishes no new fact: the cup goes from an unspecified spot on the table to an unspecified spot on the table.
17. Reasoning about fiction is lazy, not exhaustive (2026-11-05). Exhaustive reasoning concludes that the teapot comes with the table; lazy reasoning declines to modify the fact that the teapot is on the table. A secret door in a bookshelf does not have to imagine fifty books moving: the books remain as established. "It's a sort of compression." The working question is "If I move this table, which of these established facts need to be reconsidered?" A pyramid of wine-glasses stacked precariously on the table jumps out, and the glued teapot gets to be ignored.
18. `Reading player intent` and the rule's "defaults to moving" are the old voice, and should describe fictional inertia instead (on v8).
19. It is permissible for the LLM to be a little dumb, so long as it is not recalcitrant (2026-11-05). Users understand that they sometimes said too little for a system to parse their intent, but they get rightly frustrated when the system resists a legitimate intent.
20. Be skeptical of negative instructions that modify positive instructions: LLMs don't seem to deal well with that structure, so state the test positively (2026-11-05, on the chasm sentence).
21. Rules state the constraint plainly, as a rule, in a context that has already explained that rules can be dissolved through action (2026-11-05, on JP-1). "Cannot leave ... until freed" was awkward because it embedded the puzzle-solving mindset, that rules are meant to be bent or broken, in the rule itself.
22. `contingent`, `incomplete` and `complex` may be independent gates, of which we recognize only the first to fire (2026-11-05): an attempt to pry the teapot off with a screwdriver could be all three.
23. The one-word judgment is used for deterministic routing, and any more capable LLM that gets deferred to receives the whole output, including `Needs` and `Revises` (2026-11-05). This was the user's condition for the gates direction.
24. `Reading the scene` aligns with established against unestablished, not present against absent (2026-11-05, on v18). The prompt does not affirm that an unstated thing is neither present nor absent, only that it is not established as either. `Fiction` describes what has been established, since what the place "really is" can change through minting. `Graph` "adds no facts of its own but can help disambiguate the language of the fiction section" (the user's wording).
25. The `Fiction` part is tiny, with the details of established against exhaustive added later as clarifications and exceptions. Migrate them earlier, into `Fiction`, so they frame the later sections immediately (2026-11-05, on v19).
26. Don't tie the scene render to player perception (2026-11-05, on v20). "Reasoning is grounded in this established fiction" replaces "This is the story you are reasoning about" (the user's wording).
27. The lazy view does not need calling out against the graph in the prompt: building lazy-change expectations into `Fiction` and then listing the graph is enough to draw the parallels functionally (2026-11-05, closing JP-11).
28. `incomplete` is renamed `obstructed` from v24 (my suggestion, the user agreed, 2026-11-05). Earlier notes and rows keep the old name where they record what was said at the time.
29. JP-14 may be mixing two types of challenge (2026-11-05): can you do this thing you attempt, against do you even have a plan for the attempt? In the Coyote Game, "Wire the cloud-machine to the tesla coil to make a lightning-storm generator" is an insanely difficult skill challenge that the genre says the Coyote passes without issue, and "Catch the Road-Runner" is a challenge where plan after plan fails to be the right plan.

### Settled

Decisions a fix must not undo without saying so. A "was JP-n" label resolves any older reference.

- **The replacement rule (was JF-1):** it stands, as [When a candidate replaces the baseline](../../../../../lambda/ephemera/calibration/AGENT.md#the-built-judge-prompt-v45) now words it. A label the fixture tolerates is a border, not a lost pass. The `teaTable` table tolerates `complex` (user, 2026-11-06), since that division waits for the planner and `complex` fails safe, as the `tavern` table already does.
- **Two uses of "you" (was JP-3):** a sentence in `Reading the scene`: 'In the scene, "you" is the player'. The render stays as it is.
- **The user's `SECURED` passage (was JP-5):** it stays out. Its removal was mine, and this is its explicit decision. A code comment in `sceneRules.ts` records that it made things worse, and the rule and the inertia framing now cover its job. It is the first thing to try if the table refusal survives Slice 4.
- **"Text adventure" (was JP-7):** not named. The genre may suggest things are fixed in place, which could feed the table refusal. The text-adventure reading stays a requirement of the behaviour, and `game master` stays.
- **Lazy view and the graph (was JP-11):** no further prompt text (note 27). `Fiction` is the framing that replaced the old `LADDER` steps and the "what goes with what" wording of `PRECEDENCE`.
- **Transitory against established (was JP-12):** no further text. Only what the action depends on can change the label: `Needs` ("could not work without") and `Revises` ("established facts") leave a detail the action merely produces, such as a slick of moisture, to the narration. The full judgment of what is worth recording is for the future.
- **Rule wording (was JP-1), replaced by M28 to M30:** a rule states an invariant under a handle, and the judge gives each relevant rule a verdict. The hosted rule reads `[teapot1] stays fixed relative to [table1]'s frame. When [table1]'s frame moves, [teapot1] travels along with [table1].` (user's first sentence; second mine, with the user's "implies no restriction" as the fallback). A player can still set out to change the facts behind a rule. The rule never says "glued"; the `Rules` bullet's "facts behind it" is the only join.
- **Open world (was JP-9):** what is unstated is not established as either present or absent. Details get established because they are newly relevant, not because they newly occurred. Plausible improvisation is wanted, and improvisation for convenience is not. Silence can count as evidence: a bridge over a yawning chasm "would have been mentioned if it were there", so it leaves `contingent` for `incomplete`.
- **Improvised details (was JP-13):** the `contingent` label, with sure and unsure suggestions going to the same place. Whether to mint is decided by a more capable engine, which is for CA-6; a new established fact reaching the graph leaves a note there too. Fault tolerance: most border errors recover, through another turn or the engine's second look. A wrong `simple` has no recovery, and a wrong `impossible` recovers only if the player has something to add, so it does not excuse the table refusal.
- **Independent gates (was JP-15):** `Answer` is one word, the first gate that fires, with the obstacle before `Needs`, and code routes on that word alone. `contingent`'s and `incomplete`'s sentences stay for the first probe. `complex` stays a judgment, since `Revises` alone can't decide it. For CA-6: a deferred LLM gets the whole output as a first pass's notes, not as established facts, and its prompt has to say so, or a wrong `Needs` could anchor it.
- **The judgment schema (was JP-6):** five labels for this iteration, with `confusing` added at v37 (user) as a fall-through when no test says "yes". Calculating likely consequences nobody referred to, such as a precarious pyramid of wine-glasses on the table, is a known weak point, deferred to a future iteration as its focus (user, 2026-11-05). So Slice 4 does not grade it, and my reading of it as `complex` was not adopted. `JUDGE_LABELS` in code has the five; `TRIAGE_LABELS` keeps three as the control (M26).
- **`obstructed`, and `impossible` (was JP-10, under the name `incomplete`):** the touchstone is respect for player ingenuity (user, from GMing indie RPGs): going from "It's an adamantium door... No man. Didn't you listen?" to "Well, I don't know. Can you? What do you want to try?". It differs from `Consult`, which asks the player to clarify and sets no puzzle. Freeing is not the only way past an obstacle (tipping the table to pour), so the judge names the obstacle and no way past it. The tone of the invitation is the whole system's, not this check's. `impossible` is a mismatch of shared reality, not "stop trying": "I don't think you and I have the same idea of the size of shoeboxes or motorcycles." For CA-6: an `obstructed` entry will at some point go to an LLM that decides how to present the possibilities to the player, and which will sometimes describe it as impossible if the player has no clue a path exists, so the judge need not draw that line. `obstructed` still says "getting past it is up to the player" as a placeholder (JP-14).
- **Module boundaries (was JP-8):** `Reading the scene`, `Reading player intent` and `Improvising` become modules, and `Task` belongs to the judge (mine, the user agreed).
- **Reasoning and answer order (was JP-2):** the lines are `Picture`, `Rules`, `Obstacle`, `Needs`, `Revises (if it happens)` and `Answer` (`Rules` added by M28). To watch in Slice 4: the model may recite the structure, or decide first. Slice 3: the scorer stops reading the last line alone, reads `Answer:` plus a sentence, and gets the label with code alone, since routing depends on that word (the user agreed).
- **A direct attempt on a rule (was JP-14):** note 29 settles it (my reading, the user agreed). `obstructed` means the player has no plan yet: "pick up the teapot", "catch the Road-Runner", and "up to the player" is correct for it. A request with a plan makes the obstacle its target, so the fact appears in `Revises`, not `Obstacle`: "pry it off with a screwdriver" reads `Obstacle: nothing`, `Needs: a screwdriver`, `Revises: glued to the table`, and answers `contingent`. Whether the attempt works is a skill question, and whether it was the right plan is an outcome question. Neither is the judge's, and today the game's genre answers them. To watch in Slice 4: a model that still names the target as the obstacle answers `obstructed`, a recoverable error; "pry it off" is graded only as not `simple`. Thin plans ("with a feather") are a tolerated border. To revisit when non-genre-resolved challenges arrive, with real rules and skills (user, 2026-11-05).
