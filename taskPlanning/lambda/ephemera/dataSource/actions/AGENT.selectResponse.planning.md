# Select response on the command transcript bubble

**Status:** Drafted 2026-10-09 (ISS8252), SR-1..SR-8 decided. Slices 1 (wire type and client rendering), 2 (producer), 3 (row and handler), 4 (answer ingress and resume) and 5 (payoff test) shipped 2026-10-09; next is Close-out (the manual dev check from Verification is still outstanding). Follows the shipped command-outcome bubble and persistent-command row (rules in [`actions/AGENT.contract.md`](../../../../../lambda/ephemera/dataSource/actions/AGENT.contract.md) "Persistent command" and "Command outcome"; leftovers in [`AGENT.implementation.md`](../../../../../lambda/ephemera/dataSource/actions/AGENT.implementation.md) "Shelved: asking the player").

Task-planning conventions: [`taskPlanning/AGENT.md`](../../../../AGENT.md).

## Purpose

When a command is ambiguous between objects ("get cup" with a red cup and a blue cup in reach), the player gets `Did you mean "..." or "..."?` as a dead-end `Error` line, and has to retype. Instead, the bubble should show the choices as selectable options; picking one sends a structured answer, the stored command resumes with that answer applied, and the bubble is replaced in place by the command's outcome.

Most of the machinery exists: the bubble is revised in place under its `MessageId` (`Outcome`), the persistent row freezes Plan's output and accepts `referentAnswers` (`stableRefKey` to thing id), and `resumePersistentCommand` reruns from `compileAttemptsFromSkeleton` with them. What is missing is (a) a wire arm for a question, (b) the producer handing the handler each option's `referentAnswers` and the frozen root, (c) the handler writing the row and publishing the question, (d) an `answer` ingress, and (e) a payoff proof across the whole loop. The first prototype is **referent ambiguity only**.

| SR-4 | **No choice history on the bubble.** The Select is replaced by the resumed command's own outcome (or by the next Select if still ambiguous). Nothing echoes "you chose X". | 3, 4 | Decided 2026-10-09 |
| SR-5 | **Producer shape (producer half shipped in Slice 2: `referentAnswers`/`label` on alternatives, `root` on the Consult result; remaining here is the handler half --- it owns the row write, `optionId` minting and all copy).** `GroundedAttemptCandidate` and `ConsultAlternative` gain `referentAnswers: Record<stableRefKey, objectId>` (a copy of the identities already in scope); an alternative is a whole joint assignment, so an option may carry several keys. `compileAttemptsFromSkeleton`'s `Consult` result gains `root: PersistentCommandRoot` (command, skeleton, attempts via `toJSON`, classify confidence), built in that one place so the fast path, the general path and resume are all covered. `parseCommand` does not write the row: it sees neither session nor transcript, and a store write would break its shape. The handler owns the row write, `optionId` minting and all copy. | 2, 3 | Decided 2026-10-09 |
| SR-6 | **Copy and when to ask.** Labels are `RenderTree`, built only in the handler (replacing `consultMessageForPlayer`), from the alternative's `proposedCommand` / `label`; identically named objects read "cup" / "cup" until qualified referents (`{ objectSpan, qualified }`) exist, then the label improves with no wire or row change. Offer a Select only when the alternatives differ in `referentAnswers` (a Consult that differs by plan is the deferred `selectedAttempt` case), and only when `ResponseContext.transcript` exists (no session means no row key and no bubble). Otherwise keep today's `Error` copy. | 3 | Decided 2026-10-09 |
| SR-7 | **Wire name and shape of the answer message.** Recommend a sibling of `CommandAPIMessage`: `{ message: 'answer'; CharacterId; messageId; optionId }` handled in `app.ts` next to `isCommandAPIMessage`, session from `internalCache.Global`, forwarded through an `apiEphemera` `send*` helper like `sendParseRequested`. | 4 | Decided 2026-10-09 |
| SR-8 | **Row lifecycle: one row per character per session, answered in place.** A typed command's `put` overwrites the key (a new command replaces the pending one), so no clear-at-start. An answer runs `ephemeraDB.optimisticUpdate` on the row: the reducer sets `pending.answer` to the `optionId` only if `pending.options` holds it and `answer` is unset (its being defined is what marks the question answered), else makes no change; the winner resumes from `successCallback`'s `prior` (the pre-answer state, so no separate `get`). A duplicate answer (the question is already answered, by any option) is a silent no-op: the first answer's outcome owns the bubble, and an `Error` there would overwrite it. A late answer to an overwritten question, a missing or expired row, or an unknown `optionId` is a no-op that gets the stale-answer `Error` on the bubble (copy written in Slice 4). If the resume is still ambiguous (`Consult`), a second conditional update replaces `pending` with the new question in the same row; a terminal result leaves the answered row to its TTL. `optionId`s are fresh UUIDs per question, so they are the nonce (every Select revision shares the bubble's `messageId`, so `messageId` cannot tell questions apart), and a late write from an answer whose question was overwritten fails its condition. The reducer runs under Immer: take the payload from `prior`, not from inside the reducer. The helper bug that would have broken the answer write (`optimisticUpdate` set `updated = true` after a failed conditional write, so a retry ending in `ignore` fired the loser's `successCallback`) is fixed at the source in `mixins/update.ts`, with a regression test in `update.test.ts`. | 4 | Decided 2026-10-09 |

## Risks

- **A Consult is not always a referent question.** Alternatives can differ by plan over one assignment. SR-6's "differ in `referentAnswers`" test keeps those on the old `Error` path; if it is too loose, a Select could offer indistinguishable options.
- **Identical labels.** Two same-named objects produce "cup" / "cup". Accepted for the prototype (SR-6); a Select must still map each option to its own answer, which the tests should pin by clicking the second option.
- **Root size.** `Consult` now carries the frozen root. It is plain data already stored by the row design, but check the published result is not logged or published to the bus wholesale.
- **Type change fan-out.** `CommandOutcome` and `ParseCommandConsultResult` are consumed widely and by tests outside tsconfig; run the full suites, not just touched files.
- **Whole-body revisions.** The Select revision and the final outcome must each resend the echo text, as every revision does; the row's `transcript.command` is the source.
