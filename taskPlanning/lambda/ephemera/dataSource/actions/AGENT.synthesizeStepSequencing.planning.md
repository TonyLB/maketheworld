# Object manipulation: generalized Synthesize step sequencing (iteration 8)

**Status:** Scheduled 2026-07-21 --- work is now underway. Split out 2026-07-21 while investigating BD-16's `sameHost` rebuild --- caught before it became scope creep on that work: shipping `sameHost` didn't require this generalization (an ad hoc, route-specific Expansion check was enough, matching the existing precedent `expandTransferMembership.ts` already set on the membership route), but it surfaced a real, distinct gap worth naming on its own. See [`AGENT.objectManipulationIterations.planning.md`](AGENT.objectManipulationIterations.planning.md) for the full iteration ladder.

Task-planning conventions: [`taskPlanning/AGENT.md`](../../../../AGENT.md).

## Purpose

Design and (eventually) build one real, generic Synthesize-side executor that walks an ordered sequence of ungrounded steps --- `Change`s and `Assertion`s alternating as needed --- performing Grounding, Expansion (inserting repair steps when an `Assertion` is violated), and Validation per step, so that a repair (a `TransferMembershipStep`, say) becomes a first-class step in a real grounded sequence rather than a bolted-on field on some other step's result. The executor's own shape is decided (see "Expansion execution model" below, BD-29/BD-30): Expansion splits into operand-expansion (set-closure fixpoint) and command-expansion (step emission over the closed set), and the whole ground -> operand-expand -> command-expand cycle runs as a phase-stratified worklist over progress-tagged instructions, not as recursion.

This is **not** new design from nothing: the shape already exists, unwired, in two places:

- `plan/compileUngroundedPlan.ts`'s `compileRelationalUngroundedPlan` already returns a real `UngroundedPlanStep[]` of exactly `[sameHostAssertion, change]` --- written, tested in isolation, never called by any live route.
- `sandboxPlan.ts`'s `evaluateSandboxPlan` already folds a step array through state generically, and is the one place (`selectIdentityPlanTuple.ts`, membership dry-run only) where an Expansion-inserted repair (`expandTransferMembership.ts`'s `dissolveSteps`) gets appended into one real array before evaluation --- but it never reaches the live commit path.

Two shipped live examples now exist to design the generalization against, where previously there were none: BD-13 (`computeCarryClosure`, cascading fixpoint entirely within Expansion, no Plan involvement needed) and BD-16 (`expandSameHost`, a genuine Assertion-shaped precondition with a real repair step, currently bolted on as `transferFromHostId` rather than appended to a sequence). Per this project's own "expand as concrete cases demand" discipline (the same principle that kept `Assertion`'s union to one member until BD-16 needed a second), this is the point at which designing the general shape stops being premature.

**A third worked example, found 2026-07-21 (BD-28): relation dissolution during carry is itself a live case of exactly this incoherence, not just a motivating analogy.** Verified concretely: `classifyInteractionUnderTransfer`/`boundaryEdgeOutcomes` (`positions/positionGraph/expandValidate/interactionUnderTransfer.ts`) gets independently re-derived in **two** places against what should be the same graph state --- once in `enrich/objectManipulation/synthesize/expandTransferMembership.ts` (live-wired via `selectIdentityPlanTuple.ts`'s dry-run, producing real grounded `DissolveRelationStep[]`), and again inside `positions/positionGraph/expandValidate/applyTransferSet.ts` at actual commit time. **That dry-run/commit-time recomputation itself is correct and deliberate** --- the same concurrency-safety pattern already shipped for membership (sandbox dry-run + `MultiKeyUpdate` atomic re-check, see `applyObjectSetTransfer.ts`): dry-run reads a possibly-stale snapshot, and commit-time re-verification against the live graph, inside the transaction, is what catches drift between the two. **The actual defect is a second, unrelated duplication living entirely inside commit time:** the explicit `DissolveRelationStep[]` from the dry-run computation never reaches the live apply --- it only feeds the dry-run's own legality re-check (`evaluateSandboxPlan`) and is then discarded; only the closure's `objectIds` set crosses into `applyObjectSetTransfer.ts`, where dissolution actually happens purely as an implicit side effect of `EphemeraPositionGraph.removeObject`'s automatic edge-stripping --- a second mechanism, at the same moment, doing the same job the discarded explicit steps already described. Net effect: no player-facing fact is ever streamed when a carried object's relation to something left behind is severed (unlike BD-16's compound apply, which does stream `Object Relation Changed`). See BD-28 below.

## BD-27b reshaping findings (2026-07-22)

Read `compileUngroundedPlan.ts`, `sandboxPlan.ts`, and their immediate neighbors (`ungroundedPrimitive.ts`, `parsePlanStep.ts`, `sandboxStep.ts`, `toSandboxPlanStep.ts`, `sandboxState.ts`, `selectIdentityPlanTuple.ts`, `applyTransferSet.ts`, `interactionUnderTransfer.ts`) in full, per the Getting Started step above. Findings, grounded in the actual code rather than restated intent:

**`plan/compileUngroundedPlan.ts` (`compileMembershipUngroundedPlan` / `compileRelationalUngroundedPlan`):**

1. **Wrong input shape.** Both functions consume legacy `MembershipManipulationFrame`/`ManipulationFrame` types, not Parse's tokenized skeleton or `matchRelationalTemplate.ts`'s role-tagged output --- the live relational route already builds its ungrounded steps a different way (`compileRelationalFromSkeleton.ts`), bypassing this function entirely. Reshape must repoint at the live Plan-stage output per route.
2. **Missing `stableRefKey`.** `objectSpanRef(...)` calls here never pass a `stableRefKey` (legacy frames only carry span text) --- BD-23 needs it for Grounding to disambiguate repeated spans; live callers (`groundReferent.ts`) already expect it.
3. **Output shape is a fixed 1-2-element array, not a worklist seed.** `CompileUngroundedPlanResult.steps` is a bare `UngroundedPlanStep[]`, hand-built as exactly `[change]` or `[sameHostAssertion, change]`. BD-30's worklist needs an *appendable*, progress-tagged instruction list (command-expansion pushes new items to the front) --- today's return type has no per-item progress tag and no identity to append against. This return type is a prerequisite for BD-30's worklist design, not an independent concern.
4. **No `IsolatedFromRelations` emission path.** Neither compiler emits BD-28's proposed primitive, and `ungroundedPrimitive.ts`'s `Change`/`Assertion` union has no member for it yet.
5. **Two independent hand-rolled tuple-builders**, no shared "append a step" helper --- if BD-27a's "one executor" holds, output *construction* should converge even though input *parsing* legitimately stays route-specific.

**`evaluateSandboxPlan` / `sandboxPlan.ts` (+ `sandboxStep.ts`, `toSandboxPlanStep.ts`, `sandboxState.ts`):**

1. **Candidate-wrapped, not Plan-IR-shaped --- and not the target output shape at all.** `SandboxPlanStep` wraps `IdentityPlanCandidate`/`RelationalIdentityPlanCandidate`, both carrying proposer-only bookkeeping (`label`, `jointRelevance`, `sourceTags`, `confidence`) that Validation never reads --- confirmed directly: `toSandboxPlanStep.ts`'s own converter pads all of these with placeholder values (`''`, `1`, `[]`) purely to satisfy the type. `SandboxPlanStep` is `evaluateSandboxPlan`'s **input**, not Synthesize's output --- and it is not what the ground -> expand -> synthesize instruction set should eventually produce; it is today's caller (`selectIdentityPlanTuple.ts`) hand-building a lossy adapter from real grounded steps just to feed the old fold. The generalized executor should operate on the grounded `ParsePlanStep` union (or its BD-27c-generalized descendant) directly, retiring `SandboxPlanStep` and this placeholder-padding converter entirely, not reshaping them in place.
2. **No `Assertion` step kind at all.** Only `transferMembership`/`relational` exist. Assertion evaluation + repair-insertion happens entirely in caller code today (e.g. `selectIdentityPlanTuple.ts`'s `sandboxMembershipDryRun` hand-calls `expandTransferMembership` and splices the resulting dissolve steps into the array *before* calling `evaluateSandboxPlan`) --- Expansion is precomputed and spliced in, not part of the walk. BD-27's executor requires Expansion to be inline.
3. **Flat `reduce` over a fixed-length array, not a worklist.** The exact opposite of BD-30's model (mutable frontier, per-item progress tags, priority-ordered driver, shared expansion environment). This is the single biggest reshape: replacing the `reduce` with a worklist loop.
4. **Step-sequence-walking layer is dry-run-only; the low-level primitive one layer down is not (review correction, 2026-07-22).** The *low-level* boundary-edge-classification-and-mutate primitive (`applyTransferSet`/`boundaryEdgeOutcomes`/`computeCarryClosure`) is already genuinely shared --- `applyObjectSetTransfer.ts` and `applyObjectRelationalChangeWithTransfer.ts` both call `applyTransferSet` directly, not a reimplementation, and neither touches `SandboxState`/`SandboxPlanStep` at all. What's actually unreached is one layer up: `evaluateSandboxPlan`'s **step-sequence walk** itself, which no commit path calls, mirrors, or has an equivalent of --- commit goes straight from one pre-decided set to `applyTransferSet`, never constructing or walking a sequence. Whether the reshaped walker (once it operates on real `ParsePlanStep`s rather than `SandboxPlanStep`, per finding 1) becomes one executor with two modes or stays sandbox-only alongside a separately-reshaped BD-27c kernel walker is **not resolved here** --- tracked as BD-31 above.
5. **No BD-27c primitive dispatch.** `applyTransferMembershipStep`/`applyRelationalStep` (`sandboxStep.ts`) are still two route-specific appliers, each inlining its own graph mutation --- not dispatched through one generic primitive-apply keyed on step kind.

## Expansion execution model (BD-29 / BD-30 rationale)

The two-kinds-of-expansion decomposition (BD-29) and the worklist driver (BD-30) are the same design seen at two altitudes: BD-29 is *what the phases are*, BD-30 is *how they run*. Recording the reasoning here rather than in the table cells, since it's the load-bearing part.

**Why two phases, ordered.** Operand-expansion (the carry fixpoint) and command-expansion (step emission) have a real data dependency, not just a stylistic split: you cannot know which edges cross the operand set's boundary until the set is *closed*, because closure itself manufactures boundary edges. `cup On tray` + `cup Under chandelier`, player takes the tray: cup-chandelier is not a boundary edge at rest --- it only becomes one once operand-expansion absorbs the cup and leaves the chandelier behind. So command-expansion (which severs crossing edges) must wait for operand-expansion's fixpoint. This is exactly the cut today's `boundaryEdgeOutcomes` fails to make --- it classifies every edge as absorb-or-dissolve in one pass and then re-sweeps, which is why the classification ends up computed twice (BD-28).

**Why a worklist, not recursion.** A command-expansion can spawn a step that itself needs the full ground -> operand-expand -> command-expand cycle (e.g. `sameHost` inserts a `transferMembership`, and if that object carries a saucer, the inserted transfer needs its own carry-closure). That looks like recursion, but modelling it as a phase-stratified worklist over progress-tagged instructions (BD-30) is strictly better here, for two reasons that are not cosmetic:

- **The shared expansion environment is first-class.** The "compute the closure once and share it between the `transferMembership` and the `IsolatedFromRelations` over the same group" requirement (the whole point of killing BD-28's duplication) wants a *global* environment the loop reads and writes, not a closure-map threaded down and back up recursive frames. Draining all operand-expansion before any command-expansion means the shared set is saturated once, then every consumer reads the identical settled set.
- **The reified state is suspendable.** An explicit worklist + per-item phase tags can be paused at a phase boundary and resumed --- an addressable resume point, which is precisely the shape iteration 4 (BD-18, backtrack channel) will want. Not designed in here, but the formulation doesn't fight it, where recursion (state buried in the call stack) would.

**Soundness invariants the eventual implementation must preserve:**

- **Monotone per-item progress.** Every instruction only advances forward through its tag states (`ungrounded -> grounded -> operandExpanded -> retired`); nothing regresses. The frontier grows (command-expansion pushes new items), but each individual item is on a one-way ratchet.
- **Command-expansion is the sole producer, and every phase acts only on the one instruction it is handling.** Two claims. (1) **Sole producer:** only command-expansion mints new instructions --- grounding and operand-expansion never do, they only transform an item in place (advancing its tag). That is *why* draining the two in-place phases before firing a producer is the correct scheduling policy --- every consumer sees fully-resolved operands and a fully-populated shared set. (2) **Locus-confined:** each phase touches only the single item it is currently processing --- grounding/operand-expansion rewrite that item in place; command-expansion *retires* that item and *mints* zero-or-more brand-new children pushed to the frontier. No phase reaches sideways to edit the fields of a *different*, already-existing instruction. Note command-expansion does two things per fire (retire the fired item + mint children), so it is not "only a producer" --- retiring-self is not production. An `IsolatedFromRelations` "replacing itself" with its `DissolveRelation`s is exactly this locus behavior (retire-self + mint-children), *not* mutation of another instruction --- the same shape as a `violated` `sameHost` retiring itself and minting its repair transfer. (An earlier draft, 2026-07-22, added a `pairedWith` exception letting a `sameHost` assertion edit its paired `Change`'s host --- the one genuine violation of claim (2); it was **retired the same day** in favor of the assert-and-throw principle below, which removes the need for any cross-instruction edit, so claim (2) now holds with no exceptions.)
- **Atomic effects retire into the output; generators retire producing nothing --- and this split is per-primitive, not per-`kind` (corrected 2026-07-22).** Two retirement fates, both via the same command-expansion mechanic. **Atomic effects** (`transferMembership`/`establishRelation`/`dissolveRelation`) bottom out in a kernel primitive and retire *into* the output-ordered list. **Generators** (`sameHost`/`containedBy`/`isolatedFromRelations`, folded into `Assertion` --- see BD-34) contribute no kernel step of their own --- they retire having minted their children (zero or more). Today every `Change` happens to be an atomic effect and every `Assertion` happens to be a generator, but the driver dispatches per specific primitive/predicate, never on the `kind: 'change' | 'assertion'` grouping itself --- see "Dispatch is per-primitive, not per-`kind`" in "Executor design" below. This is why "command-expansion is the sole producer" and "an `isolatedFromRelations` disappears, replaced by its `DissolveRelation`s" are the same statement, not a tension.
- **New items are causally downstream.** A child instruction did not exist when its parent command-expanded, so it can never retroactively invalidate anything already emitted; "push to front, drop back to operand-expansion" is consistent, not just convenient. (Within a single intent, sets never retroactively grow --- command-expansion emits steps *over* a final set, it does not enlarge an existing one.)
- **Termination rides on a settled-groups ledger.** The worklist analog of carry-closure's existing visited-set: before operand-expanding a grounded item, check whether its base object-group is already settled in the shared environment and reuse if so. That single check does double duty --- it is both the dedup (BD-28) and the guard that stops a pathological graph (isolating A forces moving C which carries A) from looping. "operand-expand as necessary" is carrying exactly this lookup.

## Executor design (BD-29/BD-30 concrete realization, 2026-07-22)

Realizes the shape decided above against BD-13, BD-16, and BD-28 as the three required worked examples, per BD-32's confirmed scope (the worklist operates on **one already-selected grounded candidate's step sequence at a time** --- Grounding's joint-candidate-space fan-out (BD-23) and selection-among-survivors stay in the existing, unchanged outer layer).

**Effect steps assert-and-throw their own preconditions --- the load-bearing principle (decided 2026-07-22, BD-33 below).** Every grounded *effect* primitive verifies its own structural preconditions against live state at apply time and throws on violation, because a dedicated upstream `Assertion` + repair was responsible for *making* those preconditions true. This is the exact generalization of BD-28's `removeObject` decision (assert "no relations remain," throw if any do, because `IsolatedFromRelations` was supposed to dissolve them): `EstablishRelation`/`DissolveRelation` assert "subject and target share a host," derived from the endpoint ids the step already holds (`getCurrentHost(subject) === getCurrentHost(target)`), and throw if not --- because `sameHost` was supposed to confirm-or-transfer them into sharing one. The whole reason an earlier draft needed a `pairedWith` sibling-patch was to hand the relational `Change` a corrected host; under assert-and-throw the effect step *isn't handed a host at all* --- it derives and verifies its own from ids it already contains. So `pairedWith` is gone, and (see the `parsePlanStep.ts` consequence below) `hostRoomId` leaves the grounded relational step entirely.

**Instruction representation:**

```ts
type InstructionId = string  // stable identity for causal tracking + settled-groups ledger keys

type WorklistInstruction =
    | { id: InstructionId; tag: 'ungrounded'; step: Change | Assertion }
    | { id: InstructionId; tag: 'grounded'; step: ParsePlanStep | GroundedAssertion }
    | { id: InstructionId; tag: 'operandExpanded'; step: ParsePlanStep | GroundedAssertion }
    // 'retired' isn't a worklist tag --- retired instructions leave the worklist
    // and land in the output-ordered list; Assertions retire by resolution
    // (satisfied/consumed), contributing no kernel step.

type GroundedBinaryAssertion = { kind: 'assertion'; predicate: 'containedBy' | 'sameHost'; subjectId: EphemeraObjectId; objectId: EphemeraObjectId; negate: boolean }
type GroundedIsolatedFromRelationsAssertion = { kind: 'assertion'; predicate: 'isolatedFromRelations'; objectIds: ReadonlySet<EphemeraObjectId> }
type GroundedAssertion = GroundedBinaryAssertion | GroundedIsolatedFromRelationsAssertion
```

`WorklistInstruction`'s signature above needs no change to accommodate `isolatedFromRelations` --- `GroundedAssertion` (2026-07-22, BD-34) just widens internally to cover both the binary predicates (`containedBy`/`sameHost`, subject/object/negate) and the unary one (`isolatedFromRelations`, a widening `objectIds` set instead --- singleton right after Grounding, carry-closed after operand-expansion, via the identical `GroupId`-reuse mechanism `transferMembership` already uses).

**Shared expansion environment** (BD-30's "common referent" / settled-groups ledger; revised 2026-07-22 --- Fix 2, member-indexed lookup):

```ts
type GroupId = string

type ExpansionEnvironment = {
    settledGroups: Map<GroupId, ReadonlySet<EphemeraObjectId>>
    groupIdByObject: Map<EphemeraObjectId, GroupId>  // every member of a settled group indexes back to it
    getGraph: (hostId: EphemeraMembershipHostId) => EphemeraPositionGraph | undefined
    getCurrentHost: (id: EphemeraObjectId) => EphemeraMembershipHostId | undefined
}
```

**Why the `GroupId` indirection (Fix 2):** operand-expanding a `transferMembership`-shaped instruction first looks up `groupIdByObject.get(startId)`; if present, reuses `settledGroups.get(thatGroupId)` rather than recomputing `computeCarryClosure`; if absent, computes fresh, mints a new `GroupId`, stores the closure under it, and indexes every member object id to that `GroupId`. A plain string-keyed map (the original sketch) only reuses a closure when a later lookup happens to use the *same* starting id --- but BD-16's inserted transfer and BD-28's `IsolatedFromRelations` each start their carry-closure from a *different* object than BD-13's original transfer. Without member-indexing, "reusing `settledGroups` if the object was already touched" (as the worked-example traces below claim) has no mechanism to actually succeed --- this is the fix that makes it real.

**Worklist driver** (BD-30's priority loop, realized): per iteration, (1) any `ungrounded` -> ground it via `groundChange`, taking the single-candidate path per BD-32 (error if Grounding produces more than one candidate here --- unreachable once the outer layer has already selected one); (2) else any `grounded`-not-`operandExpanded` -> operand-expand it (a universal phase, no-op except where an instance's own semantics define a closable set --- see below); (3) else fire one command-expansion on the frontmost `operandExpanded` item, pushing any new instructions (already `grounded`, per BD-30's 2026-07-22 simplification above) to the front, and retiring the fired item into the output list.

**Dispatch is per-primitive, not per-`kind` (correction, BD-34, 2026-07-22).** Neither operand-expansion nor command-expansion ever needs to ask "is this a `Change` or an `Assertion`" before asking "which specific primitive is this" --- each phase is really a lookup keyed on the primitive/predicate name:

```ts
type PrimitiveBehavior = {
    operandExpand?: (env: ExpansionEnvironment, step: ...) => ...  // absent = no-op (the common case)
    commandExpand: (env: ExpansionEnvironment, step: ...) =>
        | { retireAsOutput: true }                                     // atomic effect: retires into the output list
        | { retireAsOutput: false; children: WorklistInstruction[] }   // generator: retires producing 0+ children
        | 'defer'
}
```

Per-primitive behavior: **`transferMembership`** operand-expands via `computeCarryClosure`; retires as an atomic effect --- its own kernel-level apply (BD-27c/BD-33, one layer past this worklist) is what actually tests "no relations remain outside the transferred set" and persists. **`establishRelation`/`dissolveRelation`** have no operand-expansion; retire as atomic effects --- their own kernel-level apply derives and tests the shared host (BD-33) and persists. **`sameHost`/`containedBy`** have no operand-expansion; retire as generators --- evaluate live state, produce 0-1 repair children on violation. **`isolatedFromRelations`** (BD-34, folded into `Assertion` --- see below) operand-expands via the same `computeCarryClosure` (shared `GroupId` with a same-object `transferMembership`, when one exists); retires as a generator --- evaluates the closed set's boundary, produces 0+ `DissolveRelationStep` children.

`Change`/`Assertion` remain the durable Plan-authoring vocabulary (`AGENT.concepts.md`'s "an effect" vs "a precondition-shaped check") and `kind` stays on the types as an inherited discriminant, but nothing above requires grouping by it --- today every `Change` happens to retire as an atomic effect and every `Assertion` happens to retire as a generator, but that is an observation about the current five primitives, not something the driver enforces via `kind`. This is also more consistent with `AGENT.concepts.md`'s own "grow the technique set as concrete cases demand" discipline than hard-coding a two-bucket taxonomy the runtime never actually needed.

**`isolatedFromRelations`, concretely (BD-34):** ungrounded shape `{ kind: 'assertion'; predicate: 'isolatedFromRelations'; object: Referent }` (no `negate` --- this predicate has no meaningful negated form Plan would ever emit), added as a third `Assertion` member alongside `containedBy`/`sameHost`. Grounds its one `object` referent via the existing `groundReferent` (single-candidate path, BD-32) --- no new Referent-level shape needed, superseding BD-28's original "needs a closed-set Referent shape" framing; the closed set only appears via operand-expansion's existing tag-transition widening. Command-expansion sweeps `boundaryEdgeOutcomes(objectIds, graph)` (the existing shared function, unchanged): a `carry` outcome present is an internal-consistency error (unreachable --- operand-expansion already absorbed every carry edge; same guard `expandTransferMembership.ts` already has); a `defer` outcome present defers the whole run (BD-31's mode split governs meaning); otherwise, zero `dissolve` outcomes retires producing no children, and one-or-more mints one `DissolveRelationStep` per severed edge (reusing `expandTransferMembership.ts`'s existing per-edge mapping logic, relocated not rewritten; no `hostRoomId`, per BD-33), pushed to the front already grounded.

**Sequencing (resolves BD-28's sequencing wrinkle, 2026-07-22):** `isolatedFromRelations` is seeded *before* its paired `transferMembership` --- `[isolatedFromRelations, transferMembership]`, mirroring the existing `[sameHostAssertion, change]` convention already used for the relational route. No new driver machinery is needed to guarantee `DissolveRelationStep`s retire before `transferMembership`: BD-30 already specifies strict list-order (FIFO) selection at every phase ("ground the **first** such," fire command-expansion on the **frontmost** `operandExpanded` item) and already pushes new children to the front. Given that, seeding order alone is sufficient --- `isolatedFromRelations` stays frontmost through grounding and operand-expansion (nothing reorders the list), fires first, pushes its `DissolveRelationStep`s to the front as a contiguous block, and retires; those retire into the output list ahead of `transferMembership`, which is now frontmost and retires last. (An earlier draft proposed a new "generator before atomic effect" priority tier in the driver to guarantee this; retired on review --- unnecessary, since FIFO + push-to-front + seed order already deliver it.) Paired with a **kernel-apply contract** (a requirement for BD-27c's upcoming concrete kernel design): the kernel applies the output-ordered list in exactly the order the worklist produced it, within one transact. No double-apply risk: `removeObject`'s BD-28/BD-33 contract is assert-only (check no edges remain, throw if any do) --- it never itself calls `applyRelationalPatch`'s remove op, so there is no second mechanism competing with the explicit `DissolveRelationStep`s to remove the same edge.

Today, `isolatedFromRelations` is emitted paired with every `transferMembership` Change, referencing the same object referent, **in the seed order above** --- structurally similar to BD-15(1)'s "prepend `sameHost` before every relational Change." **Enforced by construction, not left to convention (revised 2026-07-22):** `expandSameHost`'s `violated` case mints a repair `transferMembership` directly from live KR state, not via Plan --- if nothing also mints its paired `isolatedFromRelations` (in the same seed order), the repair transfer's boundary edges never get swept and `removeObject`'s assert-and-throw spuriously fires on a legitimate, unaddressed edge. So "introduce a `transferMembership` instruction" is centralized as one constructor that *always* also introduces its paired `isolatedFromRelations`, in order --- used both by the initial Plan-seed step and by the driver's wrapper around any repair output (`expandSameHost`'s `transferStep`, any future `computeCarryClosure`-driven insert). `expandSameHost.ts` itself stays unchanged (still returns its bare `transferStep`); the pairing and its order are added by whatever consumes that output before pushing it onto the worklist, preserving "BD-13/BD-16 must be expressible without changing their own Expansion logic." This narrows --- not reverses --- the "not a rule the executor enforces" framing: it now applies specifically to *future, differently-shaped* primitives (external relationships, multi-hosted objects), not to the current `transferMembership`/`isolatedFromRelations` pair, whose pairing (and order) **is** enforced, because assert-and-throw's correctness depends on it. (Two alternatives considered and rejected: relaxing `removeObject`'s assert-and-throw for repair-minted transfers reopens BD-28's original silent-stripping bug; having the kernel auto-derive dissolve steps for any transfer regardless of Synthesize-side instructions regresses to implicit, non-fact-streamed dissolution --- the original problem BD-28 exists to fix.)

**The three worked examples traced through this model:**

- **BD-13 (carry, `computeCarryClosure`) --- corrected 2026-07-22, previously omitted dissolve-emission entirely.** A real `transferMembership` `Change` today carries a paired `isolatedFromRelations` instruction (per the "today's two concrete compilers" wiring above), both referencing the same object. Both ground; both operand-expand via `computeCarryClosure`, but only once in practice --- whichever fires first computes the closure and registers it under a `GroupId`, the other finds it already settled via `groupIdByObject` and reuses it (Fix 2), the direct mechanism that kills BD-28's duplication. The `transferMembership` retires as an atomic effect with its now-carry-closed `objectIds`; the paired `isolatedFromRelations` retires as a generator, sweeping the same closed set's boundary and minting the `DissolveRelationStep`s --- superseding `expandTransferMembership.ts`'s own dissolve-branch (already flagged for retirement at the Migrate line; this is the concrete mechanism that supersedes it). **No `computeCarryClosure`/`boundaryEdgeOutcomes` logic changes** --- only the call site does (the driver calls them directly per BD-29's phase split, rather than through `expandTransferMembership`'s combined wrapper).
- **BD-16 (`sameHost`, `expandSameHost`):** a `sameHost` `Assertion` + paired relational `Change`, exactly `compileRelationalUngroundedPlan`'s existing `[sameHostAssertion, change]` shape. Both ground together (share referents); the grounded relational step carries **no host field** (assert-and-throw principle --- host is derived at apply, not grounded eagerly). The assertion has no operand-expansion (BD-29: command-expansion only). Command-expansion evaluates it against live state: `satisfied` -> retire silently (subject and target already co-hosted; the relational step will confirm that itself at apply). `violated` -> mint the repair `transferMembership` (grounded, via `expandSameHost`'s existing logic, unchanged), push it to the front --- which then needs operand-expansion (its own carry-closure, reusing a settled group via `groupIdByObject` if the object was already touched, per Fix 2) before retiring --- then retire the assertion. The paired relational `Change` waits behind in the worklist; by the time it retires, the repair transfer (if any) has already mutated the threaded state so subject and target *are* co-hosted, and the effect step derives that shared host and applies its edge there --- throwing only if they somehow disagree (the loud backstop for a `sameHost` that failed to do its job). This is also what dissolves the live code's `getGraph(hostId)?.addObject(subject)` post-transfer *simulation* hack (`compileRelationalFromSkeleton.ts`): the worklist threads the real post-transfer state, so nothing needs simulating.
- **BD-28 (`isolatedFromRelations`, the case expected to change) --- concretely designed 2026-07-22, see "`isolatedFromRelations`, concretely" above.** Folded into `Assertion` (BD-34), not a fourth top-level `UngroundedPlanStep` kind. Traced in full as part of BD-13's corrected example above (they always co-occur today); each minted `DissolveRelationStep` retires as an explicit, kernel-applied, fact-streaming step --- replacing today's implicit `removeObject`-stripping path entirely (per the assert-and-throw decision already recorded above).

**Downstream consequence for the Build steps (assert-and-throw principle):**

- **`parsePlanStep.ts`: `hostRoomId` leaves `EstablishRelationStep`/`DissolveRelationStep`.** Under assert-and-throw the relational grounded step derives its host from its endpoint ids at apply time rather than carrying one, so the `hostRoomId` field (widened to `EphemeraMembershipHostId` only recently, BD-16) is removed. The Build slice carries this change; note that `groundChange`'s naive `currentHost(actingCharacter)` host-grounding for relational changes (and its BD-6 Room-only filter) also retires, since there is no host field left to ground.
- **Transaction lock footprint moves from per-step field to plan level.** `MultiKeyUpdate` must know which host graphs to lock *before* its reducer runs, so "which hosts does this sequence touch" still has to be recorded --- but as a property the executor computes from the whole grounded sequence (the union of every step's endpoint hosts), not as a `hostRoomId` on each relational step. This fits BD-27c's "general atomic apply over a step sequence" framing (the sequence declares its own footprint) rather than fighting it. The host does not vanish; it relocates from step-field to plan-footprint.

## Kernel apply design (BD-27c concrete realization, 2026-07-23)

Consumes `synthesize/executor.ts`'s terminal output --- `ExecutorOutcome`'s `{verdict:'legal', steps: readonly ExecutorParsePlanStep[]}` --- and bottoms it out in `EphemeraPositionGraph` primitives, superseding `applyObjectSetTransfer.ts`'s and `applyObjectRelationalChangeWithTransfer.ts`'s separately-inlined `MultiKeyUpdate` reducers with one generic dispatch. `ExecutorEstablishRelationStep`/`ExecutorDissolveRelationStep` (`executorTypes.ts`) are, by design, narrower than their still-live `parsePlanStep.ts` namesakes: no `hostRoomId` field (BD-33's assert-and-throw shape) --- this design derives each relational step's shared host from live graph state at apply time, never expects one pre-attached. Step order in the executor's output list is already load-bearing and guaranteed (dissolves precede their paired transfer, repair transfers precede the relational change that triggered them); this design applies the list in exactly that order, within one transact, and adds no reordering of its own.

**Footprint computation.** The transaction lock set --- "which hosts does this sequence touch" --- must be known *before* any transaction-scoped fetch, because `MultiKeyUpdate` does exactly one batched fetch per `transactWrite` call and cannot be re-entered mid-reducer to lock a newly-discovered host.

```ts
export type StepSequenceFootprint = ReadonlySet<EphemeraMembershipHostId>

export const computeStepSequenceFootprint = (
    steps: readonly ExecutorParsePlanStep[],
    getCurrentHost: (id: EphemeraObjectId) => EphemeraMembershipHostId | undefined
): StepSequenceFootprint => {
    const hosts = new Set<EphemeraMembershipHostId>()
    for (const step of steps) {
        if (step.kind === 'transferMembership') {
            hosts.add(step.fromHostId)
            hosts.add(step.toHostId)
            continue
        }
        // establishRelation / dissolveRelation carry no host field (BD-33) ---
        // derive both endpoints' pre-transaction current host.
        const subjectHost = getCurrentHost(step.subjectId)
        const targetHost = getCurrentHost(step.targetId)
        if (subjectHost === undefined || targetHost === undefined) {
            throw new Error(`computeStepSequenceFootprint: cannot resolve current host for ${step.subjectId} or ${step.targetId}`)
        }
        hosts.add(subjectHost)
        hosts.add(targetHost)
    }
    return hosts
}
```

**Resolved fork: compute once up front from a snapshot; separately re-verify inside the reducer against the freshly-fetched, locked graphs --- never trust the snapshot as ground truth.** This is not a new mechanism: it mirrors the dry-run/commit-time re-verification pattern already established and confirmed correct-and-deliberate elsewhere in this iteration (Purpose, above --- "that dry-run/commit-time recomputation itself is correct and deliberate"). If a relational step's live-derived host at commit time isn't one of the locked footprint hosts (a concurrent write moved the object between dry-run and commit), the kernel cannot fetch a third host mid-transaction --- this is not a distinct failure mode requiring new handling, it collapses into the same "stale candidate, abort" path every other drift case here already takes, per BD-31's interim collapse-to-abort policy.

**Generic primitive dispatch.** One shared, pure core walks the ordered step list once, dispatching per specific primitive (never per `kind: 'change' | 'assertion'` grouping, mirroring `synthesize/executor.ts`'s own `commandExpand` dispatch):

```ts
export type KernelApplyOutcome =
    | { verdict: 'legal'; graphs: ReadonlyMap<EphemeraMembershipHostId, EphemeraPositionGraph> }
    | { verdict: 'illegal'; reasonCode: string }
    | { verdict: 'defer'; decidable: boolean; reasonCode: string }
    // Structural-invariant violations (BD-33) are not a verdict --- they throw, uniformly in both modes.

export const applyStepSequenceCore = (
    steps: readonly ExecutorParsePlanStep[],
    initialGraphs: ReadonlyMap<EphemeraMembershipHostId, EphemeraPositionGraph>
): KernelApplyOutcome => {
    let graphs = new Map(initialGraphs)
    for (const step of steps) {
        if (step.kind === 'transferMembership') {
            const sourceGraph = graphs.get(step.fromHostId)
            const destGraph = graphs.get(step.toHostId)
            if (!sourceGraph || !destGraph) return { verdict: 'illegal', reasonCode: 'hostNotInFootprint' }
            for (const id of step.objectIds) {
                if (!sourceGraph.objectIds.has(id) || destGraph.objectIds.has(id)) {
                    return { verdict: 'illegal', reasonCode: 'staleTransferCandidate' }
                }
            }
            const outcome = applyTransferSet(sourceGraph, destGraph, step.objectIds)
            if (outcome.verdict === 'illegal') return { verdict: 'illegal', reasonCode: outcome.reasonCode }
            if (outcome.verdict === 'defer') return { verdict: 'defer', decidable: outcome.decidable, reasonCode: outcome.reasonCode }
            graphs.set(step.fromHostId, outcome.sourceGraph)
            graphs.set(step.toHostId, outcome.destGraph)
            continue
        }
        // establishRelation / dissolveRelation: derive shared host from live graph state,
        // throw on mismatch (BD-33 assert-and-throw), else apply the patch there.
        const subjectHost = findHostOf(step.subjectId, graphs)
        const targetHost = findHostOf(step.targetId, graphs)
        if (subjectHost === undefined || targetHost === undefined) return { verdict: 'illegal', reasonCode: 'staleRelationalCandidate' }
        if (subjectHost !== targetHost) {
            throw new Error(`${step.subjectId}/${step.targetId} do not share a host --- structural invariant violated (sameHost should have repaired this)`)
        }
        const patched = graphs.get(subjectHost)!.applyRelationalPatch({
            hostId: subjectHost,
            edge: { from: step.subjectId, to: step.targetId, kind: step.relationKind, ...(step.relationLabel !== undefined ? { relationLabel: step.relationLabel } : {}) },
            op: step.kind === 'establishRelation' ? 'add' : 'remove',
        })
        graphs.set(subjectHost, patched)
    }
    return { verdict: 'legal', graphs }
}
```

**Throw vs. verdict, an explicit decision.** Legitimate legality outcomes (stale candidate, `Custom`-edge defer) return through the discriminated union, matching `applyTransferSet`'s existing convention. Structural-invariant violations under BD-33 (relational host mismatch; `removeObject`'s dangling-edge check, below) **throw**, uniformly in both modes --- consistent with `applyRelationalPatch`'s existing throw-based checks, and with how a `MultiKeyUpdate` reducer throw already aborts cleanly pre-transaction (no new plumbing). One reducer body, built around this core (fetch all footprint hosts' graphs from the draft once, run `applyStepSequenceCore`, write `.positionGraph` back per touched host, capture the result via an outer closure var exactly as today's two kernels do), replaces both existing kernels' separately-inlined logic.

**`removeObject`'s assert-and-throw change, and the paired reorder it requires.** `EphemeraPositionGraph.removeObject` changes from silently stripping relational edges (today's `withoutEdgesReferencingObject`) to checking no relational edge still references the object and throwing a specific, identifiable error if one does --- play-only/exit-style edges keep today's silent strip (a distinct invariant, split out of the private helper, not touched by this change). This requires a paired reorder inside `applyTransferSet.ts`: internal (both-endpoints-in-set) edges must be stripped from `sourceGraph` *before* the per-object `removeObject` loop runs, not after, or a multi-object transfer would immediately throw on its own still-live internal edges. `applyTransferSet` also gains a residual-`dissolve`-boundary-edge check (a `dissolve`-classified boundary edge still present after its own fresh `boundaryEdgeOutcomes` recompute means an explicit `DissolveRelationStep` that should have run earlier in the same kernel-apply loop did not) returning a typed `illegal` verdict (`unresolvedDissolveEdge`) rather than letting the violation surface as a raw `removeObject` throw --- keeping dry-run callers on a discriminated result. **This is the single universal contract (BD-35, reframed 2026-07-23): there is no permanent silent-strip variant.** Every edge-severing caller --- including the object-lifecycle routes (`applyObjectClearMembership` destroy/edit, `applyObjectRoomMembership` spawn/drift-repair) that previously relied on silent stripping --- migrates onto this kernel emitting *explicit* `DissolveRelationStep`s (via `isolatedFromRelations` where it can't enumerate its own edges), so the assertion is satisfied rather than bypassed, and fact-emission per severed edge becomes a per-route policy (destroy streams, drift-repair likely suppresses). `removeCharacter` gains the identical assert (vacuously true today, since edges are object-only) as part of retiring `applyHostEffects` entirely --- see BD-36.

**Two-mode realization (BD-31).** `applyStepSequenceCore` is the identical shared body for both modes. Commit mode is `commitStepSequence`, a real wrapper (computes the footprint, builds a `MultiKeyUpdate` around the core, collapses `illegal`/`defer` into one thrown abort per BD-31's interim policy). **Dry-run mode is calling `applyStepSequenceCore` directly** --- no `checkStepSequenceLegal` wrapper exists (an earlier draft of this design proposed one; retired 2026-07-23 during Build, see the Build row below, once implementation showed it added no behavior over the core: `applyStepSequenceCore` already takes graphs by value, builds its own internal copy, and never mutates or persists anything, so "no transaction, discard the mutated graphs" is already true of calling it directly --- there was nothing left for a wrapper to do). This still mirrors how `applyTransferSet` is already identically shared between dry-run and commit today; it just does so with one function, not two.

**Fact-streaming mapping.** A generic `factsForStep(step, finalGraphs, beatAnchorTime)` walks the *output-ordered* steps (not a hand-assembled subset) and maps each to zero-or-more facts: `Object Moved` per object in a `transferMembership`'s set; `Object Relation Changed` per `establishRelation`/`dissolveRelation`, host re-derived from the final graph map the same way the apply core did. Streaming in step order is what actually delivers BD-28's original goal --- previously-silent relation dissolution finally streams a real fact: a carry's output steps are `[DissolveRelationStep*, TransferMembershipStep]`, so dissolve facts now stream *before* the moved fact, genuinely new and correct behavior. BD-16's repaired case keeps today's observed order (transfer fact before the relational change's own fact), since that pairing's step order is unchanged by this design.

**Unified commit entry point.** One `commitStepSequence(args: {steps: readonly ExecutorParsePlanStep[]}, deps: {messageBus, streamEvent, getCurrentHost, transactWrite?}): Promise<KernelCommitResult>` replaces both `applyObjectSetTransfer.ts`'s and `applyObjectRelationalChangeWithTransfer.ts`'s call surface, rather than two route-specific thin wrappers --- splitting by route would recreate, one layer up, the exact organization BD-27c exists to retire. `getCurrentHost` is passed explicitly rather than folded incidentally into `deps`, since the footprint computation above makes it a load-bearing input. Building and testing `applyStepSequenceCore`/`commitStepSequence` as real, independent modules is the next Build row (below); retiring the two existing kernels' call sites is the Migrate row after that --- both explicitly out of scope for this design row, matching the discipline already used for the Synthesize-side executor (designed, then built standalone, then migrated, as three separate rows).
