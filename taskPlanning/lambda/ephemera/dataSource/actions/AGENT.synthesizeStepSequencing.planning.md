# Object manipulation: generalized Synthesize step sequencing (iteration 8)

**Status:** Scheduled 2026-07-21 --- work is now underway. Split out 2026-07-21 while investigating BD-16's `sameHost` rebuild --- caught before it became scope creep on that work: shipping `sameHost` didn't require this generalization (an ad hoc, route-specific Expansion check was enough, matching the existing precedent `expandTransferMembership.ts` already set on the membership route), but it surfaced a real, distinct gap worth naming on its own. See [`AGENT.objectManipulationIterations.planning.md`](AGENT.objectManipulationIterations.planning.md) for the full iteration ladder.

Task-planning conventions: [`taskPlanning/AGENT.md`](../../../../AGENT.md).

## Purpose

Design and (eventually) build one real, generic Synthesize-side executor that walks an ordered sequence of ungrounded steps --- `Change`s and `Assertion`s alternating as needed --- performing Grounding, Expansion (inserting repair steps when an `Assertion` is violated), and Validation per step, so that a repair (a `TransferMembershipStep`, say) becomes a first-class step in a real grounded sequence rather than a bolted-on field on some other step's result. The executor's own shape is decided (see "Expansion execution model" below, BD-29/BD-30): Expansion splits into operand-expansion (set-closure fixpoint) and command-expansion (step emission over the closed set), and the whole ground -> operand-expand -> command-expand cycle runs as a phase-stratified worklist over progress-tagged instructions, not as recursion.

This is **not** new design from nothing: the shape already exists, unwired, in two places:

- `plan/compileUngroundedPlan.ts`'s `compileRelationalUngroundedPlan` already returns a real `UngroundedPlanStep[]` of exactly `[sameHostAssertion, change]` --- written, tested in isolation, never called by any live route.
- `sandboxPlan.ts`'s `evaluateSandboxPlan` already folds a step array through state generically, and is the one place (`selectIdentityPlanTuple.ts`, membership dry-run only) where an Expansion-inserted repair (`expandTransferMembership.ts`'s `dissolveSteps`) gets appended into one real array before evaluation --- but it never reaches the live commit path.

Two shipped live examples now exist to design the generalization against, where previously there were none: BD-13 (`computeCarryClosure`, cascading fixpoint entirely within Expansion, no Plan involvement needed) and BD-16 (`expandSameHost`, a genuine Assertion-shaped precondition with a real repair step, currently bolted on as `transferFromHostId` rather than appended to a sequence). Per this project's own "expand as concrete cases demand" discipline (the same principle that kept `Assertion`'s union to one member until BD-16 needed a second), this is the point at which designing the general shape stops being premature.

**A third worked example, found 2026-07-21 (BD-28): relation dissolution during carry is itself a live case of exactly this incoherence, not just a motivating analogy.** Verified concretely: `classifyInteractionUnderTransfer`/`boundaryEdgeOutcomes` (`positions/positionGraph/expandValidate/interactionUnderTransfer.ts`) gets independently re-derived in **two** places against what should be the same graph state --- once in `enrich/objectManipulation/synthesize/expandTransferMembership.ts` (live-wired via `selectIdentityPlanTuple.ts`'s dry-run, producing real grounded `DissolveRelationStep[]`), and again inside `positions/positionGraph/expandValidate/applyTransferSet.ts` at actual commit time. **That dry-run/commit-time recomputation itself is correct and deliberate** --- the same concurrency-safety pattern already shipped for membership (sandbox dry-run + `MultiKeyUpdate` atomic re-check, see `applyObjectSetTransfer.ts`): dry-run reads a possibly-stale snapshot, and commit-time re-verification against the live graph, inside the transaction, is what catches drift between the two. **The actual defect is a second, unrelated duplication living entirely inside commit time:** the explicit `DissolveRelationStep[]` from the dry-run computation never reaches the live apply --- it only feeds the dry-run's own legality re-check (`evaluateSandboxPlan`) and is then discarded; only the closure's `objectIds` set crosses into `applyObjectSetTransfer.ts`, where dissolution actually happens purely as an implicit side effect of `EphemeraPositionGraph.removeObject`'s automatic edge-stripping --- a second mechanism, at the same moment, doing the same job the discarded explicit steps already described. Net effect: no player-facing fact is ever streamed when a carried object's relation to something left behind is severed (unlike BD-16's compound apply, which does stream `Object Relation Changed`). See BD-28 below.

## BD-27b reshaping findings (2026-07-22)

Read `compileUngroundedPlan.ts`, `sandboxPlan.ts`, and their immediate neighbors (`ungroundedPrimitive.ts`, `parsePlanStep.ts`, `sandboxStep.ts`, `toSandboxPlanStep.ts`, `sandboxState.ts`, `selectIdentityPlanTuple.ts`, `applyTransferSet.ts`, `interactionUnderTransfer.ts`) in full, per the Getting Started step above. Findings, grounded in the actual code rather than restated intent:

**`plan/compileUngroundedPlan.ts` (`compileMembershipUngroundedPlan` / `compileRelationalUngroundedPlan`):**

1. **Wrong input shape.** Both functions consume legacy `MembershipManipulationFrame`/`ManipulationFrame` types, not Parse's tokenized skeleton or `matchRelationalTemplate.ts`'s role-tagged output --- the live relational route already builds its ungrounded steps a different way (`compileRelationalFromSkeleton.ts`), bypassing this function entirely. Reshape must repoint at the live Plan-stage output per route.
2. **Missing `stableRefKey`.** `objectSpanRef(...)` calls here never pass a `stableRefKey` (legacy frames only carry span text) --- BD-23 needs it for Grounding to disambiguate repeated spans; live callers (`groundReferent.ts`) already expect it.
3. **Output shape is a fixed 1-2-element array, not a worklist seed.** `CompileUngroundedPlanResult.steps` is a bare `UngroundedPlanStep[]`, hand-built as exactly `[change]` or `[sameHostAssertion, change]`. BD-30's worklist needs an *appendable*, progress-tagged instruction list (command-expansion pushes new items to the front) --- today's return type has no per-item progress tag and no identity to append against. This return type is a prerequisite for BD-30's worklist design, not an independent concern.
4. **No `IsolatedFromRelations` emission path.** Neither compiler emits BD-28's proposed primitive, and `ungroundedPrimitive.ts`'s `Change`/`Assertion` union has no member for it yet.
5. **Two independent hand-rolled tuple-builders**, no shared "append a step" helper --- if BD-27a's "one executor" holds, output *construction* should converge even though input *parsing* legitimately stays route-specific.

**`evaluateSandboxPlan` / `sandboxPlan.ts` (+ `sandboxStep.ts`, `toSandboxPlanStep.ts`, `sandboxState.ts`):**

1. **Candidate-wrapped, not Plan-IR-shaped --- and not the target output shape at all.** `SandboxPlanStep` wraps `IdentityPlanCandidate`/`RelationalIdentityPlanCandidate`, both carrying proposer-only bookkeeping (`label`, `jointRelevance`, `sourceTags`, `confidence`) that Validation never reads --- confirmed directly: `toSandboxPlanStep.ts`'s own converter pads all of these with placeholder values (`''`, `1`, `[]`) purely to satisfy the type. `SandboxPlanStep` is `evaluateSandboxPlan`'s **input**, not Synthesize's output --- and it is not what the ground -> expand -> synthesize instruction set should eventually produce; it is today's caller (`selectIdentityPlanTuple.ts`) hand-building a lossy adapter from real grounded steps just to feed the old fold. The generalized executor should operate on the grounded `ParsePlanStep` union (or its BD-27c-generalized descendant) directly, retiring `SandboxPlanStep` and this placeholder-padding converter entirely, not reshaping them in place.
2. **No `Assertion` step kind at all.** Only `transferMembership`/`relational` exist. Assertion evaluation + repair-insertion happens entirely in caller code today (e.g. `selectIdentityPlanTuple.ts`'s `sandboxMembershipDryRun` hand-calls `expandTransferMembership` and splices the resulting dissolve steps into the array *before* calling `evaluateSandboxPlan`) --- Expansion is precomputed and spliced in, not part of the walk. BD-27's executor requires Expansion to be inline.
3. **Flat `reduce` over a fixed-length array, not a worklist.** The exact opposite of BD-30's model (mutable frontier, per-item progress tags, priority-ordered driver, shared expansion environment). This is the single biggest reshape: replacing the `reduce` with a worklist loop.
4. **Step-sequence-walking layer is dry-run-only; the low-level primitive one layer down is not (review correction, 2026-07-22).** The *low-level* boundary-edge-classification-and-mutate primitive (`applyTransferSet`/`boundaryEdgeOutcomes`/`computeCarryClosure`) is already genuinely shared --- `applyObjectSetTransfer.ts` and `applyObjectRelationalChangeWithTransfer.ts` both call `applyTransferSet` directly, not a reimplementation, and neither touches `SandboxState`/`SandboxPlanStep` at all. What's actually unreached is one layer up: `evaluateSandboxPlan`'s **step-sequence walk** itself, which no commit path calls, mirrors, or has an equivalent of --- commit goes straight from one pre-decided set to `applyTransferSet`, never constructing or walking a sequence. Whether the reshaped walker (once it operates on real `ParsePlanStep`s rather than `SandboxPlanStep`, per finding 1) becomes one executor with two modes or stays sandbox-only alongside a separately-reshaped BD-27c kernel walker is **not resolved here** --- tracked as BD-31 above.
5. **No BD-27c primitive dispatch.** `applyTransferMembershipStep`/`applyRelationalStep` (`sandboxStep.ts`) are still two route-specific appliers, each inlining its own graph mutation --- not dispatched through one generic primitive-apply keyed on step kind.

## Expansion execution model (BD-29 / BD-30 rationale)

The two-kinds-of-expansion decomposition (BD-29) and the worklist driver (BD-30) are the same design seen at two altitudes: BD-29 is *what the phases are*, BD-30 is *how they run*. Recording the reasoning here rather than in the table cells, since it's the load-bearing part.

**Why two phases, ordered.** Operand-expansion (the carry fixpoint) and command-expansion (step emission) have a real data dependency, not just a stylistic split: you cannot know which edges cross the operand set's boundary until the set is *closed*, because closure itself manufactures boundary edges. `cup On tray` + `cup Under chandelier`, player takes the tray: cup-chandelier is not a boundary edge at rest --- it only becomes one once operand-expansion absorbs the cup and leaves the chandelier behind. So command-expansion (which severs crossing edges) must wait for operand-expansion's fixpoint. This is exactly the cut today's `boundaryEdgeOutcomes` fails to make --- it classifies every edge as absorb-or-dissolve in one pass and then re-sweeps, which is why the classification ends up computed twice (BD-28).

**Why a worklist, not recursion.** A command-expansion can spawn a step that itself needs the full ground -> operand-expand -> command-expand cycle (e.g. `sameHost` inserts a `transferMembership`, and if that object carries a saucer, the inserted transfer needs its own carry-closure). That looks like recursion, but modelling it as a phase-stratified worklist over progress-tagged instructions (BD-30) is strictly better here, for two reasons that are not cosmetic:

- **The shared expansion environment is first-class.** The "compute the closure once and share it between the `transferMembership` and the `IsolatedFromRelations` over the same group" requirement (the whole point of killing BD-28's duplication) wants a *global* environment the loop reads and writes, not a closure-map threaded down and back up recursive frames. Draining all operand-expansion before any command-expansion means the shared set is saturated once, then every consumer reads the identical settled set.
- **The reified state is suspendable.** An explicit worklist + per-item phase tags can be paused at a phase boundary and resumed --- an addressable resume point, which is precisely the shape iteration 4 (BD-18, backtrack channel) will want. Not designed in here, but the formulation doesn't fight it, where recursion (state buried in the call stack) would.

**Soundness invariants the eventual implementation must preserve:**

- **Monotone per-item progress.** Every instruction only advances forward through its tag states (`ungrounded -> grounded -> operandExpanded -> retired`); nothing regresses. The frontier grows (command-expansion pushes new items), but each individual item is on a one-way ratchet.
- **Command-expansion is the sole producer.** Grounding and operand-expansion transform in place; only command-expansion mints new instructions. That is *why* draining the two in-place phases before firing a producer is the correct scheduling policy --- every consumer sees fully-resolved operands and a fully-populated shared set.
- **New items are causally downstream.** A child instruction did not exist when its parent command-expanded, so it can never retroactively invalidate anything already emitted; "push to front, drop back to operand-expansion" is consistent, not just convenient. (Within a single intent, sets never retroactively grow --- command-expansion emits steps *over* a final set, it does not enlarge an existing one.)
- **Termination rides on a settled-groups ledger.** The worklist analog of carry-closure's existing visited-set: before operand-expanding a grounded item, check whether its base object-group is already settled in the shared environment and reuse if so. That single check does double duty --- it is both the dedup (BD-28) and the guard that stops a pathological graph (isolating A forces moving C which carries A) from looping. "operand-expand as necessary" is carrying exactly this lookup.
