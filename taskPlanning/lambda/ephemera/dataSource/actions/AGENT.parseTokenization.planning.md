## Purpose

"Parse" names the functionality currently split across classify's `objectSpans` extraction and the separate `frameExtract` LLM hop. Consolidating these into one hop that emits a referent-substituted **command skeleton** --- an ordered sequence of `{ type: 'objectSpan', span } | { type: 'text', text }` tokens --- would let a deterministic Plan-stage matcher pattern-match structure directly (a keyword scan over the `text` runs), instead of a Plan-stage LLM re-deriving structure from raw spans every time. **Correction (2026-07-18):** this iteration is *buildable* in parallel with iteration 2, but not fully independent of it --- iteration 2's plan-only and joint fallback steps should consume Parse's skeleton once it exists, rather than re-deriving referent structure from raw command text, so those two steps are paused until this hop is real. See `AGENT.objectManipulationIterations.planning.md`'s ladder note for the full correction.

## Design debt carried over from the original planning doc

**"Down" bullet (deterministic relational fast-path, from "Legacy hop retirement"):** closed-grammar relational frames (`put` / `place` / `lean` / `take off` + known prepositions) --- relation phrase is enum lookup, `operationKind` from verb template, roles from `V NP prep NP`. Does not exist today; would be the relational analog of the membership fast path already in `deterministicChecks.ts`. This `V NP prep NP` role extraction is currently only *simulated* by the frame-extract LLM's free-form field emission --- no real tokenizer/skeleton-matcher exists. Consolidating frame-extract with classify's `objectSpans` extraction into "Parse" (emitting a shared referent-substituted skeleton) is the concrete target this bullet was gesturing at. This deterministic regex/keyword fast-path remains an independent, orthogonal zero-Bedrock optimization for known phrasings, not a prerequisite for Parse --- correctness of Parse's own (possibly imperfect) LLM-driven output is enforced via the Backtrack channel (iteration 4), not via verifying spans against the raw command text (concluded a "fool's errand," see History).

**Assertion-emission prerequisite (from BD-14's "Ungrounded position planning primitive shape"):** the Plan-stage compiler (`enrich/objectManipulation/plan/compileUngroundedPlan.ts`) is built and tested but only emits `Change` steps, never `Assertion` steps --- confirmed during implementation that `MembershipManipulationFrame` carries no field a `containedBy` assertion could be built from (only `rawObjectSpans` + `verbClass`, no location-disambiguating span like "table" in "get bag from table"). Extending classify + frame extraction to capture such a span is the actual prerequisite for real `Assertion` emission --- this is the same gap BD-21 names from the opposite direction (Plan needing structure Parse doesn't yet produce), not a second, independent problem.

## History

Full reasoning trail behind BD-21's Open-decisions row above, kept for provenance --- not needed to know what to do next, only *why* the resolution mechanism landed where it did.

**Found (2026-07-18), assessing whether this codebase does any positional/structural tracking of a command once object spans are identified within it.** Motivating example: "get container from tablee" --- Identify fuzzily resolves `"container"` -> `OBJECT#BAG` and `"tablee"` -> `OBJECT#TABLE` (typo/paraphrase-tolerant, unchanged from today); the proposal was to *also* capture the surrounding structure once those spans are excised, e.g. `["get", {ref: BAG}, "from", {ref: TABLE}]`, so a deterministic Plan-stage matcher could pattern-match the skeleton (`GET <ref> FROM <ref>`) against a closed template registry --- "Synthesis is basically operating on `get ${BAG} from ${TABLE}`," not on the raw command string.

**Assessed as of 2026-07-18: this codebase had nothing like it.** `rawObjectSpans`/`subjectSpan`/`targetSpan` (`manipulationFrame.ts:25-37`, `membershipFrame.ts:14-22`) are LLM-emitted freestanding strings with no verified positional link back into `command` --- no `indexOf`, no offset, no capture-group provenance (`intentClassification.ts:116-147`'s validator only checks non-empty trimmed strings). `command` is carried as a single opaque string alongside these span fields on every frame type; nothing resembling `token`/`offset`/`wordIndex` exists anywhere in `dataSource/`/`llm/` for this domain (confirmed via broad grep --- the only "tokenization" hits are unrelated: test-harness slash-command splitting, catalog-shortName lexical matching, LLM context-window token counts). Perception narration (`objectManipulationPresentationLegAdapters.ts`) confirms the raw command is discarded after compile --- output is built purely from grounded `objectId` -> canonical `shortName`, never by revisiting the original text.

**An initial objection was raised and retracted in the same conversation.** Fault-tolerant paraphrase-based identity resolution (embedding/lexical matching, e.g. "sweeping tool" -> broom) was first thought to make positional tracking pointless or incompatible --- **this was wrong, and the error is worth recording so it isn't repeated:** *content* fidelity (does the resolved object's canonical name equal the span text) and *positional* extraction (does the span occupy a known, locatable slot in the command) are orthogonal axes. A tokenized skeleton only needs the *span itself* to be a genuine contiguous substring of `command` at some location --- what that span's content then fuzzily resolves to is unaffected by knowing where it sat.

**Two concrete payoffs identified beyond the motivating example:** (1) it would resolve, with real position data instead of a fragile proxy, the same-span-text ambiguity `resolveRelationalGrounding`'s (now-deleted) inlining once had to handle only via *array-order* positional correspondence --- content-matching breaks when `subjectSpan === targetSpan` textually (e.g. "put the bag in the bag"), and array-order is not a substitute for knowing which literal occurrence was meant. (2) It would give the "Legacy hop retirement" "Down" bullet (`V NP prep NP` role extraction from closed grammar) an actual deterministic mechanism to exist as --- that idea describes a *simulated* version of this same thing, entirely performed by the frame-extract LLM's free-form field emission, with no real tokenizer or skeleton-matcher anywhere; BD-19 (2)'s "Infocom-parser style, `V NP prep NP` role extraction" language described this same not-yet-built mechanism, not something already shipped --- worth being explicit about, since it reads like a description of working code on first pass.

**Open question raised, then retracted (2026-07-18): verifying span-substring-fidelity against `command` is not the right resolution --- concluded a "fool's errand," not merely a hard problem.** This codebase's Bedrock invocation path (`llm/invokeBedrockConverseText.ts`) has no constrained decoding anywhere --- "return the exact substring" is a prompt request, not an enforced constraint, and it fights the model's dominant training signal (understand/correct, not reproduce literally). Confirmed by re-reading the actual prompts: `buildIntentClassificationPrompt.ts` **explicitly instructs** normalizing transformations (strip the verb, strip leading articles, trim whitespace) that make the returned span a *designed*, not accidental, non-substring on the golden path (e.g. `"order a giant rubber band" -> ["giant rubber band"]`); `frameExtract`'s `relationSpan` is pushed toward canonical-preposition vocabulary, inviting real paraphrase ("on top of" -> `"on"`). Critically, **the cases where a span isn't literally faithful are disproportionately the cases where the model did something valuable** (typo correction, paraphrase resolution, per the "get bagg from talbe" -> "bag"/"table" case) --- gating a skeleton on string fidelity would penalize exactly the behavior the fault-tolerant design elsewhere in this pipeline exists to reward. (Also checked and ruled out as a reusable tool: `sellersApproximateSubstringMatch.ts` looked like a candidate for "locate a span's position in a longer text," but it's actually a span-vs-single-catalog-shortName content scorer, not a positional locator --- no such tool exists in this codebase today.)

**Resolution reached (2026-07-18): Parse's output is allowed to be imperfect by construction; correctness is enforced downstream via Backtrack, not upstream via self-verification.** "Parse" consolidates classify's `objectSpans` extraction and `frameExtract` into one hop emitting the referent-substituted skeleton. When Identify, Plan, or Synthesis cannot make sense of Parse's skeleton (a genuine structural misparse, not just fuzzy-content resolution), the answer is the Backtrack channel's now-generalized scope (iteration 4) --- a structured critique sent back to Parse (e.g. "'get bag' is not any recognizable verb on its own," "'from' doesn't match any object," "'table' is an unknown modifier"), not a downstream attempt to deterministically repair or re-derive structure from the raw command string. This is the resolution now stated compactly in the Open-decisions row above.

**Skeleton type shape, first proposal and rejection (2026-07-18).** Initial proposal: a discriminated union with a token *per grammatical role* --- `{ type: 'verb', verbClass }`, `{ type: 'preposition', relationKind }`, `{ type: 'unclassified', text }`, alongside `{ type: 'objectSpan', span }` --- reasoning that maximally-classified tokens would make Plan's template matching maximally deterministic. **Rejected on pushback:** referent identification and grammatical role-tagging are not the same kind of task, even though both look like "classify this span." Referent extraction is a proven, existing competency (classify's `objectSpans`, frame-extract's `subjectSpan`/`targetSpan`); asking Parse to *additionally* tag which token is "the verb" vs. "a preposition" is a new, untested classification with no schema precedent and no guarantee of consistent LLM application --- particle verbs, passives, and idiomatic phrasing ("the string wraps around the top") don't have a clean single verb token to find. **And nothing was actually being bought by it:** Plan already owns the closed verb/preposition grammar (BD-19 (2)) --- once Parse hands Plan a referent-segmented skeleton, distinguishing `[text:"take", objectSpan, text:"off", objectSpan]` from `[text:"take", objectSpan]` is a trivial deterministic keyword scan over the `text` runs, no LLM judgment required for that part at all. Pre-tagging verb/preposition upstream just moved a reliability risk into the one stage that has to run before any template match is even attempted, for zero determinism gain. **Also resolves escalation-to-fallback more cleanly:** with grammatical tagging, "does this need the LLM fallback" was decided partly by Parse's classification and partly by Plan's template match; with the binary split, it's entirely Plan's call (keyword scan matches a known pattern -> deterministic; doesn't -> defer), the same shape `deterministicChecks.ts`'s existing regex fast path already uses today. **Settled shape:** `{ type: 'objectSpan', span: string } | { type: 'text', text: string }` --- referent tokens carry only the span text (no role, no id: role is assigned by *position in the matched template*, per BD-20's "position, not content, disambiguates" precedent; an explicit id would be redundant with array position). Deliberately one step more primitive than BD-14's `Referent` type --- a skeleton `objectSpan` token is the raw material Grounding later turns into a real `Referent.objectSpan`, not a `Referent` itself, mirroring the existing relationship between `ObjectSpanCandidate` (Identify's resolved output) and `Referent`.
