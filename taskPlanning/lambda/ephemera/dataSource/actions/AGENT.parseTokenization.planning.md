Task-planning conventions: [`taskPlanning/AGENT.md`](../../../../AGENT.md).

## Purpose

"Parse" names the functionality currently split across classify's `objectSpans` extraction and the separate `frameExtract` LLM hop. Consolidating these into one hop that emits a referent-substituted **command skeleton** (e.g. `["get", {referent}, "from", {referent}]`) would let a deterministic Plan-stage matcher pattern-match structure directly, instead of a Plan-stage LLM re-deriving structure from raw spans every time. This iteration can proceed in parallel with iteration 2 (fallback LLMs) --- the fallback LLMs don't consume Parse's output, they operate independently once deterministic parse/plan has already failed.

| BD-21 | **Tokenized command skeleton for referent-aware Plan template matching --- named 2026-07-18, found while assessing whether this codebase does any positional/structural tracking of a command once object spans are identified within it.** Motivating example: "get container from tablee" --- Identify fuzzily resolves `"container"` -> `OBJECT#BAG` and `"tablee"` -> `OBJECT#TABLE` (typo/paraphrase-tolerant, unchanged from today); the proposal is to *also* capture the surrounding structure once those spans are excised, e.g. `["get", {ref: BAG}, "from", {ref: TABLE}]`, so a deterministic Plan-stage matcher can pattern-match the skeleton (`GET <ref> FROM <ref>`) against a closed template registry --- "Synthesis is basically operating on `get \${BAG} from \${TABLE}`," not on the raw command string. **Assessed as of 2026-07-18: this codebase has nothing like it.** `rawObjectSpans`/`subjectSpan`/`targetSpan` (`manipulationFrame.ts:25-37`, `membershipFrame.ts:14-22`) are LLM-emitted freestanding strings with **no verified positional link back into `command`** --- no `indexOf`, no offset, no capture-group provenance (`intentClassification.ts:116-147`'s validator only checks non-empty trimmed strings). `command` is carried as a single opaque string alongside these span fields on every frame type; nothing resembling `token`/`offset`/`wordIndex` exists anywhere in `dataSource/`/`llm/` for this domain (confirmed via broad grep --- the only "tokenization" hits are unrelated: test-harness slash-command splitting, catalog-shortName lexical matching, LLM context-window token counts). Perception narration (`objectManipulationPresentationLegAdapters.ts`) confirms the raw command is discarded after compile --- output is built purely from grounded `objectId` -> canonical `shortName`, never by revisiting the original text. **An initial objection was raised and retracted in the same conversation:** fault-tolerant paraphrase-based identity resolution (embedding/lexical matching, e.g. "sweeping tool" -> broom) was first thought to make positional tracking pointless or incompatible --- **this was wrong, and the error is worth recording so it isn't repeated:** *content* fidelity (does the resolved object's canonical name equal the span text) and *positional* extraction (does the span occupy a known, locatable slot in the command) are orthogonal axes. A tokenized skeleton only needs the *span itself* to be a genuine contiguous substring of `command` at some location --- what that span's content then fuzzily resolves to is unaffected by knowing where it sat. **Two concrete payoffs beyond the motivating example:** (1) it would resolve, with real position data instead of a fragile proxy, the same-span-text ambiguity `resolveRelationalGrounding`'s (now-deleted) inlining once had to handle only via *array-order* positional correspondence --- content-matching breaks when `subjectSpan === targetSpan` textually (e.g. "put the bag in the bag"), and array-order is not a substitute for knowing which literal occurrence was meant. (2) It would give the "Legacy hop retirement" "Down" bullet below (`V NP prep NP` role extraction from closed grammar) an actual deterministic mechanism to exist as --- today that idea describes a *simulated* version of this same thing, entirely performed by the frame-extract LLM's free-form field emission (`subjectSpan`/`targetSpan`/`relationSpan` as named output fields), with no real tokenizer or skeleton-matcher anywhere; the original doc's BD-19 (2) "Infocom-parser style, `V NP prep NP` role extraction" language described this same not-yet-built mechanism, not something already shipped --- worth being explicit about, since it reads like a description of working code on first pass. **Open question retracted (2026-07-18): verifying span-substring-fidelity against `command` is not the right resolution --- concluded a "fool's errand," not merely a hard problem.** This codebase's Bedrock invocation path (`llm/invokeBedrockConverseText.ts`) has no constrained decoding anywhere --- "return the exact substring" is a prompt request, not an enforced constraint, and it fights the model's dominant training signal (understand/correct, not reproduce literally). Confirmed by re-reading the actual prompts: `buildIntentClassificationPrompt.ts` **explicitly instructs** normalizing transformations (strip the verb, strip leading articles, trim whitespace) that make the returned span a *designed*, not accidental, non-substring on the golden path (e.g. `"order a giant rubber band" -> ["giant rubber band"]`); `frameExtract`'s `relationSpan` is pushed toward canonical-preposition vocabulary, inviting real paraphrase ("on top of" -> `"on"`). Critically, **the cases where a span isn't literally faithful are disproportionately the cases where the model did something valuable** (typo correction, paraphrase resolution, per the "get bagg from talbe" -> "bag"/"table" case) --- gating a skeleton on string fidelity would penalize exactly the behavior the fault-tolerant design elsewhere in this pipeline exists to reward. (Also checked and ruled out as a reusable tool: `sellersApproximateSubstringMatch.ts` looked like a candidate for "locate a span's position in a longer text," but it's actually a span-vs-single-catalog-shortName content scorer, not a positional locator --- no such tool exists in this codebase today.) **Resolution (2026-07-18): Parse's output is allowed to be imperfect by construction; correctness is enforced downstream via Backtrack, not upstream via self-verification.** "Parse" consolidates classify's `objectSpans` extraction and `frameExtract` into one hop emitting the referent-substituted skeleton. When Identify, Plan, or Synthesis cannot make sense of Parse's skeleton (a genuine structural misparse, not just fuzzy-content resolution), the answer is the Backtrack channel's now-generalized scope (iteration 4) --- a structured critique sent back to Parse (e.g. "'get bag' is not any recognizable verb on its own," "'from' doesn't match any object," "'table' is an unknown modifier"), not a downstream attempt to deterministically repair or re-derive structure from the raw command string. See [`AGENT.backtrackChannel.planning.md`](AGENT.backtrackChannel.planning.md) for the mechanism and its still-open sub-questions (addressable resume points, bounded retry, cost/latency) --- this row no longer carries its own open question, it defers entirely to that plan's. **Independently still valid, orthogonal to the above:** the deterministic regex/keyword closed-grammar fast-path described below (extending `deterministicChecks.ts`'s existing membership pattern to relational) remains a sound, separate optimization for well-known phrasings --- it sidesteps this whole problem for the commands it covers, by never invoking an LLM at all, but is not required for (and does not substitute for) the Backtrack resolution above for the general case. | Iteration 4 (Backtrack channel, resolution mechanism); Iteration 2's BD-19 (2) (Infocom-parser template-matching claim, needs Parse consolidation to become literally true rather than LLM-simulated) | **Named, not scoped --- resolution mechanism identified (defers to iteration 4); Parse consolidation itself not yet designed** |

## Design debt carried over from the original planning doc

**"Down" bullet (deterministic relational fast-path, from "Legacy hop retirement"):** closed-grammar relational frames (`put` / `place` / `lean` / `take off` + known prepositions) --- relation phrase is enum lookup, `operationKind` from verb template, roles from `V NP prep NP`. Does not exist today; would be the relational analog of the membership fast path already in `deterministicChecks.ts`. This `V NP prep NP` role extraction is currently only *simulated* by the frame-extract LLM's free-form field emission --- no real tokenizer/skeleton-matcher exists. Consolidating frame-extract with classify's `objectSpans` extraction into "Parse" (emitting a shared referent-substituted skeleton) is the concrete target this bullet was gesturing at. This deterministic regex/keyword fast-path remains an independent, orthogonal zero-Bedrock optimization for known phrasings, not a prerequisite for Parse --- correctness of Parse's own (possibly imperfect) LLM-driven output is enforced via the Backtrack channel (iteration 4), not via verifying spans against the raw command text (concluded a "fool's errand," see BD-21 above).

**Assertion-emission prerequisite (from BD-14's "Ungrounded position planning primitive shape"):** the Plan-stage compiler (`enrich/objectManipulation/plan/compileUngroundedPlan.ts`) is built and tested but only emits `Change` steps, never `Assertion` steps --- confirmed during implementation that `MembershipManipulationFrame` carries no field a `containedBy` assertion could be built from (only `rawObjectSpans` + `verbClass`, no location-disambiguating span like "table" in "get bag from table"). Extending classify + frame extraction to capture such a span is the actual prerequisite for real `Assertion` emission --- this is the same gap BD-21 names from the opposite direction (Plan needing structure Parse doesn't yet produce), not a second, independent problem.
