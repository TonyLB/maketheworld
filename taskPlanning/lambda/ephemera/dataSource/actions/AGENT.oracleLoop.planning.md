## Pilot findings

Where a clause of the [proposed variant](../../../../AGENT.designVariant.proposed.md) fights the work, or says nothing it needed to. Each is harvested into the proposal (or the tally, for a correction) and then removed from here.

- **The standings have no place for a principle** (2026-11-09, mine). The inherited table holds the user's accounts of what the system is for ("fiction is not a simulation", "a little dumb, never recalcitrant"). These aren't guesses about how subsystems fit, and no run grades them, so Guess, Observed and Locked don't fit. The table marks them as *principle*. The same goes for a decision about the plan's own direction (JF-9, JF-14, JF-18), which the Settled register marks as *direction*.
- **A probe needs a budget and an exit, as well as an unknown outcome** (2026-11-09, user's question, mine in form). "Does Micro read a candidate?" read as one batch can only answer yes; a no starts a tuning series nobody decided on. Slice 2.5 bounds it with a model comparison in the first batch, a budget of three drafts, and an exit for each outcome. The proposal's probe clause says only that the outcome must be unknown.
- **"Revise when" fits a guess, not an open question** (2026-11-09, mine). The open rows here are questions with no current guess, so what they need is what would settle them. The open table uses **Informs build** and **Settled by** in its place.
- **A test's expected outcomes need the same split as the design's guesses** (2026-11-09, user's question, mine in form, agreed). A corpus case written for an imagined loop expects intermediate steps (a verdict, the frontier, a direction) and an end result. If every expectation binds, a draft that finds a better route fails. If none does, no draft can fail. The corpus's [How a case is written](AGENT.oracleLoop.corpus.planning.md#how-a-case-is-written) now says the end result is what a case tests, and a draft that gets it wrong fails; the intermediate steps are guesses that a draft may revise; and an end result that is mine is still a guess, revised only by the user. The proposal's prototype obligations say nothing about a test's expectations; this is a candidate clause for them. **Refined by the user (2026-11-09):** the split is per subsystem, not per loop. An oracle round's output (the verdict, a candidate's potential, the direction) is the oracle step's end result, measurable in one call and binding on an oracle draft; what the player ends up with is the loop's. The guess sits at the seam between them: whether that output is what the engine can use. It came from OC-13, whose loop end result had been written into a one-round harness case and looked like a contradiction of OC-30's round 2.

- **A Prototype whose consumer is a probe closes after its build** (2026-11-09, mine). The harness's consumer is draft 1 run through it, an invoke the user runs, so the build's session can't close the step. Slice 3 carries the consumer run as its own sub-row. The proposal's obligation says a Prototype needs a consumer that runs, and says nothing about whether the step is done before that run.

- **The proposal has a place for sub-plans and nothing that opens one** (2026-11-09, the user's question, mine in form, agreed). Its organs name "implementation plans that build a subsystem on the map", and its Lifecycle hands Observed guesses to "the implementation plan that inherits the work", but nothing says when a build leaves the orchestration plan. Every build here stayed a row, and Slices 1 and 3 grew into build logs. Candidate clause: a build that runs over several sessions, with its own loop, gets its own plan; a build that fits in a session stays a row, and its row keeps only what it rested on, its trigger, its consumer and where it lives. The oracle drafts are the first sub-plan, and they test PV-3 too: whether findings travel back to the ledger when the work happens elsewhere. **Refined by the user (2026-11-09):** a sub-plan is one episode of back-and-forth iteration (the oracle, the engine, the oracle again), so what later episodes need (the drafts, the harness's cases, the corpus) stays with the orchestration plan, and the sub-plan holds only the episode's order and state. Candidate clause, second half: a sub-plan's artifacts that outlive the episode belong to the orchestration plan.
- **An exploratory step has no shape in an implementation plan** (2026-11-09, the user's proposal, its forms mine). A drafting series has no fixed list of steps: what to try next depends on the last result. Trialled on the oracle drafts: a file of **problems** (each with what "solved" means), a **library** of one-change entries ("try X for Y", with a source) and a one-line **ledger** of batches, kept with the drafts so it outlives the episode ([`oracleLoopDrafts/iterations.md`](oracleLoopDrafts/iterations.md)); and a **looping slice** in the episode's plan that pulls from the library until (a) it runs out, (b) the problems are solved, (c) something needs a new approach, with (d) a checkpoint with the user every three batches. A candidate shape for the proposal, or for the base guide once it has run.
- **A subsystem's boundary is a guess too** (2026-11-10; the user's observation, mine in form). The map listed the oracle and the engine as two imagined subsystems, and marked their behaviour as imagined but not their boundaries. Slice 4 tuned one prompt for twelve drafts inside a boundary nobody had tested. Under it, the question of whether the play-by-play belonged to the oracle or the engine (L-17, L-23) was really a sign that too much had been put into one prompt. Candidate clause: the map marks where a subsystem's boundary is drawn as a guess, with its own standing. For an LLM subsystem, the test of the boundary is whether it makes one judgment per call.

## The design

The user's reframing (2026-11-07): the oracle answers a different question. Given the scene, the answer-to-beat (possibly empty), the open questions, conflicts and challenges known to it, and a proposed new answer, it asks whether the new answer is better, whether there is an untested idea for doing better than the answer-to-beat, and if so how the improvisation engine should be prompted for further candidates. The oracle and the engine are two phases of one thing, not two engines pursuing different aspects of the goal (user). The full design and its history are in the [proposal record](AGENT.oracleLoop.proposals.planning.md#a-comparative-oracle).

The vocabulary the rows argue in:

- **Answer-to-beat:** the best finished product so far, what returns if the loop stops now. It starts as the floor, "I don't see how".
- **Candidate, or completion:** the request plus whatever has to be true for it, saying what it reuses and what it adds, and who supplied each step.
- **Frontier:** one or two candidates that lost as products but have an improvement worth a round. Potential never displaces the answer-to-beat.
- **Works:** a candidate works when every slot it opens is filled. As a product, every candidate that works beats every one that doesn't; potential counts not working as a malus, so a candidate waiting for a filler can sit on the frontier (user, 2026-11-08).
- **Direction:** what the oracle writes when something could do better than the answer-to-beat, and where the new information would come from: the engine (improvisations, repairs, worlds), which means another round, or the player (what and how questions, readings, plain or with options), which ends the round loop. The loop then restarts from the request with the player's answer (user, 2026-11-08; JF-19).
- **Round, turn:** a round is one oracle call in the loop over one request; a turn is the player's, and each one restarts the loop.
- **Slot, improvement request, improvisation, stretch:** a slot is what a candidate needs that isn't established. An improvement request asks for something in context, such as a filler for a slot, and carries no price. An improvisation is what comes back, an improvised fact (a bar-rag, the trees' canopy). A stretch is the oracle's judgment of how far the improviser went out on a limb, given the scene: little for a bar-rag in a tavern, high for an ancient manuscript in a 7-11 (user, 2026-11-08). It is the cost in the [formula](AGENT.oracleLoop.proposals.planning.md#judging-an-improvisation); exposition value and challenge are what it is worth.
- **Method dial:** how much of the how the system may supply, separate from the charity budget over facts (JF-15). A fact's role, challenge or texture, sets where it bites (JF-17).
- **Found out, granted out:** a found out is the player's own method over established facts, and earns credit. A granted out is a favourable improvisation from the system.
- **Elaborating, substituting:** filling in the steps of the player's own method, which is unbudgeted, against supplying a method the player didn't bring, which the dial limits (JF-16).

## How we work

- **A build that runs over several sessions, with its own loop, gets its own plan;** a build that fits in a session stays a row (user and mine, 2026-11-09). A sub-plan inherits this plan's premises and guesses, names the map's future subsystems it touches, and returns its findings here as seam-ledger entries. A row keeps what the build rested on, its trigger, its consumer and where it lives; the detail goes to the code, its docs and the ledger. The oracle drafts are the first (`AGENT.oracleDrafts.planning.md`, retired 2026-11-10).
- **What later iterations need stays here, not in a sub-plan** (user, 2026-11-09). The work goes back and forth: a run of oracle drafts, then the engine, then the oracle again. A sub-plan is one episode of that; the drafts, the harness's cases and the corpus carry across episodes, so this plan owns them.
- Rules for writing a draft for Nova Micro are in [Writing prompts for Nova Micro](../../../../../lambda/ephemera/calibration/AGENT.md#writing-prompts-for-nova-micro): one change per draft, positive rules, examples outside the fixtures' domains, and the rest.
- **Drafts** are files in [`oracleLoopDrafts/`](oracleLoopDrafts/), numbered from 1 across every sub-plan that drafts, each with a `.notes.md` beside it: the change, a rubric written before the batch, and the results. [`oracleLoopDrafts/iterations.md`](oracleLoopDrafts/iterations.md) holds the problems, the library of changes to try and a one-line ledger of what was tried, across episodes. A draft is probed through `OracleProbe`. I write each batch's payload with the draft's text as `instructions`, without its trailing newline so hashes compare across batches.
- **A piece's drafts** go in a directory of their own inside `oracleLoopDrafts/`, such as [`oracleLoopDrafts/ruleCell/`](oracleLoopDrafts/ruleCell/iterations.md), with their own numbering and `iterations.md` (user, 2026-11-10). A piece's batch runs through `PieceProbe` and is graded by its tally: I read the tally first, then only the wrong and malformed replies. Each batch's notes list the expected inputs hashes, rendered locally, as the deploy check. A piece's verdict goes last, after a description of what its inputs say, as a fenced `json` block (the rule cell's draft 3).
- Code changes only at the fixture builder, the oracle harness, the piece probe and its pieces, and the engine stub.
- The user runs each probe and pastes the result. Keep batches small: the smallest call count that answers the question, at most 12 per invoke.
- Each change is attributed. Anything not from the user is labelled "mine" until accepted.
- **Labels go on containers, not sentences** (pilot, 2026-11-09). The subsystem map says the oracle and the engine are imagined, so prose about them is imagined by default, and nothing is rephrased for that alone. A label is written in the sentence only where imagined content is stated as a requirement, a constraint or a settled fact.
- **A build or probe writes a seam-ledger entry** for what it showed, and books what that implies where the work belongs.
- **A v45 measurement is a test to run again,** not a result for the oracle. The corpus's per-case "On v45" line is Observed for v45 only.
