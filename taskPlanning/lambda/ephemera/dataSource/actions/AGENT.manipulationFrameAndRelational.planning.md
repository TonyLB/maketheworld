## Purpose

Ship real implementations for the three LLM fallback entry points named in BD-19 --- identity-only, plan-only, and joint --- so a command the deterministic vertical can't resolve gets a genuine second attempt instead of a terminal Error. Steps 1-3 of the 6-step build sequence below are done (naive confidence combiner, all-three stubs, identity-only real implementation for the membership domain). **Steps 4-6 are paused (2026-07-18), waiting on iteration 3's Parse hop** --- plan-only and joint fallback should consume Parse's tokenized skeleton rather than raw command text, so building them before Parse exists would mean reworking them. **Update (2026-07-19):** iteration 3's Step 2a wired Parse into the live membership route --- a partial unblock only. **Refined (2026-07-19): the gate on steps 4-5 is per-fallback, not "all of Step 2b," since Step 2b is now shipped as native `ParseSkeleton` consumption (iteration 3, retired --- see the iteration ladder and [`enrich/objectManipulation/AGENT.md`](../../../../../lambda/ephemera/dataSource/actions/enrich/objectManipulation/AGENT.md)'s relational branch) whose deterministic matcher is the *first attempt* these fallbacks are the *second attempt* for --- both attempts must feed the same downstream `Referent`/Grounding/Validation shape, the same discipline identity-only fallback already follows by reusing the deterministic path's dry-run legality rather than inventing its own.** Plan-only fallback needs Step 2b's step 1 (`stableRefKey` on `Referent`), step 3 (the native matcher's output contract, so this fallback's LLM output normalizes into the same shape), and step 4 (the Identify-integration adapter --- plan-only's premise is consuming already-resolved, `stableRefKey`-keyed identity results as context). Joint fallback needs only step 1 and step 3 --- it resolves identity and plan together in one LLM call, so it doesn't depend on step 4's Identify adapter. **Neither strictly needs Step 2b's step 5 (Validation) or step 6 (live wiring) to begin real design work** --- Validation applies generically to any `Referent`-based plan regardless of whether a template match or an LLM produced it, and design/prompt work doesn't require production wiring to exist yet. See [`AGENT.objectManipulationIterations.planning.md`](AGENT.objectManipulationIterations.planning.md) for the current active-iteration status.

- **(1) Fallback split shape --- Decided (2026-07-17): commit to three genuinely separate fallback paths**, not an always-joint default. Identity-only fallback (Plan succeeded, given as context), plan-only fallback (Identity succeeded, given as context), and joint fallback (both failed, no confident anchor). Jointness is confirmed still load-bearing for the both-failed case (two independently-resolved LLM guesses risk an internally-incoherent pair reconciled only after the fact via an N x N cross-product of separately-calibrated confidences; a joint candidate is coherent by construction). **Expected implementation-level overlap, not three unrelated builds:** the three fallbacks will likely share prompt-construction scaffolding, the N-ranked-candidate output shape, and the `selectPlanTuple` propose-N + legality-gated-selection wiring --- three distinct *entry points* (which context each is given, what it's asked to resolve), not three independently-invented mechanisms. **Why commit now, ahead of building either:** three named, distinct fallback entry points give the backtrack channel (iteration 4) concrete resume-points to reason about --- e.g. a backtrack could plausibly target "redo the identity-only fallback with this new constraint from Synthesize" specifically, rather than an undifferentiated "redo everything." Committing to the shape now, before any of the three are built, means that future design work inherits this grounding rather than re-deriving it.

- **(2) Shortlist cross-product risk in the plan-only case, confirmed real; asymmetry Decided/Confirmed (2026-07-17).** "Identity succeeds" is not actually a single winner even today --- `selectRelationalFromPools.ts` reads `subjectPool.shortlist ?? subjectPool.candidates`, and `proposeRelationalTuples` already cartesian-products subject x target candidates specifically so a downstream legality failure on the top candidate can fall through to the next-best one. So a plan-only fallback cross-products (identity's shortlist, small, floor/margin-gated) x (the plan-fallback LLM's N ranked frame interpretations) --- bounded, not explosive, but a real multiplicative space, not a single clean anchor. **Asymmetry confirmed structural, not just likely:** every deterministic Plan path this codebase anticipates is exact-template matching, Infocom-parser style (closed verb/preposition grammar, `V NP prep NP` role extraction, enum lookup for the relation phrase --- see "Legacy hop retirement"'s "Up" bullet below, and `compileUngroundedPlan.ts`'s shipped membership/relational compilers today, whose `CompileUngroundedPlanResult` success variant already carries exactly one `steps` array, never a ranked list). A template either matches or it doesn't --- there is no deterministic notion of "second-best parse" the way embedding similarity naturally ranks identity candidates, because nothing scores a template match by degree; it's a boolean gate, not a continuous measure. So the cross-product risk is confirmed to concentrate **entirely** on the plan-only fallback case (2) and the joint case (3, where Plan itself goes through an LLM and so genuinely can produce ranked alternatives) --- the identity-only fallback (case 1) is clean by construction: its LLM candidates are evaluated against one fixed deterministic frame, never cross-produced against multiple plan interpretations, because deterministic Plan has no "multiple interpretations" to offer in the first place. `selectPlanTuple` (partition-by-legality, rank-by-confidence) is already the right tool for the resulting bounded cross-product in cases 2-3 --- reuse, not new machinery.

- **(3) Cross-source confidence combination, unstarted --- revised approach (2026-07-17), `tanh` retracted as the template.** Combining an identity-shortlist candidate's confidence with a plan-fallback LLM's confidence per tuple needs a real answer --- `proposeRelationalTuples`'s existing "confidence = min joint" convention would repeat exactly the naive cross-source blend this doc already warns against elsewhere (hint confidence must not blend as a naive additive term into the FT-5 floor): an embedding-cosine-based joint relevance and an LLM's self-reported confidence aren't obviously on the same calibrated scale. **Corrected (2026-07-17): `embeddingMatch/relevanceCombine.ts`'s `tanhCenteredFlankScore` is not the right template here.** `tanh` earns its keep there specifically because it bounds an *unbounded* raw measurement (flank character length, which can grow arbitrarily) into a centered, saturating evidence contribution before summing --- there is no unbounded-flank analog in this problem: both identity confidence and the anticipated plan-LLM confidence are already normed to `[0, 1]`. The actual tool for combining two already-bounded probability-like scores additively is a **logit transform** (`logit(p) = ln(p / (1 - p))`, the true inverse of the outer `sigmoid`, clamped near 0/1 the way `evidenceNumerics.ts`'s `SIGMOID_CLAMP` already clamps its own input) --- summing independent log-odds and squashing back via `sigmoid` is the Bayes-correct combination for genuinely independent, well-calibrated probabilities, which is the real justification underlying "sum then sigmoid," not `tanh` specifically. **This only works if both `[0, 1]` scores actually behave like calibrated probabilities, which needs checking, not assuming --- and identity already has the tooling to check it:** the existing calibration harness (`lambda/ephemera/calibration/`, `embeddingMatch/testing/calibrationSweep.test.ts`, locked constants in `thresholds.ts`, committed snapshot JSON under `calibration/objectMatch/snapshots/`, documented "When to re-calibrate" process in `embeddingMatch/AGENT.md`) already produces exactly the confidence-vs-correctness curve needed to tell whether identity's raw score needs a correction/warping curve before logit-mapping, or is already well-behaved. **Concrete next step, gated on the plan-LLM fallback existing first:** once built, run an analogous calibration study on its own confidence-vs-correctness curve (mirroring the existing embeddingMatch calibration-sweep pattern --- constructed test cases, closed-loop over/under-confidence check, ideally a committed snapshot), and design the actual combination function (per-source correction curve, if needed, then logit, sum, sigmoid) from both empirical curves --- not from an assumed shape.
