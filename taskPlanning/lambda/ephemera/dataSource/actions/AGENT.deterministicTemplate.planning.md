## Purpose

CPG-1 asks for the exact type shape of a `DeterministicTemplate`: the layer-1 rule that matches either a raw command string or a token sequence and, on a hit, emits **both** an intent classification **and** a synthesized `ParseSkeleton` at zero Bedrock cost. This plan builds that shape as a self-contained feature so the type contract is proven against real templates before anything downstream depends on it.

Two precedents in the tree produce **incompatible output shapes** that this feature reconciles:
- [`discriminateIntent/deterministicChecks.ts`](../../../../../lambda/ephemera/dataSource/actions/discriminateIntent/deterministicChecks.ts): raw string -> `ParseCommandResult` (family-level intent), **no skeleton**.
- [`enrich/objectManipulation/plan/matchRelationalTemplate.ts`](../../../../../lambda/ephemera/dataSource/actions/enrich/objectManipulation/plan/matchRelationalTemplate.ts): already-built `ParseSkeleton` -> `Change` (a Plan primitive), **no classification**, run **post**-Parse.

`DeterministicTemplateMatch` is the type that carries classification **and** skeleton together; `DeterministicTemplate` is the contract that produces it from `ParseCommandInput`.

## Scope boundary (what this plan deliberately does NOT do)

- **No plumbing.** The live classify (`discriminateIntent`) and Parse paths are untouched. Migrating today's ad-hoc checks into templates is CPG-1/CPG-3/CPG-6's plumbing work, handed back at graduation.
- **No model-dependent templates.** Only templates whose emitted shape is **invariant** to the entry-vs-bypass pipeline decision are built here: **bare-word** (Step 1) and **relational** (Step 2). **Navigation** (exit resolution) and the **`get`/membership context-gating** check are *deliberately excluded* --- their emitted shape hinges on entry-vs-bypass, so building them here would silently force a decision this plan defers to CPG. (Design rationale: a relational hit always emits classification + synthesized skeleton because object-span resolution is Identify's job under *any* model; bare words have nothing to resolve.)

## Design decisions (confirmed through conversation, 2026-07-20)

1. **`DeterministicTemplate` is a shared structural interface, satisfied by a factory function --- not a `class`.** TypeScript's structural typing means polymorphism doesn't require inheritance: any value with the right method shape conforms, whether it's produced by a class instance or a plain object literal holding function-valued properties. The contract:

   ```ts
   interface DeterministicTemplate {
     matchString(command: string): DeterministicTemplateMatch
     matchTokens(skeleton: ParseSkeleton): DeterministicTemplateMatch
   }
   ```

   This plan builds exactly **one** implementation --- the pattern-driven kind, produced by a factory `makePatternTemplate(pattern: PatternElement[], templateIntent: <partial constant>): DeterministicTemplate` that closes over its data and delegates to two **generic** (not per-template) engine functions:
   - `PatternElement = { type: 'templateText'; options: string[] } | { type: 'objectSpan'; role: IntentFieldRole } | { type: 'capturedText'; role: IntentFieldRole }` --- three kinds, cleanly split by what each does: `templateText` is a **closed-vocabulary gate**, its matched value is never threaded into intent (every template using it already fixes the relevant intent field as a constant, regardless of which listed synonym matched); `objectSpan` is a **referent slot** (feeds both a skeleton token and an intent field); `capturedText` is a **free-text slot** (feeds a skeleton `text` token and an intent field, like `objectSpan`, but carries no referent/Identify semantics --- for open-ended values like a custom relation label, see design decision 2 and DT-5). `IntentFieldRole` is a closed union (DT-6), not a freeform string.
   - `matchString` (builds an anchored, case-insensitive regex from the element list --- `templateText` options become an alternation, `objectSpan`/`capturedText` become a non-greedy bounded capture) and `matchTokens` (positional walk against an existing `ParseSkeleton`: `templateText` checks the corresponding `TextToken.text` is in `options`, `objectSpan`/`capturedText` accept the corresponding token and capture its text/span). Both are shared infrastructure, proven once against the rows this plan authors, and reused unchanged by every pattern-driven template.
   - The pattern doubles as the **skeleton synthesis template** for `matchString` hits: walking matched elements and emitting one `ParseToken` per element (`objectSpan` -> `ObjectSpanToken`, `templateText`/`capturedText` -> `TextToken`, stamped via `stampStableRefKeys`) produces the skeleton for free, with no separate hand-written synthesis step per template.

   **Why the interface, not just a `{pattern, templateIntent}` value directly:** bare-word and relational templates are *not* two implementations (same generic engine, different-length pattern arrays --- see design decision 2's granularity point). The real second implementation is the **context-dependent** family scoped out of this plan (Navigation's `roomExits` lookup, `get`'s `roomObjectLabels` gate) --- those can't be expressed as `{pattern, templateIntent}` data at all, since they read fields with no relationship to pattern-matching. Confirmed in conversation: defining the interface now, with today's only implementation being a factory-produced value, leaves that future kind a seam to slot into (a hand-written object satisfying the same two-method shape) without reshaping the registry or `DeterministicTemplateMatch` --- while keeping the ~20 pattern-driven rows in this plan as plain `{pattern, templateIntent}` **data** (testable, comparable, enumerable) fed through `makePatternTemplate` once at registry-build time, not authored as class instances.
2. **No `deriveIntent` function --- templates are granular enough that intent is a constant, assembled by one shared, generic combinator.** Earlier drafts of this design considered one template per *family* (all relational verbs + all prepositions in one matcher with internal branching, mirroring `matchRelationalTemplate.ts`'s `classifyVerb`/`normalizeRelationSpan`) with a per-template `deriveIntent(captures)` function. **Rejected on direct user correction:** there is no reason a template must be that coarse. Splitting finer --- confirmed by a direct read of `normalizeRelationSpan.ts` (DT-5) --- turns the entire non-referent part of intent into a **constant** per template, in two tiers:
   - **Enum bucket (closed, genuinely enumerable):** `normalizeRelationSpan` groups synonym phrases into exactly 3 relation kinds --- `Against` (`against`/`lean against`/`leaning against`), `Under` (`under`/`beneath`/`underneath`), `On` (`on`/`onto`/`on top of`). One template per (verb-class x relationKind) --- 2 verb-classes x 3 kinds = 6 templates --- with all synonym phrases in that template's `templateText` `options` list and `templateIntent: { primitive, relationKind }` as a full constant.
   - **Custom bucket (open-ended, not enumerable):** anything not in the enum or containment sets falls through to `relationLabel` = the matched text itself. This can't be a finite set of data rows, so it needs the third `PatternElement` kind, `capturedText` (design decision 1) --- its matched value is threaded into `templateIntent.relationLabel` by the generic combinator. This is still **shared, generic machinery** (`capturedText`'s contract is "always feed the match into the named intent field," true for every template that uses it), not per-template derivation logic.

   What remains parametric across both tiers is exactly the `objectSpan` captures (subject/target refs), which are positional data, not derivation logic; one generic combinator (`{ ...templateIntent, ...roleTaggedCaptures }`, shared core machinery, not per-template code) assembles the final intent, whether the tagged captures come from `objectSpan` or `capturedText` elements. Net effect: **more, smaller templates, zero per-template functions** --- each new template (Step 1 or Step 2) is a pure data row.
3. **Reuse `ParseCommandResult` for the intent payload --- do not invent a new "intent info" type.** The ad-hoc `verbClass` / `operationKind` encoding already lives *in* the existing result union (`ObjectMembershipIntent.verbClass`, relational's derived `Change`). The `matched` arm carries `{ skeleton: ParseSkeleton, intent: ParseCommandResult }`; the union is discriminated by construction, so structurally different families (Navigation vs membership vs relational) coexist without a flattened bag.
4. **A match is not binary --- three arms.** `noMatch | matched | defer`. `defer` preserves `matchRelationalTemplate`'s existing `nestingDefer` case ("matched the shape, but it's a known-unsupported case with its own error path") and gives deterministic `Error`-style outcomes (cf. `deterministicChecks`'s malformed-coyote-slash `Error`) a home distinct from "didn't understand this at all." The full union is defined in Step 1 so the contract is stable, even though `defer` has no producer until Step 2.
5. **`matchString` has a hard structural limit, inherent to determinism itself, not a regex weakness.** Two adjacent `objectSpan` elements with no intervening `templateText` are unsegmentable from raw text (`"put bag box"` cannot be deterministically split into one span or two without semantic/world knowledge) --- true of any deterministic grammar, not specific to a regex implementation. A pattern with adjacent `objectSpan` elements is therefore **`matchString`-ineligible by construction** (still valid for `matchTokens`, since Parse's LLM has already segmented spans by the time tokens exist). This is not a gap to close later: commands that need that segmentation judgment are exactly the ones meant to fall through to Parse's LLM. State this as an invariant of the pattern language, not an open problem.
6. **Entry-vs-bypass is a plumbing decision, deferred.** Whether a live match is an *entry* to Plan/Identify (emit classification + skeleton, resolution stays downstream) or a *bypass* (fully resolved result) does **not** change the core machinery or the `matched` type --- `ParseCommandResult` already contains both coarse-classification and fully-resolved members, so the type forecloses neither. Confirmed in conversation: this plan builds the feature model-agnostically; CPG owns the model decision when it plumbs.
