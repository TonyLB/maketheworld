# Presence nodes: reifying the bucket root

**Status: opened 2026-09-14, nothing started.** The migration proposal is the author's, from the 2026-09-14 conversation, and is recorded below in six clauses. **No clause is implemented and several depend on rows that are currently Settled or Locked elsewhere** --- [Slice 0](#recommended-order) exists to reopen those before any code is written, and it is the only slice that is not optional to do first. Next step: Slice 0.

**This is a standard implementation plan under [`taskPlanning/AGENT.md`](../../../../AGENT.md), not a design-stage plan.** The deliverable is a migration --- types, a cut, a merge, a write side and a doc sweep --- and the open rows below are forks being resolved **in order to implement** it. **It is not a design plan even though it reopens design rows**, because it is not choosing between rival schemes: the scheme is chosen, and what the rows record is what the scheme costs where it lands on settled ground. If a genuine rival appears, that belongs in a proposal in [`AGENT.abstractionLayers.proposals.planning.md`](AGENT.abstractionLayers.proposals.planning.md), not here.

**Scope in one sentence: make a presence binding a *node* of the graph rather than an index carried by a port, keep it addressable from outside the host as if it were still a port, and re-base `ludicCache`'s completeness bookkeeping on the node instead of on a field.**

## Why this is opened

**The trigger is a loss in `ludicCache`, stated by the author on 2026-09-14 and traced in the same conversation.** A cache is one merged graph over many wholes; a `ludicGraph` is many little graphs each with its own boundary. Presence in the graph is an **indexing of nodes by a boundary site**, and the merge has nowhere to put the site. Three losses follow, and they are the measure this plan is graded against:

- **(A) Enclosure of an otherwise unrelated node.** In a bucket graph the bucket *is* the node list; in a merge there is no node list to be.
- **(B) Identity of the crossing site.** `chains: EphemeraMembershipHostId[][]` names **hosts**, so a string entering one room at two places collapses to one hop.
- **(C) Presence is not a node-to-node relation.** Encoding it as an edge requires the index itself to be a node --- which is this plan.

**The cache is *true* and meaningfully *incomplete*, and adding `Present` edges alone does not fix it** --- that was the author's opening claim and it survived the conversation. What fixes it is giving the boundary site an identity the merge can carry.

**The second motive is asymmetry, and it is why this is a *hybrid* rather than a straight reification.** Component nodes want to be localized by crossing ports, so their relations with other hosts are mediated. Presence nodes want the opposite: they need a reference back to *what they are presence for*, and they benefit disproportionately from being addressable **from outside** the host. Ports gave that addressing for free, which is why they were a tempting first implementation. The hybrid keeps it.

## The proposal in six clauses

**The author's, 2026-09-14. Recorded verbatim in substance; the commentary is separated below so the clauses can be read as the specification.**

1. **A presence binding is a node.** For `ludicCache` it carries `consolidated: boolean` (undefined/false meaning not consolidated); it remains addressable from outside the host in port form, `OBJECT#CONTRAPTION#{presence node id}`.
2. **A host node may have NO presence sub-nodes linked to it**, which says its graph is **unexamined**.
3. **If a host consolidates *any* presence bucket, it adds *all* of its presence nodes** and connects them to the hosting node. Zero or all; never some.
4. **Each presence node carries `consolidated`** for its own bucket.
5. **For a single-hosted node** --- exactly one presence node --- presence within that bucket is **implicit**, derivable from the hosting edges (`In`, `On`, `PartOf`).
6. **For a multi-hosted node, `Present` links are written explicitly** for consolidated buckets.

**Why clause 3 is the load-bearing one, and it should not be weakened for size.** It resolves a conflict between two things this design was otherwise holding at once. Carrying every presence port into every bucket (shipped) is what keeps **binding arity** readable from any bucket, which is what [D3](AGENT.ludicCacheRebuild.planning.md#open-decisions-implementation--plan-only)'s completeness claim rests on. The rule *a presence node is absent iff its bucket was not pulled* needs the opposite. **All-or-nothing per host gives both:** zero says *unexamined*, any says *the binding set is complete*, and the per-node flag says which were pulled. Neither scheme alone can say all three.

**Clause 3 also pays for clause 5, which answers the obvious objection to it.** An arity change (single-hosted becomes multi-hosted) flips a host from implicit to explicit and needs `Present` edges written retroactively for the first bucket --- which looks expensive until you notice that clause 3 **already** forces re-materializing all presence nodes for that host on any arity change. The conversion rides an operation that is whole-host anyway. **No row is opened for it; it is recorded here so it is not rediscovered as a cost.**

**What the proposal banks, checked against the three losses:** **(B)** and **(C)** are recovered --- two entries into one room are two nodes, and the index is a node by construction. **(A)** is recovered *conditionally*, and the condition is [PN-1](#open-decisions-implementation--plan-only). It also defeats **CC0's box-can-be-empty argument** against deriving consolidation state: an opened empty bucket is a presence node flagged `consolidated` with no members, distinguishable from no presence node at all, so the marker is the **node**, not its contents.

## What this plan disturbs, and what it leaves alone

**Cheap at the presence layer, and that is not luck.** [`AGENT.presence.planning.md`](AGENT.presence.planning.md) deliberately named the index a *presence binding* rather than a *port*, recording that *"a binding is realised as a **port** is PR-4's mechanism and stays swappable."* This plan swaps it. **PR-4 pre-answers the node-to-node objection** as well: `Present` edges run PORT -> NODE precisely so presence is not a relation between two components, and a presence node keeps that asymmetry rather than dissolving it.

**Three settled rows move, and Slice 0 owns reopening each in its home file rather than quietly working around it:**

foreign-kind edges landing there are **licensed**, and clause 1's exterior address continues that rather than departing from it. **(2) The row is two propositions with different fates.** The **denotation clause** --- an edge landing on a presence binding denotes *the part of the object present via that binding*, with the binding as the referent **itself**, "real and unmaterialized," never a pointer resolved by walking --- **transfers to a node unchanged, and is the half worth graduating.** The **terminal-only clause** --- never a crossing, the `kind === 'Present'` partition, kind-agreement as a category error --- **goes MOOT, not false**: **chaining is a port mechanism and happens across ports, never across nodes** ([`AGENT.edges.md`](../../../../../packages/mtw-wml/ts/standardize/keys/edges/AGENT.edges.md#list-typing-note)), so of a presence *node* the crossing question is **undefined rather than hard**. **(3) [PR-16](AGENT.presence.planning.md#open-decisions-design--plan-only) does NOT move with it** --- it asks whether *crossing* ports accept terminal edges, and **crossing ports are untouched by moving presence bindings off ports.** **What is actually disturbed is disposition, not doctrine:** the terminal-only clause has live consumers, and whether they stay live is [PN-8](#open-decisions-implementation--plan-only)'s question.
