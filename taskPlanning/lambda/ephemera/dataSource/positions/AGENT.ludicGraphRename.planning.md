# `positionGraph` -> `ludicGraph` rename

**Status:** In progress. Phases 0-4 done: canonical types renamed (`mtw-interfaces`), the implementation class/folder renamed (`positionGraph/` -> `ludicGraph/`), the gateway layer + `internalCache.Positions` wrapper renamed (per OD-3), the `mtw-wml` asset-level graph + `charcoal-client` editor UI renamed (per OD-2's reversal / OD-9), and the remaining local-vocabulary consumers (Deps-callback fields, local variables, test fixtures --- per OD-11) + documentation sweep renamed --- `mtw-gateways`, `mtw-interfaces`, `mtw-wml`, `charcoal-client`, `lambda/ephemera`, and `lambda/diagnostics` all green, and a repo-wide grep for `positionGraph`/`PositionGraph`/`EphemeraPositionGraph` in `*.ts`/`*.tsx` returns no hits outside historical `taskPlanning/*.planning.md` records. Phase 4 also fixed a live correctness bug it uncovered: both `lambda/diagnostics` sweeps (`orphanedImprovisedObjectSweep`, `roomOccupancyDriftSweep`) were still projecting the old `positionGraph` DynamoDB attribute name after Phase 2 moved the only writer to `ludicGraph`, so they were silently reading empty graphs. Next step is Phase 4.5 (manual reseed, per OD-8 and OD-10's corrected procedure). Seeded 2026-08-11 from conversation, as the direct execution of a decision already made and locked elsewhere --- see below. **OD-10 reversed a second time, 2026-08-11:** its 2026-08-12 "self-correcting, no force-touch needed" resolution turned out to rest on a false premise (that `cacheAsset`'s `fileAsset` is a fresh WML-text parse; it is actually a pre-serialized `.ndjson` S3 cache that can itself carry the stale `positionGraph` key, in which case `cacheAsset`'s diff compares two stale-empty sides and does nothing) --- Phase 4.5 now requires forcing WML self-repair reconstruction per asset before `cacheAsset` will correctly propagate the data; see OD-10's row for the full trace. All other ten open decisions resolved as of 2026-08-12 (OD-2 reversed after its first pass mischaracterized `mtw-wml`'s asset-level graph as out of scope --- it holds the actual authored Exit topology and is now in scope, adding Phase 3.5; OD-11 added and resolved at Phase 4 --- Deps-field vocabulary renamed for consistency, same reasoning as OD-9). This plan follows [`taskPlanning/AGENT.md`](../../../../AGENT.md); skim it once for durability and content-split conventions before editing this file.

**This plan does not re-argue whether to rename.** That decision was made in [`AGENT.abstractionLayers.planning.md`](AGENT.abstractionLayers.planning.md) --- see its [Graduation tiers](AGENT.abstractionLayers.planning.md#graduation-tiers-when-a-decision-licenses-code-2026-08-11) section (the `provisional` / `locked` / `Prototype` framework that licenses this work) and its [naming consequence](AGENT.abstractionLayers.planning.md#the-naming-consequence-positiongraph-will-be-lying) section (where `ludicGraph`, from **Ludic Network**, was settled as the replacement name and classified **locked**). What that plan did **not** do is scope the actual rename's surface area or resolve the forks the surface turned up once someone went and looked --- that is this plan's entire job. **`ludicCache` is explicitly out of scope here.** It stays **provisional** under the same Graduation-tiers framework (AB-35 unresolved) and gets its own plan once its design, not just its name, is settled.

### 8. Persisted data --- `positionGraph` is a DynamoDB field name, not only a TS identifier
`lambda/ephemera/dataSource/positions/positionGraph/index.ts`'s `fromRoomMeta`/`fromCharacterMeta` read `meta.positionGraph` directly off `Meta::Room`/`Meta::Character` DynamoDB records, and the folder's own `AGENT.md` confirms: *"Stored JSON remains `EphemeraPositionRelationalEdgeData` on `positionGraph.edges`."* **This means the rename is not purely a compile-time refactor.** A live table with saved play state has items whose `positionGraph` attribute would go unread by code that only knows to look for `ludicGraph`, unless the persistence boundary is handled deliberately. See **OD-8** --- this is the highest-consequence open decision in this plan and should be resolved before Phase 1 starts, not discovered mid-rename.

**Read/write split, confirmed during Phase 2:** the read half (`fromRoomMeta`/`fromCharacterMeta`) lives in this folder, but the only live *write* of the raw attribute is `manipulation/kernel/commitStepSequence.ts` (`updateKeys`, and the `MultiKeyUpdate` reducer's `entry.<field> = graph.toStored()` assignment) --- outside `positionGraph/`/`ludicGraph/` entirely. Phase 2 renamed both together so the boundary stayed self-consistent within the same phase; a future reader touching one should check the other. Separately, `packages/mtw-gateways/ts/ephemera/positions/fetch.ts` reads the same attribute through a **different** path (`ProjectionFields`/`Pick<EphemeraMetaRoom, 'positionGraph'>`, the play-envelope/cache route via `PositionsCacheHandler`) and was deliberately left on the old key name until Phase 3 renames that layer --- per OD-8's own reasoning this is an accepted gap, not a new risk, but it means between Phase 2 and Phase 3 landing, this specific read path returns nothing for any freshly-committed graph.

### 9. Derived/cached data downstream of the asset-level graph --- the `Affordance::` cache (added 2026-08-12, with OD-2's reversal)
`StandardArea._positionGraph`'s Exit edges are not read directly at runtime; they are projected through `packages/mtw-wml/ts/standardize/projection/projectRoomExits.ts` and `packages/mtw-gateways/ts/assets/components/componentTopology/{assemble,result}.ts` into a **separate, persisted `Affordance::` DynamoDB row** (`lambda/ephemera/dataSource/affordanceCache/hydrateAffordanceTopology.ts`), which is what `roomExitTargetsForCharacter.ts` actually reads --- not the Area's `positionGraph`/`ludicGraph` directly.

**Reversed 2026-08-11, this paragraph's premise was wrong.** `assetDB`'s Area component rows are **not** rewritten fresh from WML source text on every `cacheAsset` run. `cacheAsset.ts:40-49`'s `fileAsset` comes from `ReadOnlyAssetWorkspace.loadJSON()` (`packages/mtw-asset-workspace/ts/readOnly.ts:199-220`), which reads the asset's `{uuid}.ndjson` object from S3 --- a **pre-serialized JSON cache** of the `StandardForm`, written by `pushJSON()` in `lambda/wml/s3Storage/AssetWorkspace.ts` the last time the asset was actually edited/saved through the WML lambda, and never regenerated automatically. It does not parse `.wml` text at all; `loadJSON()` has no fallback to the raw markup. See **OD-10 (reversed)** below.

**OD-10 reversed 2026-08-11: not self-correcting --- `cacheAsset` reads through the same stale JSON cache on both sides of its diff, so it can go silently inert.** The original trace assumed `fileAsset` was a fresh WML-text parse; it is not (see above). If an asset's `.ndjson` predates this rename, it still carries a literal `"positionGraph"` key, and `StandardArea.fromJSON` (reading `props.ludicGraph`) reconstructs an *empty* graph from it. Worse: `dbAsset` (`internalCache.AssetData`, sourced from `assetDB` rows previously written by an earlier `cacheAsset` run's `fileComponent.toJSON()`) went through this exact same JSON round-trip and is *also* empty. `dbAsset.diff(fileAsset)` compares two empty graphs, sees no difference, and does nothing --- the real authored graph data is invisible to both stores, not "self-corrected."

**The actual immune path: WML self-repair reconstruction, not `cacheAsset`.** Traced `lambda/wml/s3Storage/materializedView/reconstruction.ts` and `AGENT.selfRepair.md`: chunks and snapshots are stored as raw `text/plain` WML (`lambda/wml/s3Storage/chunks/index.ts`, `snapshots/index.ts`), never JSON. `reconstructFromManifest` (`reconstruction.ts:133-183`) rebuilds via `new StandardForm(wmlText)` -> `nodeFromWML` --- a genuine markup re-parse, immune to the stale-key problem because `ludicGraph`/`positionGraph` never appears as literal text in WML source; it is purely an internal field name the *current* parser code chooses when serializing. This reconstruction (Scenario 2 in `AGENT.selfRepair.md`, "Materialized View Missing, Manifest Exists") fires when `workspace.status.s3Missing === true` --- i.e. `{uuid}.wml`/`{uuid}.ndjson` are absent from S3 while the manifest/chunks remain. **Corrected Phase 4.5 procedure, per asset:** (1) delete/move aside `{uuid}.wml` and `{uuid}.ndjson` from S3 (leave the manifest and chunks intact); (2) trigger any pipeline operation that goes through `fetchAndDecideRepair` (e.g. `appendChunk` via the `applyEdit` mutation) to force Scenario-2 reconstruction, which rewrites the materialized view under the current (renamed) parser; (3) *then* run `cacheAsset` (e.g. via the `Cache Consistency Finding` diagnostic event) so the now-correct `.ndjson` propagates into `assetDB`/DynamoDB. Running `cacheAsset` alone, without first forcing reconstruction, does not fix a stale `.ndjson`.

### 10. `getPositionGraph` as a repeated Deps-callback field name, not just the two class methods (found during Phase 2)

Item 3 names `getPositionGraph` on `PositionsCacheHandler` (`mtw-gateways`) and on `EphemeraPositionsCacheData` (`internalCache/positionsCache.ts`) as the rename targets --- **those are the only two real method *definitions*, but the name is independently re-declared as a dependency-injection callback field in roughly fifteen more files**, each with its own `...Deps`/`...Dependencies` type carrying a `getPositionGraph: (id) => Promise<EphemeraLudicGraph>` field, defaulted to `(id) => internalCache.Positions.getPositionGraph(id)`. Representative, not exhaustive: `dataSource/actions/{roomObjectCatalogForCharacter,heldInventoryCatalogForCharacter}.ts`; `dataSource/actions/enrich/objectManipulation/{membershipObservation,compileRelationalFromSkeleton,compileMembershipAtomic}.ts` (as the `positionsReadDeps.getPositionGraph` field); `dataSource/positions/manipulation/relational/applyObjectRelationalChange.ts`; `dataSource/positions/manipulation/membership/{applyObjectClearMembership,executeObjectMove}.ts`; `dataSource/positions/membership/{applyObjectRoomMembership,repairRoomOccupancyDrift,repairObjectPlacementDrift}.ts`; `dataSource/objects/clearCoyoteGameImprovisationObjects.ts` (as `getRoomPositionGraph`/`getCharacterPositionGraph`); `dataSource/actions/utilities/countCoyotePlacedObjectsAcrossRooms.ts`; `dataSource/stableKey/collectCoyoteOccupiedStableKeys.ts`; `dataSource/coyoteGame/utilities/coyoteRoomObjectSnapshot.ts`; `internalCache/{hydrateRoomRoster,index,affordanceRoomDeliverable}.ts`; every one of these files' own `.test.ts` (mocking `internalCache.Positions.getPositionGraph` directly, or passing a `getPositionGraph: jest.fn()` override).

**Two distinct pieces of fallout, not one:**
- **Compile-forcing (whichever phase renames the two real methods, per OD-3):** every default-wiring call site (`(id) => internalCache.Positions.getPositionGraph(id)`, `this._gateway.getPositionGraph(componentId)`, `handler.getPositionGraph(...)`) must update to `.getLudicGraph(...)` the moment the method it delegates to is renamed, or these ~15 files stop compiling. This is the same shape of surprise Phase 2 hit with the class rename's ~80-file blast radius --- size it into Phase 3 rather than discovering it mid-phase.
- **Cosmetic (a separate, deferrable call):** the Deps-field's **own name** (`getPositionGraph` as a parameter/property, decoupled from the class method it happens to default-wire to) is item 3/Phase 4 territory like any other local vocabulary --- it does not have to move in lockstep with the class method rename, since TypeScript doesn't care that a field named `getPositionGraph` is implemented by calling `.getLudicGraph()`. Whether to rename these ~15 field names for consistency (same question OD-9 already answered "yes" for the `charcoal-client` editor) is worth a short explicit decision when Phase 4 gets there, rather than defaulting silently either way.
