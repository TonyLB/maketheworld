### 7. `internalCache.Positions` --- already exists, and is not `ludicCache`
`lambda/ephemera/internalCache/index.ts` exposes `Positions: EphemeraPositionsCacheData`, a per-request memoization wrapper (`lambda/ephemera/internalCache/positionsCache.ts`) around `mtw-gateways`'s DynamoDB-backed `PositionsCacheHandler`. Its own method is `getPositionGraph(componentId)`, returning `EphemeraPositionGraph.fromPlayEnvelope(...)`. **This is a different thing from the `ludicCache` the parent plan's AB-35 describes** (a *denormalized, cross-host-expanded* read structure, not yet designed) --- AB-35 itself already notes this cache exists and asks how the new one interacts with it, rather than assuming it *is* the new one. Confirmed, not merely assumed: it is a real, already-shipped, narrower construct. See **OD-3** for what (if anything) about its name changes here.

### 8. Persisted data --- `positionGraph` is a DynamoDB field name, not only a TS identifier
`lambda/ephemera/dataSource/positions/positionGraph/index.ts`'s `fromRoomMeta`/`fromCharacterMeta` read `meta.positionGraph` directly off `Meta::Room`/`Meta::Character` DynamoDB records, and the folder's own `AGENT.md` confirms: *"Stored JSON remains `EphemeraPositionRelationalEdgeData` on `positionGraph.edges`."* **This means the rename is not purely a compile-time refactor.** A live table with saved play state has items whose `positionGraph` attribute would go unread by code that only knows to look for `ludicGraph`, unless the persistence boundary is handled deliberately. See **OD-8** --- this is the highest-consequence open decision in this plan and should be resolved before Phase 1 starts, not discovered mid-rename.

### 9. Derived/cached data downstream of the asset-level graph --- the `Affordance::` cache (added 2026-08-12, with OD-2's reversal)
`StandardArea._positionGraph`'s Exit edges are not read directly at runtime; they are projected through `packages/mtw-wml/ts/standardize/projection/projectRoomExits.ts` and `packages/mtw-gateways/ts/assets/components/componentTopology/{assemble,result}.ts` into a **separate, persisted `Affordance::` DynamoDB row** (`lambda/ephemera/dataSource/affordanceCache/hydrateAffordanceTopology.ts`), which is what `roomExitTargetsForCharacter.ts` actually reads --- not the Area's `positionGraph`/`ludicGraph` directly.

**The reassuring half:** `assetDB`'s Area component rows are always rewritten **fresh from the WML source text** on every `cacheAsset` run (`lambda/assets/dataSource/caching/cacheAsset.ts:112-134`, `fileComponent.toJSON()`) --- unlike `Meta::Room`'s play state, there is no "old key lingers, nothing regenerates it" problem here, because the source of truth is the authored text, not previously-stored Dynamo state. This is *lower* risk than item 8's `Meta::Room` case, not the same risk restated --- OD-8's "one clean environment, nothing to lose" argument isn't even needed here; a recache regenerates correctly regardless of what the old row held.

**Resolved by OD-10, traced 2026-08-12: self-correcting, no force-touch needed.** `cacheAsset`'s diff compares the **stored row re-parsed through current code** against a **fresh parse of the WML source text** (not a raw attribute/text diff) --- once the rename lands, a row still under the old `positionGraph` key reconstructs as an *empty* graph under the new parsing code, which is guaranteed to differ from the source-derived populated graph, driving both the rewrite and `TopologyInvalidated`. The only precondition that survives is operational, not logical: `cacheAsset` must actually be invoked per asset for this to run.
