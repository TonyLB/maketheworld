## The mechanism, relocated from the corpus

**Moved here by Slice 0 from the corpus's staged-findings section**, whose own instruction was *"move them out when P7 lands, and delete this section then."* Substituting this plan for P7 keeps that instruction intact. Condensed to what a builder needs; the derivations stay in the corpus's case text. **The move completed 2026-09-13 and that section is now gone** --- [a tombstone](AGENT.abstractionLayers.ludicCache.corpus.planning.md#mechanism-findings--moved-out-2026-09-13) stands in its place, recording where the findings went and, for the Slice 8 sweep, that they must not come back to the corpus when this file is deleted.

1. **Compose at crossing ports, never at nodes.** A merge may collapse two edges sharing a **crossing-port** terminal; never two sharing a **node** terminal. Crossing ports are not referents and nodes are, so composing across a port destroys nothing and composing across a node destroys something a player could have named. **A possible/impossible rule, not a preference.**

   **Its "required primitive" is already shipped, and the hazard it warned of is moot.** The finding demanded a port-aware terminal discriminator, on PQ-9's finding that `isEphemeraObjectId` would *crash* on a `#`-separated port address. Ports are structured values now: `EphemeraLudicPortAddress` is `{ owner, port }`, `EphemeraLudicTerminalId` is a union, `isEphemeraLudicPortAddress` exists, and [`ephemeraMeta.ts`](../../../../../packages/mtw-interfaces/ts/ephemeraMeta.ts) states outright that *the parsed shape IS the stored shape --- no string form*. `mergeReducer.ts` already discriminates this way. **Do not re-import the string-parsing hazard.**
2. **General edge-merge contains edge-stitch, and the argument is not efficiency.** Stitch is merge over a chain of length two. The general form is arguably *less* code --- stitch carries a case split (append a crossing and rewrite the endpoint, versus prepend and rewrite the start) that composition does not, since direction falls out of which terminal is shared. **The narrow form is the same code with an unsettled premise baked in as a restriction.** This is the finding [D1](#open-decisions-implementation--plan-only) turns on.
3. **Entitlement and retention are two questions, and only the first is load-bearing.** *May the reducer consult a graph it has already merged?* --- **yes, settled**, forced by [LC8](AGENT.abstractionLayers.ludicCache.corpus.planning.md#lc8-the-spring-in-the-box-and-in-the-contraption)'s sub-graphing argument. *In memory, or shard ids re-read on demand?* --- same semantics, different cost: [D4](#open-decisions-implementation--plan-only).
4. **Do not drop anything during sub-graphing is rejected, recorded so it is not re-proposed.** It would make the cache self-describing and remove recovery entirely, and it fails for the reason the cache exists: **unbounded size is what the ragged frontier and `interiorConsolidated` are there to control.**
5. **Recovery is a keyed walk, not a scan.** Every terminal that becomes newly present is a trigger; look it up against retained graphs; follow the chain, possibly across several graphs, until it grounds. **Complete because an edge is recoverable only if at least one terminal is now present, and every such terminal is a trigger.** **No index and no new store is needed** --- the port record's egress list supplies the outward half and the interior graph's own edges supply the inward half. What remains is a **lookup discipline**: both halves must be consulted, and neither direction quietly implemented one-way. A one-way walk **silently returns nothing**, which is the failure mode to write a test against rather than to guard. **This is the *both-sides navigability constraint*** --- named here because [the presence corpus's PR-11 option (A)](AGENT.presence.corpus.planning.md) cites it by that name, and because it began life as a demand on [PQ-4](AGENT.abstractionLayers.planning.md) to *build* a field. It is no longer that: the shipped port record already satisfies it from both directions, so what PQ-4 would have owned is discharged and only the consumer discipline survives.
6. **Triggering on newly-present terminals collapses stitching and recovery into one mechanism.** Starting from *edges left dangling in the cache* under-covers, because an edge dropped while **both** terminals were ungrounded leaves no dangling trace. Triggering on **every terminal that becomes representable** covers it --- and extending a cache edge into a host that just consolidated and recovering an edge sub-graphing discarded become the same operation. **This is a simplification only if a terminal is looked up the same way in both stores**; if the cache is searched one way and retained graphs another, the two mechanisms are back wearing one name.

**What the shipped code already does with all of this.** [`collapseCrossingPorts`](../../../../../lambda/ephemera/dataSource/positions/ludicCache/mergeReducer.ts) implements findings 1 and 2 for the **pairwise** case: it composes at crossing ports only, excludes presence ports, asserts both legs agree on identity fields, rewrites the port terminal to the real interior node, and groups by identity so two ports collapsing to the same `(from, to, kind)` land on one record with two `chains` entries side by side. [`subGraphFromNodes`](../../../../../lambda/ephemera/dataSource/positions/ludicGraph/presenceSubGraph.ts) implements the cut, with stub ports minted transiently and never persisted. **Findings 3, 5 and 6 have no code at all** --- they are about the fold across many graphs, which is Slice 3.

### How stub-port ids match --- a property of the construction, not a rule it obeys (recorded 2026-09-14)

**Read the status of this note before using it.** What follows is an **emergent property** of choices made elsewhere, not a design commitment anything is obliged to honour. It is written down because it is **demonstrably hard to reconstruct from the code** --- it took a wrong turn and three corrections to state it in the conversation that produced it --- and because working code now **relies on it as an assumption**. **If the decisions below change and this stops holding, that is a refactor cost, not a design regression**, and nobody should read this note as a veto on revisiting them.

**The property.** A stub port's id comes out **identical from both sides of the cut, computed independently, with neither side seeing the other**. [`subGraphFromNodes`](../../../../../lambda/ephemera/dataSource/positions/ludicGraph/presenceSubGraph.ts) gets there by minting from `stubPortIdFromEdge(edge)` on the edge **before** rewriting, so one bucket (`fromIn`) and the mirror bucket (`toIn`) still produce the same string. **That is the whole matching mechanism:** two buckets discover they hold halves of one edge not by comparing the halves but by both naming the port after the whole.

**What it is downstream of --- the list to check if it ever needs revisiting.** (i) Buckets are cut **independently**, each `subGraphFromNodes` call seeing only its own node set, with no shared state and no coordination; (ii) the id is **purely derived** from the edge's own fields and is **transient, never persisted** (LR-1); (iii) there is **no allocator** --- no central authority assigning port ids that both sides could instead consult. **The property is a consequence of those three together.** Change (i) to union-then-cut --- which [Slice 2b already does for the cross-bucket-same-parent case](#recommended-order) --- and much of the matching problem does not arise, because nothing is severed. Introduce (iii) and side-dependent ids become available. **--- amendment (2026-09-14): the id's shape now has a *second* consumer, and a change to it has to satisfy both.** As of the `STUB-` prefix (see the standing-cleanup entry in [Recommended order](#recommended-order)), a stub id is relied on to be **recognizable as a stub by inspection**, because a minted stub and an authored `EphemeraCrossingPort` are otherwise indistinguishable --- `isCrossingPort` narrows on `kind`, and a stub carries the severed edge's own `kind`. Before this, the only constraint on the id was that both sides derive it identically; now it must *also* be sniffable. **The two constraints are independent and can be broken separately**, so anyone revisiting the list above should check the prefix requirement too --- it is not downstream of (i)--(iii).

**What it rules out *while those choices stand*.** Any id component derived from *which side this bucket is on* breaks matching outright rather than degrading it --- the halves get different ids and never meet. **So a `STUB-${chainId}-${in|out}` scheme does not work here:** a tag that distinguishes the two halves destroys the match, and a tag both sides agree on is a constant that distinguishes nothing. **Proposed and set aside on this ground 2026-09-14 --- conditionally, and the condition is the list above**, not a judgement about the scheme itself.

**A related category distinction, since both mechanisms are called "ports."** Same-host severing splits **one** edge with two real terminals across two buckets of **one** host, and the halves must agree on a minted id --- `stubPortIdFromEdge`'s job. A chain crossing a host boundary is **two** legs in **two** hosts' graphs meeting at an **authored** `EphemeraCrossingPort`, whose `kind` is *"authored at mint time, never derived from an edge."* **`chainId` is a chain identity and belongs to the second; the key `stubPortIdFromEdge` derives is an edge identity serving the first.** ~~Keying one on the other is a category swap in either direction.~~ **--- amendment (2026-09-14, same day): the category distinction stands, the prohibition does not, and `stubPortIdFromEdge` now mints `STUB-${chainId}` when a `chainId` is present.** The two mechanisms really are different, and nothing above is retracted --- but *being different categories* does not make one unusable as a key for the other; it makes it usable only where the coarser identity is **injective at the scope the key must be unique over**. Both halves of that are already recorded in this note and were simply never put together: (1) this note's own chain-shape paragraph records, from the author, that doubling back through one host is neither required nor desirable, hence **at most one leg of a given chain per host** --- so within one cut the chain→leg map is injective; and (2) [the `stubPortIdFromEdge` rename entry](#recommended-order) establishes that the requirement is uniqueness **among stub ports in this cut**, not global uniqueness --- *"nobody asks whether a stub port id is globally unique."* At that scope the chain names the leg unambiguously. **What the amendment does not do is make this an invariant:** it is admissible *because of* an unenforced property of construction, which is this note's whole subject. **So the violation is now made loud rather than trusted** --- `subGraphFromNodes` throws on two stubs minting one id in a single cut, because the failure would otherwise be silent (`fromFieldPayload` copies `ports` without deduping, unlike `addPort`, and the merge resolves legs with `.find`, so the second crossing would simply vanish). **Distinguish this from the scheme still rejected above:** that one was `STUB-${chainId}-${in|out}`, and the fatal component was the **side tag**, not the `chainId`. This scheme carries no side tag.

**Chain shape, from the author (2026-09-14), recorded as design input rather than as verified behaviour --- nothing mints a `chainId` yet.** A chain is *"the graph equivalent of a bezier-curve specification: two end-points, and a third *pick some points to route through* specification."* A chain-qualified leg within one host is one of three shapes: (a) it connects two **internal** terminals; (b) it connects an internal terminal to a **port on the host's boundary**; (c) it runs **port-to-port**, where a multi-present host is a useful mediating path between otherwise very distant nodes (a *Computer System* abstraction carrying network connections). **And doubling back --- routing through one host twice --- is neither required nor desirable**, which yields the uniqueness property the rejected scheme was reaching for: **at most one leg of a given chain per host.**

**Each shape meets the cut differently, and (c) is the one to check before relying on any of this.** (a) is severed normally and mints a stub --- **so chain-bearing edges do reach the stub path**, and `chainId`'s presence in the key is *not* vestigial. (b) is skipped by [the already-port-qualified branch](../../../../../lambda/ephemera/dataSource/positions/ludicGraph/presenceSubGraph.ts) --- *"nothing is minted, since that port's home graph is the other side"* --- and passes through whole. **(c) has no clearly-correct handling in the shipped cut:** `fromIn`/`toIn` test `ephemeraLudicTerminalOwner`, which returns `.owner` for a port address, so a port-to-port leg's membership turns on whether the host's own id is in the bucket's node set --- and the node set always contains the **root**. **If `hostId` and the root coincide the leg is kept whole in *every* bucket (duplicated); if they do not it is dropped from every bucket (lost).** Neither is obviously right, **this is LC10's shape exactly**, and it should be traced against real data rather than settled from this note. **--- amendment, 2026-09-14: both readings above are superseded by the endpoint-status rule** (see Recommended order). **(b) no longer passes through whole**, and the branch quoted here is gone: its justification --- that a port-qualified far endpoint means the far node belongs to a different graph --- was false, since a node of *this* graph can name a port on its own interior, and PR-C2 had already settled that a cross-host edge is two edges rather than one. **(c) is no longer contingent on whether `hostId` and the root coincide:** both are neutral by rule, so the leg is kept in every bucket deliberately. **The sentence to keep is the conditional one** --- under the old code (c) survived *only* because the two coincided, which is to say **LC10's shape was being preserved by the very collision that was about to be fixed**, and fixing classification without deciding LC10 would have dropped it silently from every bucket. That is why the three changes are coupled rather than sequential. **LC10 itself is still open.**

**What the shipped code already does about two routes, which decides nothing but narrows the question.** [`collapseCrossingPorts`](../../../../../lambda/ephemera/dataSource/positions/ludicCache/mergeReducer.ts) accumulates a `chains` entry per collapse and then groups by `collapsedEdgeIdentityKey` --- **which includes `chainId`**. So two routes that **share** a `chainId` merge into one record carrying both routes side by side, and two routes with **different** `chainId`s stay as two records. **Both branches of [LC11](AGENT.abstractionLayers.ludicCache.corpus.planning.md#lc11-the-same-contact-reached-two-ways)'s fork are therefore already implemented, selected by `chainId` equality** --- so that case's real question is not *what does the code do* but **whether one relationship reached two ways should be minted with one `chainId` or two**, which is a question about chain minting and has no code to read it off.
