**Status:** Design stage, not started. Seeded 2026-08-05 from conversation. **No code is in scope yet** --- the deliverable of the first several phases is a settled set of answers, recorded here, and only then a vertical slice. **Sibling initiative, deliberately separate:** [`AGENT.objectManipulationIterations.planning.md`](../actions/AGENT.objectManipulationIterations.planning.md) is the standing index for the **parse and reasoning pipeline** (classify -> Parse -> Plan -> Synthesize -> kernel). They interact --- see [Relationship to the object-manipulation ladder](#relationship-to-the-object-manipulation-ladder) --- but a rung on that ladder is the wrong container for a data-structure question that also reaches WML authoring, perception, and diegetic state.

## Why this initiative exists

The shipped position model has exactly one granularity: the human-convenience scale of Object and Character nodes on a host graph, related by peer-to-peer edges (`On`, `Under`, `Against`, `Custom`) within a single host. That model is a fine starting point and is not in question. What is in question is whether it can carry complexity **without becoming unworkable to reason about** --- for an LLM in particular, but the burden is not only the LLM's.

The gap is structural, not ergonomic. **Membership is the only level-crossing relation the model has, and it is flat**: a node is in a host or it is not, with no way to be in it *as part of something*. Every other relation is intra-host by construction --- [`applyStepSequenceCore`](../../../../../lambda/ephemera/dataSource/positions/manipulation/kernel/applyStepSequenceCore.ts) derives a relational step's shared host live and **throws** on mismatch.

**Membership is not, however, single-host at the storage layer** --- a point that was overstated in an earlier draft of this file and is worth stating precisely, since AB-8 turns on it. See [Multi-host presence: what is actually true today](#multi-host-presence-what-is-actually-true-today) below.

So there is no way to say "these five things together are a thing," or "this thing has parts," or "this thing extends across those rooms," except by encoding it in a vocabulary that has no levels in it --- which pushes the level structure into every consumer's head, to be re-derived by inspection each time. That is the burden.

### The four seed examples

These are the origin cases, recorded verbatim in intent because the corpus in Phase 0 is built *from* them and must not lose their variety:

1. **Place setting.** Plate, cup, fork, knife, spoon `On` a table. At some point it should be possible to reason about and display "table with a place setting" rather than six nodes and five edges.
2. **Dismantled flashlight.** Improvise "parts" --- battery, bulb --- at a level *below* the object, on demand.
3. **Powered door.** A door that opens only when power is on, where power is an area-wide fact affected by repairs to a generator elsewhere. Demonstrates that abstractions likely convey **state** as well as position.
4. **Rope through several rooms.** Pulling it is mediated not by an individual room but by an Area or by an abstraction.

### They are probably not one structure

The examples separate along at least three axes, and conflating them is the main design risk this plan exists to manage:

| Axis | Seed examples | Character |
| --- | --- | --- |
| **Composition (part/whole)** | 1, 2 | Level-crossing, rooted, spatially coherent. The two examples are mirror images of **one** relation --- the difference is only which level pre-existed and which was improvised into being. Place setting: members primary, whole minted. Flashlight: whole primary, parts minted. |
| **Functional aggregate carrying state** | 3 | Members deliberately **not** co-located; membership is participation in a system, not containment. Carries state; the state gates behavior elsewhere. |
| **Multi-host extent** | 4 | One thing present across several hosts --- **representable today**, contrary to an earlier draft; see [Multi-host presence](#multi-host-presence-what-is-actually-true-today). Distinguished by needing a **path ordering** among its parts (AB-16), and by making the aggregate a candidate **manipulation host** peer to Room and Character. |

**Do not assume these collapse into one `Abstraction` type, and do not assume they stay separate.** Phase 1 decides it, against the corpus. Everything downstream reads differently depending on the answer, which is exactly why it is the root question.

### Multi-host presence: what is actually true today

Verified against the code 2026-08-05, because the rope case (AB-8) had been written up as breaking a hard invariant, and that is not accurate. **Multi-room object presence is representable today with no schema change.** What stands in the rope's way is narrower and more specific.

| Layer | Reality |
| --- | --- |
| **Adjacency storage** | Natively multi-host. `getMembershipContainers` returns an **array**; adjacency rows are `(OBJECT#, POSITION#ROOM#...)` with nothing unique-constraining them. `MembershipDiff.froms` is plural and [`AGENT.contract.md`](../../../../../lambda/ephemera/dataSource/positions/AGENT.contract.md) explicitly permits `froms.length > 1`. |
| **End-state planner** | **This is the actual single-host pressure.** [`computeEndStateRoomDiff`](../../../../../lambda/ephemera/dataSource/positions/manipulation/adapters/computeEndStateRoomDiff.ts) computes `froms = priorContainers.filter(!== to)`, so ordinary place / spawn / remove scrub every other room as **normal operation**, not as repair. A planner behavior, not an invariant. |
| **Cross-host move route** | Bypasses that planner entirely --- `executeObjectMove` grounds through the Synthesize executor from a host pair. The constraint is therefore **not uniform across routes**. |
| **Kernel step shape** | `MutationKernelTransferStep` has `fromHostIds: ReadonlySet<...>` but a **singular `toHostId`**. There is no add-to-many primitive. Three-room presence needs three pure-add steps or a widened field. |
| **Relational edges** | Strictly intra-host regardless. A rope in room A cannot relate to a bollard in room B under any current shape. |
| **Presentation** | Affordance compose reads `graph.objectIds` per room, so a multi-room rope renders as a **whole object in each room** with no notion of partial presence. Likely the first thing a player would notice. |
| **Drift repair** | [`repairObjectPlacementDrift`](../../../../../lambda/ephemera/dataSource/positions/membership/repairObjectPlacementDrift.ts) **has no production caller** --- only its own test. The `Object Placement Drift Finding` sweep that would feed it is deferred and does not exist in [`lambda/diagnostics/`](../../../../../lambda/diagnostics/). Nothing is eliminating multi-room presence at runtime. |

**A three-way disagreement to resolve deliberately, not silently.** The durable docs currently assert the opposite of the intended design: [`AGENT.contract.md`](../../../../../lambda/ephemera/dataSource/positions/AGENT.contract.md) says "**Steady state:** at most one room per `OBJECT#`; multi-room adjacency is drift," and [`AGENT.concepts.md`](../../../../../lambda/ephemera/dataSource/positions/AGENT.concepts.md) says "Objects follow the same steady-state rule (nodes only)." The code permits multi-host; the stated design (2026-08-05) is that a rope should eventually be present in several rooms. Either the clause was scoped to **characters** and over-generalized to objects when object membership shipped, or the design moved and the docs did not. **Fix the docs as part of Phase 1**, whichever way it resolves --- an unwired repairer plus a contract clause forbidding what the design intends is exactly the kind of stale normative text that gets obeyed by a future reader who has no reason to doubt it.

### Improvisation is the objects lane's mechanism, generalized

Settled 2026-08-05, and it changes what several rows cost. **`ASSET#IMPROVISATION` is not a flag on a special kind of object --- it is an asset layer in the participation stack.** Improvised bodies merge through composite `ComponentData` like any other layer, and spawn-time `DEFAULT` situation prose deliberately routes objects through the **same** `ensureAuthoredCatalog` render path Feature / Knowledge / Character use rather than a bespoke stub. So the mechanism's actual purpose is already the general one this initiative needs: **mint a component nobody authored, such that nothing downstream can tell the difference.** What it lacked was a name for that purpose. Full detail: [`objects/AGENT.md`](../../../../../lambda/ephemera/dataSource/objects/AGENT.md).

**What arrives already built:** the four-way split (merge body / play meta / semantic embedding / placement), a two-step existence-then-placement sequence, the **S1** compensating delete, the orphan sweep and its delete-only repair, and a best-effort **LLM-in-the-loop discipline** (Bedrock embeddings and enrich-generated prose, both failure-tolerant and non-blocking) that AB-18's cost and latency policy should start from rather than re-derive.

**This sharpens AB-12 from a philosophical question into a cost question.** If Objects are already abstractions at every level, minting a battery or a place setting **is** minting an `OBJECT#` --- the lane needs no generalization at all, only use. The Room / Feature half is different in kind: every row key, module, and type in that lane is `OBJECT#`-shaped. The two bets therefore differ by roughly *no new storage* versus *a new storage shape*, which is far more decidable than the ontology argument.

**Three gaps, all bounded, all real:**

| Gap | Detail |
| --- | --- |
| **No composition relation** | Improvisation mints a **free-standing** object and places it in a room. A *part* needs the level-crossing edge as well --- so spawn+place becomes spawn+place+compose, or the compose **is** the place if AB-4 resolves part-of as a host relationship. Either way the S1 compensating-delete story needs revisiting, since it currently compensates a two-step sequence. |
| **Recognition fits less cleanly than Improvisation** | Improvisation creates a thing from nothing, so its existence rows are the whole story. Recognition creates an aggregate **over things that already exist**: its body is nearly empty and its **member set is the content**. The lane has no concept of a component whose identity is a set of other components. |
| **`EMBEDDING#IMPROMPTU` is `shortName`-derived** | Reasonable for a battery, questionable for "the place setting on the table." Whether an aggregate gets a semantic vector, and over what text, is undecided. |

**Naming consequence --- carried as AB-0's concrete form.** If Improvisation names the *mechanism*, then Improvisation and Recognition are **not peers**: Recognition is a trigger that invokes the mechanism, and operational necessity is the other trigger. The word is currently doing both jobs, which is the same conflation AB-14 was restructured to remove. Two ways out, unresolved: **(a)** Improvisation and Recognition stay the two triggers and the shared mechanism takes its own name; **(b)** Improvisation names the mechanism and the downward trigger is renamed.

**One speculative consequence worth keeping.** Because `ASSET#IMPROVISATION` is a *layer*, an improvised thing can later be **authored over**. A recognized snare trap could graduate into canon --- a real partial answer to AB-19's cost objection that an authored pattern vocabulary limits players to what someone anticipated.

### Coyote as prior art: bounded LLM reasoning that is not bounded structurally

Identified 2026-08-05 as the **existing first-iteration attempt** at reasoning about player-assembled contraptions --- deliberately flawed and ad hoc, and the closest thing to a working answer for AB-19. Read [`coyoteGame/AGENT.md`](../../../../../lambda/ephemera/dataSource/coyoteGame/AGENT.md), [`coyoteGame/AGENT.tropes.md`](../../../../../lambda/ephemera/dataSource/coyoteGame/AGENT.tropes.md), and [`coyotePlanAffinities.ts`](../../../../../packages/mtw-interfaces/ts/coyotePlanAffinities.ts) before designing anything in this area.

**What it does, structurally:** a `CoyoteStagedObject` snapshot assembled from `positionGraph` + `Meta::Object` + the improvisation pair, grouped by room; each object carrying `tropeAffinities` (roles with graded `aptness`, plus `environmentAffordances` / `affordancesProvided`) written at **Acme enrich time**; then a multi-hop LLM pipeline (candidates -> planSelect -> narrativeBeats -> outcome) with structured parse between hops and an internal-only `gimmick` narrative spine.

**What generalizes --- keep these:**

| Pattern | Why it matters here |
| --- | --- |
| **Annotate at mint time, not at reasoning time** | One Bedrock call at object creation writes durable structure; the reasoning step then *consumes* it. This is the direct answer to AB-18's cost concern and the reason AB-22 exists. |
| **Closed structural vocabulary, open narrative content** | Roles and tropes are enumerable; `gimmick` is deliberately free text with no closed enum. Matches the standing rule that only genuinely enumerable vocabulary should be hardcoded. |
| **Graded `aptness`, not booleans** | Affordance is a matter of degree, and downstream hops can rank rather than filter. |
| **Multi-hop with structured parse between hops** | Each hop's output is validated JSON, so a later hop reasons over structure rather than prose. |
| **Internal-only reasoning handoff** | `gimmick` never reaches the client. Reasoning scaffolding and player-facing narration are separate artifacts. |

**What is ad hoc --- and it is precisely the gap this initiative would fill:**

- **There is no persistent assembly-level object anywhere in it.** Every prediction reconstructs "what did the player build" from a **flat bag** of staged objects plus per-object role affinities. The contraption is never a thing.
- **Context is scoped to rooms, not to the contraption** (`loadCoyoteRoomObjectsByRoom`, across all Coyote game rooms). The LLM receives everything staged, relevant or not.
- **Therefore its boundedness is circumstantial, not structural.** It comes from the world being tiny and the genre closed --- six tropes, a hardcoded `boulder | cactus | ...` affordance enum, a handful of rooms. Remove any of those and nothing bounds the context.
- **The seam-label hack** (prompt labels vs. canonical `EphemeraRoomId`, an explicitly one-way contract carrying a six-item warning list about reversing it) reads as a symptom of the same cause: prompt context assembled ad hoc rather than projected from a real structure.

**The load-bearing conclusion:** an abstraction layer would supply the boundedness **structurally** --- the contraption is a named subgraph, and that subgraph *is* the context. Coyote answers the annotation question per-object and the scope question per-room; the missing piece is per-**assembly**.

### `thinking` as the scheduling substrate: shipped ledger, unbuilt queue

Identified 2026-08-05 as the intended home for deferred recognition, and **verified against code** because the distinction between what exists and what does not is load-bearing. Read [`thinking/AGENT.md`](../../../../../lambda/ephemera/dataSource/thinking/AGENT.md).

**Shipped and reusable:** durable `Meta::Schedule` rows on a `TASK#${workItemId}` partition, a status vocabulary of `scheduled | claimed | cancelled | completed`, job bootstrap and adjacency, rollup to `Job Completed`, client dashboards, and `fetchThinkingResult` lookup by `workItemId`. The retention policy already anticipates this exact use: **"in-flight rows --- `scheduled` / `claimed` schedules ... do not set `deleteAt`, so *opportunistically queued work* is not TTL'd while waiting."**

**Not shipped --- and this is the actual work:** **nothing writes `claimed`.** Only `scheduled`, `completed`, and `cancelled` have producers; `claimed` appears in the type union and in `persistThinkingJobError`'s `IN_FLIGHT_SCHEDULE_STATUSES` for cancellation, with **no claimer anywhere**. Every thinking job today is bootstrapped at the start of a synchronous pipeline (Coyote hypothesis, Acme enrich) and completed within that same Lambda invocation. **The schedule rows are observability records of work already happening, not a queue anything pulls from.** A worker, deferred dispatch, and promotion-on-demand all remain to be built.

**One guarantee that comes free, and it closes AB-18's convergence requirement.** `Meta::Result` is written with `ephemeraDB.nonCollidingPutItem` --- conditional on `attribute_not_exists`, **first write wins**, duplicate finalize returns `alreadyFinalized`. That is exactly what "the deferred pass and the promoted foreground path must not produce two snares" needs, already shipped and already retry-safe. Two independently-derived requirements (AB-18's convergence, and promotion-on-demand from the thinking side) landing on one existing mechanism is evidence the framing is sound.

## What already exists to build on

Read these before answering anything. Several are not background --- they are hooks the codebase has *already pre-registered* for this work, and re-deriving them from scratch would waste the design effort that put them there.

1. **The rooted-graph trigger, already written down.** [`positionGraph/AGENT.md` --- Known limitation (deferred)](../../../../../lambda/ephemera/dataSource/positions/positionGraph/AGENT.md#known-limitation-deferred) records that `EphemeraPositionGraph` is host-bound and unrooted, that [`CarryClosureFragment`](../../../../../lambda/ephemera/dataSource/positions/positionGraph/expandValidate/interactionUnderTransfer.ts) --- `{ rootId, members, edges }` --- is "a rooted position graph in all but name," and that **if a root concept ever arrives, the fragment should collapse into it rather than persist as parallel duplication.** A composition abstraction is a named, persistent carry closure. That note is pinned in two places specifically so whoever adds a root here finds it. This is the single strongest existing anchor for axis 1.
   - One constraint travels with it: **`rootId` is recorded, never derived.** `computeCarryClosure` takes it from its `startId` argument because the BFS guards with `closureSet.has(...)`, so the traversal *tree* is order-dependent while the induced edge set is not. Any root concept must be an input.
2. **Object-as-host, already deferred rather than rejected.** [`AGENT.concepts.md` --- Fractal position graphs](../../../../../lambda/ephemera/dataSource/positions/AGENT.concepts.md#fractal-position-graphs-container-scale-and-edges) states container scale shipped for Character hosts (D16) with "**Object `OBJECT#` / Area hosts deferred until needed**." Nesting is precisely the case that makes them needed. `EphemeraMembershipHostId` is Room | Character today.
3. **Improvisation as the minting precedent.** The objects lane already brings things into existence on demand, with a two-step existence-then-placement sequence, a compensating delete, and a diagnostics orphan sweep: [`objects/AGENT.md`](../../../../../lambda/ephemera/dataSource/objects/AGENT.md), and the contract's [Object room membership](../../../../../lambda/ephemera/dataSource/positions/AGENT.contract.md#object-room-membership-nodes-only) section. Axis 1's minting question (Phase 3) should start from this shape, not invent one.
4. **Graph roles: same shape, different authority.** [`AGENT.concepts.md` --- Graph roles](../../../../../lambda/ephemera/dataSource/positions/AGENT.concepts.md#graph-roles-shared-shape-different-authority) separates authored blueprint / play manipulation / materialized presentation / ephemeral presentation for the *same* `{ nodes, edges }` shape. That table exists because conflating them cost something before. An `Abstraction` will face the same fourfold question and should be answered with the same discipline.
5. **Trim-to-valid as the decay precedent.** The eviction ladder ([`AGENT.concepts.md` --- Eviction ladder](../../../../../lambda/ephemera/dataSource/positions/AGENT.concepts.md#eviction-ladder)) answers "what survives when the world changes underneath a stored structure" by filtering to what is still valid, reading the top survivor, and **calling it a change only when the resolved answer differs**. AB-6 is structurally the same question.
6. **Projections are filters, not the graph.** Same concepts doc, core vocabulary. AB-9 leans hard on this: if level-selection is a projection concern, a large fraction of the LLM-scalability payoff lands in the presentation lane and never becomes stored truth.
7. **The step vocabulary an abstraction would have to join.** [`manipulation/AGENT.implementation.md` --- Step vocabulary](../../../../../lambda/ephemera/dataSource/positions/manipulation/AGENT.implementation.md#step-vocabulary) and the Synthesize executor's instruction language. AB-11 asks whether abstractions are new *operands* in that language or need new *step kinds*; the answer determines whether the kernel changes at all.
8. **Where state does *not* currently live.** There is no `Variable` / `Computed` in WML today, and `dataSource/state/` is asset-stack resolution, not diegetic state. AB-7 may therefore be filling a genuinely vacant slot rather than extending an existing one --- verify this before designing against it, and check [`diegeticLogic/AGENT.md`](../../../../../lambda/ephemera/dataSource/diegeticLogic/AGENT.md) for prior operator-design thinking.

**Testing authority:** [`lambda/ephemera/AGENT.testing.md`](../../../../../lambda/ephemera/AGENT.testing.md) --- `npm run test`, not `npm test`, run from `lambda/ephemera`. There is no `taskPlanning/lambda/ephemera/AGENT.development.md`.

**Hazard, inherited and repeatedly re-learned:** `*.integration.test.ts` files sit **outside** the tsconfig include and mock modules **by path**, so `npx tsc --noEmit` cannot catch a break in them. Run the full jest suite after any rename or deletion, and grep module *paths*, not only symbols.

Baseline (should pass before any edits, from `lambda/ephemera`):


**Three scheduling tiers (AB-14, AB-18, AB-24), each parameterizing the one above it:**

| Tier | Immediacy | Job |
| --- | --- | --- |
| **On-demand mint** | Blocking --- a pending operation cannot proceed | The referent must ground *now* |
| **Recognition** | Deferred, but promotable on demand | Did an arrangement compose into something? |
| **Context shift** | Low, ambient | Should we be watching for *different kinds* of meaning? |

**AB-14 is the lifecycle cluster's spine.** One mechanism --- improvisation --- invoked in two modes divided by **criticality**: on-demand (a pending operation is blocked) and recognition (nothing is blocked). ## Discussion record

Reasoning trail behind the Open-decisions rows, kept for provenance. Not needed to know what to do next --- only *why* the questions are shaped the way they are, and what a future reader would otherwise have to re-derive. Following the pattern of [`AGENT.backtrackChannel.planning.md`](../actions/AGENT.backtrackChannel.planning.md)'s History section.

**Seeded 2026-08-05 from conversation.** The initiative began from a scalability observation: the current treatment of objects is a fine starting point, but complex manipulation on top of it would become unworkably burdensome to reason about --- for an LLM in particular. The proposed answer was aggregations reasoned about in summary, at levels both above and below the human-convenience scale of objects. Four seed examples were given (place setting, dismantled flashlight, powered door, rope through several rooms) and are recorded above.

**The examples were immediately suspected of not being one structure.** Three axes were separated on first pass --- composition, functional aggregate carrying state, multi-host extent --- and AB-1 exists because collapsing them prematurely, or keeping them separate unnecessarily, are equally live failure modes. Notably, the place setting and the flashlight are **mirror images of one relation**, differing only in which level pre-existed and which was improvised: the place setting's members are primary and the whole is minted, the flashlight's whole is primary and the parts are minted.

**A factual correction, 2026-08-05.** An earlier draft asserted that multi-host presence "breaks the at-most-one-host invariant" and that `repairObjectPlacementDrift` "exists to eliminate it." Both were overstated; the verified position is now in [Multi-host presence](#multi-host-presence-what-is-actually-true-today). The correction materially changed AB-8: framing (a) is far cheaper than it first appeared, so extent's cost is dominated by the modelling choice rather than by any storage obstacle.

**The granularity insight, 2026-08-05 --- the pivot the rest of the design turns on.** A rope coiled in a backpack is a plain object: no sub-part is separately addressable, and pulling it from the pack yields the whole coil by default. Lowered into an abyss, room-level atomicity breaks down and the ends become distinct loci. **The rope did not change; the useful granularity did.** That yields a candidate criterion --- decompose when parts become independently addressable or independently positioned --- which runs *symmetrically* in both directions: the place setting aggregates because its members stopped being separately interesting, the rope decomposes because its parts started being. Evidence that aggregation and decomposition are one axis rather than two mechanisms.

**Consequences drawn the same day.** (i) The transition must run backwards --- re-coiling the rope must restore one object --- which the flashlight example hides and which makes reabsorption mandatory rather than optional (AB-17). (ii) Rope parts are unlike flashlight parts: homogeneous slices of an *ordered* continuum versus heterogeneous separable things, with the ordering load-bearing for `pull` (AB-16). This weakened an earlier claim in this plan that AB-8's segment framing cheaply collapses into AB-4. (iii) Tying the rope to a rock puts a relation on an *end*, not the whole --- which under a single multi-room node leaves the relational step's host ambiguous, and under segments is cleanly same-host. Evidence for segments, arrived at from the relational side rather than the positional one.

**The reframe, 2026-08-05 --- AB-12.** Asking *which* things can be promoted led to the observation that `<Object>`, `<Room>`, and `<Feature>` are **already abstractions**: a battery is an object, so is the flashlight it is part of, so is the casing that is part of that. There is no natural floor or ceiling, so pinning `<Object>` as a privileged origin with `<Part>` below and `<Abstraction>` above is not philosophically sound --- it would build two hierarchies for one relation. **The question may therefore not be "what is this strange `Abstraction` type" but "how do we mint and reabsorb Objects at different levels of abstraction, as they are needed."** Recorded as a candidate, deliberately not adopted: deciding is premature and there is useful discussion left.

Two objections were raised against the reframe and are carried as their own rows rather than resolved. **AB-13:** "levels" invites a scalar, but composition has overlap and multiple parents, so the shape is a partial order, not a ladder. **AB-12's own second half:** Room is a *host*, not a node, so extending the reframe to Room and Feature unifies hosts with nodes --- AB-2's most radical answer --- and contradicts the documented decision that Features are deliberately narrower participants. It would, in exchange, *explain* that narrowing rather than assert it (a part cannot be membership-moved away from its whole without an act of decomposition). Object and Room/Feature are to be weighed as separable bets.

**Two further candidate answers recorded, not adopted.** *Minting triggers (AB-14):* operational necessity and attention are unlike needs, and keeping them separate --- operations mint durably, attention selects a projection level and mints nothing --- would prevent description-time LLM inference from becoming a write path. *Authoring (AB-15):* if no level is ontologically privileged, an authored `<Object>` is plausibly the **default binding level** for unqualified reference, revisable by circumstance, which preserves a real role for authoring without pinning the ontology.

**AB-14 reshaped, 2026-08-05 --- Improvisation and Recognition.** The row's first framing (operational necessity vs. attention) was superseded on the observation that **attention is not a minting trigger at all** --- it was a projection concern in a trigger's clothing, and the row therefore described one minting operation plus a note about description. The replacement pair, motivated by the necessity of narration and the structure of the knowledge-representation system, is two genuine operations, both write-side and both consequences of player action: **Improvisation** invents detail an in-flight operation requires but nobody has authored (the flashlight's interior under a screwdriver), and **Recognition** notices that a player's arrangement has composed into something above the level they were working at (the snare trap). The displaced guardrail --- description selects among existing levels and never creates one --- moved to AB-9, where it belongs and where it is more legible as scope control.

The narration obligations were what distinguished the two most sharply. Improvisation's narration **is** the minting event: the battery and the corroded bulb come into existence for the player by being described. Recognition's narration is a **contract with the player**: it is how they learn the world has accepted their construction as meaningful, and without it a player cannot tell whether a clever arrangement counts for anything and will re-attempt it looking for magic phrasing. This is the argument that Recognition can never be a silent internal summarization pass, and it is why AB-19 (description vs. mechanism) is a real fork rather than a shading.

**Two asymmetries recorded the same day, both loading onto Recognition** (AB-18): Improvisation is *bounded by its operation* while Recognition is an unbounded search over arrangements possibly separated in time; and a wrong Improvisation is cheap (plausible detail for a player who asked for detail) while a wrong Recognition changes what exists and what is subsequently legal. The candidate that would resolve much of both at once --- restricting recognition-for-mechanism to an **authored pattern vocabulary** --- is recorded on AB-19, along with its cost: players could then only construct what someone anticipated.

**AB-14 refined again, 2026-08-05 --- the pair was marking a real distinction but naming it wrongly.** The *action* is improvisation in **both** cases: a sufficiently confident recognition of cups, plates and flatware mints a `Table Setting` component of which the others become parts, which is the same act as minting a north wall. What actually differs is **when the mint must happen, and that is downstream of whether a pending operation is blocked on it.** "Lean the table against the north wall" cannot resolve until the referent grounds --- synchronous, on the command's critical path. A loop of rope laid on a road may be understood as a snare immediately, thirty seconds later, or never, with no material loss of responsiveness. **Same persistence layer, potentially very different decision processes** --- which the previous session's finding independently supports, since `ASSET#IMPROVISATION` is a merge layer and therefore renders provenance invisible downstream.

**Timing is the symptom; criticality is the axis.** Preferring the second framing is not pedantry --- it predicts three things the timing framing does not, each now carried as its own row. **(AB-20, failure semantics):** an on-demand mint is a correctness obligation whose failure fails the command, while recognition is discretionary enrichment whose failure owes nobody anything --- and both disciplines already ship side by side in the objects lane. **(AB-20, authorization):** on-demand minting needs no confidence gate because *the player's reference licenses the existence*, whereas recognition volunteers an unprompted claim --- so AB-18's false-positive cost follows from authorization rather than being an arbitrary policy asymmetry. **(AB-18, convergence):** the mode is a property of the moment, not the thing --- "check the snare" puts recognition on the critical path, so one mint is reachable from both a blocking and a deferred path and the two must converge.

**AB-19 reframed, 2026-08-05 --- the abstraction bounds the LLM step, it does not replace it.** The row's earlier proposal (recognition-for-mechanism made tractable by an **authored pattern vocabulary with behavior attached**) is rejected on the grounds that it compiles fictional physics into a deterministic structural context. That is the wrong tool --- we are not doing physics simulation, and it is not what the fiction is about anyway --- and deriving a snare's result from first principles on every interaction is a fool's errand regardless. **Most player-assembled contraptions will require an LLM step to reason about consequences; the design goal is to give that step the right information so it is bounded and manageable.**

Description and mechanism therefore separate by **stakes, not machinery**: recognizing a place setting is a pleasant first pass over cogitation with no causally complicated consequences, and stays pure projection under AB-9's guardrail; recognizing a snare *functionally*, and reasoning about its function in the abstract, is **essential**. This is a cleaner allocation than the previous framing, and it lets AB-9's no-creation rule stand rather than straining it --- description never mints, mechanism mints because something must reason over the result.

**Coyote named as the existing first-iteration attempt at exactly this** --- flawed and ad hoc by its own author's description, and worth reading before designing. The generalizable core (annotate at mint time; closed structural vocabulary with open narrative content; graded aptness; multi-hop structured parse; internal-only reasoning handoff) and the specific ad-hoc parts (no assembly-level object at all, room-scoped rather than contraption-scoped context, boundedness that comes from a tiny world and a closed genre rather than from structure) are written up in [Coyote as prior art](#coyote-as-prior-art-bounded-llm-reasoning-that-is-not-bounded-structurally). Two rows came out of it: **AB-19** re-aimed at "what must an abstraction carry to bound an LLM step," and **AB-22** on annotation timing and vocabulary --- including the observation that member affinities are a cheap filter for *whether an arrangement is worth recognizing at all*, which attacks AB-18's unbounded search without needing a pattern library.

**Scheduling substrate and situational meaning, 2026-08-05 (two findings from one exchange).** First, `mtw.ephemera.thinking` was named as the intended home for deferred recognition --- its future possibility of work "queued for consideration as time allows, but foregrounded by necessity if the results suddenly become needed" is exactly what tier 2 requires. Verification found the **persistence and vocabulary shipped and the execution model absent** (no `claimed` producer, no claimer, every job bootstrapped and completed in one synchronous invocation), plus one free win: `Meta::Result`'s `nonCollidingPutItem` first-write-wins already satisfies AB-18's convergence requirement. Detail: [`thinking` as the scheduling substrate](#thinking-as-the-scheduling-substrate-shipped-ledger-unbuilt-queue).

Second, and more consequential: **AB-22's vocabulary question was posed statically and should not have been.** "Is the vocabulary general, or authored per world?" has no good answer because relevant meaning is **situational and varies within a world** --- ambushed by goblins, meaning is combat-relative; dining at the Faerie Court, the place setting's causal complexity becomes very real. Coyote shortcuts this legitimately, as an early iteration should, because its genre supplies a constant interpretive context. Two consequences: mint-time annotation can only be a partial answer (durable base plus situational overlay), and the member-affinity *filter* is itself context-dependent. Recorded as **AB-23**, with **AB-24** for the proposed low-immediacy scheduled task that watches for frame shifts and parameterizes recognition. Note the second deliberately-deferred axis this conversation has landed on: the render cache's `n` / mark-state axis is **built and unpopulated** (`markState` pinned to `[]`, `SITUATION#DEFAULT` only, per iteration 10), and situational *meaning* is that same axis raised from rendering to interpretation.

**And a complication surfaced by the wall itself (AB-21).** The north wall may not be *invented*: a room has walls whether or not anyone wrote them down, exactly as the flashlight always had a battery. Materializing something always implied is different from conjuring something new, and it carries an **identity obligation** --- two references to "the north wall" in one room must yield the same wall, across Lambda cold starts included, or repeated reference silently multiplies the world. `stableKey` on `Meta::Object` already solves this shape of problem for Coyote correlation and is the obvious hook. Recognition largely escapes this obligation; on-demand minting cannot.

**Naming check resolved, 2026-08-05: it is the objects lane's mechanism, raised from ad-hoc handling of one kind of thing into a general mechanism named for its purpose.** Verified against [`objects/AGENT.md`](../../../../../lambda/ephemera/dataSource/objects/AGENT.md), and the confirmation was stronger than the question assumed: `ASSET#IMPROVISATION` is an **asset layer in the participation stack**, not a flag on a special object kind, so improvised components already merge and render exactly as authored ones do. The general purpose was therefore already implemented and merely unnamed. Consequences --- what arrives pre-built, the sharpening of AB-12 into a cost question, three bounded gaps, and the naming fork now carried on AB-0 --- are in [Improvisation is the objects lane's mechanism, generalized](#improvisation-is-the-objects-lanes-mechanism-generalized) rather than here, because that content outlives this record.

**Settled, 2026-08-05:** extents spanning hosts of different kinds (two adventurers holding opposite ends of a rope in different rooms) is not a concern.

**Still open from this conversation, not yet a row:** whether born-spanning things (a river, a cable run) mean changeable granularity is a property some things have rather than a lifecycle everything passes through. Folded into the Phase 0 corpus rather than given an AB row, because the corpus should answer it directly.
