# ludicCache persistence: store the room cache, rebuild on stale read

**Status: first draft, 2026-10-13. Not started.** Next step: [Slice 0](#recommended-order) (verify premises), after the [open decisions](#open-decisions-implementation--plan-only) are confirmed. Branch `iss8265-design-ludic-cache-persistence`.

**Scope in one sentence: persist each room's `ludicCache` structure in its own row, mark it stale from the one place graphs are written, rebuild it when a read finds it stale, and give a referent miss a real fallback --- so a consumer pays the ~316ms rebuild once per change instead of once per read.**

This is a standard implementation plan under [`taskPlanning/AGENT.md`](../../../../AGENT.md). It takes over Slices 6--7 of [`AGENT.ludicCacheRebuild.planning.md`](AGENT.ludicCacheRebuild.planning.md), whose remaining work was design rather than implementation; that plan's open rows were settled 2026-10-13 and are restated [below](#inherited-decisions-settled-before-this-plan-opened) so this file does not depend on it.

## Getting Started

1. **[`positions/AGENT.ludicNetwork.md`](../../../../../lambda/ephemera/dataSource/positions/AGENT.ludicNetwork.md), sections 1, 4 and 5.** Sharding, presence as a cover, and what the cache stitches. Section 5 is the cache.
2. **[P6's five clauses](AGENT.abstractionLayers.proposals.planning.md#the-five-clauses)** --- what `ludicCache` is for. Three of them constrain this plan directly: **clause 3** (a hit returns a handle, never a subgraph), **clause 4** (a miss is never an answer of "no" --- this is why [Slice 4](#recommended-order) exists), **clause 5** (derived, never authoritative, droppable at any time). **Clause 4 covers misses only:** a stale *positive* (an object still placed where it was) produces a wrong refusal, not a slow answer, which is why [LCP-3](#open-decisions-implementation--plan-only) marks staleness inside the commit's transaction.
3. **The code being persisted.** [`ludicCache/fold.ts`](../../../../../lambda/ephemera/dataSource/positions/ludicCache/fold.ts) (`buildLudicCache`), [`ludicCache/types.ts`](../../../../../lambda/ephemera/dataSource/positions/ludicCache/types.ts) (the shape), and the two consumers: [`catalogHandles.ts`](../../../../../lambda/ephemera/dataSource/positions/ludicCache/catalogHandles.ts) (command referent pool, via [`roomObjectCatalogForCharacter.ts`](../../../../../lambda/ephemera/dataSource/actions/roomObjectCatalogForCharacter.ts)) and [`roomObjectContents.ts`](../../../../../lambda/ephemera/dataSource/positions/ludicCache/roomObjectContents.ts) (room affordance header, via `internalCache.AffordanceRoomDeliverable`). **Both seed at a room**, and both read only nodes: `shortName`, `gloss`, and each binding's `cover.members`. Nothing reads `edges`.
4. **The kernel's post-commit bundle** --- [`positions/AGENT.contract.md` --- Membership-changed bundle](../../../../../lambda/ephemera/dataSource/positions/AGENT.contract.md#membership-changed-bundle) and `seedGraphMemos` in [`commitStepSequence.ts`](../../../../../lambda/ephemera/dataSource/positions/manipulation/kernel/commitStepSequence.ts). Every play-time graph write converges there; [Slice 3](#recommended-order) puts the stale-marking in its transaction (via the `MultiKeyUpdate` cascade in [`transact.ts`](../../../../../packages/mtw-utilities/ts/dynamoDB/mixins/transact.ts)) and adds a `Ludic Cache Invalidated` fact after it.
5. **The precedent for a stored, versioned cache row** --- [`affordanceCache/AGENT.md` --- Row shape](../../../../../lambda/ephemera/dataSource/affordanceCache/AGENT.md#row-shape-d33) and [`affordanceCache/catalogRow.ts`](../../../../../lambda/ephemera/dataSource/affordanceCache/catalogRow.ts): `catalogVersion` / `hydratedCatalogVersion`, a bump on invalidation, a conditional "mark hydrated only if the version did not move" write (H6). This plan follows it, with one difference recorded in [LCP-2](#open-decisions-implementation--plan-only).

## Inherited decisions (settled before this plan opened)

Decided 2026-10-13 in `AGENT.ludicCacheRebuild.planning.md` (rows D4, D5, D9; D8 and D11 retired). Restated here because that file closes in [Slice 0](#recommended-order).

- **Cache edges are plain leg-shaped `EphemeraLudicRelationalEdgeData`**, collapsed at internal crossing ports exactly as `collapseCrossingPorts` already does, terminating at a real node or at a port on the cache's boundary. **`supportedBy` is removed.** It was maintenance state (which bindings justify a composed edge) riding on a reasoning-facing record; once `legsAgree` settled that a chain's legs are one relation of one kind, the two concerns separated cleanly.
- **This iteration is rebuild-on-stale-read.** Maintenance is a version marker plus a re-read of the shards; **nothing is stored per edge or per node to support incremental repair.** A later incremental iteration builds its own maintenance structure **beside** the cache, never inside the reasoning record. The prior design for one (D8's OR/AND/OR support structure, D11's support-removal/cull pairing) is shelved in [`positions/AGENT.implementation.md`](../../../../../lambda/ephemera/dataSource/positions/AGENT.implementation.md) by Slice 0.
- **Retention:** shards are re-read by id through `internalCache.Positions`, whose per-invocation memo is the in-memory retention. No copies of source graphs are ever stored with the cache.
- **Record key:** `EphemeraId: <roomId>`, `DataCategory: 'LudicCache::'`, one row per room. A second tenant gets a suffix after the `::`, as `Affordance::<perspectiveKey>` does.
- **The rebuild stays a pure function plus thin handlers** (old D6): consumers get handles, never `EphemeraLudicCacheData`.

## What is deliberately out of scope

- **Incremental update.** See above. A stale cache is rebuilt whole.
- **Caches seeded anywhere but a room.** Both consumers seed at a room. A non-room seed keeps today's per-request rebuild, unpersisted.
- **Attention scoping.** The cache stays exhaustive in nodes, so stale-marking walks every depth (forwarded obligations already sit in [`AGENT.attentionHistory.planning.md`](AGENT.attentionHistory.planning.md)).
- **The affordance consumer's refresh behaviour.** Who re-renders a room header when its cache goes stale is [`AGENT.affordanceLudicCache.planning.md`](../affordanceOrchestration/AGENT.affordanceLudicCache.planning.md)'s Slice 3; see [LCP-3](#open-decisions-implementation--plan-only) for the coordination.

| **LCP-1** | **Do names go in the stored row, and against which stack?** `buildLudicCache(seed, assetStack)` today resolves each node's `shortName`/`gloss` against the **viewer's** perspective stack, which would make a stored cache per-perspective and break D5's one row per room. **Decided 2026-10-13, with the author: names stored in the row, resolved against the room's Canon stack plus Improvisation.** Reasoning names do not vary by viewer: the Canon stack is per room ([`resolveCanonAssetStackForRoom`](../../../../../lambda/ephemera/dataSource/state/resolveAssetStackForRoom.ts)), and [`resolveMergedComponent`](../../../../../lambda/ephemera/dataSource/objects/objectShortName.ts) already appends Improvisation for Objects and Characters. | **LCP-2** | **Where does the version marker live?** The affordance precedent keeps `catalogVersion` on the cached row itself. **Decided 2026-10-13, with the author: a separate small marker row (`EphemeraId: <roomId>`, `DataCategory: 'LudicCacheVersion::'`, holding `version`) beside the cache row.** `UpdateItem` is billed on the larger of the item's before/after size, not on the attributes changed (one write unit per started KB; double inside a transaction; a failed condition is still billed), and CC0 recorded a fat item costing ~100 WCU per update however little changed. The marker is bumped on **every** commit or rename touching the room, far more often than the cache is rewritten, so it must cost ~1 WCU rather than the cache's size. Both rows come back in one `Query` (`EphemeraId = roomId`, `DataCategory begins_with 'LudicCache'`), so a read is still one round trip. | 2, 3 | **Decided 2026-10-13 --- separate `LudicCacheVersion::` marker row** |
| **LCP-3** | **Where does stale-marking fire?** The rebuild plan's Slice 6 and the affordance plan's Slice 3 both assumed it hangs off the `Object Moved` fact. **But `Object Moved` is one of several commits that change a room's cache** --- relational establish/dissolve, character moves (a character is a node in its room's cache), creation, destruction, presence split/join and containment population all change graphs in the walk without emitting it. **Decided 2026-10-13, with the author: the kernel bumps the marker inside the commit's own transaction, then publishes one `Ludic Cache Invalidated { roomIds }` fact.** **Why in the transaction, not after it --- and this reverses the rebuild plan's rule that cascade "must not enter `computeStepSequenceFootprint`".** That rule rested on P6 clause 4 making staleness cost only speed. **It does not hold for stale positives:** a stored cache that still places the cup in the room's bucket after it went into a box hands the old `presence` to the plan, commit-time revalidation refuses it, and a command that should have succeeded fails (silently, today). Clause 4 protects misses, not positives with the wrong structure. Any gap between the graph write and the mark, synchronous post-commit or (worse) a decoupled subscriber, is a window in which another invocation reads a cache that is wrong, not slow; and a lost decoupled mark leaves it wrong until the next change. Bumping inside the transaction closes the window: graph change and stale-mark commit together or not at all. **Mechanism, no framework change needed:** the bump is a `PrimitiveUpdate` (`ADD version :one` on `LudicCacheVersion::`, which also creates the row at `1`) returned from `commitStepSequence`'s existing `MultiKeyUpdate` cascade, which already carries its adjacency `Put`/`Delete` rows; `transact.ts` accepts `PrimitiveUpdate` from a cascade. Cost: 2 write units per affected room per commit (transactional 1KB). **Contention, accepted with a retry:** `ADD`s commute as plain `UpdateItem`s, but `TransactWriteItems` conflicts per item whatever the operation, so two in-flight commits anywhere in one room now collide on its marker (commits that write the room's own graph row already did). The kernel retries the transact on `TransactionConflict` cancellation **only** --- never on a condition failure --- via `exponentialBackoffWrapper`'s `retryErrors`; a retry re-fetches and re-validates under lock, so it cannot apply a stale plan. **Room set computed before commit:** the cascade cannot read ancestor graphs, so the affected rooms are resolved from the sequence's hosts (every host it writes, plus each destroyed host's former parents) with `roomsForHost` ahead of the transact --- the same accepted gap as audience resolution (a container moved between resolution and commit gives a slightly wrong set; over-marking is harmless, missing a room is what Slice 6 watches for). **Character-only commits mark nothing:** a room's cache never recurses into a character-hosted shard, so a commit touching only a character's inventory changes no room cache and must not add contention. **The fact, for effects:** after commit, alongside the kernel's other facts, publish `Ludic Cache Invalidated { roomIds }`; consumers that act on a cache change (the affordance refresh first) subscribe to it rather than inferring a change from `Object Moved`, so a relational change or a rename refreshes an occupied room's header too. **Sources outside the kernel are post-hoc, and accepted as such:** name sources arrive as asset events (`Component Updated`, `Canon Updated`, ...) and the three non-kernel graph writers (two diagnostics heals, the Coyote clear) are rare and not on the play path; each bumps the marker non-transactionally right after its own write and publishes the same fact, with [LCP-4](#open-decisions-implementation--plan-only)'s miss path covering the remaining window. **Routing the two heals through `commitStepSequence` instead is worth considering but out of scope here.** **Coordination:** the affordance plan's Slice 3 seam switches from `Object Moved` to `Ludic Cache Invalidated`; | **LCP-4** | **What does a miss do?** **Recommended: on zero candidates for a span, one cold rebuild with the stored row bypassed, then retry the match.** The rebuild is `buildLudicCache` itself, which is today's per-request path, so a miss costs exactly what every read costs now and a genuine no-match is no slower than today. ## Tier and rollback

**Inherited, not re-elected.** `ludicCache` is a **Prototype** (rebuild plan D7, carried forward). The dependency tag widens to include this plan's `ludicCache/store.ts` and the stale-marking calls. **Rollback is cheap by construction**: point the consumers back at `buildLudicCache` and stop reading the rows; the rows are droppable (P6 clause 5) and nothing else reads them. **Not rollback triggers:** hit latency, rebuild cost, row size. Those are what Slice 7 measures.
