# ludicCache persistence: store the room cache, rebuild on stale read

**Status: first draft, 2026-10-13. Not started.** All [decisions](#open-decisions-implementation--plan-only) settled 2026-10-13 (LCP-6 retired). Next step: [Slice 0](#recommended-order) (verify premises). Branch `iss8265-design-ludic-cache-persistence`.

**Scope in one sentence: persist each room's `ludicCache` structure in its own row, mark it stale from the one place graphs are written, and rebuild it when a read finds it absent or stale --- so a consumer pays the ~316ms rebuild once per change instead of once per read.**

This is a standard implementation plan under [`taskPlanning/AGENT.md`](../../../../AGENT.md). It takes over Slices 6--7 of [`AGENT.ludicCacheRebuild.planning.md`](AGENT.ludicCacheRebuild.planning.md), whose remaining work was design rather than implementation; that plan's open rows were settled 2026-10-13 and are restated [below](#inherited-decisions-settled-before-this-plan-opened) so this file does not depend on it.

## Getting Started

1. **[`positions/AGENT.ludicNetwork.md`](../../../../../lambda/ephemera/dataSource/positions/AGENT.ludicNetwork.md), sections 1, 4 and 5.** Sharding, presence as a cover, and what the cache stitches. Section 5 is the cache.
2. **[P6's five clauses](AGENT.abstractionLayers.proposals.planning.md#the-five-clauses)** --- what `ludicCache` is for. Three of them constrain this plan directly: **clause 3** (a hit returns a handle, never a subgraph), **clause 4** (a miss is never an answer of "no" --- here a miss is an absent or stale row, and it is rebuilt before it is read; see [LCP-4](#open-decisions-implementation--plan-only)), **clause 5** (derived, never authoritative, droppable at any time). **Clause 4 covers misses only:** a stale *positive* (an object still placed where it was) produces a wrong refusal, not a slow answer, which is why [LCP-3](#open-decisions-implementation--plan-only) marks staleness inside the commit's transaction.
3. **The code being persisted.** [`ludicCache/fold.ts`](../../../../../lambda/ephemera/dataSource/positions/ludicCache/fold.ts) (`buildLudicCache`), [`ludicCache/types.ts`](../../../../../lambda/ephemera/dataSource/positions/ludicCache/types.ts) (the shape), and the two consumers: [`catalogHandles.ts`](../../../../../lambda/ephemera/dataSource/positions/ludicCache/catalogHandles.ts) (command referent pool, via [`roomObjectCatalogForCharacter.ts`](../../../../../lambda/ephemera/dataSource/actions/roomObjectCatalogForCharacter.ts)) and [`roomObjectContents.ts`](../../../../../lambda/ephemera/dataSource/positions/ludicCache/roomObjectContents.ts) (room affordance header, via `internalCache.AffordanceRoomDeliverable`). **Both seed at a room**, and both read only nodes: `shortName`, `gloss`, and each binding's `cover.members`. Nothing reads `edges`.
4. **The kernel's post-commit bundle** --- [`positions/AGENT.contract.md` --- Membership-changed bundle](../../../../../lambda/ephemera/dataSource/positions/AGENT.contract.md#membership-changed-bundle) and `seedGraphMemos` in [`commitStepSequence.ts`](../../../../../lambda/ephemera/dataSource/positions/manipulation/kernel/commitStepSequence.ts). Every play-time graph write converges there; [Slice 3](#recommended-order) puts the stale-marking in its transaction (via the `MultiKeyUpdate` cascade in [`transact.ts`](../../../../../packages/mtw-utilities/ts/dynamoDB/mixins/transact.ts)) and adds a `Ludic Cache Invalidated` fact after it.
5. **The precedent for a stored, versioned cache row** --- [`affordanceCache/AGENT.md` --- Row shape](../../../../../lambda/ephemera/dataSource/affordanceCache/AGENT.md#row-shape-d33) and [`affordanceCache/catalogRow.ts`](../../../../../lambda/ephemera/dataSource/affordanceCache/catalogRow.ts): `catalogVersion` / `hydratedCatalogVersion`, a bump on invalidation, a conditional "mark hydrated only if the version did not move" write (H6). This plan follows it, with one difference recorded in [LCP-2](#open-decisions-implementation--plan-only).

## Inherited decisions (settled before this plan opened)

Decided 2026-10-13 in `AGENT.ludicCacheRebuild.planning.md` (rows D4, D5, D9; D8 and D11 retired). Restated here because that file closes in [Slice 0](#recommended-order).

- **Cache edges are plain leg-shaped `EphemeraLudicRelationalEdgeData`**, collapsed at internal crossing ports exactly as `collapseCrossingPorts` already does, terminating at a real node or at a port on the cache's boundary. **`supportedBy` is removed.** It was maintenance state (which bindings justify a composed edge) riding on a reasoning-facing record; once `legsAgree` settled that a chain's legs are one relation of one kind, the two concerns separated cleanly.
- **This iteration is rebuild-on-stale-read.** Maintenance is a version marker plus a re-read of the shards; **nothing is stored per edge or per node to support incremental repair.** A later incremental iteration builds its own maintenance structure **beside** the cache, never inside the reasoning record. The prior design for one (D8's OR/AND/OR support structure, D11's support-removal/cull pairing) is shelved in [`positions/AGENT.implementation.md`](../../../../../lambda/ephemera/dataSource/positions/AGENT.implementation.md) by Slice 0.
- **Retention:** shards are re-read by id through `internalCache.Positions`, whose per-invocation memo is the in-memory retention. No copies of source graphs are ever stored with the cache.
- **Record key:** `EphemeraId: <roomId>`, `DataCategory: 'LudicCache::'`, one row per room. A second tenant gets a suffix after the `::`, as `Affordance::<perspectiveKey>` does.
- **The rebuild stays a pure function plus thin handlers** (old D6): consumers get handles, never `EphemeraLudicCacheData`.

## What is deliberately out of scope

- **Incremental update.** See above. A stale cache is rebuilt whole.
- **Caches seeded anywhere but a room.** Both consumers seed at a room. A non-room seed keeps today's per-request rebuild, unpersisted.
- **Attention scoping.** The cache stays exhaustive in nodes, so stale-marking walks every depth (forwarded obligations already sit in [`AGENT.attentionHistory.planning.md`](AGENT.attentionHistory.planning.md)).
- **The affordance consumer's refresh behaviour.** Who re-renders a room header when its cache goes stale is [`AGENT.affordanceLudicCache.planning.md`](../affordanceOrchestration/AGENT.affordanceLudicCache.planning.md)'s Slice 3; see [LCP-3](#open-decisions-implementation--plan-only) for the coordination.
- **Whether asset layering is an in-play function at all.** Perspectives are unstable (a viewer's asset stack can change under them), and it is undecided whether asset layering belongs in play or only in asset assembly and editing. This plan sidesteps it: the stored row is perspective-free ([LCP-1](#open-decisions-implementation--plan-only)), and only the header's display labels read the viewer's perspective ([LCP-7](#open-decisions-implementation--plan-only)). If layering leaves play, LCP-7's per-viewer label lookup is what goes. Shelve this to [`AGENT.implementation.md`](../../../../../lambda/ephemera/dataSource/positions/AGENT.implementation.md) in Slice 7 if it is still undecided then.

| --- | --- | --- | --- |
| **LCP-1** | **Do names go in the stored row, and against which stack?** `buildLudicCache(seed, assetStack)` today resolves each node's `shortName`/`gloss` against the **viewer's** perspective stack, which would make a stored cache per-perspective and break D5's one row per room. **Decided 2026-10-13, with the author: names stored in the row, resolved against the room's Canon stack plus Improvisation.** Reasoning names do not vary by viewer: the Canon stack is per room ([`resolveCanonAssetStackForRoom`](../../../../../lambda/ephemera/dataSource/state/resolveAssetStackForRoom.ts)), and [`resolveMergedComponent`](../../../../../lambda/ephemera/dataSource/objects/objectShortName.ts) already appends Improvisation for Objects and Characters. So the stored row is perspective-independent, D5's key stands unsuffixed, and a hit costs no name reads. **What this moves:** (a) **renames become an invalidation source** --- see Slice 0's name-source item and Slice 3; (b) **the command referent pool changes behaviour** for a character whose own (non-Canon) assets rename an object: it now matches the Canon+Improvisation name. That is the intended reasoning semantics, but a test that relied on perspective-specific names will change, and Slice 4 must say so rather than adjust it silently; (c) the render consumer needs its own answer --- [LCP-7](#open-decisions-implementation--plan-only). | 2 | **Decided 2026-10-13 --- stored, resolved against Canon + Improvisation** |
| **LCP-2** | **Where does the version marker live?** The affordance precedent keeps `catalogVersion` on the cached row itself. **Decided 2026-10-13, with the author: a separate small marker row (`EphemeraId: <roomId>`, `DataCategory: 'LudicCacheVersion::'`, holding `version`) beside the cache row.** `UpdateItem` is billed on the larger of the item's before/after size, not on the attributes changed (one write unit per started KB; double inside a transaction; a failed condition is still billed), and CC0 recorded a fat item costing ~100 WCU per update however little changed. The marker is bumped on **every** commit or rename touching the room, far more often than the cache is rewritten, so it must cost ~1 WCU rather than the cache's size. Both rows come back in one `Query` (`EphemeraId = roomId`, `DataCategory begins_with 'LudicCache'`), so a read is still one round trip. | 2, 3 | **Decided 2026-10-13 --- separate `LudicCacheVersion::` marker row** |
| **LCP-3** | **Where does stale-marking fire?** The rebuild plan's Slice 6 and the affordance plan's Slice 3 both assumed it hangs off the `Object Moved` fact. **But `Object Moved` is one of several commits that change a room's cache** --- relational establish/dissolve, character moves (a character is a node in its room's cache), creation, destruction, presence split/join and containment population all change graphs in the walk without emitting it. **Decided 2026-10-13, with the author: the kernel bumps the marker inside the commit's own transaction, then publishes one `Ludic Cache Invalidated { roomIds }` fact.** **Why in the transaction, not after it --- and this reverses the rebuild plan's rule that cascade "must not enter `computeStepSequenceFootprint`".** That rule rested on P6 clause 4 making staleness cost only speed. **It does not hold for stale positives:** a stored cache that still places the cup in the room's bucket after it went into a box hands the old `presence` to the plan, commit-time revalidation refuses it, and a command that should have succeeded fails (silently, today). Clause 4 protects misses, not positives with the wrong structure. Any gap between the graph write and the mark, synchronous post-commit or (worse) a decoupled subscriber, is a window in which another invocation reads a cache that is wrong, not slow; and a lost decoupled mark leaves it wrong until the next change. Bumping inside the transaction closes the window: graph change and stale-mark commit together or not at all. **Mechanism, no framework change needed:** the bump is a `PrimitiveUpdate` (`ADD version :one` on `LudicCacheVersion::`, which also creates the row at `1`) returned from `commitStepSequence`'s existing `MultiKeyUpdate` cascade, which already carries its adjacency `Put`/`Delete` rows; `transact.ts` accepts `PrimitiveUpdate` from a cascade. Cost: 2 write units per affected room per commit (transactional 1KB). **Contention, accepted with a retry:** `ADD`s commute as plain `UpdateItem`s, but `TransactWriteItems` conflicts per item whatever the operation, so two in-flight commits anywhere in one room now collide on its marker (commits that write the room's own graph row already did). The kernel retries the transact on `TransactionConflict` cancellation **only** --- never on a condition failure --- via `exponentialBackoffWrapper`'s `retryErrors`; a retry re-fetches and re-validates under lock, so it cannot apply a stale plan. **Room set computed before commit:** the cascade cannot read ancestor graphs, so the affected rooms are resolved from the sequence's hosts (every host it writes, plus each destroyed host's former parents) with `roomsForHost` ahead of the transact --- the same accepted gap as audience resolution (a container moved between resolution and commit gives a slightly wrong set; over-marking is harmless, missing a room is what Slice 5 watches for). **Character-only commits mark nothing:** a room's cache never recurses into a character-hosted shard, so a commit touching only a character's inventory changes no room cache and must not add contention. **The fact, for effects:** after commit, alongside the kernel's other facts, publish `Ludic Cache Invalidated { roomIds }`; consumers that act on a cache change (the affordance refresh first) subscribe to it rather than inferring a change from `Object Moved`, so a relational change or a rename refreshes an occupied room's header too. **Sources outside the kernel are post-hoc, and accepted as such:** name sources arrive as asset events (`Component Updated`, `Canon Updated`, ...) and the three non-kernel graph writers (two diagnostics heals, the Coyote clear) are rare and not on the play path; | **LCP-4** | **What does a miss do?** **Decided: a miss is an absent, stale or malformed row, and `readLudicCache` rebuilds it, writes it and returns it** ([Slice 2](#recommended-order)'s read path; there is no separate miss slice). **A hit is trusted, and zero candidates from a hit is a real "no".** *Superseded recommendation, kept for the shelf:* "on zero candidates for a span, one cold rebuild with the stored row bypassed, then retry the match." | **LCP-5** | **Concurrent rebuilds.** Two readers can find the same cache stale and rebuild together. Rebuilds are byte-identical for the same graphs (rebuild Slice 3e), so a duplicate write is harmless; **the real hazard is a cache row labelled with a version newer than its content**, because that row then reads as a hit and is wrong for as long as the marker holds. ~~**Recommended:** record the marker version read at the start, and write the structure row conditionally on the marker still holding that version (the affordance H6 pattern); on a failed condition, return the rebuilt cache to this caller and write nothing.~~ **Revised 2026-10-13 after [LCP-3](#open-decisions-implementation--plan-only):** a write conditioned on the marker needs a `ConditionCheck` on the marker in a transaction, and since the marker now rides every kernel transaction in the room, that check would collide with them. ~~Recommended instead: label, don't condition. The cache row stores `builtAtVersion`; a read is a hit only when `builtAtVersion` equals the marker's `version`; the write-back is a plain unconditional `Put`. An older rebuild overwriting a newer one then labels itself older, reads as stale, and costs one more rebuild --- slower, never wrong. What makes the label honest is read order, and this is the hazard to test: the rebuild must read the marker first, then read the shard graphs fresh and strongly consistent, so the content is never older than its label. The per-invocation `Positions` memo breaks that if used naively: an invocation that memoized a room's graphs earlier, then reads a marker another invocation has since bumped, would build from the old memo and label it with the new version --- a persistent wrong hit. So the persisted rebuild path bypasses the memo for graphs it did not read after the marker (Slice 0 finds the uncached or invalidate-then-read route), and the marker `Query` and graph reads use `ConsistentRead`. Content newer than its label is harmless (it reads as stale). No single-flight: the affordance plan needed it because hydrate was expensive and frequent; here the duplicate cost is one extra rebuild in a rare race.~~ **Decided 2026-10-13: single-flight per version, a monotonic write, and one retry rule for every caller.** (1) Read the marker (N) and the row in one consistent `Query`; a row labelled `builtAtVersion` N is a hit, returned as is. (2) Otherwise run `singleFlight` (`@tonylb/mtw-lambda-patterns`, `coalesce` mode, the affordance topology-hydrate precedent) keyed on **(`roomId`, N)**. Keying on the room alone would pool a request for N+1 into a flight still building N. The flight's build step builds against N and writes the row with a **monotonic single-item condition**, `attribute_not_exists(builtAtVersion) OR builtAtVersion < :n`: no transaction and no touch on the marker, so it never contends with kernel commits, and a slow build of N can never overwrite a newer row. **On a failed condition the build step catches it and returns the row it finds** (labelled above N); it never throws it. Followers' retrieval is a plain read of the row. (3) **Every caller, builder or follower, applies the same rule to what the flight returns: labelled N, return it; anything else is a cache-update collision, so go back to (1)**, a bounded number of times. Nobody needs to know which role it played. A write of N that lands after the marker moved to N+1 is still a correct answer for every request that read N (as current as a read a moment earlier; commit-time revalidation covers the race, as for any read), and readers after it see a label below N+1 and rebuild. **Read order still matters, and the version check does not fix it:** the build reads the marker **first**, then the shard graphs **fresh and strongly consistent**, bypassing the per-invocation `Positions` memo for graphs it did not read after the marker. Otherwise an invocation that memoized a room's graphs before another invocation's bump builds from the old memo and labels it with the new version, a persistent wrong hit. Content newer than its label is harmless (it reads as stale). **`singleFlight` has a general bug this plan leans on, fixed at the source in [Slice 2](#recommended-order):** in `coalesce` mode the build runs inside the same `try` as instance creation, so (a) any `ConditionalCheckFailedException` from the build is misread as a lost creation race and the builder falls back to polling its own instance, and (b) a build that throws never marks its instance `FAILED`, so followers poll until the timeout (60s in the affordance precedent) and then self-promote. The fix narrows the `try` to instance creation and marks the instance `FAILED` before rethrowing a build error. LCP-5 is correct without the fix, because the build step catches its own condition failure; the fix is for unexpected errors (throttling, bugs), and for every other caller. | 2 | **Decided 2026-10-13 --- single-flight on (`roomId`, version); monotonic single-item write; every caller retries on a result not labelled with the version it read.** |

## Tier and rollback

**Inherited, not re-elected.** `ludicCache` is a **Prototype** (rebuild plan D7, carried forward). The dependency tag widens to include this plan's `ludicCache/store.ts` and the stale-marking calls. **Rollback is cheap by construction**: point the consumers back at `buildLudicCache` and stop reading the rows; the rows are droppable (P6 clause 5) and nothing else reads them. **Not rollback triggers:** hit latency, rebuild cost, row size. Those are what Slice 6 measures.
