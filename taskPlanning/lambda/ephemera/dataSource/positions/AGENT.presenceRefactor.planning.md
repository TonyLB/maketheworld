# Presence port population --- refactor planning

**Status: RD-1 and RD-2 decided by the user 2026-09-04; step 1 is ready to write. Everything else open.**

This plan exists because a set of **assertions about presence ports were made confidently in chat on 2026-09-04, several of them wrong**, and there were too many to unpick in conversation. They are written down here **as assertions, not as findings**, so they can be worked through one at a time. **Read every row of the register below as "this was claimed," never as "this is so."** Rows only become findings by being checked, and the check is recorded in the row.

This is a **standard-variant** task plan (see [`taskPlanning/AGENT.md`](../../../../AGENT.md)) --- an implementation plan with an unusually fat front section, not a design-stage plan. The design-stage sibling is [`AGENT.presence.planning.md`](AGENT.presence.planning.md), which owns the settled model (presence-as-a-cover, PR-1..PR-16) and is **authoritative over this file** wherever the two touch. **When a row here resolves into a design answer, it graduates into that plan, not into this one.**

### What actually survives

**Three mechanical observations** --- RA-1, RA-4, RA-5 --- all re-checkable by grep, none of them loadbearing on their own.

**Every inference drawn from them on 2026-09-04 is withdrawn or refuted.** The shared mechanism in RA-2, RA-6 and RA-7 is one thing worth naming, because it will recur in this plan: **reading the current implementation as the design.** A comment's rationale read as a decision; a missing consumer read as a verdict on consumers; a step's commit semantics read as a representation's expressiveness.

**The split is not random, and it is the reason this plan is ordered the way it is.** The survivors are exactly the assertions answerable by grep. **Every refuted row was reasoning in the hypothetical --- what a comparison would show, what a decision must have meant, what a representation could express --- and the hypothetical register is one this plan's author has demonstrated repeatedly they cannot operate in productively as a collaborator** (user's call, 2026-09-04, and it is written here as a working constraint rather than as an apology). **So: code and population get sorted first, on the user's authority, and the assessment design is written afterwards against a system that exists.** See [Recommended order](#recommended-order) --- the first draft of this plan inverted that, putting RD-5 in the gating slot, which is the same error one layer up.

**And the question the original exchange was reaching for is untouched and still good:** presence ports are populated inconsistently, which makes it unattractive to build on them, which blocks an apples-to-apples comparison against the adjacency reverse index. **RA-7's refutation makes that comparison more interesting, not less** --- if multi-port presence is as expressive as the reverse index, then the two really are candidate substitutes and the choice has to be made on other grounds.

## Recommended order

Pending work uses `[ ]`; completed work uses `[X]`. Mark nested lines `[X]` as they are done, so partial progress on a multi-part step is visible.

**Code and population first; assessment last.** Steps 1--3 make presence ports actually populated, under decisions the user owns. Step 4 designs the comparison **afterwards**, against a system that exists. This ordering is the user's, reversing the first draft of this plan --- see [What actually survives](#what-actually-survives) for why.

- [ ] **1. Split the presence step (RD-2).** Decided; this is now a write, not a fork. **Target: green suite with no observable behaviour change** --- if a test's expectations change beyond step *names* and *counts*, something in the decision was misread.
  - [ ] Re-check RA-1, RA-4, RA-5 by grep and record the result in each row. Cheap, and they are the slice plan's only load-bearing facts.
  - [ ] Rename `MutationKernelSetPresencePortStep` -> `MutationKernelAddPresencePortStep` (`kind: 'addPresencePort'`), drop the optional `port` --- the clear is now a separate step, not an omitted field.
  - [ ] Add `MutationKernelRemovePresencePortStep` as `{ kind: 'removePresencePort', hostId, fromHostId }`. **Addressed by host, not by `portId`** --- unlike `removeCrossingPort`, because the compiler cannot know a `portId` without the prior-state read that replace-all existed to avoid.
  - [ ] Reducer: the block at [`applyStepSequenceCore.ts`](../../../../../lambda/ephemera/dataSource/positions/manipulation/kernel/applyStepSequenceCore.ts) narrows from `filter(port => port.kind === 'Present')` to the same filter plus `&& port.fromHostId === step.fromHostId`. `removePort` is a plain filter, so removing an absent binding is a silent no-op --- **which is the behaviour population needs while coverage is still sparse.**
  - [ ] Compiler: emit `[...froms.map(removePresencePort), addPresencePort(to)]` in place of the single set step.
  - [ ] Sweep the mechanical sites: `isKernelMutationStep` and `computeStepSequenceFootprint` (both gain one arm), `factsForStep` (still no facts), and `publishedEvents.ts`'s guard comment.
  - [ ] Graduate RD-1 and RD-2 into [`AGENT.presence.planning.md`](AGENT.presence.planning.md), including **the note that PR-7's widening may dissolve rather than resolve** --- that plan owns PR-7 and PR-10, and both are affected.
- [ ] **2. Populate objects and characters.** RD-1 is decided; RD-3 (routing) is the remaining fork.
  - [ ] **Fix the missing clear first --- it is a live defect, not new work.** `MutationKernelSetPresencePortStep.port` is **optional**, and omitting it clears the binding ([`kernelStep.ts`](../../../../../lambda/ephemera/dataSource/positions/manipulation/kernel/kernelStep.ts)); the reducer already honours that. But [`compilePositionKernelOp.ts`](../../../../../lambda/ephemera/dataSource/positions/manipulation/kernel/compile/compilePositionKernelOp.ts) gates the step on `op.to` being truthy, so a departure to no host **emits nothing and leaves the old port standing.** Today that is a stale binding on an object leaving play; under RD-1 it is exactly the character out-of-play case. **The zero state is representable and simply never written.**
  - [ ] Then RD-3: route `executeMembershipTransfer` through the compiler, or emit per-path.
  - [ ] Drop the `moved.kind === 'closure'` gate so characters compile a binding, per RD-1.
- [ ] **3. Populate rooms, features, areas:** RD-4, on the scale-invariant framing.
- [ ] **4. Design the assessment** (RD-5) and only then run it. **Not before step 3 lands.**
