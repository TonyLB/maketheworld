## Proposal P1: single-host objects + hosting at the containing node

~~**Status: adopted provisionally as [H1](AGENT.abstractionLayers.proposals.planning.md#working-hypotheses), 2026-08-05.** Recorded first as an unjudged proposal, then promoted --- **not** to a decision, but to a *working hypothesis whose job is to ground further design*. Every answer derived from it is tagged `H1-dependent` so the rollback set stays known; see [Working hypotheses](AGENT.abstractionLayers.proposals.planning.md#working-hypotheses) for the tagging test, the falsification cases, and the named rollback triggers.~~ **Status: withdrawn 2026-08-07, along with H1 --- see [H1's status line](#h1-single-host-objects-hosting-at-the-containing-node) for the falsification.** Left in place, struck rather than removed, per this plan's supersession rule: the clause table above argues against this proposal's own numbered items by number, and cannot be read without them. It touches AB-4, AB-8, AB-9, AB-16, AB-17 and the AB-21 identity question, so it is written up here rather than inside any one row.

### The proposal

1. **Remove multi-host capability for Objects.** An Object has exactly one host. (Features may remain multi-host --- see the note below.)
2. **Give Objects a direct lookup of placement data on their `Meta`**, rather than a variable set of adjacency rows.
3. **Spanning things are modelled as parts.** "Tie rope to rock" then "drop rope into abyss" improvises **two rope parts**: one stays in the cliff-top room tied to the rock, one goes into the abyss.
4. **The whole is hosted at the node high enough in the containment tree to contain all of its parts.** The rope object itself hosts in the **Area** containing both rooms, with part connections (likely two-way) to its parts.
5. **Migration is automatic and bidirectional.** Haul the rope up, all parts in one room, and the rope migrates down from Area into that room.

### What it buys (assessed against code, 2026-08-05)

| Gain | Detail |
| --- | --- |
| **Every threatened invariant survives** | `computeEndStateRoomDiff`'s end-state scrub stays correct; adjacency stays single-valued; `MutationKernelTransferStep`'s singular `toHostId` needs no widening. |
| **The contract clause is vindicated, not stale** | "At most one room per `OBJECT#`" becomes **true as written** --- the design moves to meet the contract instead of the contract being rewritten. Materially cheaper than the widening path, and it retires the three-way disagreement recorded under [Multi-host presence](AGENT.abstractionLayers.planning.md#multi-host-presence-what-is-actually-true-today). |
| **The relational-edge problem dissolves** | Rope tied to rock is an ordinary **same-host** edge between the cliff-top *part* and the rock. This was the sharpest structural objection to multi-room ropes; it needs zero new machinery. |
| **Presentation is correct by construction** | Each room's `graph.objectIds` holds the part actually present, so no room renders a whole rope it only partly contains. |
| **The drift class genuinely shrinks** | A single-valued host cannot exhibit multi-room drift. `repairObjectPlacementDrift`'s multi-room scrub branch becomes **structurally impossible**; only field-vs-graph lag survives. A deletion, not a relocation. |
| **Improvisation is reused unchanged for parts** | A part is an Object; minting one is minting an `OBJECT#` into `ASSET#IMPROVISATION`. Only the composition edge is new (already tracked as gap 1). |

### What it costs --- concentrated almost entirely in the host containment tree

| Cost | Detail |
| --- | --- |
| **Area is further away than "parked"** | `EphemeraMembershipHostId = EphemeraRoomId \| EphemeraCharacterId` ([`ephemeraPositionAdjacency.ts`](../../../../../packages/mtw-interfaces/ts/ephemeraPositionAdjacency.ts)), and **there is no `EphemeraAreaId` in `baseClasses.ts` at all**. Area exists only WML/asset-side (`AREA#downtown`, `AREA#region`). This introduces an ephemera-side identity, not merely a deferred host kind. |
| **Containment is authored downward, with no upward index** | `StandardAreaData` carries a `positionGraph` listing its members, so "Area contains Room" is nodes in the Area's graph. **Nothing maps room -> area.** The rule needs the upward direction on every part move --- structurally the same missing thing as the parked reverse-edge-reference index. |
| **Is it a tree at all?** | Area membership is authored blueprint **merged at participation order**, so containment may be **asset-stack dependent** --- while an object's host must be world truth, not perspective-relative. `AREA#region` beside `AREA#downtown` also suggests nesting depth. And two rooms with no common Area leave the LCA undefined without a world root. **This is the load-bearing unknown for P1.** |
| **Migration is an invariant needing transactional cascade** | Every part move recomputes its whole's host, which may move the whole, which may cascade to wholes-of-wholes. `computeStepSequenceFootprint` runs **once, up front**, and `MultiKeyUpdate` cannot be re-entered --- so plan time must walk composition *upward* to pre-lock every host the cascade might touch. |

### What it changes conceptually

- **Two kinds of hosting, needing a name.** Room-hosting means *physically there*; Area-hosting is *bookkeeping*. Area-hosted objects presumably never surface in affordances --- state it, or someone writes compose that surfaces them.
- **It makes AB-9 acute rather than dodging it --- and [C5](AGENT.abstractionLayers.corpus.planning.md#c5-the-chain-mounted-at-both-ends) escalates that from acute to routine.** With all parts back in one room, the whole **and** its parts sit in that room's graph: "you see a rope, a rope end, and a rope end." Description must pick a level, unavoidably. C5 shows this is not a transient state during manipulation but the **permanent steady state of anything anchored**: a chain mounted at one end and attached to a chest at the other sits in the cell's graph as three nodes indefinitely. Level selection is therefore a default read-path concern, not an edge case.
- ~~**Migration-down and reabsorption may be the same event (AB-17).** Coiling the rope is all-parts-co-located, which is both "migrate the whole into the room" and "dissolve the parts."~~ **Falsified 2026-08-05 by [C5](AGENT.abstractionLayers.corpus.planning.md#c5-the-chain-mounted-at-both-ends).** Co-location and load-bearing are independent: the chain's parts are all in one cell *and* still carry the relations anchoring it, so the whole migrates down while the parts must persist. **P1 collapsed two conditions into one** --- AB-17's criterion was already written as a disjunction ("no part is separately referenced **or** separately positioned") and H1 clause 5 tests only the second. The two events stay separate; **AB-17** carries the split criteria. Struck rather than softened, per this plan's rule on recording supersessions.

### What it does not resolve

- **How parts *connect* is out of P1's scope.** Parts plus a whole give membership, not structure. **This is AB-26, and it is not a sequence** --- connections are adjacency-mediated edges ("the clifftop end connects to the shaft section by way of the 'into the abyss' exit"), which branch. P1 and AB-26 are complementary, not competing: P1 decides *where the whole is hosted*, AB-26 decides *how the parts relate*.
- **Multiple parents (AB-13) is fine**, incidentally: each whole computes its own LCA independently, so an object being part of two wholes creates no conflict.

### On the two sub-proposals

**`Meta` direct lookup:** single-host makes the reverse index single-valued, collapsing a variable row set into one field --- a genuine simplification of *shape*. It remains a dual write with the same atomicity discipline and the same "`positionGraph` wins" conflict rule, so it **shrinks** the drift class rather than removing it.

**Features stay multi-host:** this is **forward-looking, not preserved.** Features are not graph nodes at all today (the node `tag` union is `'Character' | 'Object'`). It is consistent with their documented narrowing --- never membership-moved, never a relation subject, therefore no transfer semantics to get wrong --- but it describes a capability yet to be built.

**And the phrasing may be wrong, not just unbuilt (added 2026-08-05, see AB-30).** "Features stay multi-host" presumes Features are the kind of thing that *has* hosts. If a wall between two rooms is better modelled as an **edge** than as a node, it is not multi-host --- it is a non-member, and the sub-proposal is answering a question that does not arise. Note the asymmetry this sub-proposal currently carries unremarked: H1's entire thrust is **removing** multi-host for Objects, while this clause **preserves** it for Features. That is either a real distinction with a reason, or the clause is describing the problem in the vocabulary H1 just abandoned. AB-30 decides which.

### Candidate: drop H1 clause 1b, and the whole chain with it

**Recorded 2026-08-06 as a candidate, not adopted --- and narrowed the same day to *extent only*.** Follows directly from the entailment above: if 1b generates 4 and 5, then declining 1b removes all three.

**Scope correction, [C8](AGENT.abstractionLayers.corpus.planning.md#c8-the-flashlight-that-vanished-when-someone-looked-at-it).** As first written this candidate was derived **entirely from C7**, an extent case, and generalised without being checked against a containment case sitting in the same document. Applied to a flashlight it is destructive: decomposition would make the whole non-positional, so the flashlight leaves the room's graph, affordance compose describes three components, and --- because the referent catalog reads the same `objectIds` --- **"pick up the flashlight" stops grounding**. Looking closely at a thing would make it unreferrable, while fictionally nothing happened.

**So the candidate holds for extent and inverts for containment:** extent makes the *whole* non-positional, containment makes the *parts* non-positional. Positional status looks like a property of the **composition kind**, not a global rule. ~~which is AB-16's distinction surfacing positionally~~ --- **that inference was withdrawn 2026-08-06 and must not be re-drawn from here.** This paragraph is a *scoping decision about this candidate*: the candidate breaks containment, so it is confined to extent. Reading the resulting asymmetry back as evidence that the two part kinds differ is circular, because the asymmetry is what this paragraph just imposed. See **AB-16** for the full withdrawal. Everything below is therefore scoped to **extent wholes**; the LCA machinery it would remove is correspondingly confined to **scattered containment** rather than eliminated. **Untested premise:** that containment and extent are cleanly separable --- a ship's rigging may be both.

**The observation that motivates it: nothing reads the whole's host.** P1 states Area-hosted objects presumably never surface in affordances. [Part-mediated reference](#part-mediated-reference-how-h1-answers-its-own-replacement-trigger) establishes that the whole is never catalog-visible and is reached by **traversal from a part**. Description reaches it the same way. So neither the reference path nor the description path consults H1 clause 4's host --- **it is bookkeeping nothing reads.**

**The alternative.** The whole becomes a **non-positional record**: a `Meta` row carrying the member set and the part-connection graph, *not* a node in any position graph. Parts remain graph nodes; the whole is structure **over** them. It then has no host, and H1 clauses 4 and 5 do not arise.

**This is already a listed option, not a new invention.** AB-4 asks whether the level-crossing relation is membership with an Object host, a new edge kind, **or something that is not an edge at all** --- and the third option is exactly what makes the whole non-positional. It has been in the row since it was written.

**What it would buy:**

| Gain | Detail |
| --- | --- |
| **P1's gains survive untouched** | All four --- gate, planner, `toHostId`, compose --- require only that no object *is* multi-present. A whole that is neither a graph node nor an adjacency row cannot be multi-present at all |
| **AB-25 deflates** | It exists almost entirely to serve H1 clause 4, and is currently both H1's critical path **and** its only live rollback trigger. It would not vanish (AB-30's walls may still need containment answers) but would stop being what H1 lives or dies on |
| **Trigger 3 evaporates** | No migration means no cascade, no concurrent-migration race, and no thrash --- three queued test cases dissolve rather than needing to be run |
| **No `EphemeraAreaId` needed for this purpose** | P1's largest single unbuilt dependency was an ephemera-side Area identity, required so wholes had somewhere to host |

**What has to be true for it to work --- and both are real questions, not formalities:**

1. **Composition must live in the record, not in position-graph edges.** ~~If wholes can themselves be parts of bigger wholes, this collapses.~~ **Decider corrected 2026-08-06 --- the original made the requirement/representation conflation this plan has just named.** Wholes-nest is **answered yes** (AB-32) and the candidate **survives it**: a record-based whole holds a member set of ids, an id can be another whole's, so nesting is free and hosts recurse to leaf parts. **The real decider, as a requirement: must a relation ever attach to a *whole* rather than to one of its parts?** Relations need nodes, so a yes forces wholes to be nodes and this collapses. Every case so far says no; "the place setting is on the table" is the untested shape. **The candidate still hinges on AB-4** --- it is that row's third option carried to its consequence --- but by way of AB-32.
2. **Lifecycle needs an owner.** With no host, what cleans up a whole when its parts are all deleted? Orphan-sweep shaped, and the objects lane has precedent (delete-only repair, the S1 compensating delete), but it is currently the whole's host that would make it discoverable.

**Clause-targeted tests this framing suggests**, replacing the habit of building one elaborate scenario and hoping it stresses something:

- **H1 clause 1a** --- hunt the corpus for a spanning thing that **resists decomposition**. If none exists, 1a holds and is close to free. AB-30's wall is the nearest candidate and is already excluded from the decomposition story, which is suggestive.
- **H1 clause 1b** --- the decisive question is not a scenario but **AB-4**: does composition live in the record or in position-graph edges? Record means [the whole can be non-positional](#candidate-drop-h1-clause-1b-and-the-whole-chain-with-it) and 1b, 4 and 5 all go; edges means wholes must be graph nodes and the chain stands. **Answer AB-4 before running any H1 clause 4 or H1 clause 5 test** --- three queued cases target machinery that may not need to exist.
- **H1 clause 2** --- dual-write drift: does the reverse index stay single-valued across a failed transaction, and does the parent index from [part-mediated reference](#part-mediated-reference-how-h1-answers-its-own-replacement-trigger) land on the same `Meta` row, making it a multi-writer hotspot?
- ~~**H1 clause 4**~~ **--- no longer a test to run (2026-09-11); see the clause row above.** The perspective-relative-LCA worry is moot because no LCA is computed: hosts are authored, not derived. ~~AB-25's three sub-questions, of which the sharpest is that Area membership is **asset-stack dependent**: if the LCA is perspective-relative then an object's host is not world truth, which is disqualifying rather than expensive.~~
- ~~**H1 clause 5** --- concurrent migration and thrash (both queued), plus AB-31's fission, where **one event migrates two wholes in opposite directions**.~~ **Dissolved 2026-09-11, not run** --- all three target migration machinery that was never built. **AB-31's fission is the one that does not dissolve with them:** it was only ever *phrased* in migration terms, and one event splitting a whole in two is still a live question about interior graphs and ports. Do not let the strike here retire it.

**Why it was promoted rather than left open.** Two arguments, of unequal strength. The weaker one, stated first and repaired: *the route non-uniformity means any single consolidated representation beats the status quo.* True about the inconsistency, but **symmetric** --- it argues equally for consolidating on multi-host. What actually selects H1 is that the five sites are not symmetric in **cost**: under H1 the membership compile gate, the end-state planner, the relational host map, the singular `toHostId`, and per-room affordance compose all become **correct as written**, no changes at any of them; under framing (a) every one needs widening. Five sites that independently decided single-host is weak evidence that single-host is natural and strong evidence that widening is expensive.

**What it buys the design, beyond the code sites.** It predicts a specific answer to AB-1 rather than dissolving it. Extent stops being its own axis (the rope is parts plus a whole, so AB-8 collapses into AB-4/AB-26), and the functional-state aggregate plausibly shares the same *carrier* --- a generator-and-door system hosts at the Area by the same rule --- while the **relation kind** differs, since a generator is not *part of* a door. That is AB-1's "one substrate, distinct types above it" option, arrived at from a mechanism rather than chosen from a list.

**What it does not buy: net simplification.** H1 retires AB-8 and buys **AB-25**, which is not close to answered and is a bigger commitment than the proposal's wording suggests --- `EphemeraAreaId` does not exist ephemera-side at all, no room -> area index exists anywhere, and containment may not be a tree. It also makes **AB-9 acute** rather than deferrable (a rope and two rope ends in one graph; description must pick a level), and AB-9 is the scope-controlling row. Forcing AB-9 is arguably good. It is not a reduction, and the promotion should not be defended as one.

## Part-mediated reference: how H1 answers its own replacement trigger

**Proposed and assessed 2026-08-05.** Written here rather than inside a row because it touches AB-6, AB-11, AB-13 and AB-15 at once --- same reason [P1](#proposal-p1-single-host-objects--hosting-at-the-containing-node) is written up separately.

**Defect found 2026-08-06, and it is in this scheme's *framing* rather than its mechanics.** As introduced, part-mediated reference was the answer **for spanning wholes**, while local `graph.objectIds` lookup stayed the unexamined norm for everything else --- **two reference paths, never reconciled.** That is [position 3](AGENT.abstractionLayers.proposals.planning.md#three-positions-on-reference-and-what-h1-clause-1b-actually-costs), the one an epicycle argument correctly kills: a second path for a subclass rather than an optimisation of one rule. **The fix is not to discard the scheme but to promote it**: make traversal the *clean* rule for all reference, with zero hops in the local case (an undecomposed flashlight's node *is* the whole), and let today's lookup be a fast path with a stated validity condition. Everything below then describes the general rule rather than a special case.

**The scheme.** In any room where "pull the rope" is a sensible thing to do, **a part of the rope is present** --- an end, a span. That part takes the identification-grounding, because it is what is locally there. It carries a **parent index** naming the whole it belongs to. Reference walks *up* that index to the rope object, which then accumulates the state of its parts across every room in order to evaluate what pulling does.

**Why this is the better answer, not merely an answer.** The alternative was to make Area-hosted wholes surface in room affordances, which would require compose to reach up the containment tree and would drag non-present things into every room's catalog. Under part-mediated reference, **P1's "Area-hosted objects never surface in affordances" stays true as written.** The whole is never in a catalog; reference reaches it by traversal rather than by presence.

**What it costs, checked against shipped machinery:**

| Step | Status |
| --- | --- |
| Part is catalog-visible in its room | **Works today, unchanged** --- the part is an Object node, so `roomObjectCatalogForCharacter`'s `positionGraph.objectIds` scan already finds it |
| Grounding binds "rope" to the part | **The one real gap.** See the naming seam below |
| Part -> whole traversal | **New**, a `Meta::Object` parent field. Cheap, but a new dual write with the usual atomicity and drift story |
| Whole -> all parts, all hosts | **New**, and it forces AB-6 (below) |
| "Pull" applied across hosts | **Shape exists.** `MultiKeyUpdate` already folds N effects into one `transactWrite` |

**It answers AB-11 with the cheap option.** "Pull" is not a new step kind --- the whole **expands** into per-part steps, which is precisely Synthesize's Expansion sub-role, already growing one ungrounded change into an ordered sequence for carry closure and `sameHost` repair. **The kernel's step vocabulary does not grow.** That is the outcome AB-11 exists to determine, reached by a scheme that was not designed to reach it.

**Three consequences it forces, recorded so they are owned rather than rediscovered:**

1. **AB-6 resolves toward *stored*.** *(Contested 2026-08-07: [AB-1](AGENT.abstractionLayers.planning.md#the-relation-kind-register)'s state facet pulls the same row toward **derived**, and [P4](AGENT.abstractionLayers.proposals.planning.md#proposal-p4-settling-dataflow-and-narrative-heat) is the candidate that dissolves the conflict --- settling is neither stored nor derived, but persisted-in-progress. Recorded here so the stored leaning is not read as unopposed.)* Evaluating the pull needs every part and its host known **before** the walk begins, because `computeStepSequenceFootprint` runs once, up front. A *derived* member set cannot supply that without already knowing where to look.
2. **The parent index is AB-25's missing upward direction, one level down.** AB-25 records that containment is authored downward with no room -> area index; this is the same gap at object scale. **Distinct from** the reverse *edge*-reference index the plan has flagged three times --- different index, same missing direction.
3. **The naming seam, and it is the step that does not fall out of existing machinery.** The catalog matches on `normalizedShortName`. The player says "pull the **rope**"; what is present is a part. If the part's short name is "rope end," the whole's name is not in the catalog and grounding has nothing to bind to. Candidates: parts alias the whole's short name, a two-phase match consults the parent index, or the catalog widens to include reachable wholes. **This is AB-15 arriving concretely** --- unqualified reference should bind to the authored level, and under H1 the authored level is exactly the thing not locally present.

**And one smaller consequence: make the parent field plural from the start.** Multiple parents (AB-13) means a part belonging to both a rope and a knotted pair, where "pull the rope" is ambiguous. The ambiguity can be deferred; the field shape should not be, since widening it later is the more expensive order.

**Trigger 2 therefore passes --- conditionally, and the condition is the point.** The trigger asked whether the whole stays referrable while Area-hosted. It does. But it passes *because* AB-6 resolves to stored, AB-15's binding question has a workable answer, and the parent index gets built. **H1 survives by acquiring three dependencies, not by needing nothing** --- a normal outcome for a hypothesis doing real work, recorded as conditional so a later reader does not read "passed" as "free."

**The failure mode this section is designed against is sunk cost, not error.** Conditional adoption goes de facto permanent once the dependent set is large enough that rollback means redoing fifteen answers --- at which point H1 survives on accumulated cost rather than merit, and this section documents a decision nobody is willing to act on. **The mitigation is ordering, not discipline:** run the two falsification cases *next*, while the rollback set is still near-empty. The tagging is insurance for what accumulates afterwards, which is when insurance is worth buying.

**Rollback mechanics.** IDs are stable and never reused, so withdrawing H1 does **not** renumber anything: every `H1-dependent` row returns to **Open** with a note naming H1 as what invalidated it, exactly as [Phase 3](AGENT.abstractionLayers.planning.md#recommended-order) already does for rows a later answer invalidates. The branch point is this section.
