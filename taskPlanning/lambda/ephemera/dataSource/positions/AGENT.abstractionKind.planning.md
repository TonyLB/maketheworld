# Abstraction: a component kind for things present only by association

**Status:** drafted 2026-11-01. Nothing is built. **Next step: Slice 0** (inventory and worked cases, no code), which decides the rows that gate every later slice. An implementation plan, per [`taskPlanning/AGENT.md`](../../../../AGENT.md), by the user's choice (2026-11-01): the open decisions outnumber the steps, but the deliverable is code. **Slices 1 onward are a sketch, each tagged with the decisions it is gated on**; Slice 0's answers will reshape them.

**What depends on this plan.** The [scene projection plan](../actions/AGENT.sceneProjection.planning.md)'s SP-2 assumes that physical placement can be cut out of the all-connections DAG as a forest over hosts, with abstractions rendered as references. That assumption holds only if this plan holds. **If this plan is rolled back, SP-2's physical-forest rendering is rolled back with it**, so SP-2 is gated here rather than decided alongside.

## Goal

Today an `<Object>` serves two purposes:

- **a physical thing** that is somewhere: a terminal, a chest, a rope;
- **an abstraction present only by association**: a Habitat Control System that is "here" because one of its terminals is, or the Inherited Furniture collection that a steamer chest belongs to.

The graph cannot tell the two apart. The presence topology of a computer system with a terminal in the lab is identical to that of a rope with an end in the lab ([C10](AGENT.abstractionLayers.corpus.planning.md#c10-the-moonbase-computer-system)). C10 concluded "no structural predicate separates them, so it must be declared," and no declaration was ever built.

This plan builds that declaration as a **first-class component kind**: an `<Abstraction />` tag in WML, a `StandardAbstraction` class, and an `ABSTRACTION#` id, used *instead of* `<Object>` for the second purpose. Things an Abstraction hosts hold a new hosting kind, **`Associated`**, rather than `In`, `On`, `PartOf` or `SectionOf`.

**What an Abstraction is (user, 2026-11-01; refined under AK-5):** a thing that is **conceptual by kind**: its only connections to physical things are associations. That is a property of the kind, not of where the thing happens to be. **Having no physical placement is a different axis**, open to any component: an Object nobody has yet placed (the Sword of Destiny, "out there somewhere") is still physical, and an Abstraction nobody has yet made relevant anywhere (a death-cult with no members placed) is still abstract. An Abstraction is **never moved**, as a consequence of AK-4 (it is never `In`, `On` or `Held`): it is never the subject of a `transferMembership`. Moving a physical whole carries its parts (carrying is what hosting does), whereas "take the habitat control system" has nothing to move.

**What it buys:** the physical surroundings can be presented on their own, with only the things that belong there, and the relevant abstractions presented in that context as references. The working hypothesis that makes this worth building is the **physical-forest invariant** (AK-2): *following hosting edges between physical components only (neither side an Abstraction; AK-4), each binding's parents all belong to one host; a binding has parents on several hosts only through association.* If that holds, physical placement is a forest over hosts, and every DAG corner case left is an association.

**Payoff, at the observable output:** an authored `<Abstraction>` (a habitat control system whose terminal sits in a room) arrives in ephemera. The **room affordance header** lists the terminal and not the system, even though the system's binding is in the room's row (AK-3): the header walks physical contents only. `take habitat control system` refuses with an outcome on the command's bubble rather than moving anything. The final shape of the payoff is gated on AK-8 and AK-9.

## What exists today (checked 2026-11-01)

- **Hosting kinds:** `HOSTING_KINDS = ['On', 'In', 'Held', 'PartOf', 'SectionOf']` in [`ephemeraMeta.ts`](../../../../../packages/mtw-interfaces/ts/ephemeraMeta.ts). Each is stored as `hostingKind` on the member's node in its host's graph, one per membership, never as an edge. The cache carries it on the cover entry ([`ludicCache/types.ts`](../../../../../lambda/ephemera/dataSource/positions/ludicCache/types.ts) `EphemeraLudicCacheCoverEntry`).
- **Host kinds:** `EphemeraMembershipHostId = Room | Character | Object | Feature | Area` ([`ephemeraPositionAdjacency.ts`](../../../../../packages/mtw-interfaces/ts/ephemeraPositionAdjacency.ts)). Every host stores a `ludicGraph` on its `Meta::<Kind>` row through one shared serde ([positions contract, "Host storage"](../../../../../lambda/ephemera/dataSource/positions/AGENT.contract.md#host-storage-one-shared-serde-one-documented-exception)).
- **Referents:** `EphemeraThingId = Object | Character | Feature` ([`thing.ts`](../../../../../lambda/ephemera/dataSource/actions/enrich/objectManipulation/thing.ts)). The command catalog lists object nodes of the actor's cache only ([`catalogHandles.ts`](../../../../../lambda/ephemera/dataSource/positions/ludicCache/catalogHandles.ts)).
- **Parent sets ([PR-25](AGENT.presence.planning.md#settled-register)):** a binding's parents are a stored set. The driving case, [PR-C5](AGENT.presence.corpus.planning.md#pr-c5-the-steamer-chest-in-the-attic-and-the-backgammon-set-inherited-twice), is abstraction-driven: `OBJECT#InheritedFurniture` and `OBJECT#Boardgames` are abstractions modelled as Objects, and the backgammon set's one binding has both chest bindings as parents. It is run end to end in [`presenceParentSets.payoff.test.ts`](../../../../../lambda/ephemera/dataSource/positions/manipulation/membership/presenceParentSets.payoff.test.ts). PR-C5 beat 1 also relies on **covers that differ per association**: Inherited Furniture covers the chest but not its contents, while Boardgames covers both.
- **A multi-parent write that may be physical:** "a join writes several parents, all bindings of one host" ([positions contract](../../../../../lambda/ephemera/dataSource/positions/AGENT.contract.md#presence-nodes-cover-consolidation-and-the-single-write-path)). It can be physical, and AK-2 admits it: the invariant is one parent *host*, not one parent binding.
- **The cache fold walks downward**, from the seed into each host's contents. A member's binding into an association host is on the member's own graph, so reaching the Abstraction's node (its name and gloss) from a member is an upward step the fold does not take today.
- **The WML side:** [`components/AGENT.implementation.md`](../../../../../packages/mtw-wml/ts/standardize/components/AGENT.implementation.md), "Adding a New Component Type", is the checklist (schema tag in `mtw-base`, converter, `PrefixKey`, factory, StandardForm, merge/diff, wire policy). `<Area>` is the most recent kind to go through it.
- **Room header:** [`roomObjectContents.ts`](../../../../../lambda/ephemera/dataSource/positions/ludicCache/roomObjectContents.ts) lists room-level Objects and one level of contents, read forward over covers.

## Prior decisions this plan re-opens or touches

The user's call, recorded here so it is not re-argued from the wrong end:

- **EP-2a, "is a new component kind wanted anyway?"**, was closed 2026-08-28 as no ([edgeAbstractions proposals](AGENT.edgeAbstractions.proposals.planning.md)). Its positive argument: "a tag meaning *this Object is an abstraction* is what *whole and part are roles, not kinds* forbids." Its re-open trigger: **"a named need a shipped kind cannot carry."** This plan names the need: a thing that is conceptual by kind (AK-5), and a physical surround that can be presented without abstractions (C10; scene SP-2). AK-1 records the re-open.
- **Whole and part are roles, not kinds** (locked frame, [abstraction layers](AGENT.abstractionLayers.planning.md), from [C11](AGENT.abstractionLayers.corpus.planning.md#c11-the-rube-goldberg-machine)). It forbids any rule that gives parts and wholes different behaviour. **The Abstraction kind must not mark whole or part.** It marks physical against associative: a flashlight stays an Object (a physical whole of physical parts), and an Abstraction can be a whole of its associates and itself associated into another Abstraction. AK-1 must show the kind passes that test, not assert it.
- **AB-12** rejected `<Object>` as origin, with `<Part>` below and `<Abstraction>` above, as "two type hierarchies for one relation". That objection is about scale along part-of. An `Abstraction` is not "the level above Object"; it hosts differently.
- **C10's apprehension scale** (a declared per-object field, never built) and **C11's position-relativity** (the same machine reads as a contraption from one room and furniture from another). Under this plan, C11 becomes a presentation question: each physical piece is an Object where it is, and "the machine" is an Abstraction referenced from wherever is useful.

## Questions this plan should surface

- **Narration audience.** A referent's audience is every room it is seen in. With AK-3's direction, an Abstraction is seen in every room that holds one of its bindings, so the existing rule may already cover it. Confirm once AK-10 lands; nothing changes an Abstraction's state today.
- **Coyote.** Does any Coyote content model an abstraction as an Object (staged objects, trope affinities)? Slice 0's inventory answers whether it is affected.
- **Recognition and minting.** The abstraction-layers record has abstractions minted in play (recognition, improvisation). This iteration covers authored Abstractions only.
- **Edge abstractions.** Whether an edge-based arrangement (`UtensilLayout`, `HeirloomSilver`) is an Abstraction under this plan's test, given EP-2's "an abstraction that gathers objects for one reason" framing.

Semantic reasoning, met when the kind is used; the alignment process (AK-10) is its likely home. PR-C5 beat 1 is the case to re-express.
- **The scene's wording** for associations ("part of", "associated with", the Abstraction's own phrasing) belongs to the scene plan's SP-3.
