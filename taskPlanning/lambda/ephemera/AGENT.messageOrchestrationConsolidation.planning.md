## Purpose

Two findings surfaced while building iteration 9's object-directed look, together pointing at one consolidation:

1. **`EphemeraDataSource.streamEvent` always stamps its own `dataSourceKey`** (`packages/mtw-lambda-patterns/ts/dataSource/index.ts:404`), so a describe/perceive publish can only ever carry the key of whichever DataSource's `streamEvent` closure calls it. `renderOrchestration`'s `Look Command Requested` subscription is keyed specifically to `mtw.ephemera.actions`, which is why `executeStepSequence`/`perceiveStepSequence` had to be called in-process from `dataSource/actions/index.ts` rather than via a bus hop through `positions/index.ts` --- there is currently no dataSource whose ownership cleanly matches "deliver a perception/narration message" as a first-class responsibility.
2. **There are two parallel, unconsolidated perception-delivery mechanisms in production today**, not a hypothetical mixed case awaiting a future command:
   - Character navigate's tail (`positions/navigate/executeCharacterNavigate.ts` -> `afterCharacterMembershipNavigateChanged.ts` -> `orchestrateNavigate.ts`): commits the position graph, then (ordered *after* commit) registers a `PerceptionThreads` entry, kicks a passive render, and lets the resulting `Character Moved` fact drive interleaved arrival/departure narration --- using `internalCache.OrchestrateMessages.newMessageGroup()` + a `messageGroupId` thread.
   - Object-look's `perceiveStepSequence` -> `Look Command Requested` streamEvent (iteration 9, Phase 3/4) --- no `messageGroupId` involvement at all.

Investigating (1) exposed that (2)'s `OrchestrateMessages` mechanism is **widely plumbed but narrowly exercised**: `messageGroupId` is threaded as an optional field through dozens of call sites (`dataSource/perception/orchestrate.ts` alone passes it through ~20+ times, plus `characterPerception.ts`, `kickRoomHeaderBroadcast.ts`, `renderOrchestration/events.ts`, `messageBus/baseClasses.ts`), but there is exactly **one producer** in the whole codebase (`orchestrateNavigate.ts`'s single `newMessageGroup()` call) and exactly **one consumer of the resulting semantics** (`publishMessage/index.ts`, which calls `internalCache.OrchestrateMessages.allOffsets()` to compute each grouped message's `CreatedTime`). The class's actual tree-splicing API (`before()`/`after()`/`next()`) has **zero production callers** --- every call to those three methods is inside `orchestrateMessages.test.ts`, testing the class in isolation.

**The simpler design** (confirmed through conversation, 2026-07-25): Plan/Synthesize's instruction compiler already produces an ordered list (`KernelStep[]`, in command order). Rebuilding a before/during/after tree to re-derive an ordering already known at compile time solves a problem this case doesn't have --- that tree exists to reconstruct ordering for callers who don't have a sequence upfront and need to splice items in as they arrive, which is not what any current caller actually does (navigate uses the tree API in its most degenerate form: one flat tag, no splicing). Instead: the compiled instruction list becomes an ordered array of narration-producing slots (e.g. `[leaveMessage, roomHeader, arriveMessage]`), known upfront at compile time; each slot is filled as its corresponding step is processed (a slot reading post-mutation state simply cannot resolve before its mutation's commit --- a data dependency, not a wall-clock choreography problem); delivery waits for the whole array to **settle** (all slots resolved, or tolerantly failed, to cover an anticipated slot's message never materializing) and then flushes in the array's original compiled order --- decoupling resolution order from delivery order without needing a graph/tree abstraction at all.

**Not requirement-gated.** Character navigate is the standing proof this pattern is needed in production today, not a speculative future case.

## Design decisions (confirmed through conversation, 2026-07-25)

The four bullets under **Delivery model and registry (confirmed 2026-07-26)** below supersede parts of the 2026-07-25 bullets where they conflict --- specifically, they replace the naive "bundle completes only when every slot's *final* content has reported, then flushes once" reading with the placeholder/incremental/terminal-standalone model. The rest of the 2026-07-25 bullets (ordered array vs tree, `FanInCluster` reuse, `api.ephemera` ingress, one terminal `publishMessage` site) stand unchanged.

- **Ordered array + settle-then-flush, not `OrchestrateMessages`'s before/during/after tree.** The compiler already knows the order; don't reconstruct it. See Purpose above for the full reasoning.
- **Resolution order and delivery order are decoupled.** A slot's resolver naturally depends on (is invoked after) whatever mutation it needs to reflect; the array is flushed in original compiled order regardless of the wall-clock order in which slots actually resolved.
- **The tree-splicing API (`before`/`after`/`next`) is dead code today, independently of everything else** --- confirmed via full-codebase grep, zero production callers. Safe to prune on its own, whenever convenient, without waiting for the rest of this migration.
- **Full retirement of `OrchestrateMessagesData` is the *last* step of this migration, not a prerequisite to it.** `publishMessage/index.ts` depends on `allOffsets()` for `CreatedTime` computation for every message carrying a `messageGroupId`, across message kinds well beyond perception/narration. Deleting the class before replacing what it does for that call site would break message ordering broadly, not just for perception.
- **PK-7's `dataSourceKey`-ownership question is inherited, not resolved by this migration's framing alone.** Whichever component ends up filling and flushing the ordered array still needs the authority to publish under whatever key downstream subscribers (`renderOrchestration`, `perception`) require. This document should resolve it concretely, not defer it again.
- **The "slot" mechanism is a `FanInCluster` spec, reusing the already-shipped fan-in framework verbatim --- not a new bespoke mechanism.** Confirmed through conversation, 2026-07-25. `mtw.ephemera.messageOrchestration` gets two ingress kinds: (1) a **bundle-declare** event --- a list of slot UUIDs plus each slot's expected publish-type, emitted by the Plan/Synthesize compiler at compile time; (2) a **slot-report** event --- for a given UUID, the resolved message content, published independently by whichever component finishes resolving that slot (a mutation's fact-streaming, the perception kernel's per-step render), in any order, decoupled from every other slot. This is exactly `FanInClusterStore`'s existing shape (`packages/mtw-lambda-patterns/ts/dataSource/fanInCluster.ts`/`fanInClusterStore.ts`, already shipped for membership presentation emission --- see `membershipPresentationFanIn.ts`): the bundle-declare event seeds a partial cluster with an *immediately known* identity (simpler than membership presentation's provisional-then-unify case, since there's no second leg needed to establish identity); each slot-report is a leg (`registerLeg`); `completed` is "every declared UUID now has a registered leg"; "settle" is `messageBus`'s existing deferral tail (`registerDeferral` -> `flushAndSettle` -> `settleDeferrals()` -> `handler({ deferralExecution: true })` for still-open partials), the same mechanism already handling "optional legs never arrive" for membership presentation today. No new caching, ordering, or settle concept needs inventing --- resolves MO-1/MO-2/MO-4 below.
- **`mtw.ephemera.messageOrchestration`'s ingress uses the `api.ephemera` "API Ingress" pattern for iteration 1, not real EventBridge/DataSource-to-DataSource subscription.** Confirmed through conversation, 2026-07-25. This lane already exists and is documented (`dataSource/localApiEvents.ts`, header comment: "API-triggered internal events... In-process only; no EventBridge") --- already used by `PutCacheRecordCommand`/`DeleteCacheRecordsCommand`/`ParseRequestedCommand`/`ActionAssessedCommand`/etc. Both of `mtw.ephemera.messageOrchestration`'s ingress kinds (bundle-declare, slot-report) become `api.ephemera`-keyed commands with direct send-helpers, mirroring that existing pattern --- callers (the Plan/Synthesize compiler; whichever component resolves a slot) invoke them directly, in-process, without needing to "be" any particular DataSource or hold any dataSourceKey-bound `streamEvent`. This sidesteps PK-7's binding constraint on **both** sides of `mtw.ephemera.messageOrchestration`, not just the output side (see the `publishMessage` bullet below) --- neither ingress nor egress needs a DataSource's own `streamEvent`. **Consequence for Phase 2:** `renderOrchestration`'s and `perception`'s existing stream subscriptions do not need to change at all for iteration 1 --- `Look Command Requested` keeps triggering `renderOrchestration` exactly as today; only the code that resolves a slot's content additionally calls a slot-report send-helper. Subscribing `mtw.ephemera.messageOrchestration` directly to other DataSources' own streamed events is explicitly deferred to a second iteration (see MO-5 below), not needed to ship the core mechanism.
- **`mtw.ephemera.messageOrchestration`'s output is a direct `publishMessage` call (terminal WebSocket delivery), not a further EventBridge/bus republish.** Confirmed through conversation, 2026-07-25 --- and confirmed against existing code, not just proposed: `perception/orchestrate.ts`'s `handleObjectRenderPertains` (and its ~20+ siblings) already terminate this way today, calling `bus.publish({ type: 'PublishMessage', displayProtocol: 'PerceptionMessage', wmlContent, metaData, messageGroupId, messageId, createdTime })` directly --- no intermediate DataSource hop. So this isn't a new pattern to introduce, it's consolidating an existing one: today, each render-pertains handler independently calls `bus.publish` the instant its own content resolves, and `messageGroupId`/`allOffsets()` retroactively patches `CreatedTime` inside `publishMessage` afterward. Under the new design, those same handlers instead report resolved content as a slot (ingress kind 2) into `mtw.ephemera.messageOrchestration`, which becomes the *one* place that calls `publishMessage`, once the whole bundle completes or settles, with the full already-ordered batch --- collapsing today's ~20+ scattered terminal-publish call sites into one.

### Delivery model and registry (confirmed through conversation, 2026-07-26)

- **A render slot is completed by its *placeholder*, not its LLM terminal; the bundle flushes incrementally; the terminal delivers standalone.** Confirmed 2026-07-26. A bundle flushes as soon as every slot has a *first* message --- narration slots (`leave`/`arrive`) resolve post-commit from the membership fan-in, and a render slot (`header`) is satisfied by its **"Generating…" placeholder** --- so the ordered batch `[leave, header-placeholder, arrive]` is delivered **without ever awaiting generation**. This flush is a **websocket push in its own right** (incremental delivery), *not* coalesced to the end-of-invocation settle --- otherwise the "Generating…" state would never be visible to the client (everything is in-invocation, so by settle the LLM has already finished). When the LLM terminal finishes later *in the same invocation*, it is delivered **standalone** (immediate, reusing the placeholder's pre-assigned `MessageId`), and **never re-enters the bundle**; the front-end aggregates versions of one `MessageId` into a single live-updating row, so the terminal needs no position/re-ordering of its own. **Rule:** the *first* header content reported fills the slot (placeholder when generating, real content on a cache hit); any *later* terminal overwrite goes standalone. **This corrects Phase 3 as shipped**, which inverted it --- Phase 3 routes the *terminal* into the bundle (forcing the bundle to wait on the LLM before flushing `leave`/`arrive`) and direct-publishes the placeholder *outside* the ordered batch. The correction (Phase 4) is essentially a swap of which frame feeds the bundle. The shared `MessageId` mechanism already exists: the pre-assigned `messageId` (Model A) on the `characterMove` `PerceptionThread`.

- **Directed-consequence perception is bundle-eligible; reactive-broadcast perception is not.** Confirmed 2026-07-26. All room renders converge on one delivery tail today (`register thread → Render Requested → render → PerceptionThreads.list(componentId, perspectiveKey) → PublishMessage`); the meaningful distinction is the **trigger's provenance/arity**, not "orchestrated vs. not." (1) **Directed-consequence** --- a specific actor's command produces perception aimed at *them* (navigate arrival header, explicit `look`, object-look `describe`): single-target, bundle-eligible. (2) **Reactive-broadcast** --- a world-state change (room content edited, roster changed) projected onto whoever is present: no actor, no command, multi-target fan-out, **no bundle**. Reactive-broadcast stays on `PerceptionThreads` (the `roomHeaderBroadcast` thread kind and the `entries.length === 0` roster-fallback path in `orchestrate.ts`); only directed-consequence moves onto the bundle.

- **One in-invocation ordering-and-target registry (the real target of MO-6); no persistence needed.** Confirmed 2026-07-26. `PerceptionThreads` and the messageOrchestration store are today *two* correlation registries, and a bundled render pays *both* tolls (a thread correlates the render completion → builds a `PublishMessage` → which is re-correlated as a bundle slot --- two hops for one message). **Everything is in-invocation**: the `messageBus` settle loop (`while (this._inFlight.size > 0) await …`) keeps the Lambda alive across the LLM `await`, so the terminal `Render Pertains` lands in the *same* invocation while both registries are still live --- there is **no cross-invocation terminal**, hence **no DynamoDB persistence** is required (an earlier read of `Generation Deferred`/the roster fallback as a later-invocation handoff was mistaken; corrected 2026-07-26). The target is to make the **bundle** the single owner of `[targets, MessageId, position]` per render slot: the slot's first frame reports into the bundle; terminal frames deliver *against the bundle's recorded target + MessageId* rather than via a parallel `characterMove` `PerceptionThreads` row. `PerceptionThreads` then retreats to the reactive-broadcast-only role. Not two bundling systems --- **one ordering-and-target registry + one render lifecycle that reports its first frame into it and streams later frames against it.**

- **The bundle's own declare-time registration becomes the match key for directed-consequence render completions, not `PerceptionThreads`' `bundleId`/`slotId` passthrough fields.** Confirmed 2026-07-26 (MO-9). Phase 3 stamped `bundleId`/`slotId` onto `PerceptionThreads`' `characterMove` thread row as extra payload, but correlation itself still runs entirely through `PerceptionThreads.list(componentId, perspectiveKey)` (`internalCache/perceptionThreads.ts:907`) --- the bundle-declare event (`MessageBundleDeclareCommand`/`MessageOrchestrationSlotSpec`, `dataSource/messageOrchestration/localApiEvents.ts:8-24`) has no matching capability of its own today, only `{ slotId, expectedPublishType }` per slot. "Remove `bundleId`/`slotId` from `PerceptionThreads` once the bundle owns this directly" (the original Phase 5/MO-6 wording) named an end state without a mechanism to reach it. **Resolution:** extend `MessageOrchestrationSlotSpec` to carry the match key directly --- `componentId`, `perspectiveKey`, `targets`, and `threadKind`/expected format --- so a slot is declared as "expect a render matching `(componentId, perspectiveKey, threadKind)`, deliver to these `targets`, in this format," the same information `PerceptionThreads.register` captures today, just seeded one step earlier, at bundle-declare time. **Cardinality:** different declared slots may share the same `(componentId, perspectiveKey)` matcher but carry different `targets`/format/`threadKind` --- e.g. two perspectives' renders of the same room-change, or two threadKinds reacting to one render-cache event --- so the new registry needs the same one-key-many-entries bucket shape `PerceptionThreads.list` already has (disambiguated the way `registrationId` disambiguates a bucket today), not a 1:1 key. **Iteration-1 scoping:** matching stays *pull*, not push --- the render-completion handler (`orchestrate.ts`, as today) queries `messageOrchestration`'s registry for a match, the same caller role it plays against `PerceptionThreads` today, rather than `messageOrchestration` subscribing directly to the render stream itself. This is a deliberate, temporary bridge, reusing the in-process query shape already proven for `PerceptionThreads`; whether `messageOrchestration` should ever subscribe directly to `Render Pertains`/`Generation Started` itself, instead of being queried by a caller who already owns that subscription, is left to MO-5's later iteration, not decided here.

- **`registerSlot` becomes the single-flight coordination point and fan-out mechanism for shared render content, absorbing `PerceptionThreads`' role for directed-consequence threadKinds.** Confirmed 2026-07-27 (MO-10), correcting a mid-conversation misstep: an initial framing (disambiguate a render completion down to exactly one matching slot) conflated **content** (the resolved render --- identical for every listener sharing `componentId`/`perspectiveKey`) with **addressed envelope** (a specific `PublishMessage`, with one recipient's own `MessageId`/`targets` already baked in). Delivering the same *envelope* to multiple bundles is wrong (traced through in conversation: mover A's `messageId`/`targets` ending up published via mover B's bundle) --- but delivering the same *content* to multiple bundles, each of which independently builds its **own** addressed envelope from it, is exactly right, and was the missing piece the first framing lacked. **Mechanism:** `registerSlot(bundleId, spec, kickoff?)` --- when a slot's `(componentId, perspectiveKey, threadKind)` bucket is empty (no other unresolved slot is already waiting on that same content), `kickoff()` runs, triggering whatever async process resolves it (e.g. the render-request pipeline `orchestrateNavigate.ts`/`kickPassiveRenderRequestedForCharacterInRoom` starts today); if the bucket already holds an unresolved entry, `kickoff` is **not** called again --- the bucket's own non-emptiness **is** the single-flight signal, no separate coordination mechanism needed, since every caller here is guaranteed same-invocation (unlike `renderOrchestration`'s own cross-invocation single-flight, see below). When the content resolves, it reports **once**, against the key, and the index fans out to **every** slot registered in that bucket, letting each build its own addressed report from its own recorded `targets`/`MessageId` (per MO-6, the bundle already owns these) before calling `sendMessageSlotReported` per slot and clearing the bucket. **This directly prevents a real, confirmed inefficiency, at the layer that actually causes it:** `renderOrchestration`'s render generation is cross-invocation single-flighted via Dynamo (`packages/mtw-lambda-patterns/ts/singleFlight`, confirmed intentional there via that package's own `AGENT.md`), but nothing today stops two same-invocation callers (e.g. two movers navigating into the same room+perspective, which routinely share a `perspectiveKey` since it's derived from room-asset visibility, not the character) from *each* independently kicking off a request and paying that Dynamo round-trip cost, even though they're in the same process. Single-flighting at `registerSlot` means the second caller's kickoff never happens at all --- strictly better than making the redundant kickoff cheaper after the fact (an alternative in-memory-memoization-at-`renderOrchestration` design was drafted and discarded as moot once this was seen --- see git history for the deleted `AGENT.renderGenerationInMemoryCoalesce.planning.md`). **Scope consequence:** this absorbs `PerceptionThreads`' entire correlation/bucket/registration role for `characterMove` (and, per Phase 7, other directed-consequence threadKinds) into `messageOrchestration` --- not just removing `bundleId`/`slotId` passthrough fields (MO-9's already-shipped scope) but retiring the parallel bucket/registration/fan-out logic `PerceptionThreads.register`/`.list` currently perform for these threadKinds entirely. This expands Phase 5's remaining two sub-items (`PerceptionThreads` retreats to reactive-broadcast-only; per-call-site audit) into the concrete mechanism for doing so, rather than leaving them as an unspecified end-state. **Not yet designed in full** (deliberately left for the slice that implements this): where per-slot `MessageId` pre-assignment (Model A) now happens if `PerceptionThreads.register` no longer does it; the exact `kickoff`/content-resolution callback shapes; whether this is scoped to `characterMove` only first (mirroring MO-9's own scoping) or designed generally enough for Phase 7's other threadKinds up front; and the Ingress/Delivery split named in the bullet directly below (direction resolved, implementation-level shape not yet decided).

- **Ingress and Delivery are two separate, loosely-coupled state machines --- the "two-wave drain" gap was an artifact of conflating them, not a real requirement.** Direction resolved 2026-07-27, via conversation, grounded against the shipped `FanInCluster`/`FanInClusterStore`/`SlotMatchIndex` code (not yet implemented). The two-wave framing (identified earlier the same day, see git history of this bullet) assumed the match bucket had to be *drained* on first content arrival so a second wave (the terminal) would have a clean signal to disambiguate "standalone" against --- that assumption is what made a second registry feel necessary. Splitting the concern in two removes the assumption instead of patching around it:
  - **Ingress** owns content resolution, single-flight, and replay --- a stream keyed by `(componentId, perspectiveKey, threadKind)` (the same key `SlotMatchIndex` already uses). `registerSlot(bundleId, spec, kickoff)`: if the stream isn't live, mark it live and call `kickoff()` (single-flight, as already designed); if the stream is already live, **replay** every event recorded on it so far to this new listener only, without re-invoking `kickoff()` --- this is the "current in-memory concurrent render, handled ad hoc" case (a second same-invocation mover registering after the first's placeholder already fired) made coherent. Critically: **listeners are never removed from the bucket on content arrival.** Every recorded event (placeholder, then terminal) is broadcast to *every currently-registered listener*, in order, for the life of the stream. There is no "first frame consumes the match" step anymore --- the thing that made a two-wave gap look inevitable.
  - **Delivery** owns bundle waiting/delivered state and is exactly today's `MessageOrchestrationFanInCluster`/`FanInClusterStore`, plus one addition. **Waiting-stage consolidation needs no new code**: `registerLeg`'s `this.reports.set(leg.slotId, message)` (`messageOrchestrationFanIn.ts`) is a plain `Map` overwrite --- if both a placeholder and a terminal report land on one slot before the bundle completes, the second `set` already clobbers the first, so the bundle flushes only the latest, for free. **The one real gap, confirmed by reading `FanInClusterStore.completeReadyPartials`** (`fanInClusterStore.ts:120-130`): once a cluster's `completed` flips true, `handler()` runs and the cluster is **permanently dropped** from `openPartials` --- the framework has no memory past completion. A slot-report leg arriving after the bundle has already flushed (the terminal, arriving after the placeholder already completed and delivered the bundle) finds no cluster to standalone against; it falls through `route()`'s fallback and seeds an orphan cluster with `declaredSlots === null`, which can never complete and just leaks until settle silently no-ops it. **Fix (app-level, not a change to the shared `FanInCluster`/`FanInClusterStore` package, keeping MO-1's "no new caching concept" commitment intact):** `MessageOrchestrationFanInCluster.handler()`, the one place that still holds the full declared slot list with each slot's `targets`/`MessageId` (per Q1's spec extension, resolved above) at the exact moment it flushes, snapshots `{bundleId, slotId} → {targets, messageId}` into a small sibling side-table (adjacent to, not inside, `SlotMatchIndex` --- different lifetime, only grows during the invocation, clears on the same `onClear`) before returning. A slot-report leg is checked against that side-table *before* being routed into `FanInClusterStore.route()`; a hit delivers standalone immediately (fresh `createdTime`, reused `messageId`), a miss routes normally.
  - **Not yet designed** (implementation-level, left for the slice that builds this): the exact shape of the Ingress stream's recorded-event list (bounded to 2 --- placeholder, terminal --- in practice, but not enforced anywhere yet); whether `SlotMatchIndex` itself grows the stream/replay behavior in place or a new sibling class owns it; the exact side-table's type and where it's instantiated (likely `dataSource/messageOrchestration/index.ts`, alongside `slotMatchIndex`'s own instantiation and `onClear` wiring).

- **Navigate is a presentation `KernelStep[]` plan (producer-side unification, optional capstone).** Confirmed 2026-07-26. Navigate *already* has a compiled plan --- the `[leave, header, arrive]` slot list --- expressed today as an inline computation in `orchestrateCharacterNavigate`. The eventual target is to express it as a first-class `KernelStep[]` flowing through the same kernel object-look uses, **generalized from a *perception* kernel (describe steps only) to a *presentation* kernel (describe + narration steps)**: `leave`/`arrive` are narration steps (deterministic copy, fact-correlated), `header` is a describe step; the kernel commits the mutation, then resolves each presentation step against committed state and reports its first frame into the bundle. This folds navigate's bespoke producer into the same kernel-as-producer model as object-look, deleting `orchestrateNavigate`'s hand-rolled slot-list computation. **Not required to retire `OrchestrateMessagesData`** (navigate's inline producer already carries no `messageGroupId`), so it is scoped as an optional Phase 9 capstone that may spin out as its own follow-on task.
