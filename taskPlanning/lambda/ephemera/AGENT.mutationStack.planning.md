## Why this initiative exists

The membership mutation stack works. Its **naming and division of responsibility do not describe it.** Both grew by accretion across a run of shipped migrations (`applyObjectSet*` -> `executeObject*` -> the unified kernel; the async fan-ins -> the presentation kernel; the object-lifecycle and character-route Migrate rows), and each migration named its output after **where it was being called from** at the time rather than after what it fundamentally does.

The result is a system whose surface **self-documents its own history**. Four symptoms, each measured against the code as of this seeding --- the fourth added 2026-09-05, and it is the one that changes what the work is: the first three are comprehension cost, while the fourth is live machinery with no remaining reason to run.

1. **Names inherited from call sites.** `executeMembershipTransfer` --- the general, six-caller entry point, used by character membership --- lives inside a file named [`executeObjectMove.ts`](../../../lambda/ephemera/dataSource/positions/manipulation/membership/executeObjectMove.ts). There are two directories named `membership/` with no principle separating them. `applyCharacterRoomMembership` no longer applies anything (the kernel absorbed persistence); its body is now character-route side effects wrapped around a transfer, and its types still carry an *"Ingress-facing stable API (S1-7)"* label with three internal callers.

2. **Divisions drawn by guard clauses.** `orchestrateCharacterDisconnect` exists, per its own doc comment, because `orchestrateCharacterNavigate` returns early on `!to`. `intentKind` appears as three overlapping subsets of one enum, each sized to whoever happens to reach it.

3. **Comments written as diffs rather than as state.** [`kernelStep.ts`](../../../lambda/ephemera/dataSource/positions/manipulation/kernel/kernelStep.ts) is 368 lines, over half comment, in a consistent register of *change*: "widened again", "widened twice", "previously gated on", "an earlier revision of this comment overstated it", "see git history for that version's own doc comment". A reader asking *what is a transfer step* reconstructs it from four amendments.

4. **Machinery retained past its justification.** **Carry closure is not weakly motivated --- it is inert**, and has been since 2026-08-22. `computeCarryClosure` is a BFS whose only absorption condition is `classifyInteractionUnderTransfer(...) === 'carry'`; that classifier is a closed switch in which `Under`/`Against`/`Custom` return `defer`/`dissolve` and `On`/`In`/`PartOf`/`Present` throw. **Nothing returns `carry`**, so the closure is always exactly `{startId}` with no internal edges. The codebase already says so in four retired tests (*"`carry` is unreachable from any relation kind"*, `selectMembershipFromPool.test.ts:124` and siblings). Everything above it is currently a distinction with no difference --- see MS-8.

**The falsifiable half of (3):** `PB-J` (12 occurrences), `PB-M` (11) and `LP4h` (12) are plan-ID markers whose defining plans have been deleted --- they have **no referent anywhere in `taskPlanning/`**. That is ~35 comment references pointing at nothing, and it is the dangling-marker anti-pattern [`taskPlanning/AGENT.md`](../../AGENT.md) already names.

**On (4), keep two things apart.** The *requirement* did not die; it moved into the representation. "Take the tray and the cup comes too" is still true, but AB-54 made it structural rather than computational --- the cup is a node of the tray's own shard, and the tray's host is what changes, so the carry happens by not happening. What is dead is closure-the-computation, not carry-the-behavior.

**This is not a correctness initiative.** The suite is green (49 suites / 514 tests) and no defect is alleged. The cost being paid is comprehension cost, at the exact layer that has absorbed the most change and will absorb more.

**Stored data is not a concern for (4)** (confirmed 2026-09-05): peer-level `On` edges could only have been persisted before 2026-08-22, and `CoyoteGame` clears all objects frequently enough that the instance is several cleanup cycles past any that existed. No migration step is owed.

## What the subtraction exposed (2026-09-08 reassessment)

Phases 1--2 removed enough noise to see the stack's actual division of responsibility, and it is not the one the original Phase 3 was written against. Recorded here because the diagnosis, not the slice list, is what the rewritten Phase 3 follows from.

**1. The verb does not track the altitude.** The kernel tier is clean --- `compilePositionKernelOp` compiles, `commitStepSequence` commits, `presentStepSequence` presents. Nothing above it is:

| Function | Verb says | Actually does |
| --- | --- | --- |
| `executeMembershipTransfer` | execute | plan + compile + commit |
| `executeCharacterNavigate` | execute | **orchestrate** (builds op, calls the coordinator, calls the tail) |
| `orchestrateCharacterRoomMembership` | orchestrate | execute + side effects, never presents |
| `orchestrateCharacterNavigate` | orchestrate | **compile + present only** --- no mutation at all |
| `orchestrateCharacterDisconnect` | orchestrate | compile + present only |
| `orchestrateObjectMove` | orchestrate | resolve + execute + present |

`executeCharacterNavigate` calls `orchestrateCharacterRoomMembership` calls `executeMembershipTransfer`: three tiers, alternating verbs, no monotone ordering. This is symptom (1) of [Why this initiative exists](#why-this-initiative-exists) --- names inherited from call sites --- one layer up from where Phase 2 looked for it.

**2. The compiled plan is not a value; it is re-derived from re-passed ingredients.** For the character routes the op is built and compiled **twice per move** --- once pre-commit for mutation steps (through the `compileMutationSteps` callback), once post-commit for narrate steps --- reconciled only by `orchestrateNavigate.ts`'s documented reliance on capture ids being a pure function of `froms`/`to`. Everything else follows from that one fact:

- **Four copies of the same closure**: `executeCharacterNavigate.ts:55`, `handleConnectionsCharactersPresence.ts:55` and `:95`, `repairRoomOccupancyDrift.ts:74`. Identical but for `intentKind` and two optional copy fields.
- **A whole route duplicated verbatim**: `handleCharacterDisconnected` and `repairRoomOccupancyDrift`'s ghost purge are the same closure, the same coordinator call, the same `orchestrateCharacterDisconnect` follow-on under the same guard.
- **Parameter ferrying**: `bundleId`, `intentKind`, `intentFromRoomId`, `exitName`, `characterName`, `characterMeta`, `captures` are threaded through the *mutation* layer by every route solely so the *presentation* layer can rebuild the op. That is why `ExecuteMembershipTransferArgs` is 15 fields.
- **MS-2 is a symptom, not a cause.** `compileMutationSteps` is a callback rather than a plan because the diff is not known until inside `executeMembershipTransfer`. Planning is fused into commit, so nothing upstream can build a finished op.

**3. `applyStepSequenceCore` is a sandbox, and nothing outside the reducer can reach it.** `applyStepSequenceCore(steps, Map<hostId, EphemeraLudicGraph>) -> { verdict, graphs, captures }` is a pure function over exactly the [`SandboxState`](../../../lambda/ephemera/dataSource/actions/enrich/objectManipulation/sandboxState.ts) shape the Plan-stage lane already uses. It is only *called* inside `commitStepSequence`'s `MultiKeyUpdate` reducer; nothing about it requires that. There are three validation moments on three snapshots:

| # | Where | Against what | Produces |
| --- | --- | --- | --- |
| 1 | Plan stage --- `sandboxMembershipDryRun` ([`selectIdentityPlanTuple.ts`](../../../lambda/ephemera/dataSource/actions/enrich/objectManipulation/selectIdentityPlanTuple.ts)) | graphs `compileMembershipAtomic` fetched | `DryRunOutcome` + player-facing reason |
| 2 | Execute --- `executeMembershipTransfer`'s `honorDefer` block | one freshly-fetched departure graph | `ok: false`, **no reason code** |
| 3 | Commit --- `applyStepSequenceCore` in the reducer | freshly-fetched **locked** graphs | `MutationKernelApplyOutcome` + `reasonCode` |

**4. `honorDefer` is a workaround for BD-31's collapse, not a property of take/drop.** Moment (2) is a partial hand re-implementation of what moment (3) already does: [`applyTransferSet.ts:41-57`](../../../lambda/ephemera/dataSource/positions/ludicGraph/expandValidate/applyTransferSet.ts) calls the same `boundaryEdgeOutcomes` on the same graph and returns `defer` (with `decidable`) or `illegal`/`unresolvedDissolveEdge`. The pre-check exists because `commitStepSequence.ts:122-127` **collapses `defer` and `illegal` into one generic thrown transact failure** ("BD-31 interim"), so the reducer knows the answer and cannot report it --- a player would get `STEP_SEQUENCE_TRANSACT_FAILED` instead of "you can't take that, it's under the lamp." The thing that would lift this is BD-18's backtrack channel, and [`AGENT.backtrackChannel.planning.md`](dataSource/actions/AGENT.backtrackChannel.planning.md) is **"Named, not started"** --- so it is not lifting on its own. MS-8's note that `honorDefer` should be *removed rather than renamed* is more actionable than it looked: the situation does not need to change, a general dry-run stage lifts the flag now.

**5. Both dissolve paths are one hand-unrolled iteration of a plan/evaluate loop.** `honorDefer` computes `dissolvedEdges` via `boundaryEdgeOutcomes` and feeds them to `buildObjectMoveOp`; the chain-aware path computes `dissolveSteps` via `findRelationalChainsTouching` and prepends them. Both **pre-compute a repair and emit a plan that already has it applied**, then never re-evaluate. `unresolvedDissolveEdge` is precisely the verdict that would have triggered a second iteration --- "repairable, and here is the repair" --- typed `illegal` only because there is no loop to hand it back to. The forward design this points at is [MS-13](#open-decisions-implementation--plan-only); what Phase 3 owes it is **named parts, not a built loop**.
