## `transactWrite`'s `MultiKeyUpdate` transaction-request kind

- `MultiKeyUpdate` is one of the `TransactionRequest` variants accepted by `transactWrite`. It fetches a set of `Keys` (each a `DBHandlerKey`), runs the fetched set through a single caller-supplied reducer, and diffs the result per key into either an `Update` or a `ConditionCheck` transact item --- all merged into the same `TransactWriteItemsCommand` as every other `TransactionRequest` kind, so DynamoDB's native all-or-nothing atomicity covers the whole set.
- The reducer operates on a `Record<string, T>`, **not** a `Map`. The key for each entry is the **marshalled key string** (`JSON.stringify(marshall(...))` of the key, via `_marshalledKeyString`) --- never a caller-supplied key type, never the raw `DBHandlerKey` object.
- **Every key in `Keys` participates in the transaction's optimistic lock, whether or not the reducer changes it.** A key the reducer leaves unchanged still gets a `ConditionCheck` item asserting every field in `checkKeys ?? updateKeys` still equals (or still does not exist, matching) what was fetched. There is no opt-out from this in the current implementation --- a caller cannot mark a fetched key "informational only."
- `MultiKeyUpdate` does **not** support a key disappearing from the reduced `Record` (no delete-from-map case). A reducer that removes a previously-fetched key throws synchronously (`MultiKeyUpdate reducer may not remove a previously-fetched key`) rather than silently ignoring the removal or corrupting the transaction. A reducer also must not introduce an entry for a key that was never included in `Keys` --- only fetched/locked keys may appear in the reduced result.
- `MultiKeyUpdate` does not accept `deleteCondition`, `deleteCascade`, `successCallback`, `deleteCallback`, or `priorFetch` --- those remain single-item `Update`-only concerns. Adding them to `MultiKeyUpdate` later is additive, not a breaking change to this contract.
- The "changed" diff path reuses `_optimisticUpdateFactory` unmodified (via a reducer that ignores its draft and returns the already-computed next value) --- it produces the identical `SET`/`REMOVE`-expression and prior-value-equality-condition shape that single-item `Update` already produces, including the "new record" (`attribute_not_exists(DataCategory)`) path when a key had no existing item.

## `MultiKeyUpdate`'s `cascade`

- `MultiKeyUpdate` accepts an optional `cascade: (prior: Record<string, T>, next: Record<string, T>) => TransactionRequest<KIncoming, KeyType>[]`. It runs **after** the reducer and receives the reducer's actual, already-computed output as `next` (never re-derived or run independently) --- this mirrors `deleteCascade`'s own precedent (`update.ts:284`, which passes `updateOutput.newState`), generalized beyond `deleteCascade`'s delete-only/final-state-only/single-key limits.
- The cascade fires **unconditionally**, even when the reducer changes nothing (a no-op reducer still invokes the cascade if one is supplied).
- The cascade's returned `TransactionRequest` items merge into the **same** atomic `TransactWriteItemsCommand` as the `MultiKeyUpdate`'s own per-key items --- not a separate call. If the transaction fails, cascade-contributed items fail with it, and vice versa.
- **There is no second fetch round for cascade output.** The batch-fetch that primes `Update`/`MultiKeyUpdate` items runs once, before the reducer/cascade ever execute. Consequently:
  - A cascade-returned `Update` item **must** supply its own `priorFetch` --- one that omits it throws synchronously (`MultiKeyUpdate cascade's Update items must supply priorFetch`).
  - A cascade **may not** return a nested `MultiKeyUpdate` item --- doing so throws synchronously (`MultiKeyUpdate cascade may not return a nested MultiKeyUpdate item`).
  - `Put`, `Delete`, `ConditionCheck`, `PrimitiveUpdate`, and `SetOperation` items need no fetched state and are unrestricted as cascade output.
- Cascade-returned items are converted via the same `_transactionRequestItemToTransactWriteItems` method used for every top-level `TransactionRequest` item (recursive reuse, not a duplicate conversion path) --- so a cascade-returned item's shape, including any `successCallback`/`deleteCallback` it carries, behaves identically to that same item supplied at the top level.
